# Kickflip hub and boards

Pages on Love's tailnet that Claude sessions serve, so the owner can follow and steer their work from a phone. The hub lists the sites and sends pushes. A board is a site that shows a session's work as tasks.

## Language

### Hub and sites

**Kickflip folder**:
The installed npm package or the owner's Git clone used through `npm link`, supplying the running app's code and linked into Claude Code's skills by init. It is separate from the live state in `~/.claude/kickflip/` ([kickflip ships as a minified npm package](docs/adr/2026-11-01-2247-kickflip-ships-as-a-minified-npm-package.md)). Init supplies kickflip's status line and hooks as well as the skill links, so setup is independent of the owner's dotfiles ([kickflip installs its own status line and hooks](docs/adr/2026-11-01-1322-kickflip-installs-its-own-status-line-and-hooks.md)).
_Avoid_: live skill folder

**Doctor**:
The hub setup check, `kickflip doctor`: each prerequisite, installed piece and site is ok, fixable by kickflip, the owner's to fix with the printed command, optional (Codex installed and logged in, or the mattpocock skills an **architecture review** follows, installed and current) or a note (a down site the hub restarts). `doctor --fix` runs the same setup as first-run `init` and checks again; another tool's status line stays the owner's choice ([doctor checks and fixes a hub](docs/adr/2026-11-01-1433-doctor-checks-and-fixes-a-hub.md)).
_Avoid_: status (the former CLI command)

**Board repo**:
A project's shared checkout in `~/.claude/kickflip/repos/<owner>/<repo>`, whether kickflip runs from a clone or an installed package ([board clones live outside the package](docs/adr/2026-11-04-0103-board-clones-live-outside-the-package.md)), chosen from the GitHub list or a pasted GitHub link or `owner/name` when making a board ([a pasted GitHub link picks any reachable repo](docs/adr/2026-11-01-1307-a-pasted-github-link-picks-any-reachable-repo.md)). Another host's git link makes a board on that plain git remote, cloned in `repos/<host>/<path…>`, whose tasks finish as pushed branches instead of PRs ([a board can work on any git remote](docs/adr/2026-11-02-1850-a-board-can-work-on-any-git-remote.md)). Each board keeps its own branch, and its builders work in separate worktrees based on that branch ([a new board chooses a repo and branch](docs/adr/2026-10-31-1636-a-new-board-chooses-a-repo-and-branch.md)). Before a session starts in it, the hub marks it trusted in Claude Code's `.claude.json`; the New board tap is the consent ([the hub trusts the clones it makes](docs/adr/2026-11-02-1549-the-hub-trusts-the-clones-it-makes.md)).
_Avoid_: repo folder (for the repo choice)

**Local board**:
A board whose builders branch from its repo's local `main` and land there, with nothing fetched: a board `kickflip join` made, marked `local: true`, on the folder it ran in, the hub board included; and a board with neither a GitHub repo nor a plain git remote, on its session's folder (`hub/boards.mjs` `buildsLocally`). Bare `kickflip join`, run in a git repo's folder, asks for the board name, records the folder's GitHub origin and branch, marks the folder trusted for Claude Code and starts the board's session, in the background or with `--hub` in the foreground in tmux, attached to that terminal ([kickflip join adds the current repository as a board](docs/adr/2026-11-03-0248-kickflip-join-adds-the-current-repository-as-a-board.md), [boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)).
_Avoid_: joined board, folder board

**Hub**:
The one server on the host that answers the tailnet address, lists every site, forwards to each, checks GitHub for the open PRs on boards' tasks, and sends pushes. Changes on the hub, boards and starter sites come from the app's own pages or non-browser clients; another site's page cannot act on them ([the hub starts a new board's session itself](docs/adr/2026-10-31-0137-the-hub-starts-a-new-boards-session.md)).
_Avoid_: portal, gateway

**Host**:
The machine the hub and its sessions run on, a Mac or a Linux machine. Its **hub service** keeps the hub running: a launchd login item on macOS, a systemd user unit on Linux, chosen by `shared/service.mjs` at init; init, doctor, the hub's restart for new code and uninstall all go through it ([the hub runs under the host's service manager](docs/adr/2026-11-01-1542-the-hub-runs-under-the-hosts-service-manager.md)).
_Avoid_: the Mac, server (for the machine)

**Sidebar**:
The list of every site beside each board and hub page: New version with Reload, only when the hub’s code changed since the app loaded (the hub pulls and restarts itself, and a failed pull or restart shows nothing; [the update row shows only New version and Reload](docs/adr/2026-11-06-0800-the-update-row-shows-only-new-version-and-reload.md)), then Hub, then Turn on notifications when needed, then Pages (sites that aren't boards), then Boards with their status words, lane chips, waiting counts and **context window** (its owner session's last reported percent, e.g. “62% ctx”, from `~/.claude/kickflip/context/<session>.json`, which the status line writes; dimmed with its age once ten minutes old; none on tasks or for subagents; a board not listening at 95% or more reads **context full**, and the hub board's session gets `/compact` typed into its tmux pane once ([a board session compacts before its context fills](docs/adr/2026-11-03-1823-a-board-session-compacts-before-its-context-fills.md))). The last row of Boards is **New board**, a + tile opening a sheet that chooses a GitHub repo from the list or a pasted GitHub link or `owner/name`, then its branch, Name, optional What it’s for and Tickets (Internal · INT by default); a line under the repo field points a repo already on the host at `kickflip join` in its folder. Start is the confirm: the hub starts the board’s session itself once the request passes its checks; a muted, non-link row shows its name, its three start steps (**cloning**, **starting orchestrator**, **landing it**) on the board's phase bars, and the step with its seconds, cloning with git's percent, until its route joins and the row turns into the board's ([a new board shows its start steps and live clone progress](docs/adr/2026-11-04-1914-a-new-board-shows-its-start-steps-and-clone-progress.md)). When claude fails to start, or after 15 minutes without a join, it keeps the board's name in red with **failed to start** under it ([the hub starts a new board's session itself](docs/adr/2026-10-31-0137-the-hub-starts-a-new-boards-session.md)); tapping it opens a sheet with the clone or session error line, what the start used, Dismiss and **Retry**, which starts it again from the same record ([a failed start retries from its sheet](docs/adr/2026-11-02-2006-a-failed-start-retries-from-its-sheet.md)). Hub carries notification problems and the tools’ 5-hour usage bars under its sub line, and a moon after its name while pushes are held or snoozed, whose tooltip says until when; the whole row opens the hub page and stays selected on the hub page and its settings modals. Boards and Pages stay apart wherever sites are listed. The header's logo toggles it at every width; it carries no count, and shows a plain accent dot while a new version waits. From 900px it is a rail, which its own logo collapses out of sight until the header's logo brings it back; narrower, it is a drawer. Its header reads Kickflip. Below 900px every page header is a bottom bar, and the drawer header sits at its foot under New board; desktop headers stay at the top ([phone headers sit at the bottom, with boards nearest the thumb](docs/adr/2026-10-31-1532-phone-headers-sit-at-the-bottom.md)). In the **app shell** it is mounted once, beside every view and framed page, and a site's row swaps the view in place. `/` opens this device's **last board**, which the app shell stores as each board opens, never a page ([a sidebar of every board replaces the hub home](docs/adr/2026-10-29-1639-a-sidebar-of-every-board-replaces-the-hub-home.md), [one app for the whole hub](docs/adr/2026-10-29-2005-one-app-for-the-whole-hub.md)).
_Avoid_: hub home, switcher, nav

**Switch mode**:
The sidebar showing each linked row's key after s is pressed twice outside a text field: the first nine boards' numbers on their tiles, and every linked row's letter from its name, in blue, while the Boards label reads "Boards – press a key to switch" over a bar that drains, and no row moves. The next key opens that row in place; Escape, a click or 3 seconds with no key ends it. Boards claim letters first, in the order they joined the hub, so a new board never takes another board's letter ([Switch mode's letters come from names, claimed in the order sites joined](docs/adr/2026-10-30-1102-switch-mode-letters-come-from-names-in-join-order.md)).
_Avoid_: shortcuts, hotkeys, jump mode

**Shortcuts sheet**:
The centred Keyboard shortcuts sheet over the dimmed page that h pressed twice within a second shows or hides, outside a text field and with no modifier, wherever the sidebar runs; Escape closes it. It lists every keyboard shortcut with its keys drawn as keycaps, from the one list in `ui-sidebar.js`. A device without a fine pointer that hovers, such as a phone, never shows it, and nothing else opens it.
_Avoid_: help modal, cheat sheet

**App shell**:
The one page a browser's load of `/`, a hub page or any site's page gets, `board/public/app.html`: the sidebar, mounted once, beside one **view** at a time, and the hub's one stream, `/_hub/stream`. Following a link to a view swaps it in place, with no reload, and leaving one with an unsaved edit asks first. Every URL stays a real address. The board server answers a board's four view paths with the shell too, and the hub every load of `/_hub/`, `/_hub/settings` and the old Polling page, `/_hub/settings/polling`, which opens Quiet hours, so curl and a frame get it; a frame's shell hands its URL to the app around it. While the host can't be reached, the hub's service worker opens the last shell the hub served, with its last sidebar, and each view shows its own offline state ([one app for the whole hub](docs/adr/2026-10-29-2005-one-app-for-the-whole-hub.md)).
_Avoid_: SPA, wrapper, frame

**View**:
One page's content in the app shell, mounted when its URL opens and unmounted, with every listener, timer and stream it added, when another takes its place. A board is a view, and so are its Waiting on you and Notes, and the **hub page**; hub settings open over Hub and Board Settings opens over its board as modals. Below 900px a board and its Waiting on you stay mounted together and switch in place, the one not shown hidden with its scroll and state, and only leaving both unmounts them ([on a phone the board and Waiting on you switch in place](docs/adr/2026-11-14-2332-on-a-phone-the-board-and-waiting-on-you-switch-in-place.md)). A board left and opened again paints from its **last visit**, live, and catches up from its **change number**. Opened again in the same page, unless its link names a task, it also returns to where the owner left it: the page's scroll, its open threads' windows and New strip edit boxes, and, with a mouse or trackpad, the box being typed in with its caret or selection; a phone keeps the keyboard shut. A reload starts fresh. Any other page, another site's or a board's prototype, is a **frame view**: the page in a frame beside the board header, or its own when it draws that header, with Open alone ↗ to load it by itself.
_Avoid_: screen, tab, page (a page is its own document)

**Page tree**:
The levels back climbs in the app shell: a board, its Waiting on you, then a separately opened prototype page tied to one of its questions by `?q=`. On each, the back arrow, the browser's back and a swipe all go up one level: from a prototype to Waiting on you on its question, from there to the board, with the task still open when the owner left the board from that task's thread. However the owner arrives, by a push, a link or a reload, the levels above are written into history under the page first ([Back follows the page tree](docs/adr/2026-10-30-1125-back-follows-the-page-tree.md)). From 900px Waiting on you is no page of its own: every URL of it shows the board at the board's URL with its topic open in the pane, so the tree is the board and a prototype ([Board and Open questions are two pages](docs/adr/2026-11-07-1300-board-and-open-questions-are-two-pages.md)).
_Avoid_: nav stack, breadcrumbs

**Hub page**:
The hub's status page, `/_hub/`, which the sidebar's Hub row opens: a pause or Keep going banner at the **pause line**, a banner while pushes are held or snoozed, with End snooze on a snooze, then **usage readings**, then the **pending prompts** of sessions that own no board, **Health**, whose Hub row reads the **hub status**, then its machine row, then the Keep awake toggle row, **Integrations**, then **Boards** and **Pages** with each site's health and each board's hub links and watcher, and on each board a Restart that stops its session, restarts its server and resumes the session ([a board restarts from its row on the Hub page](docs/adr/2026-11-02-1736-a-board-restarts-from-its-row-on-the-hub-page.md)), each session's remembered Always allow rules read-only under its board, polling status, then the **hub settings** summary rows ([a sidebar of every board replaces the hub home](docs/adr/2026-10-29-1639-a-sidebar-of-every-board-replaces-the-hub-home.md), [a background session's prompts and questions come to the phone](docs/adr/2026-10-30-1516-background-sessions-prompts-come-to-the-phone.md)).
_Avoid_: dashboard, console, hub home

**Hub status**:
The word on the Hub row of the sidebar and the hub page's Health task: **healthy** (green); **degraded** (amber) while a board's hub link stays broken past its grace period (the hub running older code than its files is no health state: the New hub version row is its only sign, [older code reads only as the New server version banner](docs/adr/2026-11-16-0600-older-code-reads-only-as-the-new-server-version-banner.md)); "1 site down" (red) only while a site is down. Integrations that aren't set up don't count. On the hub page, tapping it jumps to Integrations. A board whose link fails reads "degraded · listening" in amber, with the failing link named underneath ([the hub reads Healthy, Degraded or a site down, and notifications leave the board links](docs/adr/2026-11-03-0501-the-hub-reads-healthy-degraded-or-a-site-down.md)).
_Avoid_: broken, hub health

**Integration readiness**:
What each integration needs before its features can run: the Hub page’s Integrations section between Health and Boards lists GitHub, Codex, Linear, Slack, Tailscale and Notifications in that order. A row reading ready says what passed; one reading not ready is orange, or red when Linear or Slack refused its key ([a refused integration token reads red](docs/adr/2026-11-15-0745-a-refused-integration-token-reads-red.md)), and says what is missing, how to fix it and which features wait. While GitHub's hourly limit holds gh's account, GitHub's row is red, "rate limited · resets at <time>", every kickflip gh call on the spent budget refuses at once with that time, and boards dim their PR badges ([gh refuses while GitHub's hourly limit holds](docs/adr/2026-11-09-1626-gh-refuses-while-githubs-hourly-limit-holds.md)). Slack is ready while Hub’s Slack token is saved and Slack hasn’t refused it. A ready integration missing a permission a feature needs reads amber **degraded**; tapping the word opens a sheet with each missing permission, what stops working without it and its scope, then the one fix and the key button ([an integration missing a permission reads degraded](docs/adr/2026-11-15-0730-an-integration-missing-a-permission-reads-degraded.md)). the hub shares the same readiness and words with feature gates ([integrations show readiness, and features wait until theirs is ready](docs/adr/2026-11-02-1118-integrations-show-readiness-and-features-wait.md)).
_Avoid_: integration health, availability

**Usage reading**:
The last reported Claude or Codex usage for its 5-hour and weekly windows, with reset times and when read. The sidebar’s Hub row shows each tool’s 5-hour bar, and a second “Claude week” bar once Claude’s live week is within the **near** band under the **pause line** (orange under the line, red at it; none with the line Off), and the hub page shows both windows with the **pause line** tick; a reading older than its window reads “last seen” with a grey striped bar, otherwise a window whose reset passed reads as reset. Claude appears after its status line reports usage. Codex's bars show only while the **Codex setting** in effect isn't Off; the hub page keeps Codex's block either way, opening with the setting's control ([the sidebar shows Claude and Codex usage under Hub](docs/adr/2026-11-01-1338-the-sidebar-shows-claude-and-codex-usage-under-hub.md), [the sidebar shows the week once it is near the line](docs/adr/2026-11-10-1215-the-sidebar-shows-the-week-once-it-is-near-the-line.md), [Codex share sits in the Usage card](docs/adr/2026-11-01-1428-codex-share-sits-in-the-usage-card.md), [Codex share follows whether Codex is usable](docs/adr/2026-11-01-1521-codex-share-follows-whether-codex-is-usable.md)).
_Avoid_: quota, live usage

**Pause line**:
The Usage task's “Pause work at”, last in the group below Codex: `pauseAt` in `~/.claude/kickflip/settings.json`, 50–100 in steps of 5, default 90 (10% buffer); 100 reads Off. Either live Claude window at or over it pauses new work until that window resets, and a **task pause** stops each running Claude build ("usage limit") until it resets; new agents wait, watchers hold the hub's work events, and the orchestrator keeps sorting, readying, screening and answering. Keep going lifts that window's pause until its reset; Stop restores it. Codex hands work to Opus builders at the same line, without pausing. The Hub banner and sidebar and board header status slots show the pause, never the logo. Claude's reading joins the status line's with every headless run log's newest `rate_limit_event`. Within twice the buffer of the line the gate is **near**: the pull's cap halves, rounded up (5 to 3), and the Hub banner reads "Approaching usage limit, reducing parallel tasks in progress" with its own Keep going, which restores the full cap until the reset. `shared/usage-gate.mjs` owns it; `kickflip usage-gate` prints it ([work pauses at the pause line](docs/adr/2026-11-01-1710-work-pauses-at-the-pause-line.md), [the pause line reads every headless agent's usage](docs/adr/2026-11-06-1249-the-pause-line-reads-every-headless-agents-usage.md), [a card pause stops its builder at its next stopping point](docs/adr/2026-11-09-1300-a-card-pause-stops-its-builder-at-its-next-stopping-point.md)).
_Avoid_: buffer threshold, quota guard

**Task pause**:
How the board stops a running build without moving its task: blocked (the **owner's block** included), the usage pause (the **pause line**, **Pause board** and **Pause hub**, "board paused" or "hub paused" for those two, and a builder that hit its hard limit). The pause sits on the task's open build record (`pause {cause, words}`) and the build stays In Progress. The builder stops at its next stopping point, the reply to its next progress report, call or ask, which tells it to commit and end its turn; one waiting in `builder asks --wait` is already at one, and after 15 minutes the board stops it. The task reads "pausing · blocked by #53" in orange, then "paused · blocked by #53" in grey, its phase bars dimmed at the phase it stopped at, with the thread line "Paused at building: blocked by #53. It resumes once nothing blocks it." A paused build keeps its task's **implementer slot**, since the task stays In Progress. Once the cause clears the board writes "Resumed: nothing blocks it." and resumes the builder's own session (`claude --resume`) in its worktree with its record, before the pull starts new tasks, unless that session is past 150k tokens of context and its last turn is an hour old: then a fresh builder on the build's model carries on with a handoff, under the thread line "Fresh builder: its session was over 150k." ([a cold resume past 150k starts a fresh agent with a handoff](docs/adr/2026-11-15-0040-a-cold-resume-past-150k-starts-a-fresh-agent-with-a-handoff.md)); a session's builder gets the same reply, and the clear sends `builder-resume` for the orchestrator to tell it to carry on. A cause that clears before the builder stops drops the pause. A **busy Mac** still lets running work finish ([a card pause stops its builder at its next stopping point](docs/adr/2026-11-09-1300-a-card-pause-stops-its-builder-at-its-next-stopping-point.md)).
_Avoid_: stopped, sent back, suspended

**Pause hub** and **Pause board**:
The owner's manual pause, first in Hub settings and Board settings, with the snooze picker's chips, Forever included, and Custom: until its end (Forever's lasts until Resume) it pauses new work exactly as the **pause line** does, Codex builders included, on every board for Pause hub (settings.json's `paused_until`) and on that board alone for Pause board (board.json's `paused_until`, no board setting). It outranks the usage pause and Keep going, Pause hub first. Resume ends it, and the end wakes the boards with `usage-resumed {window: "manual"}`. It reads paused in gray wherever the usage pause shows: Pause hub on the Hub banner and row and every board, Pause board on its own sidebar row, header and tasks ([Pause board and Pause hub pause new work by hand](docs/adr/2026-11-05-1849-pause-board-and-pause-hub-pause-new-work-by-hand.md)).
_Avoid_: snooze (pushes only), hold (one task)

**Busy Mac**:
This Mac at memory pressure critical or a 1-minute load of 4× its cores or more, until pressure is warn or lower and load is under 3× its cores. While busy every board holds all new work as the **pause line** does, Codex builders, landers and bumped tasks included, and running work finishes. A test run (`board.mjs test`, a land's or the full suite) waits to start, reading "waiting: the host is busy" ([test runs wait while the host is busy and leave nothing behind](docs/adr/2026-11-14-1217-test-runs-wait-while-the-host-is-busy-and-leave-nothing-behind.md)). The hub's tick keeps the state in `~/.claude/kickflip/machine-state.json` (`shared/machine-gate.mjs`), which the one gate carries as `machine`. It reads busy, in words only, on the Hub row, every board row, the board header and Health's Machine row, and a task whose launch it holds gets a thread line ([a busy Mac holds new work](docs/adr/2026-11-06-0106-a-busy-mac-holds-new-work.md)). Tapping the Hub row's busy words opens what's loading the host: the load now and over the hour, from a sample a minute the tick keeps, and the processes by group, with Stop on the orphans ([the busy Hub row opens what's loading the host](docs/adr/2026-11-13-0026-the-busy-hub-row-opens-whats-loading-the-host.md)).
_Avoid_: resources low, overload

**Claude model**:
The Usage task's Opus · Auto · Sonnet control, opening Claude's block: `claudeModel` in `~/.claude/kickflip/settings.json`, default Auto. It decides which model builds a task Claude builds: Opus or Sonnet always, or under Auto the task's own `--model`, else Sonnet for a task `--size small` and Opus for the rest. `builder pick` prints it with why, and a build's `builder start` refuses a `--model` it rules out. Codex builds, prototypes and grills don't read it ([usage picks Opus, Auto or Sonnet for Claude builders, and builder pick says which and why](docs/adr/2026-11-03-1526-usage-picks-opus-auto-or-sonnet-for-claude-builders.md)).
_Avoid_: Opus builders, allow Opus

**Audit log**:
One JSON line for each call the code makes on its own, with when, the call, the task, its result, the reason and the inputs it read: a board's in its `data/audit.jsonl`, such as the pick a build started on, a pull, a relaunch or an auto-merge, and the hub's own (usage pauses and resumes, Linear moves) in `~/.claude/kickflip/audit.jsonl`. Each keeps the last 30 days. `board.mjs audit [<card>]` and `kickflip audit` print them ([the hub and each board keep an audit log of the calls their code makes](docs/adr/2026-11-05-0913-the-hub-and-each-board-keep-an-audit-log-of-the-calls-their-code-makes.md)).
_Avoid_: hub.log (the hub's free-text stderr), history

**Board registry**:
`hub/boards.mjs`, the only hub code that reads a board's `board.json` and item files. Every hub feature that serves boards (the GitHub check, wakes, rules, the handshake, the not-listening push) takes its boards from it, so a board over `~/.claude/waves` and a board over its own file get the same links ([one board registry for every hub feature](docs/adr/2026-10-29-1639-one-board-registry-for-every-hub-feature.md)).
_Avoid_: board list, wave boards and file boards (as separate code paths)

**Site**:
A route on the hub (`/<route>`) served by one owning Claude session, or by none for a **plain page**.
_Avoid_: app, page (a site has several pages)

**Plain page**:
A site joined with `kickflip page <name>` (`/kickflip page`) and `--port` (a server its session runs, which reads Down while nothing answers) or `--dir` (files the hub serves itself), without `--session`. It has no owning session, events, watcher or Needs you badge, and shows under Pages like any site that isn't a board. `--watch --session <id>` joins a site with all of those ([a page joins without a session](docs/adr/2026-11-01-1446-a-page-joins-without-a-session.md)). Every join's `--name` gives the site's title and route, the name hyphenated ([kickflip join adds the current repository as a board](docs/adr/2026-11-03-0248-kickflip-join-adds-the-current-repository-as-a-board.md)).
_Avoid_: minimal site, unwatched site

**Owner**:
Love, the person the sites serve. The word for the session that serves a site is **owning session**.
_Avoid_: user, admin

**Board session**:
A board's owning session as the manifest records it in the site's owner: its id, its folder (`repo`, where `claude --resume` finds it) and an optional model. `kickflip start` launches one in the background; `kickflip resume` brings it back and records the id it comes back under. A rejoin keeps the label, model and folder it leaves out.
_Avoid_: orchestrator process, agent

**Hub session**:
The owning session of the **hub board**, the one board whose manifest entry has `hub: true` (`kickflip set <route> --hub`, `kickflip join --hub`). It is the one board session that runs in the foreground, inside the tmux session `kickflip-<route>` the hub starts, which `kickflip hub` attaches the owner's terminal to; it gets the phone permission hook like a background session. Nothing else sets the hub board apart: it works on its own folder as a **local board**, closes and restarts like any board. Code finds it by the flag, never by its route. A hub board is optional, and no feature depends on its session ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)).
_Avoid_: hub server, permanent orchestrator

**Live**:
A session whose `~/.claude/sessions/<pid>.json` record names it and whose process still runs, started when the record says. A live session is never started or resumed again.

**Listening**:
A board is listening while its owner session is live and a watcher runs for it. A watcher outlives its session, so a watcher alone isn't listening. A board that isn't listening is waking, **asleep** or not listening. The board header, the sidebar, the events link and the not-listening push read that state, and the **session wake** uses this test ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md)).

**Asleep**:
A board whose owner session isn't live but that the hub can wake on its next event or a tap on its page: a session and folder are recorded, and no **session wake** of this outage has failed or gone unanswered. It reads asleep in grey in the sidebar and the board header, its events link passes, and it gets no not-listening push. Once the hub resumed its session it is waking, and reads waking… in grey until it listens. A board that is neither listening, waking nor asleep is **not listening** and reads so in red ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md), [boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)).
_Avoid_: idle, stopped, offline

**Not listening**:
A board that isn't listening, waking nor **asleep**: its session or watcher isn't running and the hub can't wake it, so events wait. It reads not listening in red in the board header, the sidebar and the hub page, "Not listening: …" in its events link and "X isn't listening" in its push ([status words are lowercase, and a board nothing will wake reads not listening](docs/adr/2026-11-03-1822-status-words-are-lowercase.md)). A board whose session runs idle and stays not listening for 2 minutes gets an **automatic restart**.
_Avoid_: deaf, stopped, not responding

**Automatic restart**:
A restart the hub makes by itself, once per outage: of a board's session that runs idle but hasn't been listening for 2 minutes (stopped and resumed), or of a board server that is up but hasn't answered for 1 minute. Neither runs while the board's session is busy, a builder of the board is open or a land is queued or landing. Each restart goes to `~/.claude/kickflip/auto-restarts.jsonl` with whether it brought the board back, and to the board's Hub row for a day ("restarted the session 2m ago: not listening"). The owner gets a push only when a restart fails ([the hub restarts a session not listening and a server not answering](docs/adr/2026-11-15-0123-the-hub-restarts-a-session-not-listening-and-a-server-not-answering.md)).
_Avoid_: auto-heal, self-repair

**Restart row**:
The sidebar row under New version · Reload, worded for a restart: New server version · Restart on a board whose server runs older code than its files, New hub version · Restart on the hub's pages while the hub does. A tap restarts that server, or the hub, and reloads the page once it answers. New code never restarts a running server or the hub at once: each restarts by itself once idle, by the same holds as an **automatic restart** (a hub restart waits on every board), unless the Hub page's `auto restart` box is off; a crash or a missing server still restarts at once ([new server code waits behind a Restart row and restarts itself once idle](docs/adr/2026-11-15-2221-new-server-code-waits-behind-a-restart-row-and-restarts-itself-once-idle.md)).
_Avoid_: restart banner, reload banner

**Status word**:
A word in a status slot: beside a status dot, in a hub page row's status, in the board header's time slot, in a running or failed build chip, or as a usage block's tag. It is lowercase (down, starting, working, implementing, paused, healthy, degraded, up, not listening…), while sentences, toasts, tooltips, pushes, titles and button labels keep their capital ([status words are lowercase, and a board nothing will wake reads not listening](docs/adr/2026-11-03-1822-status-words-are-lowercase.md)).
_Avoid_: status label, badge text

**Session wake**:
The hub resuming a board session as soon as an event lands while that session isn't live, or the owner taps the board's page while it is **asleep** (the header's refresh or any other tap or send, through `/_hub/wake`), or, as a fallback, once its board hasn't been listening for 3 minutes with an event its session hasn't heard. Once per outage, then one push to the owner if the board still isn't listening 5 minutes later. A session that idles out with nothing waiting stays stopped. The hub board's session comes back in its tmux session ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md), [boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)).
_Avoid_: auto-resume, respawn, wake (a daily wake is the morning `check-github`)

**Push**:
A notification from the hub, on the phone or a desktop browser, that opens a page. Each push has a kind, and `hub/push.mjs` `deliver()` refuses any other: `action` when a task's **Action needed** appears or changes, `prompt` for a **pending prompt**, `fault` for what only the owner can fix (a board not listening, a session that didn't come back, an urgent production problem) ([a push goes out only when something waits on the owner, on the hub's schedule](docs/adr/2026-10-29-1639-pushes-only-when-something-waits-on-the-owner.md)). Answers, merges, Stale and other news never push; the threads' unread marks and the board carry them. What waits on the owner on a board is one **live notification**, tagged `board-<route>`, which the board server pushes itself and pushes again at once whenever it changes ([the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)). It is titled "<Board> (N)" with what the owner's taps unblock ("2 builds wait on you · 1 question") and opens Waiting on you; with one thing waiting it reads and opens as that thing. Only its first push alerts: later ones replace it silently, through quiet hours too, and it closes once nothing waits. Its first push waits out quiet hours like any other ([a board's needs-you pushes are one live row](docs/adr/2026-11-15-1300-a-boards-needs-you-pushes-are-one-live-row.md)). When the queue goes out, a board's live notification goes as itself; of the rest, a board with one queued push gets it as it is, and a board with several gets one summary of what waits on its Needs you then, tagged `summary:<route>` so the newest replaces the last, or nothing when nothing waits ([queued pushes go as one summary per board](docs/adr/2026-11-02-1733-queued-pushes-go-as-one-summary-per-board.md)). Replies don't push; a push that goes out anyway says how many came since the last one. With notifications off every push is dropped; a snooze and Off on weekends hold pushes until they end, and urgent ones go through those holds ([notifications can be off, snoozed, or off on weekends](docs/adr/2026-10-29-1639-notifications-can-be-off-snoozed-or-off-on-weekends.md)). Every push goes to every subscribed device ([every push goes to every device](docs/adr/2026-11-05-2230-every-push-goes-to-every-device.md)).
_Avoid_: alert, notification (for the act of sending)

**At the host**:
The owner's presence, which sets the **Check cadence** and the moon: the host's screen is unlocked and a key or the pointer was used in the last 3 minutes, whatever app is in front (`hub/presence.mjs`). It is read from macOS `ioreg`, so on a Linux host the owner always reads away.
_Avoid_: at the Mac, active, online, desktop app active

**Check cadence**:
How often the hub checks: every minute while the owner is present (the Mac in use, or a board page tapped on any device) and every 5 while away ([boards read PR state from the hub's check](docs/adr/2026-11-09-1556-boards-read-pr-state-from-the-hubs-check.md)), or every 5 and 15 while GitHub has under 1,000 points left. Coming back checks at once. Each check fetches and pulls every board's repo and reads every task PR in one GraphQL query, wakes a board's owning session with `github-change` when a PR on its tasks changed, pushes once for each board that isn't listening, then sends the queued pushes. While away, a moon sits right of the board title ([the hub checks every minute while you’re here and every 5 when away](docs/adr/2026-11-04-0226-the-hub-checks-every-minute-while-youre-here-and-every-5-when-away.md)).
_Avoid_: polling interval, polling window, push schedule, cron

**Quiet hours**:
A start and end time, 10:00pm to 8:00am by default. With its hold on, pushes queued inside it wait for its end. Snooze tonight ends at its start, morning at its end and monday at Monday's end; Off on weekends runs from Friday's start to Monday's end. At its end the hub sends each board one `check-github {reason: "morning"}`, the daily wake, unless Daily wake is off in **Overnight work** ([the hub checks every minute while you’re here and every 5 when away](docs/adr/2026-11-04-0226-the-hub-checks-every-minute-while-youre-here-and-every-5-when-away.md)).
_Avoid_: overnight window, wake times

**Overnight work**:
The jobs the hub runs at night, a group in the Quiet hours modal under Starts, Ends and Hold pushes: a line saying it starts at the middle of quiet hours (3:00am by default), then a row per job with its line, its last run (Last run <time> · ok in green, · failed in red linking its card or log, Never run and Off in grey) and a toggle, on by default; an off row greys. Daily wake and Triage overnight are rows ([quiet hours list the overnight work, each job on by default](docs/adr/2026-11-15-0700-quiet-hours-list-the-overnight-work-each-job-on-by-default.md)), and so is Nightly full suite: once a night from that middle, every board's tests in full on its main, one board at a time, each a New task on its board when its main fails, which the row's red result links ([the nightly full suite runs every board's main and files a task on failure](docs/adr/2026-11-15-2300-the-nightly-full-suite-runs-every-boards-main-and-files-a-task-on-failure.md)).
_Avoid_: nightly jobs, cron

**Hub settings**:
The summary rows below the **hub page**’s health and status: **Pause hub** first, then Notifications, Quiet hours, Rules for every board and Closed boards. Each opens its controls in a centred modal with its own scroll area. Snooze and Pause hub share one duration picker: 1h, 3h, 6h, 1d, Forever and Custom. Keep awake, Linear and Slack are not summary rows: Keep awake is a toggle row in Health, under the machine row, and Linear's key and Slack's token open modals from an Add key or Change key button at the end of their Integrations rows ([Linear and Slack keys open in modals from their Integrations rows](docs/adr/2026-11-09-2230-linear-and-slack-keys-open-in-modals-from-their-integrations-rows.md)). Keep awake is an on/off toggle that has the hub run `caffeinate -s`, holding the Mac awake only on AC power, and is disabled on hosts other than macOS ([Keep awake is a toggle that holds the Mac awake only on AC power](docs/adr/2026-11-09-1200-keep-awake-is-a-toggle-that-holds-the-mac-awake-only-on-ac-power.md)). Old Hub Settings links open the matching modal over Hub ([hub settings open as modals](docs/adr/2026-11-01-1221-hub-settings-open-as-modals.md)).
_Avoid_: Hub Settings page, preferences, hub config

**Shared person**:
Someone else signed in to Tailscale whose login a board's Sharing lists: they see that board in a shell whose sidebar lists only the boards shared with them, and open its Visit links; the rest of the hub refuses them ([a board is shared view only with a Tailscale login](docs/adr/2026-11-05-2215-a-board-is-shared-view-only-with-a-tailscale-login.md)). Each is **View**, looking only, or **Full**, also answering, writing in threads, attaching files, tapping task buttons and adding New tasks, named in the thread; Merge and Board settings stay the owner's at both ([a shared person is View or Full](docs/adr/2026-11-05-1912-a-shared-person-is-view-or-full.md)).
_Avoid_: guest, viewer, collaborator

**Board Settings**:
The centred modal opened from a board header’s gear, at every width, which scrolls inside on a phone. It contains only that board’s settings: **Pause board** first, then repo and branch (Change uses the same list and GitHub link search as New board), ticket source, auto-merge, auto-build, Maximum tasks in progress and planners, reviewers, sharing, rules and Close board with typed-name confirmation. Closing returns to the same board and open task without another history entry ([hub settings expand in place and board settings open in a modal](docs/adr/2026-10-31-1721-hub-settings-expand-in-place-and-board-settings-open-in-a-modal.md)).

The one choice for every board, made in Codex’s block of the hub page’s Usage task ([Codex share sits in the Usage card](docs/adr/2026-11-01-1428-codex-share-sits-in-the-usage-card.md)): Auto and Always on have Codex build and review, with Opus builders taking over while Codex is past the **pause line** until it resets; out of usage, Auto keeps Opus builders on and Always on pauses that work until a usage-reset check succeeds; Off means Opus builds and reviews. Unset means Auto. While Codex isn't usable, installed and logged in, the setting in effect is Off whatever is stored, and the control is greyed out; running out of usage doesn't make Codex unusable ([Codex share follows whether Codex is usable](docs/adr/2026-11-01-1521-codex-share-follows-whether-codex-is-usable.md)). _Avoid_: unread count, inbox

**Status word**:

Lane chips with the site's open-task counts follow it, led by a red "N need you" chip while anything waits, so the count never competes with the word ([need you is a chip](docs/adr/2026-11-07-1400-red-beats-orange-beats-blue-and-need-you-is-a-chip.md)); a calm site shows only the chips ([the hub home shows status, not descriptions](docs/adr/2026-10-29-1639-the-hub-home-shows-status-not-descriptions.md), ["N need you" outranks Working](docs/adr/2026-11-01-1252-need-you-outranks-working.md)).

### Boards

**Board**:
A site built from the board template that shows the tasks of its item files in lanes.
_Avoid_: dashboard, kanban

**Closed board**:
A board whose session and server have stopped and whose sidebar row is gone, with its folder, tasks, threads and notes kept on the host. The hub page lists it under Closed boards; Reopen restores it and resumes its recorded session. Open PRs stay on GitHub, and running builder records end with a note ([a closed board keeps its folder and can be reopened](docs/adr/2026-10-31-1603-a-closed-board-keeps-its-folder-and-can-be-reopened.md)).

**Hub links**:
What the hub owes a board, each passing or broken: GitHub polling (not on a board on a plain git remote), the repo fetch (on a board with a repo, the hub's last `git fetch` of it worked; when it failed, git's error line and the fix, such as `gh auth setup-git`, or `git ls-remote <link>` on a plain git remote), events (the board is **listening**), daily wakes and reviewer links; whether a device gets pushes is the Notifications integration, not a hub link ([the hub reads Healthy, Degraded or a site down, and notifications leave the board links](docs/adr/2026-11-03-0501-the-hub-reads-healthy-degraded-or-a-site-down.md)). _Avoid_: health, status, integrations

**Change signal**:
The board server's note on its `api/stream` that a file the board reads changed; the hub passes it on as `change {route}` on its one stream, and an open board reloads at once, naming the **change number** it shows, so a changed board comes as a patch of the tasks, questions and topics that changed after it ([the board sends per-card patches](docs/adr/2026-11-04-0332-the-board-sends-per-card-patches.md), [the board syncs by change number](docs/adr/2026-11-05-1819-the-board-syncs-by-change-number.md)). The header's time counts from the last one that brought something new, or the last ↻ tap ([the board reloads on a change signal](docs/adr/2026-10-29-1639-the-board-reloads-on-a-change-signal.md)).
_Avoid_: push (a push is a notification from the hub), live update

**Owner tap**:
A button the owner taps on the board, sent as an event. The board's rule for taps: one whose result follows from the tap alone (a bump, Block, Done, Build, an edit) is applied by the board server inside the POST, which answers with the board, and the page draws it at once, a bump, unbump, edit or delete even before the POST, taken back off with a toast if the POST fails. The event is a record for the session, never what the owner waits on; only judgment or outside tools (Grill, prototypes, triage, a GitHub check) wait on the session. A tap reloads the board once, through the change signal ([every owner tap the server can apply draws at once](docs/adr/2026-11-03-0500-every-owner-tap-the-server-can-apply-draws-at-once.md)).
_Avoid_: action, click

**Wave**:
Not a board concept any more. Order comes from a task's deps (its **blocked by**), and grouping from its Related to links and a split's Parent; no lane draws a band or group header, and there is no `wave` command, `wave:<slug>` dep or wave triage. **Item file**:
The JSON file a board's tasks are stored in, with its title, repo and reviewers: storage only, never a band, label or group on the board, so a task linked from several files shows once ([waves are dropped; deps and Related carry order and grouping](docs/adr/2026-11-14-1200-waves-are-dropped-deps-and-related-carry-order-and-grouping.md)). On a board over its own tasks `data/items.json`, named by board.json `items`, and on a board over `~/.claude/waves` each `<slug>/wave.json`. A task's key starts with its item file's slug, and code calls it `file` ([a lineup is called a wave, and the wave file an item file](docs/adr/2026-11-09-2100-a-lineup-is-called-a-wave-and-the-wave-file-an-item-file.md)).

**Architecture review**:
Claude reviewing a board's repo, chosen by `hub/board-repo.mjs` `boardRepo`, with the mattpocock skills: the bulb at the foot of the board, beside the gear, opens a sheet with the last review and Run, which confirms. The board server makes an audit task "Architecture <date>", on a board over `~/.claude/waves` in an **item file** of its own, and wakes the session with `arch-review`. The bulb glows orange while the audit task is open with no question yet. The audit task's Notes are the report, and it asks one question per finding, with possible solutions and Skip; each finding not skipped becomes a task, a Child of the audit task and blocked by it ([waves are dropped; deps and Related carry order and grouping](docs/adr/2026-11-14-1200-waves-are-dropped-deps-and-related-carry-order-and-grouping.md)). One review is open at a time, so Run while one is open opens its audit task. A board on the running kickflip clone, as the hub board is, has its review cover kickflip's code, the board template and the model, reading the live data only for its shapes. It waits, saying why, while a skill it follows isn't installed ([the bulb runs an architecture review of the board's repo](docs/adr/2026-11-02-1813-the-bulb-runs-an-architecture-review-of-the-boards-repo.md)).
_Avoid_: improvements round, audit (for the whole review), bulb round

**Reviewers**:
The people who get a board's PR links once they are ready, and the weekday digest. Each board keeps its own in `board.json`, which its Settings modal lists, and a new item file copies them into its own `reviewers`. The board server writes both an add and a remove: an add picks a Slack member and a GitHub login from lists it fetches with the hub's Slack token and `gh`, and the server opens the DM ([the server adds reviewers from fetched lists](docs/adr/2026-11-05-2100-the-server-adds-reviewers-from-fetched-lists.md), extending [the board server removes reviewers itself](docs/adr/2026-11-04-0119-the-board-server-removes-reviewers-itself.md)). The hub sends them as the owner, through the Slack user token pasted on Hub › Integrations › Slack and kept in `~/.claude/kickflip/secrets.json` beside Linear's key, opening the owner's DM with each reviewer, ending every message, or its last attachment when it has one, with a “- :claude_kickflip:” line (“- :robot_face:” while `emoji.list` doesn't show the emoji, as under a token without `emoji:read`), and an edited one with “ · _updated HH:MM_” after it, by which the hub tells its own and the orchestrator's posts from the owner's ([every Slack message ends with a sign-off line](docs/adr/2026-11-12-0400-every-slack-message-ends-with-a-sign-off-line.md)), and records each message as it posts, so a failed one goes again next poll and a posted one never twice ([the hub sends reviewer Slack messages with its own token](docs/adr/2026-11-05-0141-the-hub-sends-reviewer-slack-messages-with-its-own-token.md)). _Avoid_: approvers, watchers

**Task**:

**Linear key**:
The owner’s Linear personal API key, pasted in Hub › Integrations and kept only on the host; pages learn only whether it is set, whether Linear refused it and its workspace. It saves and is checked with Linear on paste, with no Save button, and the hub remembers a refusal until a call with that key gets an answer ([a board picks Linear only while Hub's key works](docs/adr/2026-11-02-1712-a-board-picks-linear-only-while-hubs-key-works.md)). kickflip lists teams and projects, creates projects and issues, and moves tickets with it. The hub's poll uses the saved key's viewer as the owner and advances their Linear tickets from PR state, aggregating every carrying task across boards; without a key the poll moves none ([the hub's poll moves the owner's Linear tickets](docs/adr/2026-11-02-0023-the-hubs-poll-moves-the-owners-linear-tickets.md)). Without a key, no board can pick Linear, and removing the key moves every Linear board to no ticket source ([a task is a card with no ticket, keyed T-<n>](docs/adr/2026-11-09-1500-a-task-is-a-card-with-no-ticket-keyed-t-n.md)).
_Avoid_: Linear token, API secret

**Internal item**:
A work item about the sites themselves rather than the product. Its legacy ref `S<n>` reads `INT-<n>`.
_Avoid_: meta task, chore

**Badge**:
A chip on a task or page that shows a status, such as Install or a PR's state. It may link to what it is about: on a closed task, Install goes straight to the thing to act on (owner, question `badge-tap`). A task's badges are its ticket ID, New on an unsorted ask, and PR and try-build state; the owner's block is a grey word on its time line instead, blocked by and Action needed orange ones, and ready a green one, and a bump shows only as the filled bump icon ([Build on a blocked card queues it, and blocked, bumped and Action needed leave the badges](docs/adr/2026-11-03-0301-build-on-a-blocked-card-queues-it.md)). A badge never acts on the board; a **button** does.
_Avoid_: chip (in what the owner reads), tag, label

**Button**:
A control that acts: it sends something to the board, such as Merge, Block or Grill, or opens a place to act, such as Questions. The open task's workflow row holds Merge, Block or Unblock, the **action button**, Serve or Build when the task has a build script and branch changes and Auto-build is off, and last **Implement** on a Todo task that can start (an owner-blocked Todo task's Implement takes the place of its Unblock), below the details list whose final line holds Notes, Install and Review on GitHub links in that order ([a card's external links share the last details line](docs/adr/2026-10-30-2008-a-cards-external-links-share-the-last-details-line.md)). A task that can be bumped, every open work task in Todo, In Progress or In Review apart from one whose code landed and waits on its owner step ([a bump marks the priority through every lane](docs/adr/2026-11-06-1700-a-bump-marks-the-priority-through-every-lane.md)), carries its bump as an icon at its top right instead, closed or open, as a New task does (the empty icon always shows on a touch screen and with a mouse only while the task is hovered or has focus; a bumped task's filled one always shows) ([a card that hasn't started, or is running, can be bumped](docs/adr/2026-10-29-1639-a-card-that-hasnt-started-can-be-bumped.md)). It sends with no confirm, and on a bumped task it is filled orange and unbumps (`card-unbump {key}`) ([Build on a blocked card queues it, and blocked, bumped and Action needed leave the badges](docs/adr/2026-11-03-0301-build-on-a-blocked-card-queues-it.md)). The control that clears the task's **Action needed** is orange.
_Avoid_: badge, pill (a pill is only a look)

**Badge tone**:
The color of a badge (a status chip on a task or page), picked from one fixed set by what the badge says, through `BoardUI.badge` in `board/public/ui.js`: quiet (gray), normal (blue), notice (orange), danger (red) or ready (green). Each tone takes its color from a **status color**, so a badge is one consumer of the colors, not their source. No badge has a look of its own, so the same tone looks the same everywhere. Buttons and links styled like chips, such as quick replies, **Implement** and "Review on GitHub →", aren't badges; the orange of the button that clears Action needed is the same notice color.
_Avoid_: chip color, badge style, variant

**Status color**:
A color named by what it means, `--color-quiet`, `--color-info`, `--color-notice`, `--color-danger` or `--color-success`, in `shared/colors.css` beside the base palette, in light and dark. That file is the one set of colors for the hub and every board; no page's CSS defines a color of its own ([one colour constants file shared by the hub and every board](docs/adr/2026-10-29-1639-one-colour-constants-file-shared-by-the-hub-and-every-board.md)). Which one a meaning takes follows the **colour rule**; done or passing is success.
_Avoid_: tone token, theme color, badge color

**Colour rule**:
A colour says whose turn it is: red (danger) for faults, such as failed, down, not listening or spending, and the sidebar's "N need you" chip; orange (notice) for attention and work, such as Action needed, the Needs you box, a New task, a Next line while it is someone's turn, a builder's line, Working or Starting; blue (info) only for review and notice, something for the owner to read or see, such as an unread review, a card's Open items, a New task's word, a new version to reload or a changed line's flash; grey (quiet) for idle, such as ticket ids, a Todo or Done task's Next, the Done ring, Stopped or usage that is fine, which takes no other colour. A sidebar row whose board's newest needs read failed keeps its last good line and goes flat gray, "(stale)" after its word, once that line is 15 seconds old; stale outranks every colour on that row, the one place a lower colour hides a higher. When several statuses compete for one mark, the order is red > orange > blue > green > purple > grey (AGENTS.md); purple is a merged PR's badge, past done. Pick a new colour by it ([colour says who's waiting](docs/adr/2026-11-01-1817-colour-says-whos-waiting.md)).
_Avoid_: warning colour (for attention), action colour (for blue)

**Follow-up**:
A work item with a **Parent**: work spun out of another task. It is an ordinary task in every way, shown only by its Parent link ([a follow-up is a work card with a Parent](docs/adr/2026-11-03-0526-a-follow-up-is-a-work-card-with-a-parent.md)).
_Avoid_: backlog item, todo, follow-up tag

**Parent**:
The one task a work item was spun out of, or none: set when a task is created from another task's conversation (its thread, a grill or an answer) with `item add --ask --from`, which files it as an ask through New ([a task the orchestrator files comes in as an ask through New](docs/adr/2026-11-16-1100-a-task-the-orchestrator-files-comes-in-as-an-ask-through-new.md); its threads read a blue Created ticket and Created from line, [a spun-out ticket is a child](docs/adr/2026-11-12-2000-a-spun-out-ticket-is-a-child-with-a-blue-created-line.md)), none for a task from the + or New task. The Parent lists it among its **Children**. The open task shows both as rows of task labels, with **Related to**, Blocked by (every blocker, a Done one kept) and Blocks, the mirror of Blocked by ([a follow-up is a work card with a Parent](docs/adr/2026-11-03-0526-a-follow-up-is-a-work-card-with-a-parent.md), [the open card's rows start at its links](docs/adr/2026-11-15-0840-the-open-card-rows-start-at-its-links-and-drop-status-review-and-ci.md)).
_Avoid_: filed from, origin, epic

**Related to**:
Similar tasks that should be cross-referenced, shown on both tasks. The session links a new task in the call that files it: `item set --relate` adds links, `--unrelate` takes them off on both tasks, and `--related` replaces the list. Planner and builder briefs list a task's Related to, Parent and deps with their notes, for context ([the orchestrator links a new card when it files it](docs/adr/2026-11-05-0130-the-orchestrator-links-a-new-card-when-it-files-it.md)). It neither blocks nor orders anything; Blocked by does that ([cards wait on explicit blocked-by links](docs/adr/2026-10-29-1639-cards-wait-on-explicit-blocked-by-links.md)).
_Avoid_: sibling, link (alone)

**Split**:
A task a grill broke into smaller tasks: the grill planner proposes it, when the code shows separable parts, as one question, Split as proposed or Keep as one task, and on Split the orchestrator files the tasks when the task stages, as Children of the original, each blocked by the earlier ones it conflicts with, and the original closes Done "Split into …" ([a grill can propose splitting its card into a wave](docs/adr/2026-11-07-1216-a-grill-can-propose-splitting-its-card-into-a-wave.md)). The close, `item set --done --split-into <id>,<file>/<id>`, moves every open task that waited on the original onto the tasks it split into ([waves are dropped; deps and Related carry order and grouping](docs/adr/2026-11-14-1200-waves-are-dropped-deps-and-related-carry-order-and-grouping.md)).
_Avoid_: breakdown, epic

**Done archive**:
`data/done-archive.json`, where a finished work task goes once 100 newer Done tasks close, with its resolved questions and the asks it was made from, unless an unfinished task or an open question still needs it. The board build never reads it. The Done list pages it in 100 at a time as Show more reaches the tasks the page holds, each task built as it pages in ([archived Done cards are built as they page in](docs/adr/2026-11-04-1056-archived-done-cards-are-built-as-they-page-in.md)), and a command that names an archived task brings it back to its item file. Its thread stays whole ([the board keeps the newest 100 Done cards, and older ones page in from an archive](docs/adr/2026-11-04-0307-the-board-keeps-the-newest-100-done-cards.md)).
_Avoid_: history, old tasks

**Lane**:
Where a task sits (In Review, In Progress, Todo, Done), set by who acts next ([the lane follows who acts next, and a card waiting on the owner says Action needed](docs/adr/2026-10-29-1639-the-lane-follows-who-acts-next.md)). In Progress means a builder runs on the task: a running build agent, a **checking** item, or a started task between runs; a ready PR whose CI is red, or a red draft on a board that **skips the draft**, waits in In Review reading "Fix the failing CI" until a fix builder starts ([In Progress means a builder runs](docs/adr/2026-11-09-1804-in-progress-means-a-builder-runs.md)). A work task stores its **lane** (todo, progress, review, done, with `lane_at`), which one writer moves with a "Moved to <lane>: <why>" thread line; a task has no status, and blocked, merged and dropped are facts beside the lane ([a card stores its lane, and facts replace statuses](docs/adr/2026-11-07-1400-a-card-stores-its-lane-and-facts-replace-statuses.md)). A work task that has left Todo never drops back to it: blocked, the owner's block included, its build takes a **task pause** In Progress ([a card pause stops its builder at its next stopping point](docs/adr/2026-11-09-1300-a-card-pause-stops-its-builder-at-its-next-stopping-point.md), [a card moves to In Progress only once building starts](docs/adr/2026-11-03-0202-a-card-moves-to-in-progress-only-once-building-starts.md)). A running grill or prototype agent shows its live status but leaves the task where it is. In Review means finished work waits on a person: the reviewers, or the owner's review of a draft ("Review draft PR #n", whatever its CI), Merge, manual steps or the Done of an ask (see **Action needed**), or of a reopened task. An owner message or a new question on a Done task, merged or not, reopens it into In Review: "Your reply waits on the orchestrator" until Claude answers, then the owner's Done, its next step "Tap Done" ([a message or question on a Done card reopens it until the owner's Done](docs/adr/2026-11-02-1952-a-message-or-question-on-a-done-card-reopens-it.md), [a merged card reopens on a message, and its PR badge shows the PR's state](docs/adr/2026-11-03-1843-a-merged-card-reopens-and-its-pr-badge-shows-the-prs-state.md), [a card waiting only to be closed has no Action needed](docs/adr/2026-11-03-0137-a-card-waiting-only-to-be-closed-has-no-action-needed.md)). A reopened task goes to In Progress only once a builder starts on it ([In Progress means a builder runs](docs/adr/2026-11-09-1804-in-progress-means-a-builder-runs.md)). A task waiting only on those moves there from In Progress; one Claude still works on stays in In Progress. A task with several PRs, in any repos, sits where its least-ready PR puts it, shows a PR badge for each, and is Done once every PR has merged or closed with at least one merged ([a card holds several PRs across repos](docs/adr/2026-11-03-1904-a-card-holds-several-prs-across-repos.md)). Todo holds work that hasn't started building: every sorted work task with no build yet, where its **Implement** shows. Discussion keeps a task there: open questions or a prototype pick, with Action needed, answered or resolved questions, grill and prototype agents, a working mark on a message in its thread and a prototype recorded for it ([a card moves to In Progress only once building starts](docs/adr/2026-11-03-0202-a-card-moves-to-in-progress-only-once-building-starts.md)). Todo's header has a filter: a funnel opening four boxes (Ready, Discussing, Planning, Blocked, the owner's block included), all checked, where an unchecked box hides every Todo task with that property and nothing else; the funnel goes orange and the count reads "N of M" while one is unchecked ([the Todo header has a filter](docs/adr/2026-11-12-0600-the-todo-header-has-a-filter.md)). A started task that gets a question keeps its lane ([an unstarted card waits on its questions in Todo, and its one action button follows what it waits on](docs/adr/2026-10-30-1309-an-unstarted-card-waits-on-its-questions-in-todo.md)). Each lane has one fixed order, with no sort menu ([each lane has one fixed order](docs/adr/2026-11-03-0223-each-lane-has-one-fixed-order.md)): every lane but Done lists its bumped tasks first, the earliest bump on top ([a bump marks the priority through every lane](docs/adr/2026-11-06-1700-a-bump-marks-the-priority-through-every-lane.md)); Todo then lists the rest oldest made first, so a new task joins the bottom ([new Todo cards join the bottom, so old ones leave first](docs/adr/2026-11-05-2345-new-todo-cards-join-the-bottom.md)); In Progress, after its bumped tasks, by when each came into the lane, its reopening or its latest build agent's start, the newest arrival on top; In Review, after its bumped tasks, by when the PR was first sent to a reviewer, or a reopened task's reopening, the newest on top; Done by when each task closed, or for an answered ask when Claude last answered, the most recent on top. Done shows 10 tasks, then a Show more, the thread's, that adds 10 and says how many are left; a task the owner has open stays shown ([answered asks fold into the one Done list, the kind shown in the ticket slot](docs/adr/2026-11-09-1430-answered-asks-fold-into-the-one-done-list.md)). Every task, a New task included, ends with one muted line holding the time its lane sorts by: the time only today, the day too before today ("10/31, 2:49 PM"), and the year too past 365 days. A task with no such time has no time on that line.
_Avoid_: column, status (status is the item's own field)

**Checking**:
The item status a builder's `builder done` sets when it hands back finished work with unverified judgment calls, including one naming why it couldn't finish. The task sits in In Progress reading "Orchestrator review" while the owning session verifies the calls; its `builder verified` **finishes** the task ([finishing a build is one step](docs/adr/2026-11-04-1611-finishing-a-build-is-one-step.md)). Only a task in Done unblocks dependents ([site cards build in parallel when their files don't overlap](docs/adr/2026-10-29-1639-site-cards-build-in-parallel-when-their-files-dont-overlap.md), [the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)).
_Avoid_: verifying, in QA, review (review is the reviewers' part)

**Stale**:
A task the board reads as having had no updates for a while, on the signals it already checks: a run still recorded as running with no progress line and no change to its Claude transcript for at least 15 minutes (counted from its start before its first progress), or whose headless process is gone; or a review waiting more than seven days since its first review link went out, which stays In Review ([a PR in review shows its age, and goes stale after seven days](docs/adr/2026-10-29-1639-a-pr-in-review-shows-its-age-and-goes-stale-after-seven-days.md)). Its **footer status** reads a grey "stale", a stale run's live status and phase bars keep their colour, with no tap on it, and the task is a `stale` wait on the orchestrator, which restarts it or flags it **stalled** ([stale is automatic, stalled is the orchestrator's flag](docs/adr/2026-11-06-1252-stale-is-automatic-stalled-is-the-orchestrators-flag.md), [stale is a footer word after 15 minutes](docs/adr/2026-11-13-2030-stale-is-a-footer-word-after-15-minutes.md)). Silence calls for a check, without establishing that the process has failed.
_Avoid_: stalled (only the orchestrator's flag), old, overdue

**Footer status**:
The words after the time on a task's last line: the **owner's block** ("blocked" or "blocked until <time>"), then blocked by, or the task's **phase** word (every lane but In Progress) when neither is there, then a grey "stale", a grey "held while host recovers", an orange "pausing · <cause>" or a grey "paused · <cause>" in place of the block it names ([a card pause stops its builder at its next stopping point](docs/adr/2026-11-09-1300-a-card-pause-stops-its-builder-at-its-next-stopping-point.md)), then an In Progress task's phase bars (owner, gh327-pause; [every lane has phases](docs/adr/2026-11-11-1200-every-lane-has-phases.md)). Action needed, the unread count and a red "stalled", rightmost, go on a row of their own under it, drawn only when it has one ([Action needed and new messages get their own row](docs/adr/2026-11-12-0630-action-needed-and-new-messages-get-their-own-row.md)).
_Avoid_: time line, status line (the line under the title)

**Next step**:
Claude's next step on a task and what sets it off, such as "Next: merge when CI is green", kept in the item's `next` and cleared once done. A task waiting on its reviewers reads its next step from GitHub instead ([a card derives its lane and its review next step from GitHub, never from a kept status](docs/adr/2026-10-29-1639-a-card-derives-its-lane-from-github.md)), and one waiting on the owner reads its action. It is orange while it is someone's turn and grey on a Todo, Done or owner-blocked task. It shares its place under the title with the builder line, which takes it while a builder record is open, and an In Progress task with neither reads "Next: none set yet": the CLI refuses a `builder done` or `item set` that would leave one so without `--next` ([an In Progress card always has a builder line or a Next](docs/adr/2026-11-03-0237-an-in-progress-card-always-has-a-builder-line-or-a-next.md)). A Next set while the task has an open question clears once a build starts on it, or once Claude's acting leaves none of its questions unresolved ([an answer stops waiting once it's acted on, and a Next set during the card's questions clears](docs/adr/2026-11-03-1313-an-answer-stops-waiting-once-its-acted-on.md)).
_Avoid_: plan, notes (**Notes** is the task's write-up), todo

**Waits on**:
Who the task is waiting for: the owning session's check, the owner's Ready, the owner's other action, the builder, the reviewers, the merge, or nobody.
_Avoid_: blocked by, assignee

**Phase**:
Where a work task is within its lane, stored on the task beside its lane and written with it ([every lane has phases]({ADR})). Todo: new, discussing, grilling, prototyping, staging, ready. In Progress: reading, building, checking, landing, shown only as the progress bar; a builder's own tests are part of building and the land's run part of landing ([builders run only their own tests](docs/adr/2026-11-14-0600-builders-run-only-their-own-tests-and-the-land-runs-affected-once.md)). In Review: draft, reviewers, merge, stale. Done: merged, closed. The settle pass writes In Progress and In Review phases from the builder and the PR, a close writes merged or closed, and a phase change inside one lane writes no thread line. Every lane but In Progress ends the task's last line with the phase word, toned by who acts next: grey new, draft, stale, closed; blue grilling, prototyping, discussing on the owner's turn; orange staged (the stored phase stays staging), "pending review", "pending merge"; green ready; purple merged; grey discussing on the orchestrator's turn.
_Avoid_: state (the old name of a Todo task's phase), status (an item's `status` field is a different thing)

**Todo phase**:
What a task made from a **New task** does next: **discussing** (a conversation in its thread, from the orchestrator's first reply: a New task's Discuss, a reviewer's Slack request for work, or a GitHub or Linear issue named in an ask; it reads just "discussing", blue on the owner's turn and grey on the orchestrator's, never goes to In Review, and a discussion the owner settles without a build is closed from there with no ticket), **grilling** (questions on the task), **prototyping** (takes on the task; answering a round returns the task to discussing), **staging** (the owner has acted: a Send that left a grilled task nothing open, an Implement, or a Reply on a ready task, whose words the board wrote into its notes; the orchestrator judges it, first folding a discussed task's agreement into a Build notes section) or **ready** (its notes leave the owner nothing to decide, so it can be built; the plan lives only in the notes). The orchestrator reaches for the next step in one order: keep discussing, a visual once the topic is complicated, a grill or prototype when asked or clearly useful, and Implement only on the owner's explicit word ([a new task is a conversation](docs/adr/2026-11-12-0500-a-new-task-is-a-conversation.md)). Only the board sets staging; the session sets the others with `item set --phase` (`reply` on a New task sets discussing), and ready only from staging, with a `--text` line saying what it checked against the board, or on an Implement ask it files. A finished grill's questions are **screened** first: they wait on the orchestrator, which settles the ones the board already answers, and reach the owner with `question publish` or 15 minutes on ([every signal that wakes the orchestrator says what to do](docs/adr/2026-11-07-0043-every-signal-that-wakes-the-orchestrator-says-what-to-do.md)). A question added on a ready or staging task moves it to grilling. Moving a discussing, staging or ready task to grilling or prototyping starts that round from code ([staging, then ready](docs/adr/2026-11-07-0700-staging-then-ready.md)). The board enforces the five: `--phase` refuses any other, on a task that has left Todo too, and `--state` is refused with a pointer to `--phase`, and ready while the task has an open question. Until it has one, the task reads New beside its ticket id and is never pulled. So does an older task an agent added with `item add` and no `--phase`, which a `card-added` event hands the session to link and file ([the orchestrator links a new card when it files it](docs/adr/2026-11-05-0130-the-orchestrator-links-a-new-card-when-it-files-it.md)); on a board `item add` now refuses a task with no `--phase` ([a board's lessons live in the product](docs/adr/2026-11-06-1700-a-boards-lessons-live-in-the-product.md)). A Ready task's time line reads a green "ready" in Action needed's place ("10:26 · ready · 2 new messages") while nothing blocks it and nothing waits on the owner, and the idle pull takes it like any settled task; a staging task reads an orange "staged" there and is never pulled ([a new card is ready, grilling or prototyping, and reads ready in green when it is](docs/adr/2026-11-03-0516-a-new-card-is-ready-grilling-or-prototyping.md)).
_Avoid_: triage state, task state, status (an item's `status` field is a different thing)

**Action needed**:
The orange words last among the orange ones on a task's time line ("10:26 · blocked · blocked by #53 · Action needed"), on a task waiting on the owner, in any lane ([Build on a blocked card queues it, and blocked, bumped and Action needed leave the badges](docs/adr/2026-11-03-0301-build-on-a-blocked-card-queues-it.md)): an open question or a prototype pick, a green draft's Ready, the Done of an ask, manual steps on an approved PR, with **auto-merge** off an approved PR's Merge, or a **stalled** task's "stalled: <why>", which a message in its thread clears, its Send or Reply orange. It links to the thing to act on. Reviewer waits and owner-blocked tasks get none ([the lane follows who acts next, and a card waiting on the owner says Action needed](docs/adr/2026-10-29-1639-the-lane-follows-who-acts-next.md)), and so does a reopened task waiting only on the owner's Done, which is only waiting to be closed ([a card waiting only to be closed has no Action needed](docs/adr/2026-11-03-0137-a-card-waiting-only-to-be-closed-has-no-action-needed.md)). An unstarted task with open questions carries it in Todo ([an unstarted card waits on its questions in Todo, and its one action button follows what it waits on](docs/adr/2026-10-30-1309-an-unstarted-card-waits-on-its-questions-in-todo.md)).
_Avoid_: open items, needs you (Needs you is what waits on the owner)

**Request**:
The owner's ask for a grill, a prototype or a **visual** on a task: the thread composer's fire, eye or image, each sending at once, or /grill, /prototype or /visual typed in the box on Reply, sending `grill-more`, `prototype-request` or `visual-request` with whatever was typed; a question's own eye on Waiting on you asks for a prototype of that question. A request with nothing typed is one gray **status log** line in the thread, "Grill requested", "Prototype requested" or "Visual requested", keyed `grill`, `prototype` or `visual` as every button without a text box keys its line ([a button without a text box posts a keyed status line](docs/adr/2026-11-06-0021-a-button-without-a-text-box-posts-a-keyed-status-line.md)); one with text is the owner's message carrying it, with that status in the message's footer, and "waiting…" to its right until Claude picks it up, then "thinking…". An answer submitted from Waiting on you is likewise a message whose footer reads "answers submitted". A question asked for a prototype reads "prototype requested", locked, until a question naming it in `round_of` resolves it, and `question resolve` refuses it; a prototype request still waiting 30 minutes on with no prototype agent running comes back to the session as `prototype-overdue` ([a button tap is a status line or a message footer](docs/adr/2026-11-04-2130-a-button-tap-is-a-status-line-or-a-message-footer.md), [a prototype request waits for its prototype](docs/adr/2026-11-04-2130-a-prototype-request-waits-for-its-prototype.md)).
_Avoid_: Grill button, Prototype button (on a task)

**Brief**:
The orchestrator's handover to a grill, prototype or **visual** agent: what the discussion settled, what is still open, what the agent's questions, takes or page should cover, and the files that matter. Every such launch needs one: a **request**, a task filed or sorted into grilling or prototyping, a gate's yes, a prototype answer with no pick or `item set --phase grilling|prototyping` leaves the task owing it, a `brief` wait for the orchestrator, and `item brief <key> --kind grill|prototype|visual --file <draft.md>` writes it into the task's notes as "Brief for <kind> round N", from which the board launches the agent, which reads it first. **Visual**:

**Action button**:

While the task carries **Action needed**, the button that clears it is orange, in the notice color: the task's `resolvedBy` from `board/domain.mjs`, by the action's kind. A question or a pick makes Questions orange (a pick makes Prototypes orange too), a green draft's Ready or manual steps make Review on GitHub orange, and an approved PR's Merge makes Merge orange. An owner-blocked task's Questions stay plain. A reopened task waiting only on the owner's Done has its thread's Done primary, in the accent color ([a card waiting only to be closed has no Action needed](docs/adr/2026-11-03-0137-a-card-waiting-only-to-be-closed-has-no-action-needed.md)).

**GitHub tick**:
The session's steps for PR comments, CI, review, conflicts and merging, defined in SKILL.md. The hub polls GitHub with Node and gh, writes new owner and reviewer comments into each task's thread, closes a task whose PR merged, then wakes the board on a change ([the hub's poll records merges and PR comments on the card](docs/adr/2026-11-02-2335-the-hubs-poll-records-merges-and-pr-comments-on-the-card.md)); the tick reads each task with `board.mjs pr` and records the newest handled event with `item set --gh-since`. With Hub's Linear key set, the poll also moves the owner's Linear tickets from PR state, so the session leaves those moves to the hub; without a key the poll moves none ([the hub's poll moves the owner's Linear tickets](docs/adr/2026-11-02-0023-the-hubs-poll-moves-the-owners-linear-tickets.md)). The owner's monitor skill is optional ([the hub reads GitHub itself](docs/adr/2026-11-01-2314-the-hub-reads-github-itself.md)).

**Auto-merge**:
A board setting, `auto_merge` in its `board.json`, off unless set: on, the hub's GitHub tick merges a PR once it is approved, CI is green and its merge state is CLEAN; off, the task shows the owner Action needed and a Merge button, which reads "Merging…" until the board server merges the PR or says in the thread why it didn't. The board's Settings modal toggles it, and the watcher prints it with every wake as `setting auto-merge on|off`. A setting, not a **rule**, since the board itself acts on it ([Auto-merge is a board setting, off by default, and the owner merges from the card](docs/adr/2026-10-29-1752-auto-merge-is-a-board-setting-off-by-default.md)).
_Avoid_: merge rule, merge policy

A task with no PR lands the same way: with Auto-merge off its builder's `done` stops after the tests, and the task waits in In Review with a Merge button; the tap makes the board server rebase it onto main as it is now, rerun the tests and land it, sending a conflict or a failing test to the task's own builder, its session resumed with the lander's brief, or a fresh headless lander when no session can be resumed or the session is past 150k tokens and an hour cold, a cold one's lander on Sonnet with a handoff ([a cold resume past 150k starts a fresh agent with a handoff](docs/adr/2026-11-15-0040-a-cold-resume-past-150k-starts-a-fresh-agent-with-a-handoff.md), [a land waits for your Merge](docs/adr/2026-11-04-2100-a-land-waits-for-your-merge.md), [a builder resumes to land its own conflict](docs/adr/2026-11-09-1500-a-builder-resumes-to-land-its-own-conflict.md)).

**Rebase run**:
The headless run the board server starts on a task whose open PR, draft or ready, GitHub reads CONFLICTING, once per head and base: in the task's worktree, or one made from the PR's branch, it rebases onto the board's branch and finishes with `builder done`, which runs the tests the change affects once and force-pushes the PR's branch with a lease and leaves the PR as it is. The task stays In Review, its live status the run's; one it can't resolve hands the task back with a judgment call, to the orchestrator before the owner. A merge counts the run's push after an approval as trivial when it only replayed the PR's commits, and says so. The GitHub tick no longer rebases ([the board rebases a conflicting PR with a headless run](docs/adr/2026-11-06-0200-the-board-rebases-a-conflicting-pr-with-a-headless-run.md)).
_Avoid_: rebase lander, conflict fix

**Orchestrator stop**:
The orchestrator's stop of a run the board launched on a task, with every process under it: `board.mjs builder stop` for its headless builder, lander or rebase run, `board.mjs land stop` for its land, the suite included. A stopped build stays In Progress, waiting on the orchestrator, and nothing relaunches it; a stopped Merge land leaves the land queue and the task's Merge shows again. The task's live status and status log line read the stop in one pattern, "build stopped by orchestrator" or "land stopped by orchestrator". A bump, the owner's or the orchestrator's `item bump`, puts the task's land ahead in the land queue without stopping the one running ([the orchestrator stops the board's own runs](docs/adr/2026-11-05-1809-the-orchestrator-stops-the-boards-own-runs.md)).
_Avoid_: kill, cancel, Stopped (the status), land first

**Commit standard**:
Every commit a task lands has a Conventional subject of at most 100 characters, "<type>(<scope>): <summary>", the type one of the Angular set (feat, fix, refactor, docs, test, chore, perf, build, ci, style, revert), a "!" for a breaking change, the scope optional, lowercase and naming the area; the task's ref is never in the subject but in a `Refs: <ref>` trailer above Co-Authored-By. Land squashes the task's branch into one such commit: the builder's `--title`, else the first commit's subject, over the first commit's detail, then `Refs: <ref>` and each Co-Authored-By the branch's commits carry, once, with no blank line between; it refuses a squash subject in any other shape ([every land squashes the branch into one commit](docs/adr/2026-11-11-2318-every-land-squashes-the-branch-into-one-commit.md)). A GitHub board's PR title is the same kind of subject and its squash merge is that title over the PR's body and trailers; a release is `chore(release): <x.y.z>` listing the subjects landed since the last tag ([commits are Conventional and name their card in a Refs trailer](docs/adr/2026-11-11-1700-commits-are-conventional-and-name-their-card-in-a-refs-trailer.md)).
_Avoid_: "#N: subject", ref prefix, Version X.Y.Z (as a release subject)

**Release task**:
An ordinary task whose commit is `chore(release): <x.y.z>`, made by `scripts/release.mjs <x.y.z> --ref <ref>`. Its land checks the version against `package.json`, tags the landed commit `v<x.y.z>` and pushes the tag after main while Push release tags is on; the tag publishes to npm.
_Avoid_: release step, tagging by hand

**Landing**:
A board's one choice of how a task lands, a section above Auto in Board settings, shown on a GitHub board that builds in its own clone and on the hub board, which starts on Merge (no other local board shows it): **Draft PR** (each task opens a draft PR and waits for the owner to mark it ready), **Ready PR** (the hub's GitHub check marks the draft ready for review once its CI passes) or **Merge** (no PR opens; each task lands on the board's base branch, which is pushed, and turning it on needs Push main granted, except on the hub board). On a PR mode the hub board's builders branch from origin's base branch in its folder and each finish opens a PR; on Merge they branch from the folder's own base branch and land there, pushing it only with Push main granted. Reviewers show only while tasks open PRs. The words never say "main", whatever the base branch. **Auto-merge** stays its own switch and covers both: merging an approved PR, and landing a build that waits to merge into the base branch ([Landing is one choice](docs/adr/2026-11-05-0200-landing-is-one-choice-draft-pr-ready-pr-or-merge.md), [the hub board shows Landing](docs/adr/2026-11-05-1100-the-hub-board-shows-landing-and-defaults-to-merge.md)).
It is stored as two `board.json` settings, read together: `prs`, on unless set (off is Merge), and `skip_draft`, off unless set (on is Ready PR); `board.mjs settings set prs|skip-draft` sets each. With no reviewers on the board a PR merges once it is green and clean, with no approval ([a land waits for your Merge](docs/adr/2026-11-04-2100-a-land-waits-for-your-merge.md), [a board can skip the draft](docs/adr/2026-11-04-1913-a-board-can-skip-the-draft.md)).
_Avoid_: PRs switch, Skip the draft, PR mode, no-PR mode, auto-ready

The hub's one **Triage overnight** switch, a job in **Overnight work**, on by default and the same for every board; no board has a setting for it ([one hub Triage overnight switch replaces the board toggle](docs/adr/2026-11-16-0100-one-hub-triage-overnight-switch-replaces-the-board-toggle.md)). On, once a night from the middle of the hub's quiet hours (03:00 by default) to their end, when two or more tasks wait on open questions, nothing builds, usage isn't paused and something changed since the last triage, the board server declares topic `overnight-triage-<date>` ("Overnight triage <date>") and sends `overnight-triage {date, topic, cards}` before any pull. The session merges overlapping questions onto the newest of their tasks, resolving the others "Replaced by" it and copying the owner's answer onto each task once it lands; merges duplicate tasks; and does the Todo hygiene over the Todo and Stale tasks, never Done: duplicates, tasks a newer task covers, tasks ready to close and stale deps. It asks one question per finding it can't settle on that topic, held until morning by quiet hours, and replies to the event, which lets the pull go ([triage runs once overnight on cards waiting on your answers](docs/adr/2026-11-04-1900-triage-runs-once-overnight-on-cards-waiting-on-your-answers.md)).
_Avoid_: cleanup, grooming

**Auto review**:
The board's `auto_review` setting, off by default, whose helper in Board settings' Auto section says it may use a lot of usage. On, the hub's poll lists the repo's open PRs from others that touch a file one of the board's tasks changed, or that ask the owner for review, in `data/incoming.json`, and while the board is idle as for **Auto-pull** the board server sends `pr-review` for one at a time. The session posts one Comment review per PR head under the owner's login, adding only new points, or holds it for the owner when it finds a blocker, disagrees with a task's decision or clashes with a task in progress, and records it with `review record`. The board's "Auto Review" lane shows each PR as needs you, reviewing or posted, older posted ones under "Posted earlier"; a held one is also in Needs you and pushes ([each board reviews incoming PRs that touch its work, in an Auto Review lane](docs/adr/2026-11-03-1731-each-board-reviews-incoming-prs-that-touch-its-work.md)).
_Avoid_: review mesh, PR watcher

**Idle notification**:
The board's `idle_notification` setting, off by default, which reads "Idle notification" in Board settings' Auto section and turns on or off with no confirmation. On, once the board has been strictly idle for 15 minutes (no agent running, no grill or prototype under way, nothing in Orchestrator review and no pulled task waiting; a working mark doesn't count), the board server pushes "<board> has gone idle" once, with the tasks landed since the last idle push; it pushes again only after the board has been busy and idle again ([an idle board pushes once when it has gone idle](docs/adr/2026-11-04-0257-an-idle-board-pushes-once-when-it-has-gone-idle.md)).
_Avoid_: idle reminder, armed reminder

**Notes**:
The owning session's understanding of a work item so far: what was asked, what is settled, what is open. The task's own Markdown file in its item file's folder, named in `plan`: the board makes `<id>-notes.md` with the task and is its only writer, appending a section on each `item notes` and keeping it read-only, so no two tasks share one ([the board owns a card's notes file](docs/adr/2026-11-09-1100-the-board-owns-a-cards-notes-file.md)); a task from before then keeps the name it had, or with no file shows its short `notes` text. "Notes ↗" opens them as a page sized for the phone, first on the open task's final details line before Install and Review on GitHub; the board keeps no summary of them and a task with no notes omits the link. The thread keeps the short news ([notes replace the full plan, and a card starts on its own](docs/adr/2026-10-29-1816-notes-replace-the-full-plan-and-cards-start-on-their-own.md), [notes is a link in the details list, with no stored summary](docs/adr/2026-10-30-1626-notes-is-a-link-in-the-details-list.md), [a card's external links share the last details line](docs/adr/2026-10-30-2008-a-cards-external-links-share-the-last-details-line.md)).
_Avoid_: full plan, plan, spec

**Owner's block**:
A block the owner sets on a work task with its Block button, which opens the shared duration picker: Forever, until the owner taps Unblock, or until a time, its **pick-up time** ([the owner's hold is a block](docs/adr/2026-11-15-2230-the-owners-hold-is-a-block.md)). Block and Unblock apply on the board at once, and the board server writes them to the item file with the owner's thread line, "Blocked", "Blocked until <time>" or "Unblocked" ([the CLI and board server do the board's housekeeping](docs/adr/2026-11-02-2044-the-cli-and-board-server-do-the-boards-housekeeping.md)); the item file keeps it as `held` and `pick_up_at`, the event is `card-hold`, and the built task carries `ownerBlock {until}`. The task is **blocked**: it doesn't start, and a running build takes a **task pause** "blocked" In Progress, until it is unblocked (an owner-blocked Todo task's Implement unblocks and starts it, [a held Todo card shows Build in place of Unhold](docs/adr/2026-11-03-0234-a-held-todo-card-shows-build-in-place-of-unhold.md)) ([the board applies the owner's Hold, Resume and Done at once](docs/adr/2026-11-02-0009-the-board-applies-the-owners-hold-resume-and-done-at-once.md)). The task's last line reads "blocked" or "blocked until Wed 9:00 am" after its time. A task that leaves Todo is never still owner-blocked: any write that takes it out (a build's start, a hand-back, `--done`, `--pr`, `--pushed`) clears the block and its pick-up time. The board shows it on a Todo task, and on an In Progress task the owner blocked, whose build the block pauses until the Unblock beside Reply in its thread or the action row's Unblock ([threads say Reply, with Hold, Resume and Reopen beside it](docs/adr/2026-11-12-1300-threads-say-reply-with-hold-resume-and-reopen-beside-it.md)). Every other action-row button, Unblock included, asks to confirm first, through `B.confirm` (`dialogs.js`). It is separate from the usage pause, **Pause board** and **Pause hub**, which read paused.
_Avoid_: held, hold, on hold, frozen

**Blocked**:
A work task that waits before it can start, on any of three things, each reading blocked: other tasks (its deps, until each reaches Done), a condition an agent can check, which the orchestrator clears with `item set --blocked-until ""` once it holds, either with a reason, or the **owner's block**. Its time line reads "blocked by #53" or "blocked until <condition>", then ", <reason>", and the owner's "blocked" or "blocked until <time>". A time is the owner's block, never a condition ([nothing waiting on the orchestrator is missed](docs/adr/2026-11-05-2358-nothing-waiting-on-the-orchestrator-is-missed.md)). A block only keeps a task from In Progress: a blocked task in Todo is grilled, prototyped, staged and set ready as any other. A ready task whose block ends waits in Orchestrator review for a **re-check** (`recheck_at`): the orchestrator re-reads its notes and answered questions against what landed, settles a stale one with `question settle <id> --note` or sends the task back to grilling, and releases it with `item set --phase ready --text "<what it re-checked>"` ([a block only keeps a card from In Progress](docs/adr/2026-11-09-1939-a-block-only-keeps-a-card-from-in-progress.md)). Blocked In Progress, its build takes a **task pause** and the task stays In Progress ([a card pause stops its builder at its next stopping point](docs/adr/2026-11-09-1300-a-card-pause-stops-its-builder-at-its-next-stopping-point.md)); blocked In Review, it stays but can't land, its Merge disabled ([a block past Todo bumps a build and holds a land](docs/adr/2026-11-06-0102-a-block-past-todo-bumps-a-build-and-holds-a-land.md)).
_Avoid_: held (the owner's block is a block), waits on (who the task waits for)

**Pick-up time**:
When the **owner's block** until a time ends itself: `pick_up_at` in its item file (`board.mjs item set --pick-up-at`), or the `until` of the owner's newer `card-hold`. Within a minute of it the board server unblocks the task, writes a thread line, and sends `card-unblocked {key, until}` unless a dep is unfinished, so it starts on its own once nothing else blocks it ([a card can be held until a time](docs/adr/2026-11-02-1727-a-card-can-be-held-until-a-time.md)). A bump doesn't skip it; unblock the task or change the time to start early. It is separate from a Linear due date.
_Avoid_: due date, reminder, snooze (for a task)

**Builder**:
An agent (Claude Opus, Claude Sonnet, Codex…) working on a work item, which owner-facing words call an implementer ([a Todo card's button reads Implement, and Build and Serve only mean the package](docs/adr/2026-11-03-1549-a-todo-cards-button-reads-implement.md)), with one builder record each (`board.mjs builder … --agent <name>`; the first is `main`). The record holds its label, kind (claude or codex; a record written as opus or sonnet reads as claude with that model), model (opus or sonnet for claude, set by `builder start --model`, which prints "model: Claude Sonnet"), start, ETA and finish, not its progress. Each progress line (`builder progress --phase <phase> "<detail>"`, which needs `--site`) goes only to the task's thread, as a **status log** line: a phase, Reading, Building, Checking or Landing, and a detail of at most 80 characters, refused when longer ("Building: fix for the scroll jump"; another agent's reads "Codex building: …"), shown as one line with no bubble. Status log lines written before phases stay as written ([a builder status line is a phase and a short detail](docs/adr/2026-11-03-0128-a-builder-status-line-is-a-phase-and-a-short-detail.md)). The task's status line under its title is the thread's newest status line since its earliest running agent started, its phase first ("Building · fix for the scroll jump · 3m ago"), or "Starting" before the first, with its age, behind a pulsing dot as Orchestrator review and Working on it have, and, once a status log line has a phase, five bars at the end of the task's time row, after its unread count, finished phases filled and the current one pulsing, only on an In Progress task while a builder runs ([a building card's phase bars end its time row](docs/adr/2026-11-03-1519-a-building-cards-phase-bars-end-its-time-row.md)), and an optional "ETA about 4:30 pm" line under that (owner ask on INT-76). In the thread every implementer's status log line stays orange, dot included, whether its agent is working or done (owner, task INT-77). `builder done` marks the record done and keeps it; with judgment calls on it the record is marked `handed_back`, the fact that replaces the old checking status, until a handover or a close. The thread shows each record as **agent lines** among its messages, with no bubble: "Claude Opus implementer started" (or "Claude Sonnet implementer", "Codex implementer"; the model, not the label, names it, a label's builder reading implementer) at its start, always orange and with its ETA while the agent runs, and "Claude Opus implementer finished" at its finish, the only green one (owner, question `int42-agents-look`, option C; owner ask on INT-63). The session's own thread summary closes the work. A builder is a **planner** or an **implementer**: planners are the grill and prototype agents, which write no output code; every other kind is an implementer. A planner's model defaults to Sonnet for a prototype and Opus for a grill ("Claude Sonnet prototype started"); its status and started lines in the thread are the owner's blue (`--accent`, the one human blue, [one human blue](docs/adr/2026-11-03-1627-one-human-blue.md)), and on the task take the task's lane colour, Todo's grey with grey dashes ([every run takes its lane's colour](docs/adr/2026-11-06-0145-every-run-takes-its-lanes-colour.md)); while a build runs, the build's line wins on the task; and a running planner takes no implementer slot and leaves the board idle ([planners and implementers are two kinds of agent](docs/adr/2026-11-03-1551-planners-and-implementers-are-two-kinds-of-agent.md)). The kind words are for code and ADRs; the screen says what each agent does.
_Avoid_: worker, bot

**Helper**:
An agent that another agent on a task, or the orchestrator, asks the board for with `board.mjs agent launch <key> --name <n> --task "<t>" [--writes]`. It runs beside the task's build under its own name, and its status log lines carry that name ("Tests building: …"). The board server launches it headless on Claude. It launches at once on its task's **implementer slot** ([the implementer limit counts cards In Progress](docs/adr/2026-11-13-1126-the-implementer-limit-counts-cards-in-progress.md)). One that writes works in its own worktree off the task's branch, which the task's builder brings in with `agent merge`. It hands back with `builder done --agent <n> --text`, which its spawner reads with `agent wait` ([the implementer limit counts agents, and any agent on a card can ask the board for helpers](docs/adr/2026-11-06-0425-the-implementer-limit-counts-agents-and-a-card-spawns-helpers.md)).
_Avoid_: subagent (for one the board runs), sub-builder

**Dispatched record**:
A builder record open before its agent runs, marked with who opened it: `dispatched: 'tap'` when the owner's Implement tap (or the start of a build ready released) opened it, `dispatched: 'hub'` when the board server opened it to launch a pulled build or a planner (a grill or a prototype) itself, `dispatched: 'session'` when the session ran `builder start --dispatch` right before it launches some other agent. Either way the task's builder line reads "starting" from then until the agent's first status log line. The agent's own `builder start` takes it up: the kind, a Claude model and the worktree stay, the record starts again at now and is no longer dispatched. A `--dispatch` on a record the tap opened changes nothing and prints "already open"; a `builder start --agent <other name>` refuses while the tap's main record is open and not taken up. The session never posts "a builder is working" itself ([the session opens the builder record when it dispatches an agent](docs/adr/2026-11-03-0513-the-session-opens-the-builder-record-when-it-dispatches-an-agent.md), [a card reads starting from its tap, with one dispatched mark](docs/adr/2026-11-03-1718-a-card-reads-starting-from-its-tap-with-one-dispatched-mark.md)).

**Judgment call**:
A decision a builder makes that its brief didn't settle, recorded on its builder record as it makes it (`builder call <key> "<call>"`, one plain line), or a "Question: …" it asks the session before building. The thread shows a record's calls as one collapsed entry under its agent lines. The session checks them against the owner's words and the other tasks and marks the record **verified** (`builder verified`), which finishes a handed-back build in the same step; finishing refuses while a record on the task has a call after that mark. A builder start on a record with unverified calls resumes that build, calls and worktree kept ([a builder records its judgment calls and the session verifies them before land](docs/adr/2026-11-03-0514-a-builder-records-its-judgment-calls-and-the-session-verifies-them.md)).
_Avoid_: guess, assumption, decision log

**Builder ask**:
A question a running builder puts to the board's session, the **orchestrator**, only when blocked (every way forward would likely be thrown away: a spec that contradicts itself or the code, a rule that needs the owner's go before code is written, or a fact only the orchestrator has; `builder ask <key> "<question>"`, id `ask<n>`), then waiting with `builder asks <key> --wait` (returns within 10 minutes) and handing the question back as a "Question:" call after 30 minutes without a reply. Everything else it decides and records as a **judgment call**, an out-of-scope finding as "Found: …". It shows in the task's thread as a normal message named by the builder's model, "Claude Opus builder", and wakes the session with `builder-ask {key, ask, agent, text}`. The session answers it (`builder answer`) or, when it isn't confident or wants the owner's opinion, defers it (`builder defer`); both show as "Orchestrator", the name the thread gives every line the session writes. The task stays quiet meanwhile: neither line is unread, pushed, nor answers an owner message. A deferred ask is a "Question:" **judgment call**, and the session's review puts it to the owner as a task question naming the ask, after its other checks and before a draft PR or In Review; `builder verified` refuses until it has. A task whose only open questions are deferred asks waits on the owner from In Progress with Open questions, its new questions one unread message on the task and one stored "N questions added" line in its thread ([a Questions added line is stored and stays in the thread](docs/adr/2026-11-13-0130-a-questions-added-line-is-stored-and-stays-in-the-thread.md)), and no **Action needed** ([a builder asks the orchestrator mid-build, and only what it defers reaches the owner](docs/adr/2026-11-04-0247-a-builder-asks-the-orchestrator-mid-build.md)). The owner never answers a builder mid-build.
_Avoid_: builder question, check-in

**Board ask**:
A question one board puts to another board in the same hub, which that board's **orchestrator**, the steward of its topic, answers: any agent on the asking board asks (`ask <route> "<question>" [--from <key>]`) when its own repo doesn't explain why something is the way it is, and carries on, reading the answer later with `asks` (`--wait` to wait). On the answering board it is a `board-ask` event, an entry in the **New strip** reading "Asked from /<route>" with no Edit or Delete, and an `ask` wait on the orchestrator until it answers (`answer <id> --text`, links welcome, no confidence); while no orchestrator runs there it stays queued and its wait carries over. On the asking task it is a quiet grey "Asked <route>: <question>" line, then the answer as an ordinary thread message named for the answering board, whose `board-answer` event wakes the asking board ([a board asks another board and its orchestrator answers](docs/adr/2026-11-15-0200-a-board-asks-another-board-and-its-orchestrator-answers.md)).
_Avoid_: ask alone (in code an ask is a **New task**), cross-board question

**Stalled**:
The orchestrator's flag on a **stale** task it can't restart, `board.mjs item stall <key> --reason "<why>"`: its run stops, its record stays open and stopped, its worktree stays, and it keeps its implementer slot while it stays In Progress. The task stays in its lane with a red "stalled" in its **footer status** and an Action needed "stalled: <why>" in Needs you, with one push, waiting on nobody but the owner, whose next message in its thread clears the flag and reaches the orchestrator ([stale is automatic, stalled is the orchestrator's flag](docs/adr/2026-11-06-1252-stale-is-automatic-stalled-is-the-orchestrators-flag.md)).
_Avoid_: stale (the board's automatic reading), stuck, hung, failed

**Worktree**:
The git worktree a builder works in, never the folder the session, a running app or the hub uses. A board's is `~/.claude/kickflip/worktrees/<card id>` on branch `<card id>` from its chosen repo branch, or from the local copy of its recorded default branch for a **local board** ([a local board builds and lands on its default branch](docs/adr/2026-11-03-1851-a-local-board-builds-and-lands-on-its-default-branch.md)), of the board's own folder, the hub board's included (`hub/board-repo.mjs` decides which), made by a build's `board.mjs builder start` (or `--worktree`, or the Implement tap) and kept on the builder record; the builder checks and commits there, and **finishing** the task (its `builder done --text`, the session's `builder verified`, or `board.mjs land`) **lands** it: squashed into one commit and rebased onto that branch ([every land squashes the branch into one commit](docs/adr/2026-11-11-2318-every-land-squashes-the-branch-into-one-commit.md)), refused if it adds an ADR named with a number instead of a timestamp, tested, fast-forwarded into the live folder's copy of it, the hub or board servers restarted, the worktree and branch removed, and with the board's "Push main after a land" switch on, the branch pushed to origin. On a GitHub board finishing pushes the task's branch and opens a draft PR instead, and on a plain git remote pushes the branch. A repo task's is made by `builder start` ([every builder works in a worktree, and the hub's own fault shows once](docs/adr/2026-10-30-1654-every-builder-works-in-a-worktree.md)).
_Avoid_: copy, checkout, live folder (for the builder's)

### Talking with the owner

**New task**:
A free-form request or question the owner sends from the board's + button (or by pressing n twice). Code and events call it an **ask**: an `ask` event whose thread is `ask:<event id>`. From the moment it arrives it is a task, keyed `T-<n>` and titled from its first line, whose thread opens with the owner's message: a **New task**, which draws in no lane but as an entry in the **New strip** above the lanes, the owner's whole message with Edit and Delete and a grey "waiting…" counting up, then "processing..." while the orchestrator triages it with item triage ([a new task is triaged in one command before it is investigated](docs/adr/2026-11-15-0730-a-new-task-is-triaged-in-one-command-before-it-is-investigated.md)) ([new asks sit in a New strip above the lanes](docs/adr/2026-11-12-0228-new-asks-sit-in-a-new-strip-above-the-lanes.md)), until Claude sorts it one of three ways ([the + makes a New card, which Claude files, folds or answers](docs/adr/2026-10-29-1639-the-plus-makes-a-new-card.md), [every ask is a task card from the moment it arrives](docs/adr/2026-11-09-1900-every-ask-is-a-task-card-from-the-moment-it-arrives.md)): sets its **task state** (`item set --phase`); merges it into the task it's about, which drops the New task and shows its thread in the other task's (`item relate-ask`, undone by `ask unfold`); or answers it (`reply <key>`), which starts its discussion: the task reads **discussing** in Todo, never In Review, and an answer that never goes to build is closed from there ([a new task is a conversation](docs/adr/2026-11-12-0500-a-new-task-is-a-conversation.md)). A Discuss task is answered this way unless it asks for a grill, a prototype or a visual itself; an Implement task is filed ready. Once ingested, its strip entry reads "Ticket created: T-177" or "Added to T-123", a blue link to the task, with Dismiss, until dismissed or the task is read. Deleting the message of a task still New removes the task. An ask never draws as its own row: the board server files one from before asks arrived as tasks as its task, an answered one closed in Done at its answer time ([old asks migrate into cards, and the ask-only records retire](docs/adr/2026-11-09-2000-old-asks-migrate-into-cards-and-the-ask-only-records-retire.md)). An answer that leaves a question open on it keeps it in Todo with Action needed, never in Done, until the owner answers and Claude replies, or it is closed; it stays in Todo while Claude takes up the answer ([an unstarted card waits on its questions in Todo, and its one action button follows what it waits on](docs/adr/2026-10-30-1309-an-unstarted-card-waits-on-its-questions-in-todo.md)). When another board fits it better, the owner can have it **moved there** (`handoff`, or `ask move`): it becomes a New task on that board reading "From /<this board>", and here its unstarted task is dropped, leaving only the ask's thread line linking to it. Any other task can be **handed off** to another board (`handoff <file>/<id> --to <route>`): it becomes a New task there reading "From /<this board> · <ref>" with the sender's note quoted under it, its thread opening with a blue "Handed from" line, and here it gets a grey "Handed to /<route> · <ref>" line and stays open as a pointer, closed only for a full handoff (`--done`) ([handoff moves a ticket to another board and leaves a pointer](docs/adr/2026-11-14-2340-handoff-moves-a-ticket-to-another-board-and-leaves-a-pointer.md)). Folding is within one board; a move or a handoff is between boards._Avoid_: ask (in what the owner reads), message, prompt, Waiting for Claude strip

**Router**:
The hub's one-shot Haiku call that sends an incoming request naming no board (a Slack @kickflip, or a **session handoff** with no board) to the board it fits, as an ask. It only routes; the board's orchestrator sorts it. The ask's thread opens with a blue "Routed here from Slack: <reason>" status log line, and the hub page lists each request in its **New** strip (the board's own New strip, which also lists the asks other boards put to a board, queued or answered); the hub page's own + button and New task sheet send a request to it too ([the hub's New task box files through the router](docs/adr/2026-11-16-0600-the-hubs-new-task-box-files-through-the-router.md)). ([a Haiku router files each incoming request on a board](docs/adr/2026-11-12-2345-a-haiku-router-files-each-incoming-request-on-a-board.md)).
_Avoid_: uber orchestrator, classifier, hub orchestrator

**Session handoff**:
`/kickflip handoff [board]` (`kickflip handoff`): a Claude session sends its objective to a board, where it becomes a New task like any ask, its thread opening "Routed here from a handoff: <label> named this board"; with no board the **Router** picks one. A board's orchestrator moving one of its own tickets uses `board.mjs handoff` instead, which leaves a pointer behind. The skill's other entry points are `/kickflip page <route>` and `/kickflip board <route>` ([/kickflip is handoff, page and board](docs/adr/2026-11-15-0014-kickflip-is-handoff-page-and-board.md)).
_Avoid_: send-in, spin out

**Live status**:
The one current line in a card's header: the builder's newest progress as "Building · <detail>", or "starting", "thinking…", a land step's words, a refusal or a planner's running grill, replaced as it changes and never kept. Its history is the **status log**.
_Avoid_: status line, progress line

**Status log**:
The board's and the builders' lines in a **thread**, each a mark and at most 100 characters, appended in order and never replaced: a builder's progress lines ("Building: <detail>"), the board's moves, holds, launches and faults. The newest one from an agent still working is what the card's **live status** reads.
_Avoid_: status line, progress feed

**Thread**:
The conversation on one work item: Claude's reports, builders' status log lines, the board's status log lines, the owner's messages, mirrored GitHub comments, and answers to the item's questions. Every line the board (Kickflip) writes is a status log line, a mark and at most 100 characters, red when it is a fault, which alone of them counts as unread; only the orchestrator's own words make a message titled Orchestrator, at most 2000 characters ([the board writes status lines, and only the orchestrator writes messages](docs/adr/2026-11-09-1200-the-board-writes-status-lines-and-only-the-orchestrator-writes-messages.md)). An In Review task's reply form sends with Reply then Done, which closes the task; a Todo task closes from Done, right of Block in its actions, and an In Progress task has neither, only Send ([Done shows only in In Review, beside Reply](docs/adr/2026-11-05-1918-done-shows-only-in-in-review-beside-reply.md)).
An open task shows its thread's newest 3 messages as it opens, or from its oldest **unread message** when more than 3 messages follow it, at most 10, unread as of when the task opened. Messages that arrive while it is open add below, hiding none. Messages are the owner's, Claude's (replies included) and other people's; builder, status and ask-link lines show among the messages they sit between and don't count. "Show more · N previous messages" at the top adds the next 3 older messages each tap and goes when nothing older is left. The expansion lasts while the task stays open, through repaints and new messages, and closing the task puts it back to 3. A message waiting on Claude shows only where the window reaches it.
An owner message's footer starts with its time. A message typed into a thread box shows at once, its footer reading a grey **sending…** while it waits in the browser's **outbox** for the board to record it, one at a time per task in the order written, kept through a reload; a send that failed reads a bold red **not sent** with Retry and an X that puts its text back in the box, and holds the messages behind it. The questions sheet's Send works the same way for each answered question, one at a time: each waits in the browser's **answer outbox**, its footer line reading "<time> · sending…", and its line in its task's thread too, until the board has it and it reads Sent.; a failed one reads not sent with Retry and an X that opens the question again with its pick and note, holding no other answer back, and the sheet stays on its topic until every question on it is sent ([each answered question shows at once as sending](docs/adr/2026-11-16-0500-each-answered-question-shows-at-once-as-sending.md)). No thread message can be edited or deleted: a follow-up message is the correction ([a thread message shows at once, and the browser keeps it until it is sent](docs/adr/2026-11-12-2030-a-thread-message-shows-at-once-and-the-browser-keeps-it-until-sent.md)). An owner message Claude hasn't answered yet ends with a grey **waiting…**, or a blue **thinking…** with the working dot once Claude has it, counting up (**thinking… 3m**) and falling back to waiting… while its session doesn't listen ([working reads only while the session listens](docs/adr/2026-11-13-1800-every-wait-is-listed-and-working-is-display-only.md)): from its watcher's wake, or from the first tool call after it arrived while Claude was mid-task ([the owner's words reach the orchestrator after its next tool call](docs/adr/2026-11-10-1056-the-owners-words-reach-the-orchestrator-after-its-next-tool-call.md)). Only a Claude line written after that handover answers the message; one written before it, while the message hadn't reached Claude, answers nothing. The card's live status reads the same **thinking…** from the handover of any of its events until Claude next writes on the card, in place of waiting for orchestrator ([a card reads thinking from its event's delivery until the orchestrator writes](docs/adr/2026-11-15-1700-a-card-reads-thinking-from-its-events-delivery-until-the-orchestrator-writes.md)). An answer to a question stops waiting once it's acted on: its question resolved after it, a later prototype round on it, or a build started on the task after it ([an answer stops waiting once it's acted on, and a Next set during the card's questions clears](docs/adr/2026-11-03-1313-an-answer-stops-waiting-once-its-acted-on.md)). A batch of the owner's answers in a row in the same state carries it once, under the last answer.
_Avoid_: comments, chat

**Unread message**:
A message in a task's thread from Claude (replies included) or GitHub, newer than the task's **read mark**. The owner's own lines, their copied-in answers included, other people's Slack lines, and builder, status and ask-link lines are never unread. Their count reads in bold blue (info) in every lane as "3 new messages" on the row under the task's footer, after any Action needed, until the task is opened.
_Avoid_: inbox, notification. "New" names it only in that count's "N new messages"; a New task is an unsorted ask.

**Read mark**:
How far the owner has read a task: the time of the newest message, question or answer it showed when they last opened it, kept on the board in `data/read.json`, one set for every device, so a task opened on the phone reads on the Mac too. A task new to the board is read up to when the server first sees it, so it badges only what comes after; a task leaving the board, dropped or past the newest 100 Done, loses its mark ([read marks live on the board](docs/adr/2026-11-05-0910-read-marks-live-on-the-board.md)). Every board answer carries it as the task's `readAt`.
_Avoid_: seen mark, last seen

**Last visit**:
The board and threads this device last showed, with the board's **change number**, kept in its browser's IndexedDB. The next visit paints it live at first paint, readable at any age, and asks the board only for what changed after its number; the lines that catch-up changes flash a fading blue border round each lane count, Needs you line or thread message ([the board opens on the last visit](docs/adr/2026-10-29-1639-the-board-opens-on-the-last-visit.md), [the board syncs by change number](docs/adr/2026-11-05-1819-the-board-syncs-by-change-number.md)); a task that changed shows its own sign ([an updated card takes a brief tint](docs/adr/2026-11-02-2354-an-updated-card-takes-a-brief-tint.md)). It paints only under the build that saved it, a hash of the shell's file versions (`hub/shell.mjs` `shellHtml`), so code that changed since never reads it, except while the board is out of reach, when the page paints another build's copy inside a guard; where there is none, or IndexedDB refuses, the page paints nothing until the whole board lands, and shows the **down landing** if the load fails. Out of reach, the copy stays undimmed and readable, with only the header time red and the buttons that send held, each labelled one saying "Waits for the board"; Waiting on you shows the same copy, and Notes and Settings keep their own, Settings read only ([a board out of reach keeps its copy or shows a landing](docs/adr/2026-11-06-0135-a-board-out-of-reach-keeps-its-copy-or-shows-a-landing.md)). In code it is the copy.
_Avoid_: cache, offline copy, stale board

**Down landing**:
What a board's view shows in place of the board when the board can't be reached and the device has no copy to show: the kickflip mark, one bold line and one muted hint, the look of the no-access page. The line and hint name one of six states, read from what the hub marks on its answer (`x-kickflip-down`, `x-kickflip-hub`): Board restarting (its code changed, it's starting, or it crashed and the hub is relaunching it), Board stopped, This board is gone, You no longer have access, Board restarting (it answers with errors) and Board offline (nothing answers). It retries every 5 s while the board can come back by itself ([a board out of reach keeps its copy or shows a landing](docs/adr/2026-11-06-0135-a-board-out-of-reach-keeps-its-copy-or-shows-a-landing.md)).
_Avoid_: offline page, error page, landing (alone: a task lands)

**Change number**:
The board server's one counter, which steps once for each built board that differs from the one before and is the board's version. Each task, question and topic carries the number of its last change, and a removal leaves a tombstone with its number, all kept in `data/sync.json` so a restart carries on counting. A page naming the number it holds gets only what changed after it, answered from the current board; one older than the oldest tombstone kept gets the whole board ([the board syncs by change number](docs/adr/2026-11-05-1819-the-board-syncs-by-change-number.md)).
_Avoid_: sync id, version hash

**Answer banner**:
The one line at the top of a board, above Needs you, naming new tasks Claude answered without making work whose answer came after the task's read mark: "1 answer · <ask>" or "2 answers · <newest> and 1 more". A tap opens the newest one's task; opening a task anywhere takes its answer off at once, and ✕ marks every answer shown read, on every device. No push goes for an answer ([a push goes out only when something waits on the owner, on the hub's schedule](docs/adr/2026-10-29-1639-pushes-only-when-something-waits-on-the-owner.md)).
_Avoid_: notification, toast

**Owner question**:
A multiple-choice question Claude needs the owner to decide, attached to a topic. A builder's judgement call becomes one. One marked **urgent** blocks a build or a merge and shows alone; Claude resolves a question in the step that acts on its answer ([Needs you gathers what waits on the owner, and a topic's questions are answered on one page](docs/adr/2026-10-29-1639-needs-you-gathers-what-waits-and-questions-answer-on-one-page.md)), except an answer with a note and no option, which resolves its question as it arrives ([a pick with no note settles a prototype round](docs/adr/2026-11-02-1607-a-pick-with-no-note-settles-a-prototype-round.md)), and recording a task's close in the item file resolves each of its questions that has an answer; one with no answer yet stops that write unless forced. The owner's Done still moves the task on the board at once ([the board applies the owner's Hold, Resume and Done at once](docs/adr/2026-11-02-0009-the-board-applies-the-owners-hold-resume-and-done-at-once.md)). Adding a question on the same task or setting its notes file resolves answered questions still waiting on Claude; once a task's Action needed is gone, the board server drops its queued push ([the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)).
_Avoid_: poll, decision task

**Suggested answer**:
The option of an owner question the overnight triage is confident the owner already chose, from their answer on another task or their long-running context, never from an ADR or CONTEXT.md. The question shows it pre-checked with a blue line under its label, "Orchestrator choice: <reason>" (the orchestrator's reason, else you answered this on #N: "<answer>"), and only the owner's Send answers it ([overnight triage suggests your earlier answers](docs/adr/2026-11-04-2200-overnight-triage-suggests-your-earlier-answers.md)).
_Avoid_: auto-answer, default, recommendation (the grill's own pick)

**Topic**:
The group an owner question belongs to; an item's questions use the topic `item:<file>/<id>`. A Done task's topic with no open question is resolved, so it never waits on Claude.
_Avoid_: category, section

**Needs you**:
What waits on the owner on a board, led by the board session's **pending prompts** ([Needs you gathers what waits on the owner, and a topic's questions are answered on one page](docs/adr/2026-10-29-1639-needs-you-gathers-what-waits-and-questions-answer-on-one-page.md)): the hub's count of it per board, and its lines in the hub's needs. The board draws no box of it ([the board has no Needs you deck or pane](docs/adr/2026-11-12-0700-the-board-has-no-needs-you-deck-or-pane.md)): a task waiting on the owner shows its **Action needed**, a pending prompt waits on the hub page. The board and Waiting on you are a board's two pages: from 900px side by side, Waiting on you embedded in the **pane** beside the lanes, and narrower one at a time, the board header's ? (with the open-question count as its badge) opening Waiting on you, whose check goes back to the board ([Board and Open questions are two pages](docs/adr/2026-11-07-1300-board-and-open-questions-are-two-pages.md), [the desktop pane is back without the Needs you deck](docs/adr/2026-11-12-2330-the-desktop-pane-is-back-without-the-needs-you-deck.md)).
_Avoid_: inbox, digest

**Pending prompt**:
A permission prompt or `AskUserQuestion` from a background board session, which its hook hands to the hub and holds the session on until the owner answers on the hub page, which lists every pending prompt, a board session's naming its board: Allow once, Always allow or Deny, or the question's options. Always allow returns the session rule to Claude Code and keeps that same rule in the hub's `prompts.json`, keyed by session id. The hub remembers rules only with a reliable process start time and binds board rules to the current ownership's `owner.since`; ownership commands clear remembered rules and pending prompts for both the old and new sessions, including boardless entries, even while the hub is stopped. A later exact match on its command, absolute path, domain or bare tool name is allowed immediately, with no push or Needs you line; prefixes and globs never widen a match, and `AskUserQuestion` always asks. Rules end when the session stops or its board's owning session changes, and the hub page lists them read-only under the board. With no answer in 10 minutes the call is denied with a note to ask on the task instead ([a background session's prompts and questions come to the phone](docs/adr/2026-10-30-1516-background-sessions-prompts-come-to-the-phone.md)).
_Avoid_: permission request, approval, dialog

**Event**:
A signal that wakes the owning session: something the owner did on a page (an ask, an answer, a button), or a board change such as `card-unblocked {key}` when a waiting task’s last unfinished dependency finishes ([cards wait on explicit blocked-by links](docs/adr/2026-10-29-1639-cards-wait-on-explicit-blocked-by-links.md)).
_Avoid_: action, request

**Rule**:
A standing instruction from the owner to the sessions that own boards, one line of text kept on Settings. Hub rules apply to every board; each board adds its own on top. The watcher prints both with every wake, and a save wakes each session to say what changes. One Claude codified on the owner's word reads "Added by Claude" ([rules live on Settings, at hub and board level](docs/adr/2026-10-29-1639-rules-live-on-settings-at-hub-and-board-level.md)).
_Avoid_: preference, setting, policy

**Reply**:
Claude's answer to one event, shown under it on the page.
_Avoid_: response, comment

**Pending message**:
A New task's message, or the owner's message in a thread, that Claude hasn't answered yet: no reply, no later Claude line on its task other than a builder status log line or agent line, no later reply to its task's ask, its ask not turned or folded into a task, no later orchestrator command on its task (item set, item notes, item brief, reply, thread, a question's add, resolve, settle or publish, builder verified, answer or defer, item stall, bump or relate-ask), and its task not closed since. It reads "Working on it" once the watcher prints it to the session, and is display only: it holds back no pull, auto-grill or idle check ([every wait is listed, and working is display only](docs/adr/2026-11-13-1800-every-wait-is-listed-and-working-is-display-only.md)), and the owner can edit or delete a New task's message. While one goes unanswered, the watcher Stop hook keeps the owning session's turn from ending once, naming it ([the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)).
_Avoid_: unread, queued


**Prototype**:

## Board page files

The board page's scripts in `board/public/` are plain scripts with no bundler, loaded in the order `app.html`, the app shell, lists them, from `/_hub/app/`. The `ui*.js` files hold pure renderers on the `BoardUI` global, which `ui.test.mjs` tests. `app.js` defines `BoardView`, and each `app-*.js` file after it registers one part of the board view with `BoardView.part((B) => …)`. `BoardView.create(root, site, opts)` gives each board its own `B` (state, `ClaudeSite.site`, store, and a `$` scoped to the view's root), and a part adds listeners, intervals, timers, watches and unmount steps only through `B.on`, `B.every`, `B.later`, `B.watch` and `B.atUnmount`, so `unmount()` leaves none behind; `view.test.mjs` checks that. Nothing waits while the owner types: a repaint patches the lanes and each thread in place, and a box being typed in keeps its text, cursor and focus ([a repaint patches in place, so nothing waits while you type](docs/adr/2026-10-30-1122-a-repaint-patches-in-place-so-nothing-waits-while-you-type.md)). An open task moves to its new place at once and the page follows it: the box being typed in, else the open task's title row, stays where it was on screen ([an open card moves at once and the page follows it](docs/adr/2026-10-30-1637-an-open-card-moves-at-once-and-the-page-follows-it.md)); `view.test.mjs` checks both on a board mounted on `board/mini-dom.mjs`, a small DOM. The board's other views (`view-*.js`) get the same site, `$` and recorders from `BoardView.page(root, site, run)`. The view's state, such as `offline` and `data-board`, sits on its root (`.view-board`), not on `<body>`. A site task names the files it expects to touch from this table ([site cards build in parallel when their files don't overlap](docs/adr/2026-10-29-1639-site-cards-build-in-parallel-when-their-files-dont-overlap.md)).

Refs in text that Claude or the owner wrote are linked by the renderer, never by hand: pass the text through `ui-links.js` (`linkText`, or `linkHtml` for an HTML reply or line) with the item's `linkContext`. A task's ref (`INT-<n>`, `#n` for a GitHub ticket, or any `ref` on the board) or its id opens its task, a Linear id or PR opens its page, and a bare URL becomes a link. Write refs as plain text in thread lines, replies, questions and plans.
