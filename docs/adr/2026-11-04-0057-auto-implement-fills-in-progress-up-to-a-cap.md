# Auto implement fills In Progress up to Maximum parallel implementers, on every board change

Superseded in part by [In Progress has a Queued section, and the pull takes its top under the cap](2026-11-04-0121-in-progress-has-a-queued-section.md): with Auto implement on, ready cards wait in In Progress's Queued section, and the free slots take the queue from its top.

The owner asked on #177 (11/03) whether the pull should wait for idle at all: "just it automatically tries to suck in to do tasks. At any time, because the orchestrator should be free, right? Maybe we cap at 10 in progress items at a time, and that can be set on a per board basis in settings." On the #127 thread (11/04) they renamed the switch to an auto-implement one: with it on, a card whose grill completes never reads ready in Todo, it goes straight to In Progress. The #177 grill settled the rest.

This supersedes in part [an idle board pulls in its top Todo card](2026-11-02-1754-an-idle-board-pulls-in-its-top-todo-card.md) on when the pull runs, how many cards it takes and what its toggle reads.

- **The switch.** Board settings' Auto section reads "Auto implement Todo cards" where it read "Pull in Todo cards". It keeps the stored key `auto_pull`, its CLI name `settings set auto-pull on|off` and the wake line `setting auto-pull on|off`, so a board that had the pull on keeps it with no migration.
- **Maximum parallel implementers.** A number beside the switch, `max_implementers` in `board.json`, a whole number from 1 to 99, 10 when absent (`domain.mjs` `MAX_IMPLEMENTERS`, `store.mjs settingsOf`). It saves on change with no confirmation, waiting on the server like a toggle; a number outside the range, or a refusal, puts the saved one back. `board.mjs settings set max-implementers <n>` sets it and every wake prints `setting max-implementers <n>`. Cards with a running build count, and cards waiting in Orchestrator review; a running planner (grill or prototype) and a card waiting on the owner don't (owner, gh177-counts).
- **Every free slot.** `domain.mjs` `pullOf` takes the cap and the cards already pulled: free slots are the cap less the implementers and less the pulled cards that haven't started, which still hold their slot while they stay pullable or a session works on them in Todo. The top pullable cards in board order fill them, one `card-pull {key}` each, with the thread line "Pulled in: an implementer slot was free." What is pullable is unchanged: ready cards only ([the idle pull takes ready cards first](2026-11-03-1631-the-idle-pull-takes-ready-cards-first.md)). With nothing building, a cap of 10 and three ready cards, all three go at once.
- **No idle gate for the pull.** The pull no longer waits for the board to be idle. Triage, card-plan and PR review still do: idle stays "no build running and nothing in Orchestrator review" (owner, gh177-idle-rules). A triage under way still holds the pull until its reply, and a pulled card not yet started still holds the plan and the review.
- **On every board change, not each minute.** The board server runs the Auto jobs (`server.mjs` `checkAuto`) on each change its data watch signals, the same signal that reloads the pages, and once at start (owner, gh177-tick). A build finishing, a card landing, a card set ready or a pull answered is a write under `data/` or a wave folder, so a slot is filled as soon as it frees. A settings save appends a `settings` event, so turning the switch on or raising the cap counts too. A check asked for while one runs runs again after it. The jobs' own writes (`pulled.json`, `planned.json`, `triaged.json`, events) change the board too, so each marker is written only when its keys move, and the re-run that follows finds nothing to send.
- **The pause line.** Nothing goes out while usage is paused. The pause lives outside the board's data, so while a check found it paused, the minute check runs the jobs once it lifts; it does nothing otherwise.
- **`data/pulled.json`** becomes `{keys, at}`: every pulled card still waiting to start. A card is never pulled twice while it waits; once it starts building it counts as an implementer instead, and once it stops being pullable for another reason (a question, a hold) its slot frees, as before. A marker from before, `{key, at}`, reads as one key. The event log still covers a restart between an event and the marker. `data/planned.json` takes the same shape and still holds one card.

Considered:
- migrating `auto_pull` to a new `auto_implement` key: the meaning is the same switch with a wider reach, and a rename would need a migration on every board for no behaviour;
- a separate In Progress lane for cards over the cap: a card waiting for a slot is still Todo work, ready, at the top of its lane;
- keeping the minute check beside the change trigger: the owner asked for it gone where the data allows; only the pause, which the board can't watch, keeps one;
- counting every In Progress card: a card waiting on the owner's Ready or Merge would hold a slot it isn't using (as the first pull's ADR found for idle).
