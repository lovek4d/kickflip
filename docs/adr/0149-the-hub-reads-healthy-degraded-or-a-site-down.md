# The hub reads Healthy, Degraded or a site down, and notifications leave the board links

This supersedes in part [0046](0046-hub-links-turn-red-only-after-a-grace-period.md): its push link and that link's grace period go, and a link past its grace period reads amber on the hub page, not red. It also changes the "<n> broken" and "Needs a restart" words of the hub's status ([0064](0064-every-builder-works-in-a-worktree.md) keeps its stale-code detail).

The owner asked on the `hub-orchestrator` board (#57, 11/03): "It should not say one broken like that. The one broken makes it look like one of the websites is down." The hub's status read a red "1 broken" while every site was up. The only failing link was `push`, "No device has turned on notifications", a setup step. Then: "It wasn't broken. it was kinda like a warning. In fact, notifications shouldn't even be one of those things … It should say healthy or degraded. And then you click in and you see the integrations for more information." The owner settled the grill and take A of prototype `gh57-linkrow`.

- **Three words.** `hubHealth` (`hub/home.mjs`) reads **Healthy** (green), **Degraded** (amber) or "1 site down" (red, "2 sites down" for two). Red is only for a site whose process is down. Degraded counts a board link broken past its grace period and the hub running older code than its files, nothing else; an integration that isn't set up doesn't count. The detail adds "· 1 link failing" to "3 of 3 sites up", and the stale-code words as before. The sidebar's Hub row and the hub page's Health card show the same word. Lowercase status words are a separate card (#79).
- **Tapping the status jumps to Integrations.** On the hub page the Hub row's word is a button that scrolls to the Integrations heading, with each board's links below it (`board/public/view-hub.js`).
- **A board whose link fails reads amber.** `siteHealth` (`hub/views.mjs`) reads "Degraded · listening" (or asleep, waking, not listening), amber, with each failing link named underneath, never red. A settling link reads as before.
- **Notifications leave the board links.** `LINKS` (`hub/boards.mjs`) loses `push`, and `pushLink` and its grace period go. Whether a device gets pushes is the hub's, not any board's: it is the Notifications row of Integrations (`hub/readiness.mjs`), which keeps the device count. An old `push` entry in `link-faults.json` drops on that board's next `linksOf`.
- **The page tells the hub when its subscription goes.** Turning notifications off on a device never reached the hub, so Integrations kept reading "Pushes on · 1 device" from a stale subscription. Each time the device row shows (`board/public/hub-kit.js` `device`), the page keeps the endpoint it gave the hub in this browser's storage. When the browser no longer has that subscription, has a new one, or notifications are blocked, it posts `/_hub/push/unsubscribe {endpoint}`, and `removeSubscription` (`hub/push.mjs`) drops it from `~/.claude/kickflip/push/subs.json`. A subscription the push service reports gone (404 or 410) still drops on send, as before; no other send-side drop was added.

Considered:
- Keeping the push link and counting a missing device as a warning. The owner: "notifications shouldn't even be one of those things." No board can fix it, and Integrations already says it.
- Take B, the board row still red with the hub amber: the board row would still read like an outage.
- Take C, the board row saying nothing about links: the owner wanted the failing link named where it fails.
- Dropping a subscription only when a send fails. Without a send it never drops, and the owner settled on the page telling the hub.
- Listing each device in Integrations. A later, low-priority follow-up ("Low priority later follow up").
