# Every wait on the orchestrator is listed, and working is display only

Two cards sat for hours on 11/12 with nobody acting. T-182 and T-183 carried a stray owed grill brief past Todo, and their builders' judgment calls went unverified for about 1.5 hours because a card's wait on the orchestrator was one wait, and a brief outranked calls: the watcher printed only "waits brief". T-175 sat ready and unpulled for 2.5 hours because the owner's "Send it" marked it working, the orchestrator readied it without a thread line, and the pull skipped any card with a working mark.

- **A card lists every wait it has.** `domain.mjs` `orchestratorWaitsOf` returns each wait a card has, in the old order (builder ask, staging, owner answer, owner reply, brief, then, unless the owner owes the card an answer, stale, calls or checking, grill, prototype, unasked, recheck, refused, unowned, unblocked). The card shows the first as `orchestrator` and keeps the rest as `moreWaits`; an intake or screen wait goes first and pushes the others behind it. `orchestratorWaits` has one entry per wait, so the watcher prints a waits line for each, and `waitsStep` wakes on each new one. A stale builder and a stale review stay one stale wait, and a builder waiting on its own ask is the ask's wait, not a stale one.
- **A brief is owed only in Todo.** A card past Todo has its build under way, so a brief left owed there is no wait.
- **Working is display only.** "thinking…" still shows on the owner's message and the card, but `pullOf`, `arrivalsOf`, `strictlyIdle` and a started card's "none set yet" Next no longer read it: a card's phase alone decides its pull, auto-grill and idle. A pulled card holds its slot only while it is pullable.
- **Any orchestrator command ends working.** `bin/board.mjs` `ACTS` names the orchestrator's commands on a card (item set, item notes, item brief, item stall, item bump, item unbump, item relate-ask, reply to a card, thread as Claude, question add, resolve, settle and publish, builder verified, answer and defer). After one succeeds, `store.mjs` `markActedOn` stamps the card in `data/acted-on.json`, one write in the CLI's dispatch rather than one per command. The build reads it as `actedOn`, and `threadOf` treats the stamp, or the card's close (its `closed_at` or the owner's Done tap), as a later Claude line: the messages before it read answered. A builder's own commands (builder start, progress, call, ask, done, agent …) aren't the orchestrator acting.

Considered: dropping the working mark entirely. It earns its keep as a display, telling the owner Claude has the message (owner, 11/12: display only, cleared by any action of the orchestrator's on the ticket).

## Working reads only while the session listens, and counts up (11/14)

"thinking…" must not end before a reply, and must not stick. What ends it is unchanged: any later Claude line in the thread, the card's close or the orchestrator's last command (owner, 11/14: "Anything that posts in the thread is fine to end"). What keeps it from sticking is the session being alive (owner: "tied to the session being alive, with a timer"), so there is no cutoff while the session listens.

- **A working mark reads working only while the session listens.** `threadOf` takes `listening` (the server passes `listenState(board) === 'listening'`) and reads a marked message waiting while it is false. `withHub` does the same for a card and its New ask on the board's payload: a listen state that isn't `listening` (asleep, waking, deaf) reads them waiting, and the mark comes back with the session. The shared build keeps its working marks, so a pull, a wait or the idle check never reads the listen state, as before.
- **The count.** A message marked working carries `since`, the mark's time (`data/working.json`), and a New ask's `ask.since`. The thread footer reads `thinking…`, then `thinking… 3m`, `thinking… 1h 5m`; the New strip's processing status reads `processing... 4m`. Each such element holds `data-since` and its word, and `app-header.js` repaints their text every 30 seconds in place (`ui.js` `recount`), so a tick repaints no board.

Considered: a fixed cutoff (say 30 minutes), which would end a long build's thinking… while its session works.
