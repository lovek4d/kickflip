# A board asks another board, and its orchestrator answers

#733 (hub/T-388), the first slice of #350 ("Kickflip hubs link up and ask each other's orchestrators"). The owner: an agent unsure why something was built a certain way should be able to ask the orchestrator that stewards it, "The orchestrator is the whole point, the steward of a topic board answers the question. Otherwise we wouldn't need the other board". The grill and two prototype rounds settled the shape: any agent asks through the CLI and carries on; the answering board shows the question in its New strip and its orchestrator answers; the asking task gets a quiet ask line, then the answer as an ordinary thread message (round 2, take A); no confidence anywhere (round 1). This slice is boards in one hub. Own-identity hubs (T-389), routing an unnamed ask (T-390) and the hub's Asked section (T-391) build on it.

- **Asking.** `board.mjs ask <route> "<question>" [--from <key>]` (`store.mjs askBoard`) takes one line, and refuses before sending anything when the route isn't another board in the hub's manifest or `--from` names no task. It appends a `board-ask {text, from {route, title, key?, ref?}}` event to that board through its server, as `handoff` does, so it wakes the board's session; with the server down it lands in the board's log directly. Here it appends `{id, to, text, key?, at}` to `data/board-asks.jsonl`, and on the `--from` task the grey status line `board-asked`, "Asked <route>: <question>". It prints `asked /<route>: <id>`, and a queued line while no orchestrator listens there.
- **Answering.** The answering board reads its questions from its log (`domain.mjs boardAsksOf`). Each unanswered one is an `ask` wait on the orchestrator (`boardAskWaits`), keyed by its event id after the cards' waits, as an overnight triage is; like a triage it never pushes the owner, since it isn't a card. The watcher marks `board-ask` working (`WORKING_KINDS`), which is the wait's pickup. The board's payload carries the unanswered ones as `boardAsks`, which the New strip draws "Asked from /<route> · <ref>", linking the asking task, with waiting… or processing... as an ask reads, and no Edit or Delete. `board.mjs answer <id> --text` (`answerBoardAsk`) appends a record-only `board-ask-answered {id, text}` here, which ends the wait and the entry; posts the answer on the asking task through `appendMessage`, `who` the answering board's route and `via: board`; and appends `board-answer {id, from, key?, question, text}` to the asking board, which wakes its orchestrator.
- **The answer is an ordinary message.** A `via: board` message draws as markdown, so its links render, and counts unread like the orchestrator's own.
- **Queued.** With no orchestrator running on the answering board, the `board-ask` event waits in its log, its wait listed on the next session's first wake. `asks` says "queued: /<route>'s orchestrator isn't listening" for it (`hub/boards.mjs isListening`), else "waiting on /<route>'s orchestrator", or the answer. `asks --wait` blocks until every question is answered, giving up after `--timeout` minutes (9), as `builder asks --wait` does.
- **Who asks.** The builder's and the planners' briefs say to ask another board when the repo doesn't explain why; SKILL.md says the same for the orchestrator.

Considered:
- Filing the question as an `ask` event, which would make it a New task card on the answering board, as `handoff` does. It would need sorting and closing like work, and the board's own task numbers would fill with questions; a question is answered, not worked.
- An answered question staying in the New strip until dismissed, as an ingested task does. The answer lives on the asking task, and T-391's hub Asked section is where the owner reads answered questions, so the entry ends with its wait.
- Writing the answer as a status line under the ask line. The owner asked for "just a thread message" (prototype round 2).
