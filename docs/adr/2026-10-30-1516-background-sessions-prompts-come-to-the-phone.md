# A background session's prompts and questions come to the phone

A board session the hub starts or resumes runs in the background with no terminal, so a permission prompt or an `AskUserQuestion` it raises would wait on a dialog nobody sees. Instead a `PermissionRequest` hook hands it to the hub, which pushes the owner and shows it in that board's Needs you, and the owner's tap answers the hook.

- **The hook lives in `BG_SETTINGS`** (`hub/sessions.mjs`), the inline settings every hub start and resume passes with `--settings`, not in the plugin. The plugin loads in every session, the owner's terminal sessions too, where it would push for prompts the owner already sees and race the terminal's own dialog. A board session started by hand in a terminal keeps its dialog. Nothing goes to the dotfiles. A board session running now picks the hook up only once restarted.
- **`hub/permission-hook.mjs`** posts the hook's input to the hub on 127.0.0.1, then polls until the owner answers. It prints allow, deny with a message, allow with `updatedPermissions` for Always allow, or for an `AskUserQuestion` allow with `updatedInput` set to its input plus `answers: {<question>: <picked label>}`. Claude Code leaves the session on its dialog when a hook times out or prints nothing, so the script always prints a decision and exits 0 before the hook's timeout: it denies with a note at the hub's deadline, 10 minutes after the prompt ("No answer from the owner; ask this as an open question on your board's card instead."), and at once when the hub can't be reached. The hook's timeout, 660 s, stays a minute past that wait.
- **Always allow lasts until the session ends** (owner, `always-scope` on hub/INT-113). It adds the prompt's own `addRules` suggestions with their destination forced to `session`, or, with none, one rule for that exact call: `Bash(<the command>)`, a file tool's absolute path, WebFetch's domain, else the tool's name. It never passes a `setMode` suggestion, which would take the session out of auto mode, and never another destination, since `localSettings` writes the board's repo.
- **The hub remembers Always allow too**, in `prompts.json` under `remembered`, keyed by session id, since Claude Code's `ask` rules outrank its session allow rules. The hub stores the same rules it returns to Claude Code, and answers a later matching permission prompt with allow in its create response, before recording a pending prompt or pushing. Matching is exact: the command string, an absolute path in Claude Code's `//path` syntax, the URL's domain, or a bare tool name. Prefixes, globs and unknown rule contents never widen a match; uncertain matches still ask. `AskUserQuestion` always asks, and Allow once and Deny store no rules. Rules are tied to the live process's pid and valid start time; without a reliable `procStart` the hub keeps no rule and later prompts still ask. Board prompts and remembered rules also carry the ownership's `owner.since`, so an owner change away and back drops old rules and prevents an old board prompt from remembering new ones. Every manifest ownership write (join, leave, start and resume) clears remembered rules and prompts for both the old and new sessions, including boardless entries, before publishing the change. The CLI and hub share the prompt file lock and atomic write path, so invalidation works with the hub stopped and a concurrent prompt write cannot restore cleared entries. The `owner.since` checks remain a second line of protection. A stopped or replaced process, a removed board or a changed ownership drops the rules. A hub restart keeps rules only for that same live run. The hub checks before using or listing rules and every 15 seconds, before waking stopped sessions. The hub page lists each session's rules read-only under its board, with sessions without a board listed separately.
- **A background session's `AskUserQuestion` comes to the phone too** (owner, `bg-ask-question` on hub/INT-113). The push carries the question, and Needs you shows each question's options as buttons. One question answers on the tap; several, or one that takes several picks, send with Send once each has a pick. Skip denies it with a note to ask on the board.
- **The hub holds the pending prompt**, in `~/.claude/web-ts/prompts.json`, not in board data, so it survives a hub restart while the hook keeps polling. It finds the board whose manifest owner is the hook's session; a session that owns no board waits on the hub page, labelled by its folder. A board's prompts are lines of its `/_claude/needs`, so they count in the sidebar and the badge like the rest of Needs you ([sites report what waits on the owner through `GET /_claude/needs`, and the hub reads only that](2026-10-29-1639-sites-report-what-waits-through-claude-needs.md)); the board server reads them through `hub/prompts.mjs`, as it reads its hub links through `hub/boards.mjs`. A prompt whose hook stopped polling for a minute, or never fetched its answer, expires.
- **Taps.** Allow once, Deny, Skip and a single question's option send on the tap, with no dialog: each answers one call, and a session denied by mistake can ask again. Always allow confirms first, naming its rule, since it covers every later call like it for the rest of the session, in [a card can be held, and every card button confirms](2026-10-29-1639-a-card-can-be-held-and-every-card-button-confirms.md)'s spirit that a tap with a lasting effect asks first.

The probe on hub/INT-113 found the hook fires in a `--bg` auto-mode session whenever a dialog would show: an `ask` rule, `AskUserQuestion`, a protected path, or auto mode's fallback after repeated blocks. A block by auto mode's classifier is a plain deny with no dialog, so the phone never sees those. It also found that a hook killed by its timeout, or one that prints nothing, leaves the session waiting forever, that echoing every suggestion applied `setMode: acceptEdits`, and that the suggested destination writes the repo's `.claude/settings.local.json`.

Considered:
- the hook in the `web-ts-hooks` plugin with a gate on background sessions, which still loads in every session;
- the hook's own timeout as the 10-minute limit, which leaves the session stuck;
- Always allow written to the repo's settings, or as a prefix rule such as `Bash(curl:*)`, wider than the owner picked;
- only reading `claude agents --json`'s `waitingFor` to show that a session waits, with no way to answer from the phone.
