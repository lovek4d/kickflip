# An @kickflip in a Slack DM is filed as a routed ask

The owner asked that an @kickflip in any Slack DM they receive start a task (T-228). The grill (11/14) settled it: anyone in the workspace may start one, it is strictly an ask-type Todo ticket that always discusses first, only 1:1 DMs count, one Slack search a poll finds them, and the task's first message is the @kickflip message with the thread's earlier replies. T-228 is split in three; this is the first slice, intake. Slice 2 (the orchestrator's replies go to the Slack thread, with an end line) is T-395, slice 3 (later Slack replies land on the task) is T-396.

- **One search a poll.** `hub/slack-intake.mjs` `fileSlackAsks` runs on the hub's poll, after the reviewer sends: one `search.messages` call for "kickflip", the newest 100 matches, then a text match on `@kickflip` (case-insensitive). Hub's token is the owner's user token with no bot user, so there is no real mention to find. The app manifest gains `search:read`.
- **What counts.** A match in a 1:1 DM (`channel.is_im`, not `is_mpim`), from anyone, the owner included. Not counted: group DMs and channels; our own signed-off posts (`isSignedOff`); a board's day thread or any thread a board posted (`boardPosts`), where an @kickflip stays a `slack-question` (ADR 2026-11-12-0000); and a thread already filed, whose later replies are slice 3's.
- **No backfill.** `~/.claude/kickflip/slack-intake.json` holds `since` and `threads`. The first poll records `since` past every match already there and files nothing. Each filed thread (`"<channel>:<thread_ts>"`) is kept for 30 days by its match's ts, and no match older than that is read, so pruning never files a thread twice.
- **The request.** The match's thread up to the match: for a reply, `conversations.replies` gives the opener and the replies before it; a top-level match is alone. Each message is `<name>: <text>`, Slack mentions written as `@<name>`, joined by blank lines. Names come from one `users.list` a poll, only when something is new. `from` is `{via: 'slack', by: <sender's name>, link: <permalink>, slack: {channel, thread_ts, ts}}`, and the router copies `slack` onto the ask's `routed`, where slices 2 and 3 find the thread.
- **Queued, not routed in the poll.** Intake calls `queueRequest` rather than `routeRequest`, so no Haiku call holds up the poll; the hub's 15-second tick routes it (ADR 2026-11-12-2345) and logs where it went. A request is queued before its thread is recorded, so a failure between the two can file a thread twice but never drops one.
- **Theirs always discuss first.** `item add` and `item set` refuse `--phase ready` for an ask whose `routed.via` is `slack` until the owner stages its card, even when an Implement on the New card would make it a Quick build: "file it --phase discussing; the owner's Implement after the discussion readies it". The owner said these "strictly become ask type todo tickets", so the refusal covers the owner's own @kickflip too.
- **Missing scope.** A token without `search:read` gets `missing_scope`: intake files nothing and records `unsearched_at` on the saved token, and the Integrations Slack row shows "Can't find @kickflip in your DMs: add search:read to the Slack app, reinstall it and paste its new token." until a search works. A new token clears it. There is no push: sends and hearing go on.
