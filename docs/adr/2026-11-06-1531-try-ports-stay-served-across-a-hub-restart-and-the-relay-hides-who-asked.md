# Try ports stay served across a hub restart, and the relay hides who asked

Two faults left prototype and Main try pages broken from the phone (#410).

**The relay passed tailscale serve's identity headers on to the app.** A try port is `tailscale serve --https=850x` → the card's relay on 127.0.0.1, which asks the hub's gate who the visitor is ([the whole hub answers only the owner](2026-11-04-2156-the-whole-hub-answers-only-the-owner.md)). The relay then proxied the request with all its headers. The prototypes and Main builds run a demo hub, whose `.kickflip/build` puts a stub `tailscale` that fails first on its PATH. That demo hub's own gate saw a tailnet login from an address that isn't the host's, asked its stubbed tailscale, got nothing and answered 503 "Tailscale didn't answer". It worked on the host itself, where the address check passes. Now the relay drops `Tailscale-User-Login`, `Tailscale-User-Name`, `Tailscale-User-Profile-Pic` and `X-Forwarded-For` before the app, on plain requests and upgrades. The app sees a direct loopback caller. A shared login stays limited by the relay's own verdict: GET or HEAD only, no upgrades ([a board is shared view only](2026-11-05-2215-a-board-is-shared-view-only-with-a-tailscale-login.md)).

**A stopping hub removed mappings the next hub had just added.** Every run's close ran `tailscale serve --https=<port> off` ([a try build serves on its own Tailscale port](2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)), shutdown included. A restart starts the new hub before the old one has finished stopping its builds. Both hubs then change the serve config for the same fixed ports. hub.log at 2026-11-06T23:17:39Z shows the old hub's `off` meeting "Another client is changing the serve config" and "etag mismatch", and afterwards try.json still had Main ready on 8500 while `tailscale serve status` listed only 443. Each stop also logged "handler does not exist" for ports the new hub's startup sweep had already cleared. Now a stopping hub leaves its try ports mapped. The next hub's startup sweep removes any port no run claims, and its runs re-serve the same fixed ports. As a backstop against any other client changing the config, each try tick (every 15 s) reads `serve status --json` and re-serves any ready run's port whose `/` isn't its relay, logging `try port <n>: its serve mapping was gone|changed; serving it again`.

Not timestamped across a live restart: the builder couldn't restart the hub, so the race is read from hub.log and the serve config, not instrumented. The tick's re-serve repairs the mapping whichever party removed it.

Rejected (owner, q410-simplify-protos): dropping served prototypes for the base skill. The serving design was sound; these two faults broke it.
