# A chip per PR reviewer, and git_approved waits for GitHub's decision

A card's PR row showed a chip only for the board's reviewers, and a separate `codex N` chip counting Codex's unanswered findings. Anyone else who approved or asked for changes didn't show. Slack's `git_approved` reaction ([review posts go into one day thread per board](2026-11-11-1600-review-posts-go-into-one-day-thread-per-board.md), T-88) went on once anyone approved, code owner or not. The owner asked for both to change (T-107, #592).

**A chip per person.** The PR row shows one chip per person on the PR: the card's reviewers first, as before, then each other GitHub login whose latest review approved, asked for changes or commented, in the order GitHub lists them. Each chip reads the GitHub username and its mark: gray ● pending, orange ● commented, red ✗ changes asked, green ✓ approved. A board reviewer who hasn't reviewed is pending whether or not their link went out; the tooltip says which (“not sent yet” or “sent, not reviewed yet”), and a sent link still shows its age after a day. An other login's tooltip says it isn't a board reviewer. A dismissed or pending review draws nothing. The rules for live and kept chips are unchanged ([a card's PR badges stay once added](2026-11-06-1547-a-cards-pr-badges-stay-once-added.md)): coloured while the PR is open, gray at their last state once it merged or closed. The owner picked this shape from a three-take prototype (take A, question t107-chip-style), with GitHub usernames rather than names.

**Codex is a reviewer chip.** The `codex N` chip is gone (question t107-codex). Codex's bot reviews as `COMMENTED`, so it shows as one more chip under its GitHub login, orange ●, like any commenter. The hub's check no longer counts Codex findings (`codexOpen` left `hub/pr-report.mjs`, the hub's summary, the board's PR view and a kept PR). The orchestrator still reads each finding from `pr`'s `codex` events.

**Where the states come from.** No new GitHub call: the hub's check already brings each login's latest review (`latestReviews`), kept as the PR's `reviews`. `board/domain.mjs` reads the card's reviewers from it (`review`, now with `commented`) and every other login (`otherReviews`).

**git_approved waits for GitHub's decision.** `review due` reacts `git_approved` once the PR's `reviewDecision` is `APPROVED`. With “Require review from Code Owners” on, GitHub gives that only once a code owner approves, so this is the code-owner signal without parsing CODEOWNERS (GraphQL has no per-review code-owner flag). On a branch that asks for no review, `reviewDecision` is empty and any approval reacts, as before (question t107-codeowner). `git_merged` and `x` are unchanged. The review digest still leaves out a PR anyone approved.
