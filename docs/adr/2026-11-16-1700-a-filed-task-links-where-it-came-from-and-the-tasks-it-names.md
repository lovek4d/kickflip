# A filed task links where it came from and the tasks it names

#864 (hub/T-344). The owner, on T-342: "Can this be mechanically enforced? Like if the orchestrator is making a ticket outside of a new task it must come from an existing one right?" On T-110 the orchestrator named #689 in a task's notes without linking it; asked whether this should catch that too, the owner answered "Yes: notes naming a task must link it." Shown the five link flags, they asked "Do we really need all of these?", then "From? What about before/blocks/blocked by?"

- **One flag per link row on the card.** A card stores three links (parent, related, deps) and shows them as Parent, Children, Related to, Blocked by and Blocks (`app-cards.js`). `item add`, `item add --ask`, `item triage` and `item set` take the rows the orchestrator sets, by their names: `--parent <task>`, `--relate <tasks>`, `--blocked-by <tasks>` (deps) and `--blocks <tasks>` (the other end of the same dep, `item add` only). `--from`, `--split-of` and `--parent` all set the Parent, so `--from` and `--split-of` go; `--after`, `--before` and `--deps` go for `--blocked-by` and `--blocks`. A command given an old name is refused saying the new one (`board.mjs` `RENAMED_LINKS`). `ask <route> --from` and `item notes --from` are other flags and stay.
- **`--split` is a modifier on `--parent`.** What `--split-of` did beyond setting the Parent, copying the Parent's gates so the split's grill doesn't ask the prototype question again, is `--parent <task> --split` on `item add --ask` and `item triage`. The grill's proposed split is filed that way.
- **A task filed with a Parent is born from it.** `--from` read Created ticket and Created from, blue, where `--parent` read Follow-up; with one flag, a new task with a Parent reads Created ticket in the Parent's thread and Created from in its own. Setting a Parent on a task that exists (`item set --parent`, `item triage --parent`) still reads Follow-up.
- **A task you file names where it came from.** `item add --ask` refuses one with neither `--parent` nor `--relate`, and `item add --title` on a board one with no `--relate` (its `--parent` goes through `--ask`). The refusal names the flags. `--blocked-by` and `--blocks` order a task; they don't say where it came from. The owner's own tasks need none: a New task (the board files it from the ask, never through `item add`), a `--from-ask` filing of the owner's ask, an imported ticket (`--ticket`, or an id naming one), a Slack task, and the board's own cards.
- **The tasks its words name are linked.** A request (`--ask`) or a new task's title and notes that name a task on the board, by `T-<n>`, `GH-<n>` or another id of that shape, `#<ticket>`, or `<file>/<id>`, matching a card's id, ref, ticket or key, must link each, by any of the four links. The add is refused before anything is written, naming each unlinked one and `--relate` with their keys. A name that matches no card (a PR number, a task on another board) is not a task here and is let be.
- **Quoted words name nothing.** Text inside double quotes (straight or curly) is someone's quoted words, the owner's mostly, as the notes quote them verbatim; a task named there isn't the filer's to link.
- **Notes link what they name rather than refusing.** Notes are written while investigating, so `item notes` never refuses: a task its new section (heading and body) names that the task has no link with, either way round (its Parent or a child, Related to, Blocked by or Blocks), becomes Related to, with the usual line in both threads, and prints `related: <key>`.
