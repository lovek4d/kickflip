# The board syncs by change number: a saved copy on the phone, then only the changes since

Since #191 a page names the version it holds and gets a patch, but the server could only diff against the last 8 boards it built, kept in memory. A phone that slept past 8 changes, or any page after a board restart, downloaded the whole board, and every app open did too, since the last-visit snapshot kept no version. The owner asked for something in the style of Linear's sync engine: a hydrated baseline, then sync events on top, with versions as pointers for items and topics (#204; the grill's research write-up is in the card's notes).

**What the day's counts said (#274).** `data/since-counts.json` on hub-orchestrator, from 2026-11-05 07:21 to 2026-11-06 02:19 UTC: 5,076 patches, 151 misses (a since naming a board no longer kept), 243 loads with no since (the first load after each open), and 60 board restarts. About 3% of catch-ups missed, and every open, about 4% of all board answers, downloaded the whole board. The patch count is high partly because the counter's own file sat in `data/`, so each write of it sent a change signal that every open page answered with another count. That file and its counting go with this change: they answered the question they were added for.

- **One counter, and each record carries its last change (owner, gh204-syncid "pointers").** `board/sync.mjs` stamps each page board the server builds. It hashes every card, question and topic (leaving out its own `changed`), each list's order, and every other part of the board (`needs`, `checks`, settings…). When any hash differs from the last board's, or anything went, the counter `n` steps once, and each changed thing takes `n` as its stamp. Cards, questions and topics carry it as `changed`, and the board carries `n` as its `version` and ETag. A removal leaves a tombstone `{id, n}`; a record that comes back loses its tombstone.
- **Catch-up is answered from the current board (gh204-build "core").** `GET /api/board?since=<n>` and a tap's POST with `since` get every record with `changed > n`, the tombstones above n as drops, each other part stamped above n, and a list's order when its order changed. `patchSince` makes it, and `ui-patch.js applyPatch` applies it on the page in the same shape as before. `BOARDS_KEPT` and the kept boards go. The server still builds the board whole and compares it, so changes that come from other cards and from the clock still show up, as #191 required.
- **The state is on disk.** `data/sync.json` holds `{n, floor, stamps, hashes, tombstones}` (owner, gh204-saves-clear). No answer names a number before the file holds it, so a restart carries on counting and a page from before the restart still catches up. Tombstones beyond the newest 1,000 are dropped, and `floor` rises to the newest dropped tombstone's number. A since below `floor`, above `n`, or not a number gets the whole board. A new file counts from the time in ms it begins, so a number from a lost or replaced file is always below its floor. Writes to `sync.json` send no change signal.
- **`onHost` rides beside the board.** It is set per request, so a phone and the host's browser used to hold different versions. Now it's a field on the answer, whole or patch, and every page reads the same numbers.
- **The page keeps its copy in IndexedDB and paints it live (owner, gh204-replica "indexeddb").** `app-snapshot.js` saves the board, its number and the threads of its cards into IndexedDB (`kickflip-boards`, one row per board), and keeps `{build, version}` in localStorage as `copyVersion`. On open, `app.html`'s boot reads `copyVersion` and asks `?since=<n>`, while the view reads the copy, paints it live (not dimmed) and lands the catch-up on it. The lines the catch-up changed flash as before. A copy saved under another build reads as none. Where IndexedDB is missing or refuses, nothing paints until the whole board lands. The localStorage snapshot, its size cap, the dimmed view, its held controls, and the shell's "left fresh with no change since" tracking all go. Stream reconnects and tab returns already reload with the number on screen, so they catch up the same way.
- **A tap builds the board once (from #208, gh208-tap-twice).** A tap's answer needs its own build. Before, the next change signal built again: the watcher's report of the tap's own `events.jsonl` append stepped the data version, and so did the POST's `send`. Now `appendEvents` records the file's size and time after its append, and a watcher report that still finds the file that way only signals. It doesn't step the data version, since the append already did. `send` skips its step when the answer carries a board built after the request's writes (`answerBoard`). The signal's reloads then share the answer's build, and they get 304 or an empty patch.
- **Done stays as #190 has it (gh204-done).** Archive pages are fetched fresh. Offline taps are #220 (gh204-offline): a tap still waits for the server.

Considered:
- change numbers emitted by the writers, Linear-style: they would miss changes from other cards and the clock, as #191 found;
- a counter starting at 0 with a separate epoch in the version: two fields to compare where one floor does both jobs;
- keeping the dimmed snapshot for pages without IndexedDB: it would keep two ways to paint the board; without IndexedDB the page now waits for the board instead.
