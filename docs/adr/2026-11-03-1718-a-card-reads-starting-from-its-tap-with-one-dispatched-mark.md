# A card reads starting from its tap, with one dispatched mark

This supersedes in part [a Build tap starts the build in the board server](2026-11-03-0219-a-build-tap-starts-the-build-in-the-board-server.md), on the tapped mark and the "Waiting for orchestrator" line, and [the session opens the builder record when it dispatches an agent](2026-11-03-0513-the-session-opens-the-builder-record-when-it-dispatches-an-agent.md), on the dispatched mark and a dispatch on a tapped card.

The owner asked on #135 why a card whose implementer had already started still read "Waiting for orchestrator". The Build tap opens the record, makes the worktree, puts the card In Progress and wakes the session, so to the owner the build has started; the line said the orchestrator hadn't acted until the agent's own `builder start` took the record up (29 to 92 seconds on that day's taps). An agent started under another `--agent` name never took up main, so the line stayed until a status line came. A record the session opened with `--dispatch` read "starting" for the same gap: two words for one state, decided by who opened the record.

- **The card reads "starting"** from the Implement tap, or the session's dispatch, until the builder's first status line. The "Waiting for orchestrator" line and the builder's `waiting` flag (`domain.mjs` `builderOf`, `ui-cards.js` `builderLine`) are gone.
- **One mark.** An open record not yet taken up carries `dispatched: 'tap'` (the Build tap, `startTappedBuild`, a queued build's start included) or `dispatched: 'session'` (`builder start --dispatch`), replacing the separate `tapped: true` and `dispatched: true`. The take-up is unchanged: the agent's own `builder start` keeps the kind, a Claude model and the worktree, and starts the record again at now with no mark. Records written with the old marks are not read.
- **A dispatch on a tap-opened record changes nothing.** `builder start --dispatch` on an open `dispatched: 'tap'` record leaves it as it is (its start time, so "ago" and Stalled keep counting from the tap) and prints "<ref>: already open: the Implement tap opened its record; launch the agent, whose own builder start takes it up". The session can run its dispatch step on every launch without checking who opened the record.
- **Another agent name waits for main.** `builder start --agent <name>` (any name but main) refuses while main's record is open with `dispatched: 'tap'`: "the Implement tap opened <key>'s main builder record and no agent has taken it up; run builder start <key> without --agent first". The tap's record is the build's; a second agent beside it would leave it open with nobody to close it, since the SubagentStop hook closes only the records an agent's own start made.
- **`builder progress` needs an open record**, as `builder call` does: "builder progress needs an open builder record on <key>; run builder start first". It no longer makes a record or reopens a finished one, and no longer strips the `progress` and `progress_at` fields nothing writes.
- **A build's start clears the card's Next** (`builder start --kind build`, `claude` or `codex`, and the Implement tap). A ready card's "Next: Implement" no longer stays on the card while it builds. A planner's start or an install leaves Next alone. A Next that waits on the card's questions still clears once they are acted on ([an answer stops waiting once it's acted on, and a Next set during the card's questions clears](2026-11-03-1313-an-answer-stops-waiting-once-its-acted-on.md)); a build's start now clears any Next, not only that one.

Considered:
- keeping "Waiting for orchestrator" until the agent's start and naming it better: the owner sees no step between the tap and the agent, so a second word for the same state reads as something stuck;
- dropping the mark altogether and reading take-up from the label: a dispatch and an agent's own start can write the same label, so nothing would tell an open record from a running one;
- `builder progress` opening a record as before: a line with no record made a builder the card shows as running that nothing closes.

Still open from the #135 audit: the take-up rewrites `started`, so the agent's start, not the tap, starts the thread's started line and Stalled; and the wave item's `building` status repeats the open build record.
