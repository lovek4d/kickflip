# Board settings grant a board's session permissions

The owner, on #12's thread: "How can I have this permission added just for this board? Could the hub server offer a permission system in the board settings?" Claude Code reads permission rules per folder, and a board's session runs in its repo folder, so that folder's `.claude/settings.local.json` applies to that board alone. #130's grill settled every pick on its recommended option.

- **A fixed list of switches.** Board settings has its own Permissions section below Auto (prototype `board-permissions` take A). Push main after a land writes `Bash(git push origin main)` (#129's pick), Push release tags `Bash(git push origin v*)`, Open draft PRs `Bash(gh pr create --draft *)`, and Approve PRs `Bash(gh pr review *)` (#488: any `gh pr review`, approve, request changes or comment; merge and close stay refused). The board's brief tells the session to review only PRs the owner names on the board, and its reply names each PR it approved, linked. Each switch's helper names the rule it writes. `board/permissions.mjs` `PERMISSIONS` holds the list.
- **The board folder's settings.local.json.** The folder is the board's repo (`hub/board-repo.mjs` `boardRepo`'s `repo`, from the manifest). `GET /api/permissions` reads `permissions.allow`; `POST /api/permissions {id, on}` adds or removes that one rule. The write keeps every other key and rule, removes only its own rule when off, and writes through a temp file. A file that isn't a JSON object, or whose `permissions` isn't an object, is refused and left as it is. A board with no repo folder recorded is refused rather than written relative to the server's folder.
- **Live.** A rule written while a session runs reaches its next command; checked once on Claude Code 2.1.318, where a `touch` refused before the write ran after it in the same `claude -p` session. Nothing restarts the session.
- **A refusal shows under its switch.** `hub/sessions.mjs` `BG_SETTINGS` adds a `PermissionDenied` hook for Bash (`hub/permission-denied-hook.mjs`), which posts auto mode's refusal to the hub's `/_hub/permission-denied`. When the command matches a switch that is on, the hub notes it in the board's `data/permission-refusals.json` (`recordRefusal`), and the switch shows "Auto mode still refused this once: <command>. Approve it under /permissions, Recently blocked." A `PermissionRequest` for such a command (the rule hasn't reached the session) is noted the same way and says it applies once the session restarts. Turning that switch on or off clears its note. The hook can't reverse a refusal, so it prints nothing.
- **Host only.** `POST /api/permissions` answers 403 unless `board/on-host.mjs` `fromHost` says the browser runs on the hub's machine, the one shared check (#112). Elsewhere the switches are disabled with "Only the host can change these. Change on the host." The signed-in owner replaced the host here (docs/adr/2026-11-04-0502-only-the-signed-in-owner-changes-permissions-or-restarts.md).
- **A tap waits for the server.** The switch keeps its face, disabled through `BoardUI.waitOn`, with a spinner beside it (#163's look for toggles), and changes only once the server answers ([a tap waits for the server to record it](2026-11-03-1850-a-tap-waits-for-the-server-to-record-it.md)). A refusal puts its reason in the switch's status line.

Considered: free-text rules (the owner picked a fixed list); the user's global settings or the hub's own `--settings` (they apply to every board); restarting the session after a change (it applies live); a CLI the session calls to report a refusal (the hook sees every refusal without the session's help).
