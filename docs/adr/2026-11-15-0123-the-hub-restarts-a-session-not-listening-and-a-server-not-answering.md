# The hub restarts a session not listening and a server not answering, and logs each restart

The owner asked on hub/T-296 to audit the board restart process and consider making it automatic. The audit traced what Restart on a board's row (`hub/restart-board.mjs`, [a board restarts from its row on the Hub page](2026-11-02-1736-a-board-restarts-from-its-row-on-the-hub-page.md)) fixes that the hub doesn't fix by itself. Two cases came out. One is a session that runs but isn't listening: the wake (`sessions.mjs checkSessions`) skips a live session, so only the 15-minute not-listening push told the owner. The other is a board server that runs but doesn't answer: the hub restarts a server only when it exits. The owner chose to automate both, keep it one card, and wrote: "This should log, and we should audit after a few days. Don't want this to hide issues with resiliency."

- **A session not listening.** A board whose session is live, says idle in its `~/.claude/sessions` record, and hasn't been listening for 2 minutes (`RESTART_AFTER`) gets its session stopped and resumed (`sessions.mjs restartSession`). The resumed session's first turn relaunches its watcher. The hub can't restart only the watcher, which the owner asked about: the watcher is a background command inside the session, and the hub can't start one in a live session or type into one. A busy session keeps T-295's grace ([a busy session reads as listening after its watcher exits](2026-11-14-1400-a-busy-session-reads-as-listening-after-its-watcher-exits.md)) and restarts once it is idle and still not listening. A session reading anything but idle, such as shell or no status, isn't restarted. The 2 minutes count from when the hub first saw the session running and not listening (`deaf_since` in resume-state.json).
- **A server not answering.** A board server that is up (its port takes connections) but hasn't answered an HTTP request to `/_claude/health` for 1 minute (`HUNG_AFTER`) is stopped. Reconcile starts it again 1.5 seconds later (`hub.mjs watchHung`). The TCP probe alone can't tell: a server whose event loop is stuck still accepts connections. Only board servers are checked.
- **What holds a restart.** Neither restart runs while the board's session is busy, while a builder of the board is open, or while a land is queued or landing on the host (`auto-restarts.mjs restartHeld`). It waits and rechecks on the next pass. A session restart also waits while the board's usage is paused, since a resumed session would only hit the same limit. A held session restart goes once to the board's audit log (`session-restart`, `held`). A held server restart goes in the hub log.
- **Once per outage.** Each restart happens once per outage. The outage ends when the board listens again, or when the server answers again. A restart that fails at once (claude stop or resume refuses) pushes at once. A session still not listening 5 minutes after its restart (`COMEBACK_WAIT`, as for the wake) pushes "X's session didn't come back". A server still not answering 2 minutes after its restart pushes "X's server didn't come back". A restart that works pushes nothing. The 15-minute not-listening push (`boards.mjs checkListening`) now fires only when no restart already pushed for the outage. It still fires for a session that runs and stays not listening because something held its restart.
- **The log.** Each restart appends a line to `~/.claude/kickflip/auto-restarts.jsonl`: `{at, board, what: 'session' | 'server', why, outcome}`. The outcome is `restarted` or `failed` (with `error`) when the restart runs. A second line follows with `back` or `not back` once the hub knows. The board's Hub row shows its newest restart for a day, as a line under its status: "restarted the session 2m ago: not listening". hub/T-433 reads the log after the first days.

Considered:
- Restarting the board's server too, as Restart does: the session alone is what isn't listening, and a server restart would interrupt the page for nothing.
- Any session status but busy counting as idle: a session waiting at a prompt or running a shell command would be stopped mid-task.
- One log line per restart, written when the outcome is known: the Hub row needs the restart the moment it happens, and an audit needs the restarts that never settled.
- Restarting any server the hub runs from a `cmd`: the card asked for board servers.
