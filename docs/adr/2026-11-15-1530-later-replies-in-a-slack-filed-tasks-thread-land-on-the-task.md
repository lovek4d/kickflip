# Later replies in a Slack-filed task's thread land on the task

A task filed from an @kickflip in one of the owner's 1:1 Slack DMs (ADR 2026-11-15-0130) is T-228's first slice. This is its third (T-396): the Slack thread keeps feeding the task. The owner's answers on T-228 (11/15): copy every later reply, waking the orchestrator on the asker's and on the owner's own @kickflip ones, until the task is Done.

- **Which threads.** `board/store.mjs` `followedSlackThreads` reads a board's asks whose `routed.via` is `slack` and keeps those whose card (`from_ask`) exists and is not Done. Each carries the ask's `routed.slack {channel, thread_ts, ts}`, its sender's name (`routed.by`) and permalink. An ask with no card yet is skipped until the board files it; a Done card, or one archived out of the item files, is followed no more, with nothing written at the end.
- **A cursor per thread.** `data/slack-threads.json {threads: {"<channel>:<thread_ts>": ts}}` in the board holds the newest reply read. It starts at the @kickflip's own ts, since the replies up to it are already the ask's words. It lives with the board rather than the hub, as the task does.
- **On the hub's poll.** `hub/slack-intake.mjs` `followSlackAsks` runs after intake on the hub's poll: one `conversations.replies` read per followed thread, from the cursor, under the `im:history` scope the day threads already need. Without that scope it reads nothing and pushes nothing, as hearing the day threads already pushes it. Names come from one `users.list`, only once something is to be copied. Each reply is marked read as soon as it is in, so a failure part way copies none twice.
- **What wakes.** A reply from the @kickflip's sender (by Slack name against `routed.by`), or the owner's reply naming `@kickflip`, goes to the board as an `item-message` event `{key, text, sendId, slack: {by?, link}}`, which wakes the orchestrator through the watcher as any message on a task does, and reads waiting until it replies. Its `sendId` is `slack:<channel>:<ts>`, so the board server's recorded-send check makes a resend a no-op. `board/domain.mjs` draws it under the sender's name (the owner's own with none), via Slack, linked to the reply; `bin/event-lines.mjs` says who wrote it in the Slack thread. As a message, it also clears a stall and stages a ready card, as the owner's own message does.
- **What doesn't.** Every other reply (the owner's plain ones, or the other person's when the owner sent the @kickflip) is a thread line, `appendMessage` with `who` the writer's name (`love` for the owner) and `via: 'slack'`, which wakes no one.
- **Not copied.** The boards' own Slack posts (`boardPosts`), the owner's signed-off posts (the orchestrator's words through Hub's token), Slack bot messages and event subtypes other than `file_share` and `thread_broadcast`, and a reply with no text and no files.
- **Files.** A file in a reply is copied as `<name>: <permalink>` under its text. A Slack file opens only with a token, so bringing it onto the board as an attachment would mean downloading it with Hub's token; a link is what the notes allowed when attachments are not simple.
