# A board server whose code changed on disk restarts once its board has no running builder

#170: after a pull or upgrade changed `board/` or `hub/` files, a board server kept running its old code while browsers loaded the new client files it serves from disk. On Backend Audit the Done lane counted 12 cards and drew 1: the old server sent fold names the new `app-lanes.js` no longer reads. The owner chose (11/04) to restart stale board servers, by code hash, restarting only the server and not its session, once that board has no running builder. The upgrade path matters most: "this mostly is going to be run through the npm install" (`hub/upgrade.mjs`, #116); a git pull of a clone (`hub/try.mjs` Main pull, #60) is the other case.

- **The hash.** `hub/boards.mjs` `boardCode(site)` hashes the `board/server.mjs` in a board site's `cmd`, resolved from the folder the hub starts it in, and every file it imports by a relative path, as `hubCode` does for the hub ([the hub restarts itself from its stale-code notice](2026-11-03-1638-the-hub-restarts-itself-from-its-stale-code-notice.md)). It hashes the files wherever the server runs from, so an npm upgrade of the installed package and a pull of a clone look the same. Nothing looks at what changed them.
- **Taken as the server starts.** The hub's `start` records `boardCode` on the process entry just before it spawns the server, so the hash is the code that process loaded. The hub records it rather than the server itself: the hub is what compares and restarts, and it starts every board server, so no file or endpoint carries the hash between them.
- **Compared on every reconcile.** Each 2-second reconcile hashes the files again for every running board server, skipping a board whose Restart (`restart-board.mjs`) or close is out. A differing hash with no open builder record (`board/store.mjs` `openBoardBuilders`, as Upgrade waits on) stops the server, and the reconcile starts it again from the same entry. Its session keeps running. While a builder runs, the hub logs once per newer hash that the board waits and keeps the old server, as the owner chose.
- **What a browser sees.** From the stop until the new server answers, the hub's down page for the board reads `restarting · its code changed` (wait tone) instead of `down · restarting (last exit: SIGTERM)`, and retries every 5 seconds. While the server waits on a builder it still serves the new client files from disk, so the mismatch #170 saw can show for the rest of that build.
- **The hub itself.** A hub restart stops and restarts every server it runs, so a stale hub needs nothing new here: its notice and Restart hub (#146) and the hub board's rule to restart after its own pull stay as they are.

Considered:
- the board server writing its own hash at start: the same moment as the hub's spawn, plus a file or endpoint the hub then reads;
- restarting the session too (`restart-board.mjs`): the owner chose the server only;
- the client accepting the old fold names: fixes one mismatch, not the next one;
- the stale server keeping its startup-time client files in memory, so it never serves client code newer than itself: more state for the length of one build; not done.
