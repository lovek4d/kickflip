# A schedule files a Quick build on a cadence

#1135 (hub/T-517). The owner (11/16): "could we have custom polling commands as well? Something like every 30 minutes we emit a certain task? … A chron job running instructions in plain English so to speak. Maybe could even prompt the orchestrator to make a quick build task and auto run it on a cadence." Two grill rounds settled it; the second dropped a cardless Run kind: "drop the run type entirely, too much to maintain … lets make all schedules a quick build task", and "scheduled tasks should be sized by the orchestrator still, they need to go through staged > ready as a task". On overlap: "it should not fire until the task it created last is done, notably to catch the case where something might still be in PR … having each job maintain a pointer to its current task or last created task and also mechanically use that as the related to".

## Decision

- **A schedule lives in its board's `board.json`.** `schedules: [{id, text, cadence, due_at, last?, fired_at?, skipped?}]` (`board/schedules.mjs`). The cadence is "every <n>m|h", at least 15 minutes, or "at HH:MM [daily|weekdays|mon,wed…]" on the host's clock; no cron.
- **The orchestrator adds it; the owner edits it.** `board.mjs schedule add <id> --cadence --text`, `set`, `rm` and `list`. Board Settings' Schedules lists each with its cadence, next fire, last task and a skipped fire, and edits its text and cadence or removes it (`GET/POST /api/schedules`). An edit to the cadence counts from the edit.
- **A fire is an ask filed to build.** It writes the `ask` event the owner's New task writes, with `quick: true`, so `implementAsk` holds and `item triage` stages it, and `asked {by: 'schedule', schedule: <id>}`, so its thread opens "From schedule <id>" linked to the last fire's task, the watcher names the schedule, and its words are never read as the owner's. The orchestrator judges and sizes it as any staged task, and it is pulled, built, reviewed and landed like one. No per-schedule model or time limit.
- **Each schedule points at its last task.** A fire whose `last` task is on the board short of Done (In Review or an open PR included) is skipped, and `skipped {at, key}` notes it on the row. Otherwise the new ask is related to `last` (`links.related`), and `last` moves to the new task. Each fire is a card of its own, so a builder starts fresh and the history is one link back.
- **The board server fires it.** Each minute (`server.mjs` `checkSchedules`, a step of the Board minute poll) fires every schedule whose `due_at` has passed and sets the next one cadence on from now. Nothing fires while the board is paused (a usage pause, Pause board or Pause hub); the due time stays, so the fires a pause or a sleeping host missed come as one when the board runs again, then on cadence.
- **An `every` fires at once when added; an `at` waits for its time.**

Rejected: the Run kind, a headless `claude -p` with narrow tools writing a served page and no card (dropped by the owner as too much to maintain); one card per schedule that comes back each fire (a long thread a builder would read every time); firing from the hub's clock, which would write every board's `board.json` from outside its server.
