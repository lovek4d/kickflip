# A new task is triaged in one command before it is investigated

The owner on hub/T-401: "I see some new tasks process for quite some time, wondering if they should instead be strictly triaged first before the agent investigates." From ask to a card's first thread line took 21 seconds to about 2.4 minutes, mostly the orchestrator reading code to write notes and a title before its first move, while the New card showed nothing. The owner wants the orchestrator to keep the triage, "for the sake of folding in and relating to other cards", and picked "item triage first, then investigate". This builds on [the orchestrator sorts new tasks itself](2026-11-07-0115-the-orchestrator-sorts-new-tasks-itself.md).

- **Triage and investigation are two moves.** Triage (what it is, which cards it touches, which phase) needs the board, not the code; investigation (notes with file:line) needs the code. `item triage <key> --title <Conventional> --phase discussing|grilling|prototyping|visual [--relate] [--split-of] [--deps] [--ticket] [--text]` (`store.mjs` `triageItem`) does the whole first move in one call: it sets the title, phase and links through `item set` and posts one message, "Triaged: <phase>[, relates to …, split from …, after …]; <text>". The phase sorts the card, so it leaves the New strip and its intake wait ends. `visual` sorts it discussing, for the visual's brief. `ready` is refused: it follows the investigation, with `item set --phase ready`.
- **A duplicate folds.** `item triage <key> --fold-into <task> [--text]` merges the New card into that task as `item relate-ask` does: the card goes, the ask's thread has the card-merged line naming the task, and the task's thread reads "Triaged: folded in <ref> "<title>"; <text>". It takes a New task an ask became; an agent-added card is filed, then closed.
- **Triage refuses a card already sorted**, and an ask edited after its working mark, as every sorting command does.
- **A triaged Quick build ask still goes ready as its filing.** `item set --phase ready` on a card whose ask was a Quick build skipped staging only while the card had no phase. The card now records `triaged: {at, phase}`, and keeps that path while its phase is still the one triage gave it, so an Implement ask triaged discussing goes ready once investigated with `--size small` and notes.
- **The intake wait asks for triage first and names the likely related cards** (`domain.mjs` `relatedCandidates`): open work cards sharing two or more significant title words (four letters or more, not a stop word, plural and verb endings dropped) or the scope of a Conventional title when both have one, most shared words first, at most five, as `<key> "<title>"`. The watcher's line for a new task and an agent-added card says the same (`bin/event-lines.mjs`).
- **A New strip entry waiting for pick-up reads a grey "triaging"**, its dot still, counting up from when it was asked through the shared duration (`ui-progress-bar.js` `liveFor`), so it reads "triaging" for its first minute and "triaging (1m)" after. Picked up, it reads "processing...", as before.

Considered: the haiku router writing the title and phase at intake (the owner wants the orchestrator to triage, since only it knows the board); a live "Sorting (40s)" line with no change to the flow (it shows the wait without shortening it). When the orchestrator is mid-way through a land or a verify, the intake still queues behind it; that latency is T-299's and T-394's.
