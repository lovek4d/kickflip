# A tap waits for the server to record it

Superseded in part by [owner taps wait for the host in the outbox](2026-11-16-1600-owner-taps-wait-for-the-host-in-the-outbox.md): bump, unbump, delete, an edit's Save, Hold, Unhold, Done, Implement and Merge no longer wait on their button. Each draws at once from the outbox and reads sending… until the board's answer lands. The server's side, on disk before it answers, stands.

This supersedes in part [every owner tap the server can apply draws at once](2026-11-03-0500-every-owner-tap-the-server-can-apply-draws-at-once.md): its bullets that bump, unbump, a New card's bump, delete and edit draw before the POST, and that the bump icon's fill fades in and out. The rest of that ADR stands: the server applies the tap inside the POST, which answers with the board, and the page lands that board with no reload of its own.

**The rule.** A tap never waits on a session, but every tap that saves something waits on the board server, which answers only once the change is on disk. Nothing on the card changes before that answer. Only taps that save nothing, such as opening a card or a sheet, stay instant.

- **The waiting button.** `BoardUI.waitOn(button, promise)` (`board/public/ui.js`) disables the button until the promise settles and marks it `tap-waiting` and `aria-busy`. `style.css` `button.tap-waiting` keeps the button's own colours and width. Its content stays, so the width can't change, but is hidden, and a spinner in its text colour sits in its place. A bump icon (`[data-card-bump]`, `[data-bump]`) keeps its arrow and pulses orange until the card moves. A repaint while it waits patches the button back to its markup, so `setHTML` marks it again. It finds the button again by its id and data attributes when the repaint replaced the node. Settling gives the button the disabled state its latest markup had. The helper takes any button and any promise, so other controls can use it as they are.
- **What waits.** A work card's bump and unbump, a New card's bump (from its icon or the prototype button), delete, an edit's Save, Hold (its card's Hold button, after a sheet chip), Unhold, Done, Implement and Merge. Implement no longer reads "Starting…". Merge reads "Merging…" only while the card's `merging` says the session is merging it.
- **One round trip.** `B.send(kind, data, answered)` (`board/public/app.js`) posts the event and lands the board the POST answers with. `answered()` runs once the server has answered, before that board lands. Done uses it to close its card, so `steady` doesn't anchor the card as it moves into Done. `BoardUI.closeDetails` closes it at once, since its toggle event comes a task later and a repaint before it would reopen it.
- **A refusal says why.** `send` throws with the server's `{error}` as `reason`, and `B.failed(e)` toasts that reason, or "That didn’t go through. Is the host awake?" when the server never answered. The card stays as it was, and an edit's box stays open with what was typed.
- **Hold and Done are on disk before they answer.** The server writes the card's wave file first (`store.mjs` `recordOwnerTap`), then appends the event. A write that fails answers 500, or 400 for a `BoardError`, with "Couldn’t write <key> to its wave file: <reason>", and records no event. A merged or dropped card answers 400 "<key> is already merged or dropped, so its wave file stays as it is.". Before, the event was appended first, and a failed wave-file write was only logged while the POST answered success.
- **Deleting is one request.** `ask-withdrawn {id, key?}` appends the event and hides the message (`setHidden`, as `POST /api/hide` does) in the same POST. The page sends nothing else. It used to call `/api/hide` after the event and never checked its answer. The page's own list of withdrawn asks is gone: the POST's board no longer has the card.

The owner (2026-11-03, during the #119 batch Send grill): "we shouldn't be optimistically making buttons do things without a server round trip. I still want the server round trip to promise that the changes were recorded to the file system, both for this and for the 95 taps I just don't want to wait for an agent. But we can wait for the server, that's fine." The picks for #123: only things that save nothing stay instant. The waiting look is a spinner, and the button keeps its colour ("keep the color of the button"). The bump pulses orange "until it changes and moves". A refusal is a toast with the server's reason. Hold and Done fail unless the card's file was written. Delete is one request that records both. The look is prototype `tap-waiting-2` take A.

Considered:
- drawing at once and taking the drawing back off on a failure, as before: the owner saw a change the server might not have recorded;
- a waiting word ("Holding…", "Sending…"): a word changes the button's width, and [the board applies the owner's Hold, Resume and Done at once](2026-11-02-0009-the-board-applies-the-owners-hold-resume-and-done-at-once.md) had dropped pending words;
- swapping the button's content for a spinner with a pinned `min-width`, as the prototype did: a repaint while it waits puts the label back, and a pinned width needs a measurement before every swap. Keeping the content hidden keeps the width with nothing measured;
- appending the event and then writing the wave file, refusing on a failed write: the event would already say held or done, so the board would show the tap the POST refused.
