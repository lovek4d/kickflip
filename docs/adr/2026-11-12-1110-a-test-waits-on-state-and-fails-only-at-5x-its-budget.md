# A test waits on state, and fails only at 5× its budget

Card #596. Builders on a loaded host (load 50–100) saw the same suite tests time out that pass alone, and land runs the full suite, so a flake refused a land. Each one waited on wall-clock time somewhere, either a fixed delay standing in for an event or a ceiling sized for an idle host.

- **`until` budgets, it doesn't cut off.** `shared/test-helpers.mjs` `until(predicate, message, budget = 30000)` polls the state. Past its budget it warns with how long the wait took and goes on; it fails only at 5× the budget. A slow host makes a slow pass, and a wait that never comes still fails inside land's per-test limit.
- **A stand-in says when it is ready.** A fixed delay that stood for "the other process is now in state X" is replaced by a signal from that state:
  - the try restart test (`hub/try.test.mjs`) lets each serve exit only after the hub has marked that run up (its relay opened and the state reads ready). Its old 300 ms exit could come before the hub's probe on a loaded host, which reads as a build that failed rather than a serve to restart;
  - the stopRuns grace test waits for the stubborn process to print that it ignores SIGTERM, not 200 ms;
  - the land queue bump test holds `#1`'s lock until the bump is made, not 400 ms.
- **A fake planner lives until the test ends and names its session.** `board/server-stale.test.mjs` `launchingBoard`'s fake claude prints claude's init event, so each launch returns at once instead of waiting out the adapter's 15 s wait for a session (`board/agents.mjs`). The arrivals grill test launched two such planners in turn, about 30 s on an idle host, right at the old ceiling. One that stays now lives until the test process ends (`untilTestEnds`), since the board closes the record of a planner whose process is gone and a 20 s planner could free its slot partway through a slow test. The arrivals test's server runs on a frozen clock, and reads a planner gone unless its process started in the minute before the launch it recorded on that clock, which a real process never did: the 15 s session wait used to hold the board's next pass back long enough to hide it. Its server now gets `stallingPs`'s stand-in ps, which says each running process started a second before the frozen clock, so a planner reads gone only once its process is.
- **A test reads only the writes it compares.** The re-ask request test (`board/server.test.mjs`) drops the server's own `orchestrator-waits` lines from events.jsonl, as its neighbours already did, since that pass can append between the two reads.
