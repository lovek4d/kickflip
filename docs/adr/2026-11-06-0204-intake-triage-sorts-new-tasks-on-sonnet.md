# Intake triage sorts new tasks on Sonnet

The Opus orchestrator sorted every new task itself: each `ask` event woke it to file the task as a card, fold it into one, or answer it, and each `card-added` woke it to link and file an agent's follow-up. #317 (from #297's gh297-quick and #300's gh300-offload) hands that intake to a one-shot Sonnet run the board server launches, and keeps everything else with Opus.

**Who does what** (owner answers gh317-shape A, gh317-split intake, gh317-model Sonnet, gh317-opus keep Opus). Intake is what reaches the board unsorted: a new task (`ask`), the owner's message in a New card's thread (`item-message` keyed `ask:<id>`), and a card an agent added with no state (`card-added`) (domain.mjs `intakeKeyOf`). Intake triage replies, folds (`item relate-ask`) or files (`item add`, then `item set --from-ask … --state grilling|prototyping`), and links and files `card-added` cards. The orchestrator keeps the rest: judging staged cards, answers, builder asks, calls, stalls, lands. It stays on Opus; its model is still the manifest owner record's.

**The run.** One run per intake event, one at a time per board, oldest event first, so two asks can't file or fold the same work at once (domain.mjs `intakeDue`). server.mjs `runIntake` keeps data/intake-runs.json `{<event id>: {key, pid, at, ended?}}`, runs on every board change, once a minute, and when a run's process exits (agents.mjs `launchAgent`'s `exited`), and holds launches while usage is paused or the Mac is busy, as every launch the server makes. headless.mjs `launchIntake` launches Claude Sonnet in the board's repo with `intakeBrief`, and writes "Intake triage launched on Claude Sonnet in <repo>." in the card's thread as a status line, which doesn't count as an answer, so the task still reads New until the run sorts it. The run's own commands write its other thread lines; those are its report (gh317-escalate).

**What it is handed** (gh317-context, index). The brief holds every open work card's label, key, title, lane, state and notes file path, the waves a new card can go in, the task's thread with its attachments, and whether the ask asked for a Quick build. It reads a related card's notes from the path itself; the board has no command that prints notes.

**Unsure, or ended unsorted.** A run that can't tell how to sort its event runs `intake handoff <eventId> --text <why>` (store.mjs `intakeHandoff`): an `intake-handoff {event, key, text}` event and a status line in the card's thread. A run that exits, or fails to launch, with its event still unsorted and no hand-off gets one from the board (domain.mjs `intakeStranded`), with no relaunch. Either way the card gets an `intake` wait on the orchestrator's list while the event is unsorted (domain.mjs `intakeWaits`), which wakes Opus through `orchestrator-waits` like any wait.

**Quick build** (gh317-quick, staged). A Quick build ask is filed `--from-ask <id> --state staging` with its size and plan, the one filing that stages a card; `--state ready` on it is refused. Opus then judges it from staging, in context of the other cards, as the owner described (gh317-split's note): ready, or another round. Before this, filing a Quick build counted as its staging and went straight to ready.

**The watcher.** On a board, `ask`, `card-added`, `item-message` on an ask's thread and `intake-handoff` are record-only (bin/wait-events.mjs): they move the cursor and print on the next wake, but never wake the session, and the watcher marks working only the events that woke it, so intake's events never read Working on it under Opus. `ask-edited`, `ask-bump` and `ask-withdrawn` still wake Opus as before.

**Not done.** No prototype (gh317-proto no): the only visible change is the thread lines. A run that hangs has no time limit, and holds the next intake event until its process exits or the server's process check finds it gone.
