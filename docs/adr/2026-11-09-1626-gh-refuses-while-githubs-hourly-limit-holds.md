# gh refuses while GitHub's hourly limit holds

Every kickflip gh call ran its own `execFile` or `spawnSync`, so when GitHub's hourly limit was spent each call kept hitting it, and the hub's GitHub row read the failure as "gh isn't logged in". After the per-PR reads moved to the hub's check ([boards read PR state from the hub's check](2026-11-09-1556-boards-read-pr-state-from-the-hubs-check.md)), #480 handles the limit itself.

- **One gh runner holds a gate.** `shared/gh.mjs` `gh` (and `ghSync` for synchronous callers) is the only way kickflip runs gh: `hub/pr-report.mjs`, `hub/repos.mjs` `runRepo` (repos, branches, new board, and `board/tickets.mjs` through it), `shared/owner-check.mjs`, `shared/service.mjs` `runCommand` (the doctor and its skills check), `board/store.mjs` `mergeCard` and `board/finish.mjs`. The board server's reviewer picker and `hub/incoming.mjs` reach it through `pr-report.mjs`.
- **The gate file.** A call that fails with GitHub's "API rate limit exceeded" asks `gh api rate_limit`, which spends nothing, and records each budget it shows spent with its reset in `~/.claude/kickflip/gh-limit.json` `{<account>: {core|graphql: <reset>}}`. Passed resets are dropped on the next write and ignored on every read.
- **Only the spent budget of that account** (gh480-budget). A call spends GraphQL (`api graphql`, and gh's `pr`, `issue` and `repo` commands), REST's core (other `api` calls, `run`, `auth status`) or nothing (`auth token`, `rate_limit`) (`budgetOf`). The account is `primary`, gh's active login, unless a board sets its own: its `github_login` for PR posts (`pr-report.mjs` `asLogin`) or its tickets' `github.account` (`tickets.mjs` `issueRunner`). The owner: "all uses should go through the same primary account, unless explicitly defined on that repo as something else".
- **Every call refuses at once** (gh480-refuse). While the gate holds a call's budget for its account, gh never runs and the call fails with "GitHub rate limited, resets at 3:12pm" (`limitWords`). No call waits: the hub's check runs again on its next tick, a page shows the refusal, and a merge or a builder's finish fails and is run again after the reset. A rerun merge merges only the PRs still open, and a rerun finish reuses the pushed branch.
- **A refused merge or finish says so in the thread.** `mergeCard` and the finish's PR create write a red `gh-limited` status line, "Not merged: …" or "No PR opened: …", with the reset (`board/hub-lines.mjs`).
- **Only the hourly limit** (gh480-secondary). GitHub's secondary limit (too many calls at once) is a plain failure: its words don't match, and `rate_limit` shows no budget spent for it.
- **The hub's GitHub row** (take A of gh457-limit-row). While the gate holds any budget of the primary account, the row is red, "rate limited · resets at <time>", with its waits line, "GitHub polling and PR reports wait on this." (`hub/readiness.mjs`, `board/public/view-hub.js`). The gate is read on every read of the rows; only the `gh api user` login read keeps its 60-second cache.
- **PR badges dim on boards.** The badges come from the hub's GraphQL check, so while the gate holds the primary account's GraphQL each PR view carries `limited`, its reset (`board/server.mjs` `prViewOf`), and its badge, CI and Codex chips dim with the reset in their titles (`board/public/ui-cards.js` `prChip`). Boards draw no line of their own, and nothing is pushed.
