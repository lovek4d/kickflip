# Onboarding asks per script and files a task for each

The owner asked on T-834 that onboarding cover all three scripts, test, build and release, with a question for each and a task of its own for each one chosen. Amends [a board's scripts live in its repo or in kickflip](2026-11-17-1451-a-boards-scripts-live-in-its-repo-or-in-kickflip.md) (its Onboarding bullet) and [onboarding asks for a test script or a stub](2026-11-22-0200-onboarding-asks-for-a-test-script-or-a-stub.md) (its left-out `test` entry).

- **The scripts card is a chooser.** "Choose the test, build and release scripts to set up" (`board/onboarding.mjs`) writes no script. Its grill posts one round of three questions, in the order a land meets the scripts: "Set up a test script?", "Set up a build script?", "Set up a release script?", each with the options Create in repo, Create in kickflip and Don't create (the owner's words). The notes carry the questions as a JSON block the grill posts with `question add`, adding only id and topic, so what each question recommends is computed, not left to the agent. The separate home question, "Build scripts in the repo or in kickflip?", is gone.
- **What exists decides the pick.** `repoHas` and `kickflipHas` now read `test` too. A script the repo's main already has recommends and preselects Create in repo, its context and its Orchestrator choice line saying it exists there. One only kickflip holds does the same for Create in kickflip. With neither, kickflip is recommended, as before, and nothing is preselected.
- **Preselect.** The questions sheet already pre-checks a question's `suggested` option, with the blue Orchestrator choice line from its reason. `suggested` took only an earlier task's answer (task and answer required); with a `reason` they are now optional, so a question can preselect for a reason of its own. A recommended option alone is still not preselected.
- **Each create is a task.** Judging the staged card, the orchestrator files one task per create by the split path (SKILL.md, "A grill can propose a split"), its notes that script's part (contract and discovery steps) with its home and whether the home already has it; then closes the card `--split-into` them. A home that already has the script reviews it against the contract and keeps it. Don't create is a thread line on the card.
- **One home per board.** board.json `scripts` stays one home for every script. When the creates name both homes, the orchestrator asks one follow-up, "Scripts home for all: repo or kickflip?", its context naming which scripts chose which home and any script the other home already has.

Considered:
- Three script cards made up front, each free to end "not needed": rejected by the owner for asking first, so the board holds only the tasks they want.
- A home per script (board.json `scripts` per name, the resolver and Board Settings with it): left for its own card; the follow-up covers mixed answers until then.
- Yes/No questions with a separate home question: the owner folded the home into each question.
