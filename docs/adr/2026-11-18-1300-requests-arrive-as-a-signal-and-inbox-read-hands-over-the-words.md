# Requests arrive as a signal, and inbox read hands over the words

On T-558 an ask read picked up (processing…) for 4 minutes while the orchestrator never opened the watcher's output: the watcher stamped it when it printed the ask, not when anyone read it. The stamp marked the print. The owner asked for a seam instead: signal the new item only, and hand the words over through one command that marks it thinking… (T-561, T-697).

**The owner's words arrive as a signal.** The owner's own words are the kinds `bin/event-lines.mjs` `ownerWords` names: a thread message (`item-message`, a Slack-copied one included), an ask, and an ask edit, never an ask an orchestrator filed. On a board the watcher (`bin/wait-events.mjs`) prints each as one line, `new reply on <task>: inbox read <key>` (or `new ask`, `ask edited`, `Implement asked`, `new reply from <name> via Slack`; `signalLine`), never the words or the event line, and stamps nothing for it. The PostToolUse hook (`hooks-plugin/hooks/board-messages.mjs`) does the same mid-turn: it signals each one past the watcher's cursor it hasn't signalled and no read has handed over, and stamps nothing.

**`board.mjs inbox read [<file>/<id>]` hands them over.** It prints each unread one, on that task or on every task, with its sent time, age, plain line and event line (`readInbox`), and stamps it picked up in the same command, before it prints: working in `data/working.json` for `WORKING_KINDS` (the New strip, the waits' picked up), delivered in `data/delivered.json` (the thread and the card read thinking…, domain.mjs `handedAt`), and an edit's ask mark moved to now. The read is the one place the owner's words turn thinking…, and the stamp is exact: if the command printed the words, the session has them. The read acts on no card (`ACTS`), so it doesn't end the card's thinking.

**Unread is no delivered stamp.** An owner-words event is unread while `data/delivered.json` has no stamp for it and it was sent after the file's `since` (`wasRead`). A watcher's start writes `since` when the file has none, so on a new board the first request reads waiting…, not handed when sent. A wake signals a request a read already handed over again, prefixed `already read: `, so the session doesn't act on it twice; the hook's `already shown` tag is gone with the printed words.

**What stays as it was.** Every other waking kind prints in full with its plain line and is stamped working and delivered at the wake, as [a card reads thinking from its event's delivery until the orchestrator writes](2026-11-15-1700-a-card-reads-thinking-from-its-events-delivery-until-the-orchestrator-writes.md) says: an owner's answer, an ask an orchestrator filed, another board's question, overnight triage and the board's own events. Their words are their whole message, and an answer's note stays with its question's wait.

**Not done here.** An unread signal re-waking the orchestrator after 2 minutes, and the Stop hook naming unread ones (t561-rewake), key off "signalled, not read" and are their own task.
