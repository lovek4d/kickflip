# Replies to a Slack message post into its Slack thread

A task filed from an @kickflip in one of the owner's 1:1 Slack DMs (ADR 2026-11-15-0130) gets later Slack replies copied onto it (ADR 2026-11-15-1530). This is T-228's second slice (T-395), the other direction: the orchestrator's answers to the Slack asker reach the Slack thread. The owner's answers on T-228 (11/15): only the orchestrator's replies post, signed off; mirror until Done, with one end line. On T-395 (11/16) the owner narrowed it: only replies to a message that came from Slack post; a reply to the owner's own board message stays on the board.

- **What posts.** A `reply` (`board/store.mjs` `writeReply`) to an event that came from Slack: the ask itself, routed with `routed.via` `slack` and a `routed.slack` thread, or an `item-message` carrying `slack` (a Slack reply `followSlackAsks` copied onto the task). The board decides from the answered event's source, not from the orchestrator's choice. Owner messages, replies to the owner's board messages, thread lines (`thread`), status lines and builder lines never post.
- **Recorded at the reply.** `writeReply` queues the reply's file name under its card in the board's `data/slack-threads.json` `replies {"<reply file name>": {key, ts?, failed?}}`, unless the card is already Done. Recording at write time, rather than deriving the queue from every reply file, means replies written before this shipped never post.
- **Posted on the hub's poll.** `hub/slack-intake.mjs` `postSlackReplies` runs after `followSlackAsks`: for each board, `slackOutbox` lists each Slack-filed task's unposted replies in the order written, and the hub posts each into the task's Slack thread as the owner, `"🤖 " + the reply` (T-89), which the Slack client ends with the `:claude_kickflip:` sign-off (T-150). Each posted reply's Slack ts is recorded, so none posts twice, and `boardPosts` counts it as the board's own, so following the thread never copies it back (the owner's signed-off posts are skipped there too).
- **One end line at Done.** Once the card is Done, one line posts after its last reply: `🤖 Closed: <title>`, or `🤖 Built and landed: <title>` when its Done phase is `merged`. Then nothing more posts: a reply written on a Done card is not queued. `slack-threads.json` `ends {"<channel>:<thread_ts>": {ts?, failed?}}` records each thread seen while its task was open, so a task already Done when its thread was first read (one Done before this shipped) posts no end line. The end line still posts under the narrowed rule, since it closes out the Slack asker's request.
- **Failures.** A failed post writes one red `slack-post-failed` fault line on the card (`board/hub-lines.mjs`), only on its first failure, and is retried on every poll. It holds back the thread's later posts, so the thread keeps the replies' order.
