# A PR's state is reactions again, and the signature is picked

[A PR's state is a line in its message, not reactions](2026-11-18-0000-a-prs-state-is-a-line-in-its-message-not-reactions.md) put "Approved by <names>", "Merged" or "Closed" in each PR message, edited in place, and dropped the reactions. The owner reversed it (T-678, verbatim): "go back to emoji reactions only for approved/merged/closed. drop the extra line. also offer a selector for the signature emoji (robot default)". This supersedes that record's state line; its emoji picker stays.

**The state is a reaction** (`board/slack-store.mjs` `prKind`, `reviewDue`; `hub/review-send.mjs`). Each posted link, digest reply and bump sent before bumps stopped gets one reaction for its PR's state: approved, as the `git_approved` reaction always held ([a chip per PR reviewer, and git_approved waits for GitHub's decision](2026-11-12-1400-a-chip-per-pr-reviewer-and-git-approved-waits-for-githubs-decision.md)), then merged or closed in its place. Changes requested gets none. The messages carry no state line.

**A reaction follows the state both ways.** `pr-slack.json` records each reaction the hub added, `reactions: [{kind, name}]`, so it removes only its own: one whose state no longer holds (an approval taken back, or approved once merged or closed) is owed a removal, sent before the new reaction so a state picked with the same emoji as another keeps it. A reaction already there counts as added, and one already gone as removed. An earlier build recorded a reaction by its name alone (`git_approved`, `git_merged`, `x`), which stands for its state; where that build reacted with a standard emoji in its place, removing the recorded name misses it. A pick changed in Hub › Slack sets the reactions added from then on and doesn't swap those already there.

**A state line already posted is edited out once.** `review due` owes an edit for each message whose record has `state` (the line's words), sending the bar again without it; the edit's sign-off names its time as every edit does. Its record then drops `state`, so it is never edited again.

**The emoji per state stays one hub-wide pick** in Hub › Slack (`hub/slack.mjs` `PR_EMOJI`, `prEmojis`; `slack.json` `pr_emoji`), now setting the reaction: the workspace's `git_approved` and `git_merged` by default, else `white_check_mark` and `large_purple_circle`, and `x` for closed.

**The signature is picked beside them** (`hub/slack.mjs` `readSignOff`, `setSignOff`, `signOffLine`; `board/public/slack-emoji.js`). One more row, Signature, in the same popover grid, sets the emoji of the sign-off line that ends every message the hub and the orchestrator post ([every Slack message ends with a sign-off line](2026-11-12-0400-every-slack-message-ends-with-a-sign-off-line.md)). It is kept as `slack.json`'s `sign_off_emoji`; with none it is `robot_face`, whatever the workspace has, where before it was `claude_kickflip` while the workspace had it. The client no longer asks `emoji.list` to sign off. `board.mjs slack signature` prints the line, for SKILL.md's rule on Slack answers.

**The hub still knows its past posts.** The hub hears past its own posts by their sign-off (`isSignedOff`), so a changed signature must not make its earlier posts read as the owner's. A sign-off reads as ours with the picked emoji, `robot_face` or `claude_kickflip` (the two it used before the pick), or any emoji picked before, which `setSignOff` keeps in `slack.json`'s `sign_off_past`.
