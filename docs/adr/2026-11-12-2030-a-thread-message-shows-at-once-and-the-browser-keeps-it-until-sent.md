# A thread message shows at once, and the browser keeps it until it is sent

Supersedes, for thread messages, [a tap spins until the board shows its change](2026-11-05-0200-a-tap-spins-until-the-board-shows-its-change.md) (thread Send and quick replies waited through `loadThread`) and the thread half of [a pending ask or thread message can be deleted or edited](2026-10-29-1639-a-pending-ask-can-be-deleted-or-bumped.md).

Reply used to spin until the board had the message and the thread showed it, which takes seconds on a board rebuild, and the box stayed full meanwhile. The owner (card #603, three prototype rounds) wanted a message to go out at once, the box clear for the next one, and several messages in flight without waiting for the host.

- **The outbox.** Reply, Implement with text or files, and What's left? put the message in an outbox kept in the browser's storage under the board's own keys (`site:<route>:outbox`), clear the box and draw the message in the thread at once, after everything the board has. Each card's outbox sends one message at a time in the order written; a message leaves the outbox once the board has recorded it, and the thread reloads with it in place while the next goes.
- **A reload resends.** Whatever the outbox holds when the board first lands goes out again, a failed send included. Each message carries a `sendId`, and the board server answers an `item-message` whose `sendId` it already recorded with that event's id and records nothing, so a send whose answer the page never saw is not doubled, nor is an Implement staged twice.
- **The footer.** An owner's message reads its time first in its footer, not beside its name, then the tap it came from, then where it is: `sending…` until the board has it and `waiting…` until the orchestrator picks it up, both grey, then `thinking…` with the working dot in the accent blue. Blue is the owner's pick over the colour rule's orange for the orchestrator working.
- **A failed send** reads `not sent` in bold red with Retry and an X at the right, and holds the messages behind it, still sending…, so the board gets them in order. Retry sends it again under the same `sendId`; X drops it and puts its text back in the box, before whatever is typed there. Each asks first through the board's confirm, the one Hold, Done and Reopen use.
- **Only Implement waits.** Implement with text spins until its own message is sent and the thread shows it, with the card's "Marked as staging" after it ([a message sorts above the status line it causes](2026-11-12-2200-a-message-sorts-above-the-status-line-it-causes.md)); a failed send rests it. Implement with an empty box, the eye, fire and image requests, and the buttons that move a card (Done, Hold, Close, Reopen) spin as before.
- **No Edit or Delete on a thread message.** Once the board has a message the orchestrator may read it at any moment, so an edit or delete races it; a follow-up message is the correction, and the thread is append-only. An ask in the New strip keeps its Edit and Delete, and `ask-edited` and `ask-withdrawn` stay for it.
