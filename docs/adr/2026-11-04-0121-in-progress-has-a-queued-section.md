# In Progress has a Queued section, and the pull takes its top under the cap

The owner asked on #36 (11/03): "I kind of want there to be a proper cued to build, maybe a section in progress called queued … bump means if auto build is on build this as soon as possible … bumping and unbumping cards can just be where they are placed in the queue. And then there can be a getter for the top of the cue to be pulled in. This shouldn't have to come through the agent at all." The #102 grill settled the rest: one queue, which the pull takes from the top whenever In Progress is under the cap (gh102-fit); queued cards don't count toward the cap (gh102-count); it holds tapped blocked cards and bumped ready cards (gh102-members); bump puts a card at the top and unbump returns it to its place by time (gh102-bump).

This supersedes in part [auto implement fills In Progress up to Maximum parallel implementers](2026-11-04-0057-auto-implement-fills-in-progress-up-to-a-cap.md), which turned down an In Progress lane for cards over the cap and pulled the top pullable cards in Todo; [build on a blocked card queues it](2026-11-03-0301-build-on-a-blocked-card-queues-it.md), on when a queued build starts; [a card moves to In Progress only once building starts](2026-11-03-0202-a-card-moves-to-in-progress-only-once-building-starts.md), for queued cards; [each lane has one fixed order](2026-11-03-0223-each-lane-has-one-fixed-order.md), on In Progress's order; and [an idle board pulls in its top Todo card](2026-11-02-1754-an-idle-board-pulls-in-its-top-todo-card.md), on which cards are pullable.

- **One Queued section.** In Progress lists its other cards first, then one Queued section headed "Queued" with its count (`board/public/app-lanes.js` `progressRows`). A queued card is `lane: 'progress', queued: true` (`board/domain.mjs` `buildBoard`). The lane's count includes it. A wave band names it "queued" where it names other cards "in progress".
- **Members.** A card the owner tapped Implement on while a dep blocked it (`queued_at`), unless held. While Auto implement (`auto_pull`) is on, every queueable card too: a ready, unstarted work card that isn't held, nothing blocks, with no question open or waiting on Claude and no grill under way (`domain.mjs` `queueable`). That covers bumped ready cards and ready cards waiting over the cap, and a card the pull sent that hasn't started yet. With Auto implement off a ready card stays in Todo and a bump orders Todo as before, since nothing would build it from the queue.
- **Order.** Bumped cards first, the latest bump on top, then the rest oldest first by when they were asked for: the tap's `queued_at`, else the card's `created` (`board/public/ui-order.js` `laneOrder`, `sortAt`). The top is the next to build. Unbump drops the bump, so the card goes back to its place by that time. The time line shows that time.
- **The pull takes the top.** `pullOf` walks the queue in board order and fills the free slots (the cap less the implementers and the pulled cards not yet started) with the next takeable cards: a tapped card nothing blocks any more goes to `starts`, a pullable card not yet pulled to `pulls`. A tapped card still blocked is passed over and keeps its place. Queued cards hold no slot. The board server's `checkAuto` starts each of `starts` as the owner's Build tap would (`store.mjs` `startQueuedBuild`, waking the session with `card-build`), Auto implement on or off, since the owner asked for each, then sends `card-pull` for `pulls` while Auto implement is on, as before. The separate minute check of queued builds (`checkQueued`, `store.mjs` `dueQueuedBuilds`) goes; the pause line still holds both.
- **Pullable.** A ready card whose questions are all resolved is pullable now; before, any question at all kept a card out, so a card grilled and set ready was never pulled. A question open, or answered and waiting on Claude, still does. A held card is never pullable.
- **Triage** still looks at the ready cards in Queued, which are unstarted Todo work.

Considered:
- the board server starting ready cards itself, as it does tapped ones, so no `card-pull` reaches the session: the session's pull also decides between a build and one more grill, which the server can't;
- putting bumped ready cards in Queued with Auto implement off: nothing would ever take them from it, so the section would promise a build that never comes;
- the newest card first, as Todo's backlog sorts: a queue whose top builds next serves the card waiting longest first, as New cards do;
- counting only the running cards in In Progress's header: the collapsed lane would hide the waiting ones.
