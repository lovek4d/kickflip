# /review in a thread launches a reviewer

The owner asked for an adversarial review of a task in one step from its thread, instead of asking for "adversarial discuss this with a subagent" in words. The grill on T-300 settled it: the command is /review (owner: "/review for the command as well"); it reviews whichever exists, the diff once built and the plan before; the board launches the agent from a brief, as it does a visual; the findings post as one ranked message and move nothing. The prototype round picked take B: a compact grey Reviewer row while it runs, the findings a separate message under it, with no verdict line from the orchestrator. The request row's Review button is T-542.

- **Request.** /review typed in a task's thread sends `review-request {key, text?, files?}`, the same way /visual does. It is a thread word only: the New task box's /review is plain text, since a new task has nothing to review. A bare request is the line "Review requested", led by a magnifying glass. It wakes nobody. A reviewer brief the orchestrator writes with no request reads "Review started" under the same glass, as a grill, prototype or visual it starts does.
- **Brief.** The task owes the orchestrator a reviewer brief (`item brief <key> --kind reviewer --file <draft.md>`), in any open lane, not only in Todo, since a review of the diff comes once the build is under way. Its `brief` wait reads "what the review should cover". A Done task gets none.
- **Agent.** A reviewer is a planner kind: it writes no code, so it never starts a task or takes an implementer slot. Like a visual agent it runs *beside* the task's work (`domain.mjs beside`): it is not the card's status line, it doesn't hold a grill or staged questions back, its start resolves no answered question, and the task's reviews run one after another. Its record is `reviewer-<its brief's time in ms>`. It runs on Opus, because finding what is wrong takes the stronger model, in the board's repo, reading the task's worktree.
- **Target.** At the start (`store.mjs startReviewer`) the board picks what it reviews: the diff while the task's newest worktree is on disk (`git -C <worktree> diff <base>`, which holds committed and uncommitted work), else the plan (the notes and thread). The record keeps it as `target`, which the agent's own `builder start` keeps.
- **Showing.** While it runs, the thread folds its run into one grey row, "Reviewer · Reviewing the diff (2m)", counted live, and the card shows the same row under its status line. Grey, not a planner's blue: the owner asked for a "gray card" for it.
- **Findings.** The agent posts its verified findings with `reviewer post <key> --file <findings.json>`, a list of `{severity: high|medium|low, at?: "<file>:<line>", text}`. The board ranks them, most severe first and the agent's order within a severity, and writes one thread line `{who: reviewer, kind: reviewer, text, findings}`, headed "N findings on the diff, most severe first" or "No findings on the plan". The thread draws it as a grey Reviewer message: each finding's severity badge (high red, medium orange, low blue), its file:line and its sentence, the top three shown and the rest under Show all. It is written as the reviewer, not the orchestrator, so it answers no owner message and clears no wait.

A reviewer that ends without posting leaves only its finished row; there is no "unposted" fault as a visual has.

The thread's request row also has a Review button after Visual (Alt+R), sending the same `review-request` as typing /review; the card's and the New task's rows have none.
