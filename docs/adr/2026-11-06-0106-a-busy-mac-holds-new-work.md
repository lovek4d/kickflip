# A busy Mac holds new work

The owner (hub #328): "more parallel implementers should be stopped if resources are low". The grill settled it (11/06): the Mac reads busy on macOS memory pressure and load per core; while busy every board holds all new work, as the usage pause does, and running work finishes; nothing running is stopped; a bumped card gets no exception ("hard cap of no new work no matter what until it recovers to warn at least"); no new lander starts. The prototype round picked the word-only display.

- **Busy**: memory pressure critical (`sysctl kern.memorystatus_vm_pressure_level` 4), or a 1-minute load average of at least 4× the cores. **Eased**: pressure warn or lower and load under 3× the cores. The release point, 3×, is the builder's pick: a busy Mac doesn't ease the moment load dips under the line it crossed, and a 10-core Mac under parallel land suites read 15 to 73 (#306, #311), so 3× still lets a few builders run side by side. Pressure that reads nothing (off macOS) goes by load alone.
- **One owner of the state**: the hub's 15-second tick reads the Mac (`shared/machine-gate.mjs` `checkMachine`; `os.loadavg`, `os.cpus`, one `sysctl`) and keeps `~/.claude/kickflip/machine-state.json`. Hysteresis needs the state before, so one process keeps it; every other reader reads the file. Without the hub nothing runs boards, so the file doesn't outlive what it holds.
- **The one gate**: `readUsageGate` carries the file's `{state, reason}` as `machine`, leaving `state` the usage pause's. `holdsWork(gate)` (a pause or a busy Mac) holds what the usage pause holds on the board server: pulls, planners, landers, rebases, rounds, visuals, triage and the review, and the minute tick reruns them once it lifts. `heldFor` holds every kind, Codex included, at `builder start` and for launches and relaunches, except a start that takes up a record its dispatch already opened (open, not done, any dispatch: tap, hub or session): the dispatch was the gate, so the worker's own start isn't held again (#441). The Implement tap and the architecture review refuse. Keep going lifts only the usage window, so it never lifts a busy Mac.
- **Not held**: the hook, the watcher's held events and the hub's session wakes read the usage pause alone. They gate in-session agents and the orchestrator's events, and holding those would stop running builds mid-way, where the owner asked that running work finish.
- **Words**: a pause reads before a busy Mac. A refusal says "Work is held: this Mac is busy (memory pressure critical | load high). It starts again when the Mac eases." A card whose launch a busy Mac holds gets the thread line "Held: this Mac is busy. It starts again when the Mac eases."
- **Display**, word only, no numbers: the sidebar's Hub row reads busy · Mac is busy, every board row reads busy in place of its status word, the board header reads busy in place of the age (orange, its title saying why), and Health has a Machine row reading busy · <reason> or normal.
- **Readings**: the hub's audit log gets `machine-busy` and `machine-eased` on each change and a `machine-reading` every 10 minutes, each with the reading, so the thresholds can be checked against what this Mac reads (it read pressure warn and load 15 on 10 cores at grill time).
