# The orchestrator reviews every lane on a schedule

#391. On #378 the owner dropped the nudge and stale-tap logic: "The orchestrator should now be doing periodic reviews of each lane. So it should be catching anything that is flagged as stale and addressing it as necessary." Most of that review already ran: the board server checks every card on each board change and each minute, a stale run and a review past seven days are `stale` waits on `data/orchestrator-waits.json`, and the watcher prints every wait on every wake ([each lane is a queue for the orchestrator](2026-11-04-2300-each-lane-is-a-queue-for-the-orchestrator.md), [nothing waiting on the orchestrator is missed](2026-11-05-2358-nothing-waiting-on-the-orchestrator-is-missed.md)). Three gaps were left: no scheduled pass checked blocked-until conditions, a picked-up stale review waiting only on a human re-woke hourly forever, and no rule said when to restart a stale run rather than stall it.

The owner's answers (11/06): the waits list is the per-lane review, plus one walk over every lane at the morning wake (gh391-pass); one restart, then a stall (gh391-restart); a stale review waiting only on a reviewer gets a thread line naming who and a daily wake, while a change GitHub polling sees on its PR wakes at once (gh391-review); a thread line on each card acted on, nothing else (gh391-report). The owner's question about regular polling and an idle-for-an-hour option is #425's.

- **The waits list is the review.** Nothing new runs between wakes: the list already names every stale run and stale review, lanes top-down, on every wake.
- **The morning wake walks every lane once.** The hub's daily `check-github {reason: "morning"}` (`github.mjs` `sendWakes`) prints, in the watcher (`wait-events.mjs` `PLAIN`), "the daily wake: run one GitHub tick, then walk every lane top-down once: clear each blocked-until condition that holds, and act on any card stuck with no wait; a thread line on each card you act on, nothing else". That pass is the "passes over the cards" on which the orchestrator checks a blocked-until condition. A `check-github {}` from the owner's refresh is only a GitHub tick.
- **A stale run gets one restart.** Both stale-run waits' `next` (`domain.mjs` `orchestratorWaitOf`, `RESTART_NEXT`) say: restart it once from its worktree with a thread line; if the restarted run goes stale too, `item stall` it with the reason. The orchestrator tells a second stale run from its thread line, which the restart left.
- **A stale review re-wakes daily once picked up.** Its wait carries `daily: true`, and `waitsStep` re-wakes a picked-up daily wait `DAILY_REWAKE_AFTER` (a day) after the later of its pickup and its last wake, instead of `PICKED_REWAKE_AFTER`. Until picked up it re-wakes every 15 minutes as any wait does. A review, comment, CI result or merge on its PR already wakes the session by `github-change` from the hub's poll, so the daily wake only covers a review with no change. The orchestrator fixes what it can first (rebase, CI, comments), and when only a reviewer owes the review, its thread line names who; that line is the pickup.
- **It reports on the cards it touches.** A thread line on each card it acts on; nothing on cards it passes over, and no board-wide summary.

Considered:
- a new hourly lane-review event: the minute check already places every wait, so it would wake the session to read the same list;
- a daily wake for every picked-up stale review, fixable or not, versus only one the orchestrator marks as waiting on a reviewer: a fix it can make lands within the day through the PR's own `github-change` wakes, and a marker would need a command of its own;
- two restarts before a stall, or none.
