# The hub starts a new board's session itself

New board's Start is the confirm. Once the request passes its checks, the hub runs the same start that `web-ts start` runs, with no session in between, so New board needs only the hub server, as [0068](0068-the-hub-session-is-a-dev-time-role.md) requires of every feature. The owner picked this (`hub-start` on hub/INT-169): "The hub starts it as soon as the request passes its checks".

- **What is checked.** `POST /_hub/new-board` (`hub/new-board.mjs`) takes only a name, a repo folder and a purpose. The name is 1–60 characters and must make a route, lowercase letters, digits and dashes, that no site or Starting row holds. The purpose is at most 240 characters. The folder must be an existing directory under the owner's home once `~` and symlinks resolve. The route also refuses, with 403, a cross-site request (a `Sec-Fetch-Site` other than `same-origin` or `none`, or an `Origin` whose host isn't the request's) and a body not sent as `application/json` (`hub/cross-site.mjs`), so another site's page can't start a session. A refused request records nothing and starts nothing.
- **How it starts.** The hub records the Starting row (`starting[<route>]` in the manifest, with the title, folder and request time) and answers `{route}`. It then runs `startSession` (`hub/sessions.mjs`) in that folder. The prompt is the board's join flags, `--template board --title … --description …`, each value shell-quoted, as `web-ts start --prompt` passes them. The response doesn't wait for `claude`. The session it starts is recorded on the Starting row as `web-ts start` records one, and the session's join turns the row into the board.
- **A failed start shows at once.** When `claude` fails to start (not installed, not signed in, a non-zero exit, or no session id comes back), the Starting row keeps claude's first error line, cut to 200 characters. The row reads Didn't start with that line and Dismiss. A start that runs but never joins still reads Didn't start after 15 minutes.
- **The same session settings.** The session starts with `BG_SETTINGS`, which every hub start and resume passes ([0061](0061-a-boards-session-wakes-when-an-event-arrives.md)): auto mode, worktree isolation off, and the prompt hook that brings its permission prompts and questions to the phone ([0060](0060-background-sessions-prompts-come-to-the-phone.md)).
- **No hub board needed.** No ask goes to the hub board, and New board works with no board flagged `hub: true` and no hub session running.
- **Install builds are unchanged.** [0067](0067-the-hub-runs-a-boards-install-script.md) limits install builds to the owner-set script with fixed arguments. That limit is about install builds and still holds. This start runs `claude` with fixed flags, and the request supplies only the checked folder and the quoted flag values.

What's new is a fresh session, in auto mode, in a folder typed in the app from any tailnet device. The checks above, and the tailnet's own access, are what stand between a request and that session.

Considered:
- A second confirm tap (`hub-start` B): Start would make a pending row in Needs you showing the folder and auto mode, and a second tap would start the session. It guards against a mistyped folder, at the cost of two taps for every new board.
- Keeping the ask to the hub session and starting directly only while no hub session listens (`hub-start` C): the app keeps the dev-time path [0068](0068-the-hub-session-is-a-dev-time-role.md) says to remove, and the two paths can disagree.
