# Every owner tap the server can apply draws at once

This supersedes in part [the board applies the owner's Hold, Resume and Done at once](2026-11-02-0009-the-board-applies-the-owners-hold-resume-and-done-at-once.md), which applied Hold, Resume and Done at once but still showed them only once the page reloaded, and generalises it into the board's rule for every owner tap.

**The rule.** Every owner tap whose result follows from the tap alone is applied by the board server inside the POST, the POST answers with the result, and the page draws it at once. The event in `data/events.jsonl` is a record for the session, never what the owner waits on. Only taps that need judgment or outside tools, such as Grill, prototypes, a nudge, planning follow-ups, wave triage or a GitHub check, wait on the session. A new tap follows this rule.

- **The events POST answers with the board.** `POST /_claude/events` answers `{id, board}`, `board` being what `GET /api/board` answers as the tap left it, so Hold, Resume, Done, Build and every other event draw from the one round trip (`board/server.mjs`). A board's `generatedAt` is when it began reading.
- **One reload per tap.** The board view sends events through `B.send(kind, data, draw)` (`board/public/app.js`), which lands the POST's board as a load of its own; the tap's handler loads nothing more. The change signal that the event's write sends reloads the board once, as it would for any change ([the board reloads on a change signal](2026-10-29-1639-the-board-reloads-on-a-change-signal.md)). A board that lands, from a load or a POST, while a newer one is on screen is dropped, so a slow load can't undo a newer one. A tap that posts elsewhere, such as Serve/Build's `api/try`, reloads through the change signal's guard (`B.reload`), which runs one load at a time and one more when a signal came during it.
- **Bump, unbump, a New card's bump, delete and edit draw before the POST.** `draw(board) → board` changes what the tap changes: `bumpedAt` for a bump or unbump, the text for an edit, and the page re-sorts the items by the server's own order, `BoardUI.laneOrder` (`board/public/ui-order.js`, which `board/domain.mjs` runs in a vm context), so the card lands where the server will put it ([each lane has one fixed order](2026-11-03-0223-each-lane-has-one-fixed-order.md)). The drawing stays over every board that lands until the POST settles. A failed POST takes it back off, and the toast reads "That didn’t go through. Is the host awake?"; a failed edit reopens its edit box with what was typed. A delete already drew at once ([a pending ask or thread message can be deleted or edited, and a pending ask bumped](2026-10-29-1639-a-pending-ask-can-be-deleted-or-bumped.md)) and keeps doing so.
- **The bump icon's fill fades** in as a bump draws and out as an unbump does, on a toast's fade times (`board/public/toasts.js` `enterTime`, `exitTime`), through any redraw meanwhile (`app.js` `fadeBump`).

Each tap reloaded the whole board twice, the click's own load and the change signal's, and drew nothing until a load landed, so a bump the server had recorded at once waited on transport and two 870 KB board loads.

The owner (ask, 2026-11-03): "I would like it if we could make the bump faster and more responsive. I think there's a lot of things that we could just do on the front end or even on the server without waiting for an agent to respond. [...] I do want to make sure the architecture is right here and that we are doing as much as we can responsively and then cueing those actions for the agent to consume rather than waiting on the agent." The grill settled that a tap drawn at once and then failing is undone on screen with a toast saying it didn't go through, and that "the color on the bump should fade in and out along the standard toast transition".

Considered:
- dropping the click's load and relying on the change signal alone: a tap while the stream reconnects would show only at the 30 s poll; the POST's board needs no stream;
- routing the click's load through the change signal's guard: a signal arriving during the click's load still runs a second one, so a tap kept two loads;
- answering the POST with only the changed lanes: the page would merge partial boards; a smaller board load is its own card (#103);
- skipping the change signal's reload after a POST's board: the signal may carry another writer's change made meanwhile, so skipping it could lose an update.
