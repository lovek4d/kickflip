# The hub sends reviewer Slack messages with its own token

Reviewer PR links, `git_merged` reactions and the weekday digest went out from a board session through Claude's Slack connector, which `review due` listed with a `record` command for each. The connector wasn't working in any session, so the Slack row stayed Not ready and nothing was sent. The owner asked for the follow-up: a Slack token on the host, as Hub's Linear key is, so no session is involved (#35; `int271-slack` option B; `gh104-told`: "maybe this is better revisited after we move to a Slack API token").

Decision:

- **As the owner, with a user token (`xoxp-`).** A bot token can't post in the owner's DM with a reviewer or react on links sent there, so the `dm` ids and recorded links would change. The token is pasted on Hub settings › Slack, checked with `auth.test` and saved as refused when Slack refuses it, like the Linear key. A bot token (`xoxb-`) is refused when pasted. The settings row links Slack's new-app page with a manifest whose user scopes are `chat:write`, `im:write` and `reactions:write`.
- **One secrets file.** Every hub token lives in `~/.claude/kickflip/secrets.json`, mode 600, outside any repo: `{linear, slack}`, each section owned by its module (hub/secrets.mjs, linear.mjs, slack.mjs). Linear's `linear.json` moves in on the first read. `slack.json` keeps the identity, which isn't secret (owner: "make sure this and the linear token etc are gitignored, and maybe have a single file that holds tokens like this").
- **The hub's poll sends.** After each GitHub check refreshes the PR cache, the hub reads every board's `review due` and sends each review link to the DM it opens with `conversations.open` on the reviewer's `slack_user`, each `git_merged` reaction, and each digest reviewer's message and thread, then records each with `reviewSent`, `reviewReact` and `reviewDigestSent`. The record is unchanged: `review_link_ts` on the item and `review-digests.json`. One reviewer's failure leaves the others sent and that send still owed; a refused token stops every send and marks the token refused, so the row and `review due` wait.
- **Updated through a command.** Whether a change is a behavior change stays the session's call: `board.mjs review updated <wave>/<id> --text` posts “🤖 Updated: …” under each recorded link whose reviewer's latest GitHub review on every PR of the card isn't an approval.
- **Slack readiness reads the token.** The row reads no token / refused / set. The connector report (`integrations report --slack`, `integrations.json`, the session-start step) is gone, with no connector fallback.
- **Recipients** are each board's and wave's reviewers, as before. The owner's `self_dm` gets nothing. The reviewer record still requires `dm`; adding reviewers from fetched Slack lists is #193.

This replaces the "Kickflip holds no Slack token" reason behind rejecting "`review due` sending to Slack itself" in [the board records what it knows](2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md), and the session report in [integrations show readiness](2026-11-02-1118-integrations-show-readiness-and-features-wait.md). `review due` still sends nothing itself: the hub calls it.

Considered: a bot token (rejected above); the Keychain (one mode 600 file matches Linear's and the owner's single-file ask); keeping the connector as a fallback (the aim is to take Slack out of the session).
