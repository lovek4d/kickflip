# A board asks a board on another of your hubs while it's online

#1060 (hub/T-666), split 1 of T-389: the owner's other Mac runs its own hub, and an agent there should be able to ask a board here, and the reverse, as [a board asks another board](2026-11-15-0200-a-board-asks-another-board-and-its-orchestrator-answers.md) does within one hub. The owner's T-389 answers: `<hub>` is the other Mac's tailnet machine name; `boards` lists every hub's boards as `<hub>/<route>`; an offline or older hub is queued, which is split 2 (T-667). This slice refuses it instead. What's exposed (T-389, owner's "what will we be able to ask, what is exposed?"): one line of text in, one line of text back, and the list of board routes and titles. No cards, threads, notes, files or code, and nothing runs.

- **Peers are found, not listed.** `hub/peers.mjs peersOf` reads `tailscale status --json` (through the recorded daemon) on each send: a peer is a node whose `UserID` is `Self`'s, `Online`, and not iOS or Android, named by the first label of its MagicDNS name, lowercased. Its hub is `https://<MagicDNS name>/`, where that hub's own `kickflip tailnet on` maps Tailscale `/`. Nothing is cached, since machines come and go.
- **Two sets of routes.** `/_hub/peer/{ask,answer,boards}` take another hub's request; `/_hub/peers/{ask,answer,boards}` take this host's agents' and relay each to the named hub's `/_hub/peer/<same>`, adding `from.hub` (and `from.host` on an ask) as this hub's own name. The outgoing routes are loopback only, as `/_hub/build` is, so a page or a tailnet device can't make this hub send. The CLI goes through its own hub rather than fetching the peer itself so that split 2's outbox, retried on the hub's tick, sits on the one send path.
- **Trust is the tailnet identity.** The incoming routes pass the hub's owner gate and nothing else: Tailscale Serve sets `Tailscale-User-Login` on a request from a user-owned node, and the gate calls a request whose login is the host's user `owner` ([the whole hub answers only the owner](2026-11-04-2156-the-whole-hub-answers-only-the-owner.md), [only the owner's tailnet identity gets in](2026-11-18-0700-the-hub-has-no-sharing-only-the-owners-tailnet-identity-gets-in.md)). A Node fetch sends no Origin or Sec-Fetch-Site, so the cross-site check passes it. Another login, a tagged node or Funnel gets the front door's 403. No shared secret: anything that could read one already runs as the owner. T-682 (owner actions need the owner's sign-in cookie) isn't landed; when it lands, these routes stay outside the cookie check, since the other hub has no cookie and its proof is its Tailscale identity.
- **Asking.** `ask <hub>/<route>` (`board/asks.mjs askBoard`) posts `{hub, route, text, from}` to `/_hub/peers/ask`. The other hub files it with `takePeerAsk` as a `board-ask {text, from {hub, host, route, title, key?, ref?}}` and answers `{id, listening}`. Only then does the asking board record `{id, to: "<hub>/<route>", …}` in `board-asks.jsonl` and write the task's "Asked <hub>/<route>: …" line; a refusal records nothing. `asks` reads "waiting on <hub>/<route>'s orchestrator" until the answer, since the other hub's listening is read only when asked.
- **Answering.** On the answering board the question is an ordinary `board-ask`: its wait reads "Answer <hub>/<route>'s question", and the New strip "Asked from <hub>/<route> · <ref>", linking `https://<host>/<route>/#selectedCard=<key>` in a new tab. `answer` sees `from.hub` and posts `{hub, id, route, text, from}` to `/_hub/peers/answer`; the asking hub's `takePeerAnswer` takes the task and the question from its own `board-asks.jsonl` record of what it asked that board (refusing an id it never asked there), posts the answer as a `via: board` message named `<hub>/<route>`, and appends `board-answer`. As within a hub, `board-ask-answered` is written last, so an answer that didn't go keeps its wait.
- **Refusals.** Each says why, from `/_hub/peers/*`: the tailnet off here (409, naming `kickflip tailnet on` for both hubs), tailscale not answering (503), no such peer online (404, naming the ones that are), the name being this hub (400), the peer not answering (502: down, or its tailnet off), and a peer answering without JSON (501: a hub from before these routes answers an unknown `/_hub/` path with a bare 404, so "update kickflip there"). The other hub's own refusal, such as no board at that route, passes through as its JSON error.
- **`boards`.** `board.mjs boards` prints this hub's boards as `<route>: <title>`, then each peer's from `/_hub/peers/boards`, which asks every peer at once, as `<hub>/<route>: <title>`, or `<hub>: <why>`; with the tailnet off it prints this hub's and one `other hubs:` line.

Considered:
- A list of peer hubs in hub settings. The owner: "Find your own Macs on their own" (gh350-peers).
- The CLI fetching the peer hub directly. Simpler today, but split 2's queue belongs to the hub, which retries on its tick whether or not an agent is still running.
- Trusting the answer's `key` and `question` from the other hub. The asking board's own record says which task asked which board, so a stray answer can't land on another task.
