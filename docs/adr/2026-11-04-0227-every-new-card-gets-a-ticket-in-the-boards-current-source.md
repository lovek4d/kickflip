# Every new card gets a ticket in the board's current source, and Linear needs its key

The owner asked on #126 for the ticket system to be enforced: "when a new task is created, it should automatically get a linear or GitHub or internal issue … Even if the type of ticket has been changed and now we have new tickets being created. It should change to the new format." On a Linear board without a key: "we shouldn't be able to set a linear board while there is no API key and if an API key is deleted from a linear board it should probably fall back to internal And it should show that visually in the settings somehow as well." He picked take B of prototype `ticket-source`, a status word. This supersedes in part [kickflip reaches Linear with a key on the Mac](2026-11-01-1436-kickflip-reaches-linear-with-a-key-on-the-mac.md) and [a board picks Linear only while Hub's key works](2026-11-02-1712-a-board-picks-linear-only-while-hubs-key-works.md): their Linear MCP fallback is gone.

- **One way to a ticket.** Every path that makes a card gets its ticket from `resolveTicket` (`board/tickets.mjs`), through `assignTicket` (`board/store.mjs`), in the source `board.json` names at that moment. The paths are `item add` (named or not), a follow-up (`item add --parent`), `item set --from-ask` on a card without a ticket, a moved ask (`ask move` makes no card, and the card it becomes on the receiving board gets that board's source), the board server's Run review route and `arch file`. `board/ticket-paths.test.mjs` has one test per path that switches the source internal → GitHub → Linear, plus a guard: every write that adds to an `items` list must be listed there with how its card gets a ticket, `resolveTicket`'s only caller is `assignTicket`, and `createItem` assigns before it adds.
- **Old cards keep their tickets.** A source change only changes new cards. Moving old cards to the new source is a task for the session when the owner asks for one. Owner: "Any changes to old cards should be managed by just having the session do that, like a new task from user to migrate to the new ticket system." `migrateFollowups` moves old follow-ups into cards with the tickets they already had.
- **Linear needs Hub's key.** `saveBoardSettings` (Board settings, `settings set tickets`, the server's `POST /api/settings`) and New board refuse Linear while Hub has no key or Linear refused it (`hub/linear.mjs` `linearWorks`). A card on a board that is still on Linear after its key went (removed outside the hub, before the hub falls the board back) is refused with one line and nothing is written. It is never left without a ticket. The `ticket: create the Linear issue …` lines, linking a Linear id on its pattern alone, and backfill's MCP count are gone. A move without the key prints `ticket <id>: not moved, Hub has no Linear key`.
- **Deleting the key falls back to internal.** When Hub settings removes the key, and when the hub starts with no key, every board on Linear moves to internal tickets with prefix INT (`store.mjs` `fallBackFromLinear`). Each one gets a `settings {tickets}` event, as for any source change. A refused key keeps the board on Linear. Its cards fail until the key works again or the source changes.
- **Board settings shows the state as a word.** The Tickets source row starts with a status word: `linear · connected`, or `<source> · no Linear key`, `· linear key saved` or `· Linear refused the key` on an internal or GitHub board (`dialogs.js` `ticketsControl` with `keyState`). In Board settings, tapping Linear without a working key opens Hub's key field inline under the Tickets row, not the modal. Once a pasted key works, Linear is picked. New board keeps the modal.

Considered:
- Keeping the MCP fallback for a Linear board without a key: a card could exist without a ticket, which is what the owner asked to rule out.
- Making new tickets for old cards on a source change, keeping the old id as an alias: the owner chose to leave old cards alone.
- Working out the source when it is read (Linear with no key reads as internal) instead of writing the fallback: adding the key back would silently put the board on Linear again, and the take B prototype keeps the board on internal until Linear is picked.
- Take A (Linear greyed out with a link to the key field) and take C (a banner after a fallback).
