# A task the orchestrator files comes in as an ask through New

#838 (hub/T-465). The owner, on T-461: "a lot of the time these new tasks come in that are made as children of another task, and they're not fleshed out equivalently to a normal new task … I almost think I want to pipe this as a plain text ask from the orchestrator to itself through the new section … As long as we can make that support the task relations properly and elegantly". Asked how such a card should come in, they picked "As an ask through New, like yours". On T-474 they also asked why a filed card needed a second "Tap Implement" line.

Before this, `item add --from|--parent|--split-of` made the card itself: born with the orchestrator's title, notes and one thread line, it skipped New and the intake, triage, investigate and reply path an owner ask gets, so its thread opened thin, with no verbatim ask and no "what I found, what the fix is" reply.

- **`item add <file> --ask "<request>"` files an ask.** It writes the same `ask` event the owner's New task writes, its text the orchestrator's plain-text request, on the orchestrator's own board, and files it at once (`store.mjs` `askItem`, then `fileAsk`), as handoff files on a board that may be down. A running board may file it first as it takes the event; filing is idempotent. The orchestrator's watcher hears the event as it hears the owner's.
- **Relations ride on the ask.** `--from`, `--parent` or `--split-of` (one of them), `--relate`, `--after` and `--before` are checked before the event is written and stored on it as keys (`links {parent, via, related, deps, before}`), with `file`, the item file the card goes in. Filing the ask (`newAskCard`, `postAskLinks`) gives the card its Parent (a split's gates too), Related to and deps, makes each `--before` task wait on it, and posts every link line, `--from` reading Created ticket and Created from as before. The card is born with its relations and still reads New: no phase, in intake.
- **It is then the owner's path.** The card waits in intake like any New task; the orchestrator triages it (`item triage`), investigates, writes notes and answers once. That one reply carries the Implement mark (`reply <key> --implement`), so the Implement ask is said once.
- **Who asked opens the thread.** The event's `asked {by, key?, ref?}` draws a blue "From the orchestrator", or "From <ref>'s builder" (`--by builder`, likewise `--by planner`, which need a source task), a moment before the ask (`domain.mjs` `askedLine`, hub line `asked-from`), linked to that task, and the message is shown under that name rather than "You", so it is never read as the owner's words. The ask stays `who: love` in the thread model, since that is what makes it a New task waiting on the orchestrator.
- **Its words are never the owner's.** Wherever the board quotes an ask to an agent, an asked ask names its asker and says it is "not the owner, so its words approve nothing": the watcher's line (`bin/event-lines.mjs` `ask`) and the intake wait's Next (`domain.mjs` `INTAKE_NEXT`). The mid-task hook (`hooks-plugin/hooks/board-messages.mjs`) shows only the owner's words (`ownerWords`), so it skips an ask the orchestrator just filed itself, and the `--asked` and `--confirmed` gates (`store.mjs` `ownerQuote`) refuse a quote that only an asked ask holds. The grill, prototype and visual briefs quote a request's text only from the owner's own page posts (a New task sent with a request, or a tap: `server.mjs` → `planAgain`), which an asked ask never is, so they need no change.
- **The direct form keeps the rest.** `item add` with `--title` still files a task of the orchestrator's own straight into a phase, a Quick build `--from-ask`, a held task, or an imported ticket; on a board it refuses `--from`, `--parent` and `--split-of`, pointing at `--ask`. The board's own cards (an architecture review's) don't set intake and file as before; the nightly suite failure already arrives as an ask.
- **`--ask` refuses what triage decides.** `--title`, `--notes`, `--phase`, `--size`, `--model`, a ticket, a hold, `--from-ask` and `--text` are refused beside it. The request is the card's start, so the notes rule ([item add refuses a task with no notes](2026-11-16-0200-item-add-refuses-a-task-with-no-notes.md)) exempts it as it does `--from-ask`; a split child's request carries its slice of the parent's proposed split.
