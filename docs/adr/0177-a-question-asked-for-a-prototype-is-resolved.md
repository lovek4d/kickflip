# A question asked for a prototype is resolved, and the page moves on

The owner, on #157: "Requesting a prototype in the open questions should effectively resolve that item in which a prototype was requested … it should just stay resolved and we should get a new prototype. … if that was the last item, move to the next item or return to the board." This supersedes [0126](0126-each-question-has-its-own-prototype-eye.md)'s locked "prototype requested" card and [0111](0111-a-prototype-round-ends-with-a-one-take-confirm.md)'s `requested` state.

- **The request resolves its question.** The board server records `prototype-request {key?, question, note, choice}` unchanged, then resolves that question in owner.json, noting "Prototype requested" (`board/store.mjs` `resolveRequestedQuestion`), before it answers the tap. The event, with its note and pick, is the round's input, and the session draws the round from it as before. The next round arrives as a new question with `round_of` the old one, which `question add` re-notes "Followed by prototype round N". An answer newer than the resolution reopens the question, as any answer does.
- **The page moves on as Send does.** Once the server has recorded the tap (no optimistic state), Waiting on you moves to the topic's next open question, else the next topic's, else back to the board with "Prototype requested for <topic>." as the toast: the same advance as an answer's Send (`view-questions.js` `moveOn`). A refused tap keeps the question and its draft and says why.
- **No requested state.** `ownerQuestion` has no `requested` state and topics no `requested` count; a question's `request` is its newest prototype request after its last answer. The topic's round reads making while a question has a request and no later round has arrived. The locked card, its badge, tint and disabled options and note are gone.
- **The card says so.** A prototype request on any of a card's questions counts as its newest input the way a no-take answer does ([0172](0172-a-prototype-answer-with-no-pick-prototypes-again.md) `noTakePicked`): the card reads prototyping, not buildable, with Next "Prototype again" while nothing waits on the owner, until the next round's pick.

Considered: deriving the resolution from the event alone, with no owner.json write. Store-side readers (`question add`'s follow-ups, `question resolve`, the Implement gate) read owner.json without request events, so the question would stay open to them.
