# One app for the whole hub

Superseded in part by [0058](0058-back-follows-the-page-tree.md) on back in the page tree: entries for a board, its Waiting on you and a prototype page carry `up`, the router writes the missing levels into history on every way in, and their back arrow goes up a level. `idx` and `pushed` below still steer every other view's arrow.

Every board, each board's pages and the hub's own pages are views of one page, the app shell, so nothing reloads, switching boards included. Sites that aren't boards open in a frame inside it. The shell mounts a board and its Settings, Waiting on you and Notes, and the hub's page, Hub Settings and Polling, as views, and every other site's page, a board's prototypes included, in a frame.

- **The shell** is `board/public/app.html`. The hub serves its scripts and CSS at `/_hub/app/<file>?v=<version>`, read from `board/public` (then `starter/public`) on each request, gzipped, with a pinned version cached for a year. The hub writes the sidebar and its data into the shell, so the first paint has them.
- **Who gets it.** The hub answers with the shell a GET whose `Sec-Fetch-Dest` is `document`, for `/` and for any site's page, a folder or an `.html` file under its route (`hub/shell.mjs` `pageOf`), with the sidebar written in. A GET or HEAD of a hub page, `/_hub/`, `/_hub/settings` or `/_hub/settings/polling`, gets the shell whatever its `Sec-Fetch-Dest`, curl and frames included, since the hub has no other copy of those pages; a frame's shell then hands its URL to the app around it. Every other request to a site is forwarded as before: API calls, scripts, images, uploads, frames (`Sec-Fetch-Dest: iframe`), curl, a browser that sends no `Sec-Fetch-Dest`, and a page asked for with `?alone=1`. The board server answers a board's four view paths, `/<route>/`, `settings.html`, `questions.html` and `notes.html`, with the same shell, without the sidebar, which the shell then fetches (`shellHtml`), so every push URL still loads on its own. A shell loaded in a frame inside the app hands its URL to the app around it (`AppShell.open`), as a framed prototype's pick does with the next question. The hub adds `Vary: Sec-Fetch-Dest` to a forwarded page, since the same URL is the shell at the top and the page in its frame.
- **Frames.** Any other page, another site's or a board's own such as a prototype, is a frame view (`view-frame.js`): a same-origin frame filling the view beside the board header (above it below 900px, under it on desktop, [0070](0070-phone-headers-sit-at-the-bottom.md)), the same `ui-page-header.js` render with the logo, the page's title and Open alone ↗, which loads the page by itself with `?alone=1`. A page that draws that header itself hides the shell's; its own logo then toggles the sidebar as the shell's does, and hides while the rail shows. The page's own navigations stay in the frame and in the browser's history, so back steps through them, and each load copies its URL and title to the top. A tap in the frame on a link to another view, the page's back arrow and the hub's pages included, shows it in the shell. `board/public/router.js` frames exactly the paths `pageOf` answers with the shell, which `hub/shell.test.mjs` checks, so a reload lands on the same view. A page that sends `X-Frame-Options` or `frame-ancestors` shows blank; Open alone ↗ is the way out.
- **URLs don't change.** `board/public/router.js` reads every hub URL as a view and writes each view back as that URL. A tap on a link to a view the shell mounts, a sidebar row included, pushes the URL and swaps the view in place; any other link loads its page. Back and forward move between views the same way.
- **`/` has no page of its own.** The shell opens this device's last board, else the sidebar data's `start`, else `/_hub/`, and replaces the URL with the board's. It opens only a board: a site that isn't one is neither stored as the last board nor picked as `start`. It picks by [0050](0050-a-sidebar-of-every-board-replaces-the-hub-home.md)'s rule, but replaces that ADR's start page. The Home Screen manifest keeps `start_url` and `scope` at `/`, since a changed start URL would make iOS treat it as a new app and drop the push subscription.
- **One view at a time.** Leaving a board unmounts it: everything its parts added goes with it (`BoardView`, `view.test.mjs`). It saves its last visit as it goes ([0028](0028-the-board-opens-on-the-last-visit.md)). Every board's snapshots together stay within three at the 900,000-character cap, the board saved least recently dropping first, so they never crowd the drafts out of the browser's 5 MB of storage.
- **One stream.** The shell holds `/_hub/stream` (`hub/stream.mjs`) in place of each board's own stream. While any page listens, the hub holds each board server's `api/stream` ([0031](0031-the-board-reloads-on-a-change-signal.md)) and sends `change {route}` for each signal; a board whose stream comes back, as after a restart, sends one change too. It sends `sidebar`, the data `/_hub/sidebar.json` answers, whenever that differs from the last copy sent: after a board's change, and on a 15-second check for what no stream reports, such as a site going down. That replaces the sidebar's 30-second poll. The open board keeps its 30-second poll as the fallback and the offline check.
- **Coming back to a board.** One left fresh whose stream sent no change since paints live at once, controls on. Any other paints its last visit dimmed until the load lands. A dropped hub stream forgets which boards were unchanged, since it may have missed a change.
- **Back one step** ([0048](0048-a-questions-takes-show-inline.md)). In one page `document.referrer` stops changing, so the router writes `{idx}`, the entry's distance from the shell's first one, into every history entry, and a view's back arrow goes back by `idx` through `ui-page-header.js` `backStep`. A push's `from=push` becomes `pushed` in its entry's state, which a reload keeps, and leaves the URL; that entry's back arrow goes to its `backHref`, the card or the board. A framed page's back arrow goes back within its frame while a page before it is there, and otherwise by the top entry's `idx` and `pushed` in the same way.
- **The hub's pages are views too** (`view-hub.js`, `view-hub-settings.js`, `view-polling.js`). Each reads its JSON from `/_hub/api/hub`, `/_hub/api/settings` or `/_hub/api/polling?w=`, which `hub/views.mjs` builds, so the words stay on the hub, and refreshes it every 30 seconds while it shows, waiting while a field, sheet or post is open. Their forms post as before, asking for `application/json`: the hub answers the view's new data, `{sent, count}` from Send now, or `400 {error}`, and the view repaints in place and refetches the sidebar; a post without that header still gets the 303 redirect. A tap on Polling's day bar picks a window from data already there and replaces the URL's `?w=` without a history entry.
- **Unsaved edits.** Leaving a view whose root holds `[data-dirty]`, such as a rules editor mid-edit on Board Settings or Hub Settings, asks first; No keeps the view, and a refused back or forward returns to it.
- **A push tap routes in place.** `hub/sw.js` focuses an open window and posts it `{open: url}` with a reply port; the shell answers `{routed: true}` when it shows that URL in place. A window that doesn't answer within 1.5 seconds, such as an older page, or a URL that isn't a view the shell mounts, is navigated as before. The shell answers at once, before any question about an unsaved edit.
- **The app opens while the Mac is asleep.** Every shell load registers `hub/sw.js` at `/sw.js` with scope `/`, the same registration that holds the push subscription, so an edit to the worker takes effect on the next load (it skips waiting and claims open pages) with no reinstall of the Home Screen app. The worker keeps the last shell the hub served with the sidebar written in (marked `X-App-Shell: 1`), and the files the shell loads from the hub, `/_hub/app/*`, `/_hub/colors.css` and the logo, each by its full URL, a new `?v=` replacing the old. Installing it saves the shell from `/` and the files it links, so one visit is enough. A page load of `/`, a hub page or any site's page goes to the network first, fetched again by the worker with `X-App-Shell: 1`, which the hub takes as a page load (`hub/shell.mjs` `destOf`), since Chrome sends a worker's fetch with `Sec-Fetch-Dest: empty` and the hub would forward it to the site; when that fails, answers a 5xx (Tailscale's answer while the hub is down) or takes over 3 seconds (a sleeping Mac leaves it hanging), the saved shell answers. It paints the last sidebar it saw, and each view's own offline handling takes over: a board paints its last visit dimmed under the offline toast, and ↻ brings it back once the Mac answers. Nothing else is cached or answered by the worker: API calls, `/_hub/stream`, `api/*`, `_claude/*`, uploads, posts, other origins, `?alone=1` and a frame's page load always go to the network, so a frame fails as before. `hub/sw.test.mjs` checks that the worker answers exactly the page loads `hub/shell.mjs` `pageOf` answers with the shell.
- **One page, many boards.** Each board keeps its storage under its own keys (`site:<route>:`), and a composer's files upload to the site of the board view around it (`attach.js`), never to the page's own.

The owner picked one app for the whole hub over keeping each board its own page (hub/INT-117), and settled: a board you leave unmounts, with one hub stream so the page holds one connection however many boards there are; framed pages use the board header itself, and the logo collapses the sidebar ([0050](0050-a-sidebar-of-every-board-replaces-the-hub-home.md)); the app opens network first when the Mac is asleep; and plain scripts with one factory per board view. They also asked that pages use the same system as boards, and that Boards and Pages stay apart everywhere sites are listed. Before this, switching boards loaded a new page, `/` was a page that loaded another, and a push tap reloaded the window.

Considered:
- keeping each board mounted and hidden after you leave it, which keeps every board's timers, threads and state alive in one page;
- a stream per board in the app, one connection for every board the page has opened;
- a framework or a bundler, rather than the plain scripts the board pages already are.
