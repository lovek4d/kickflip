# Todo has no queue: Implement starts at once, and the pull takes Todo's top ready card

The owner on #293 (11/05), after the queued-green prototype round (gh293-queue B, no queue, Implement bumps): "the only reason the Q has to exist is because the number of parallel in progress items is limited to ten. An alternative option, I think, is that we get rid of the cap for manually clicking implement … They can go straight to in progress. And there's no other reason to have a queue because the auto pull will just pull the newest ready card. And then the bump will handle prioritization there. So yeah, I think we can totally get rid of the queue entirely."

This supersedes [In Progress has a Queued section, and the pull takes its top under the cap](2026-11-04-0121-in-progress-has-a-queued-section.md), all but its pullable rule, and [Queued sits at the top of Todo](2026-11-04-0150-queued-sits-at-the-top-of-todo.md). It supersedes in part [build on a blocked card queues it](2026-11-03-0301-build-on-a-blocked-card-queues-it.md), on the queued build (the orange words on the time line and the bump icon stand), and [Implement in the thread queues the card for the orchestrator](2026-11-05-0300-implement-in-the-thread-queues-the-card-for-the-orchestrator.md), on what ready releases the card to and on the "queued" words. #276's bump == queue is dropped with it.

- **No Queued section.** Todo lists its wave bands and loose cards, nothing ahead of them (`board/public/app-lanes.js` `todoRows`). No card is `queued`, and `queued_at` is no longer written or read. A ready card reads "ready" in green, as any ready card does.
- **One order.** Todo is bumped cards first, the latest bump on top, then the rest newest first (`board/public/ui-order.js` `laneOrder`), with Auto implement on or off. The pull walks that order, so it takes the top ready card: a bumped one before the rest, else the newest.
- **The cap limits the pull only.** Maximum parallel implementers is how far the pull fills In Progress. The owner's Implement tap starts its build at once whatever runs, as it already did on a card nothing blocks.
- **Implement on a blocked card bumps it.** The tap (the wave band's Implement, `card-build`) on a card an unfinished dep blocks makes no record and no worktree: it appends `card-bump {key}` and the thread line "Can’t start yet: waits on #53. Bumped to the top of Todo." (`store.mjs` `bumpBlocked`). Its confirm reads "Implement #92 once #53 is done? It is bumped to the top of Todo until then." The card stays in Todo; a bumped blocked card's time line reads "waits on #53" where an unbumped or held one, which the pull won't take, reads "blocked by #53" (`ui-cards.js` `blockedWords`). When its last dep finishes, `item set` prints `unblocked: <key>` and appends `card-unblocked` as for any card, and with Auto implement on the pull takes it from the top. With Auto implement off nothing starts it on its own; the session hears `card-unblocked`.
- **Ready releases an Implement message's card at once.** `item set --state ready` on a card with `implement_at` keeps it and prints `released: <key> starts building now`. Such a card, ready and blocked by nothing, is in `pullOf`'s `starts`; the board server starts it on its next check as the Build tap does (`server.mjs` `runAuto`, `store.mjs` `startReleasedBuild`), past the cap, and its start takes a slot from the pull. While it waits for that check it waits on no one: the orchestrator's `implement` wait is for a card not yet ready. A start refused or failed drops `implement_at` and leaves **Couldn't start implementing** on the card, back in Todo. A card a dep still blocks when ready releases it drops `implement_at` and is bumped as the tap bumps, printing `bumped: <key> waits on #53, so it stays in Todo, bumped to the top`.
- **No "queued" words.** An Implement message's footer reads "Implement"; its card's status line reads "waiting for orchestrator".

Considered:
- the bump as the queue (#276, gh276-queued-2b): a card in Todo already sits in the pull's order by its bump, so a separate membership adds a state to read and nothing the order doesn't give;
- "queued" in green in place of "ready" on the footer, with bumps ordering within and below the queue (gh293-queue A): it keeps a queue whose only cause was the cap on the owner's own taps;
- "next" in green on the card the pull takes next (gh293-queue C): the owner picked B, with no extra word;
- the board server starting a bumped blocked card itself once its deps finish, Auto implement off too: that is the queued build again under another name.
