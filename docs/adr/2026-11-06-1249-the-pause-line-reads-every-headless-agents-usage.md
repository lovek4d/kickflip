# The pause line reads every headless agent's usage, and slows the starts before it

On 11/06 three Opus builds started together at 87% and all hit the 5-hour limit within 12 minutes, the gate still reading normal. Headless `claude -p` runs never run the status line, so `~/.claude/kickflip/usage.json` only moved when the orchestrator's own session drew, and the reading went stale while agents spent usage. The owner settled the fix on hub/GH-383.

- **Reading.** Claude's reading is `usage.json` and the newest `rate_limit_event` in each of the most recently written run logs (`CLAUDE_LOGS`) in `~/.claude/kickflip/logs` (`<role>-<id>-<launch time>.log`) together: per window, the highest in the newest window, as Codex's rollouts are read; each log's reading is at its mtime. A window the event rejected reads 100%. `hub/usage.mjs usageReader` reads them, rereading a log only when its size or mtime changes.
- **Near the line.** Within twice the buffer of the line (from 80% for the 90% line; Off has none) the gate is `near` `{window, used, resets_at, from, going, waiting}`. While the newest Claude run (a log whose first line is a stream-json event) hasn't reported its usage, in its own log or a later status line reading, the board server starts nothing new: `launchHeld`. Each of the server's launches checks again, so near the line it starts one agent, then the next once that one has reported. A run that never reports holds the starts ten minutes at most. Codex agents aren't held by it.
- Only the board server waits. `builder start`, the Implement tap and the architecture review keep `heldFor` and `holdsWork`, so a launched builder taking up its own start, or the owner's tap, isn't refused; a tapped build whose launch the wait holds is launched by the minute check once it lifts.
- **Banner.** The Hub page shows "Approaching usage limit, reducing parallel agents" with Keep going, which saves `keepGoing {window, until, near: true}` and lets agents start in parallel until that window's reset; the banner then reads "Approaching usage limit: agents start in parallel until <time>" with Stop. It never lifts the pause at the line, which has its own Keep going.
- **Running work finishes.** Nothing stops a running agent at the line (the owner's answer, as in [work pauses at the pause line](2026-11-01-1710-work-pauses-at-the-pause-line.md)).
- **A run that hits the limit keeps its relaunch.** A tracked headless builder whose run log ends on a rejected `rate_limit_event` (`runLimit`) is held, `pid` null with `until` the reset, with a thread line, and launched once the reset has come, keeping its `relaunched` as it was. Tracked entries keep their run's `log` for this.
- **Planners asked for during a hold wait.** A grill or prototype the owner asks for, or a gate's yes starts, while launches are held waits in `data/queued-planners.json` with a thread line, and launches first in the next pass once the hold lifts.

Superseded in part by [a card pause stops its builder at its next stopping point](2026-11-09-1300-a-card-pause-stops-its-builder-at-its-next-stopping-point.md): running work no longer finishes past the line; its build pauses at its next stopping point.
