# Overnight triage proposes a stale board description as a task with one question

#880 (hub/T-527), split from T-237. The hub routes requests by each board's description (`hub/router.mjs` `routingBoards`, the manifest entry's `description`), so a description that no longer says what a board is for misroutes. The owner: "Maybe it would be cool if this just became task with a question attached? And not every night but only if the nightly triage agent thinks it is worth updating the description." A board with none gets one from its first nightly refresh, through the same approval.

- **When it's due.** A board in the hub's manifest is due a description check when no proposal is open and its description is empty, or neither set (`description_at`) nor checked (`description_checked_at`) in the last 7 days (`store.mjs` `descriptionDue`). The board server's overnight triage (`checkTriage`) goes out for that too, with `description: true`, on the same nights and terms as before: the hub's Triage overnight on, from the middle of quiet hours, the board idle, once a night. When no two tasks wait on answers, it goes out alone with `cards: []`, so it holds no pull: the hold is only the cards it names.
- **The judgment.** The session reads the description (`board.mjs description`) against the board's open and recent work. Still right: `board.mjs description checked` stamps `description_checked_at`, so the next check is 7 days off. Empty or stale: it files `chore(board): update /<route>'s description` with one question, Keep current (recommended when the text is close) and Use this, the proposed text (at most 240 characters) in the option's detail; the note is free text the owner may use to write their own.
- **One open proposal, kept by the board.** `item add` of that title records the new task's key as the manifest entry's `description_proposal` (and stamps the check), and refuses a second while that task isn't Done. Closing the task, by any path, ends the proposal: it is open only while its task is, so nothing has to clear it.
- **The owner's pick writes it.** On Use this, the session runs `board.mjs description set "<text>"` (the note's words when the owner wrote one), which saves through `saveBoardDescription` with source `triage`, so Board Settings reads "From triage, approved <date>". It closes the task with "Description updated"; on Keep current, with "Kept the current description". The session never sets a description without the pick.
- **On only in the running board.** `startServer` takes `describeNightly`, off by default; the script entry, which the hub runs for every board, turns it on. A test that starts a board server in process gets no description triage unless it passes `describeNightly: true`, so its result doesn't depend on the hour, though its scratch manifest entry has no description.
