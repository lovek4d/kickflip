# Hub links turn red only after a grace period

The board's session fixes its own hub links, and the red dot on the GitHub mark is for the faults it couldn't fix. This refines the Hub links of [0040](0040-one-board-registry-for-every-hub-feature.md) and the watcher health of [0021](0021-the-board-shows-github-checks-and-watcher-health.md).

The owner asked on the `hub-orchestrator` board (card INT-106): "why does github on this board show red dot with failed hub links? tbh this should never really happen, it should be handled by an agent." The dot was red for faults that fix themselves. A new board read "The last check didn't reach this board" until the next scheduled GitHub poll, up to an hour away. While a watcher was relaunching, or had just been stopped, the events link read "No watcher is running".

- **The session hears at once.** `hub/boards.mjs` `linksOf` still gives each link's `ok` as it is now. The watcher prints every link that isn't ok as `link <name> <detail>`, so the session fixes what it can, such as relaunching a watcher, sending a missing reviewer link or restarting the hub.
- **The board shows red only past the grace period.** Each link also gets a `state`. It is `ok`, `settling` while it has been broken for less than its grace period, or `broken`. The red dot and the sheet's red rows count only `broken`. A settling link has a muted dot in the Hub links sheet and reads "Settling: <detail>". `~/.claude/web-ts/link-faults.json` `{<route>: {<link>: since}}` records when each link was first seen broken. Every `linksOf` call keeps it up to date (board loads, the watcher, and the hub after each poll), so a fault no page looked at still dates from the poll that first saw it. A link that works again drops its entry.
- **Grace periods** (`GRACE` in `hub/boards.mjs`):
  - events: 2 minutes. The session relaunches its watcher within seconds of each event, so a gap longer than that means it has stopped. The watcher's own 2-minute relaunch allowance after a clean exit ([0021](0021-the-board-shows-github-checks-and-watcher-health.md)) comes first, so a watcher that exited cleanly turns red after 4 minutes, and one that was killed after 2.
  - github, wakes and slack: one polling interval plus 10 minutes. The next poll fixes a missed check or wake, and the session's monitor tick that it wakes sends a missing reviewer link. A poll that runs `gh` for each PR takes up to a couple of minutes, and a woken session needs a few more to finish its tick. The interval is the longer of the window when the fault began and the window now ([0025](0025-the-hub-polls-github-and-sends-pushes-on-one-interval.md)). So at 8am, a fault from the hourly overnight window doesn't turn red on the new 15-minute window before a poll could have fixed it.
  - hub: 5 minutes, which is enough for an edit and then its restart.
  - push: none. No subscribed device is the owner's to fix, and no poll fixes it.
- **Join polls at once.** `web-ts join --template board` asks the hub for one poll after its handshake, as `web-ts poll-now --keep-queue` does, so a new board's GitHub link passes within seconds. It polls once more if a poll that started before the board joined missed it, and prints `poll`.
- **The hub link catches the hub running older code than its files.** The hub once kept running code older than its own files after an edit with no restart, so `lastCheck.boards` was missing. As it starts, the hub hashes `hub/hub.mjs` and every file it imports by a relative path, followed through the skill (`hubCode`). It logs the hash and writes it to `~/.claude/web-ts/hub-code.json`. The `hub` link hashes the same files on disk and compares the two. While they differ, the link reads "The hub runs older code than its files; restart it with launchctl kickstart -k gui/$(id -u)/local.claude.web-ts-hub". Files the hub reads on each request, such as `board/public/ui-page-header.js`, aren't part of the hash.

Considered:
- Keeping red for every fault and leaving fixes to the session. The owner saw faults that would clear on their own and asked why an agent hadn't handled them.
- Showing faults only to the session, never on the board. A fault the session can't fix, such as no subscribed device or the hub never restarting, would then never reach the owner.
- Working out when each fault began from what the link already reads (`exited_at`, `lastCheck.at`). The GitHub link breaks when a PR lands on a card after the last check, so it can't tell when that happened.
- One grace period for every link. The events link would wait as long as a poll, or a missed poll would turn red before the next one.
- A hub link that compares file modification times. A save with no change would trigger it, and a copied file with an old mtime could slip past it.
