# A Merge tap waits its turn to land

Only one fast-forward of main runs at a time on the host (a land can restart the hub and every board server). A land that found the lock held used to refuse, naming the card landing, and the owner had to tap Merge again. The lock also covered the rebase and the test suite, so one card's preparing refused every other card.

- **Only the fast-forward holds the lock.** A land (`worktree.mjs landInTurn`) prepares outside it: the checks, the rebase onto main when main moved, and the suite (`prepareLand`). It then takes `~/.claude/kickflip/land.lock` and fast-forwards main to the commit it tested (`landPrepared`). If main moved past that commit meanwhile, it lets go of the lock, prepares again and asks again. On a GitHub board with PRs off, main is brought up to origin's before preparing and again under the lock.
- **No retest when nothing moved.** A passing suite records the tested commit as `refs/kickflip/tested/<branch>` in the repo. A land whose branch head is still that commit, with main not moved past it, skips the suite and says so ("A1 was tested on main as it is now; not testing it again"). A held build tested at `builder done` therefore lands at once on its Merge tap unless main moved. The ref is deleted with the branch.
- **A land that finds another landing waits, first in, first out.** It takes a place in `~/.claude/kickflip/land.queue`, named by when the land was asked, so a land that let go of the lock to retest keeps its place. This holds across every caller: a Merge tap, Auto-merge, a lander's `builder done` and `board.mjs land`. A waiter wakes when the lock or the queue changes (fs.watch). A 5 s recheck remains only to take over a lock or place whose process died, since a dead process changes no file.
- **A land on a card already landing joins it.** `~/.claude/kickflip/landing/<card>` marks a card's land while it runs. A second land asked for that card (a Merge tap during the orchestrator's land, say) waits for it to end instead of landing or refusing. It then reads the card: done, it reports "landed and done"; otherwise it finishes what the first left, such as a held build the tap now lands.
- **The card says so.** A tap that waits writes a status line, "Waiting for #210 to land", and the card reads "Merging · waiting for #210 to land". A status line does not end the card's merging. Neither do the lander hand-off lines ("Not merged yet: …", "Lander launched headless …"): the card leaves In Review once the lander starts.
- **The Merge button spins until the card moves.** The tap starts `BoardUI.pending` for `<key>:merge` (ui.js), and `mergeButton` draws BUSY while it is pending, through any repaint. Each render settles it against the board it draws. It ends only on a board made at or after the POST's answer that shows the card out of In Review, or still there and no longer merging, which is a refusal. So the render that moves the card is the first without the spinner, and a reload that races the POST (its patch then no longer fits the board on screen) keeps the spinner. A refused POST drops it. `pending` is keyed by card and action so other buttons can use it later (#260).
- **Refusals that need the owner stay**: a conflict or failing tests after the rebase hand off to a lander, and a repo off its branch is still refused.
