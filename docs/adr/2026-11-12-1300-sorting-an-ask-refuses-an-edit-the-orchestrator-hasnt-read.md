# Sorting an ask refuses an edit the orchestrator hasn't read

On T-201 (#582) the owner edited an ask 11 seconds after the watcher handed it over, while the orchestrator was writing notes from the first text. Its `item set --phase ready` went through, and the pull started a builder on the old notes 2 seconds later. The watcher showed the edit only on its next wake (#585).

**The stamp is the ask's working mark.** The watcher (`bin/wait-events.mjs`) and the PostToolUse hook (`hooks-plugin/hooks/board-messages.mjs`) write the ask's Working-on-it mark in `data/working.json` as they hand it over. That time is when the orchestrator read the ask's text; no new stamp is kept.

**Sorting refuses an edit newer than the mark.** The sorting commands on an ask, or on the card it became (`from_ask`), call `store.refuseUnreadEdit` first: `reply`, `item set` with `--phase`, `--title`, `--ticket` or `--new-ticket`, and `item relate-ask`. When the ask's newest `ask-edited` event is newer than its mark, or the ask has an edit and no mark at all, the command refuses before changing anything, so no ticket is made either. The refusal prints the edit's time and the new text and moves the mark to now, since the orchestrator has now read it: rerunning goes through, or the orchestrator changes the command if the edit changes the plan. The owner chose every sorting command, the ticket included (question t202-scope).

**Handing an edit over moves the mark too.** When the watcher prints an `ask-edited` event, or the hook shows one, it moves that ask's mark to now (`store.restampWorking`). An edit the orchestrator was already shown never trips a refusal, and an edit made before the hand-over sorts at once, since the mark is newer.

**Unchanged.** An ask with no edits sorts as before, marked or not. Owner messages after sorting don't refuse anything. The guard is in the CLI (`board/bin/board.mjs`), not in `changeItem`, so the board server's own changes, such as the owner's taps, are never refused. Other `item set` flags (`--next`, `--held`, `--done`) don't sort and pass.

**The hook, which should have shown the edit mid-task, wasn't loaded.** The hub orchestrator's Claude Code process started on 11/09, before #503 added PostToolUse to `hooks-plugin/hooks/hooks.json` on 11/10. Claude Code reads plugin hooks when the process starts, and resuming in the same process keeps that set, so the hook never ran for it; the older SessionStart and UserPromptSubmit hooks did. That's machine state, not code: `/reload-plugins` in the session, or a restart, loads it. Even loaded, the hook speaks only between tool calls, and on T-201 the notes and the ready went in one call, so the refusal is still needed. It sits beside [the owner's words reach the orchestrator after its next tool call](2026-11-10-1056-the-owners-words-reach-the-orchestrator-after-its-next-tool-call.md).
