# Each lane is a queue for the orchestrator

The owner, on #195's thread: "why is this item not being picked up by orchestrator faster? … each lane kind of works like a queue behind the scenes, with the orchestrator looping top down on items that reach an idle state like this." #195's headless builder handed back with judgment calls and nothing woke the orchestrator for 2.5 hours; #200 waited 3. `builder done` on a build with calls sets the card to checking and appends no event, and every other wait on the orchestrator woke it once at most (#214).

- **The board lists what waits on the orchestrator.** `domain.mjs` `orchestratorWaitOf` places each open In Progress or Todo work card: an open builder ask (`ask`); an owner answer not acted on (`answer`); unless the owner owes the card an answer, a hand-back with calls not verified (`calls`) or a checked build with none left (`checking`); a grill or prototype asked for with no planner of that kind running (`grill`, `prototype`); a refusal by the pull (`refused`); a started card with no live builder and nothing else placing it, which reads Next "none set yet" (`unowned`). Each has `since`, when it began to wait, and `next`, what it waits for. `orchestratorWaits` lists them lanes top-down, In Progress then Todo, in the board's order.
- **Picked up is the session's first write after since.** A thread line of Claude's other than a status, agent or refusal line, a `builder verified`, a builder start, or the watcher's working mark on one of the card's events. The card stays on the list, marked picked up, until its wait ends.
- **One generic wake.** The board server keeps the list in `data/orchestrator-waits.json` on every board change and each minute (`server.mjs` `checkWaits`), and appends `orchestrator-waits {added: [key]}` once a card joins it not picked up, or waits again with a new kind or since. One event kind covers every wait in the table, and any added later.
- **The watcher prints the list on every wake** (`waits <kind> <ref> <key> since <iso>[, picked up <iso>]: <next>`), after the events and before the rules, and SKILL.md has the orchestrator handle every card on it. A wait whose one wake was missed or mishandled comes back on the next wake of any kind. That list is the orchestrator's per-lane review, and the hub's morning wake adds one walk over every lane ([the orchestrator reviews every lane on a schedule](2026-11-06-1653-the-orchestrator-reviews-every-lane-on-a-schedule.md)).
- **A push at 30 minutes.** A card waiting `ORCHESTRATOR_PUSH_AFTER` (30 minutes), not picked up, pushes the owner once, tagged `wait-<key>`, naming the card and what it waits for; its entry keeps `pushed`, so a restart doesn't push it again.
- **The status line says it.** There is no separate line: a card on the list with no builder running reads "waiting for orchestrator · 14m", then "orchestrator review · 3m", with the working dot, once picked up. Every status line ends with how long ago that status was set (`ui.js` `lasted`), the builder's progress lines included.
- **Colours by lane.** Every status line on an In Progress card is the phase-bar orange, a planner's too; every build or plan line on a Todo card is the owner's blue. A Todo card a grill or prototype runs on draws the phase dashes in that blue, the grill's first and the prototype's second running, from round 3 of the orchestrator-wait prototype.

Considered: an event kind per wait state (`card-handed-back`, `build-refused`, `card-unowned`). Each still wakes once, and each new wait state needs its own. The list makes a missed wake harmless, and the one generic event wakes a quiet board for it.
