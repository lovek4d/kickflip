# The board CLI tests run main in-process, with one spawned smoke test per command group

Supersedes the "Considered: running main() in-process" bullet of 2026-11-05-2240-the-suite-keeps-one-test-per-path-and-splits-the-board-cli-tests.md. T-254's slow-test findings put board-items, board-builder, board-land and board-settings at about 940 s summed on a loaded land, each CLI call a node process of its own; the owner split T-254 into cards and this one (T-266) moves those calls in-process.

- **`board()` runs main in this process.** board/board-fixture.mjs `boardWith(args, env)` sets the call's env (the test's HOME, the hub port, the push stub) on `process.env`, swaps `console.log` and `console.error` for buffers, awaits board/bin/board.mjs `main(args)` and puts both back. It returns what a node process would: `{code, out, err}`, a thrown error exiting 1 with its stack. `board(...)`, `onOrch(...)`, `land()`, `recordPrototype` and `addPrototypeQuestion` go through it, so every test that used them awaits them and keeps its assertions. Test files run in their own processes and their tests one at a time, so one call's env and console never meet another's.
- **What still spawns:** `run(script, …)` keeps a node process for a command that reads stdin (`--file -`, `--notes-from -`), for the tests that run several board.mjs processes at once to check their locks (`runAsync`), and for the sibling scripts (the SubagentStop hook). board/board-cli.test.mjs spawns board.mjs once per command group (item, builder, land, settings) for what only a process shows: `--help` and no arguments print the usage, an unknown command and a usage error exit 2 with the `--help` hint, a refusal exits 1 and a write 0. That answers the earlier ADR's worry that an in-process main skips the check that the CLI really runs.
- **Paths under $HOME are read per call.** hub/boards.mjs (`wavesDir()`, `githubStateFile()`, `resumeStateFile()` and the rest), hub/live.mjs `sessionsDir()`, hub/push.mjs, hub/prompts.mjs, hub/sessions.mjs and board/render-check.mjs's `CHROME` were computed when the module loaded, so an in-process main would keep the first HOME it saw. Many test files import store.mjs or domain.mjs before the fixture, so setting HOME early instead would depend on import order.
- **One scratch repo per test file.** `scratchRepo()` builds the base commit once per process and copies it into each test's HOME.

Measured on this Mac at load about 5, one file at a time: board-items 24 s to 2 s, board-builder 30 s to 12 s, board-land 46 s to 33 s, board-settings 19 s to 7 s (119 s to 54 s). board-land keeps most of its time in real git worktrees, rebases and tags.

**server.test.mjs stays over HTTP.** Its cross-site, upload, gzip and versioned-asset checks take 5 to 80 ms each against the one server the file starts, so in-process handlers would save under a second, and server.mjs keeps its handler inside module state, watchers and timers. The file's time is its waits and stalls under load, which main shows too.

**No server test was deleted as a domain duplicate.** Checked assertion by assertion, each server test the findings named (the Build tap, Hold/Resume/Done, Reopen, auto-pull, the settings page's saves, the held Merge) asserts what only its route does: the stored write, the event or its absence, the refusal text and status, the spawned merge. The domain tests check the card that results. The two exact duplicates went: the Hold choices in the Hold test (the version test asserts them) and the Internal-tickets block in the auto-merge test (ticket-paths.test asserts it).

**Dead paths:** board-settings' auto_pull test (no code names auto_pull now) and board-threads' check for the old appendThread name went. hub/schedule's fromPolling, board-threads' S80 to INT-80 reply, board-items' shared-notes refusal and hub/repos' shared-board test stay, as their code still runs.

Considered:
- calling each store function directly instead of main: it rewrites hundreds of assertions on exit codes and printed lines, and drops the CLI's own parsing and output from the tests;
- one HOME per test process, set before anything imports the hub modules: a test file that imports store.mjs first would read the real HOME.
