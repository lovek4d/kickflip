# A task is a card with no ticket, keyed T-<n>, and its grill asks whether it gets one

Amended by [every ask is a task card from the moment it arrives](2026-11-09-1900-every-ask-is-a-task-card-from-the-moment-it-arrives.md): a dropped card leaves its number as its item file's `last_task`, so the number is not reused.

#465, split from #445. The owner, on gh445-task-is-card: "T-n should also replace internal issue mechanism, so by default with no ticketing system we get these". On #465's grill (11/09) they answered: retire Internal, every new card is a task until its ticket question gives it a ticket, the board makes the ticket at once on their yes, and no prototype round (#445's prototype take A drew the badge).

This supersedes [every new card gets a ticket in the board's current source](2026-11-04-0227-every-new-card-gets-a-ticket-in-the-boards-current-source.md) and, for Internal, [a board has one ticket source](2026-11-01-1348-a-board-has-one-ticket-source.md). It amends [a card is named by its board's ticket source](2026-11-02-2100-a-card-is-named-by-its-boards-ticket-source.md): a card without a ticket reads as its own id.

- **Internal retires.** A board's source is GitHub, Linear or none (`board/tickets.mjs` `ticketSource`). None is stored as no `tickets` key in `board.json`. `settings set tickets '{"source":"none"}'` clears it, and a stored `{source: "internal"}` reads as none. New board and Board Settings offer Linear, GitHub issues and None, and New board starts at None. When Hub's Linear key goes, a Linear board falls back to none. Stored `INT-<n>` tickets keep reading as stored, unlinked, with no migration. `tickets backfill` goes too: it linked the ids in old titles and existed only to give every card a ticket.
- **Every new card is a task.** `item add` without an id keys the card `T-<n>`. `n` is one more than the highest `T-<n>` over every item source and the Done archive, taken under the tickets lock (`store.mjs` `nextTaskId`), so a number is never reused. Onboarding's cards are `T-1` and `T-2`. A task stores no ticket, and its badge in the ticket slot is a quiet `Task` with `T-<n>` only in its tooltip (`public/ui-cards.js` `taskChip`). Follow-ups, splits, review and arch-review cards are tasks the same way.
- **A ticket comes four ways.** `--ticket <id>` links one up front, checked against the source as before; it takes `GH-<n>` as well as `#<n>` (stored as `#<n>`). The fourth is importing by the ticket's id: `item add <file>/GH-<n>` (`<TEAM>-<n>` on Linear) links that ticket as `--ticket` would, so the grill asks no ticket question, and a source with no such issue refuses the add, writing nothing. `--ticket` with a different id, or `--new-ticket`, is refused with such an id. An id not in the source's form, or a board with no source, links nothing and stays a task. Linking a ticket by any way resolves the card's open ticket question ("Ticket linked: <id>") or drops it if still staged. `--new-ticket` makes one from the title and notes, either on `item add` or later with `item set` (the orchestrator's pick for a Quick task, which has no grill). The third way is the grill's ticket question. All of them go through `assignTicket`, which is still `resolveTicket`'s only caller. With no source they fail with one line and write nothing. `item set` refuses a card that already has a ticket. The card keeps its key, so branches, worktrees and threads don't move, and its label reads the ticket once it has one. `item set --from-ask` no longer makes a ticket: the filed card is a task like any other.
- **The grill asks.** On a board with a source, a card with no ticket gets "Create a ticket for this task?" (`headless.mjs` `plannerBrief`, `ticketQuestion` from `briefFacts`) just before the prototype question, with `"ticket_gate": true` and options yes and no. Yes is recommended when the task lands code and no when it lands nothing (a publish, a setting, a one-off run). `addQuestions` refuses the flag without a source or on a card with a ticket. With no source, nothing is asked.
- **The board acts on yes at once.** `settleAnswers` makes the ticket as soon as the owner answers yes, even while the card's other questions are open, and writes a `ticket-made` line. It doesn't wait for the grill to end, because the ticket changes nothing the other answers depend on. A failure, such as no Linear key, writes an `answers-failed` line, and the card stays a task. The question is the owner's: `question resolve` refuses it, as it does the prototype question.
