# The implementer limit counts agents, and any agent on a card can ask the board for helpers

The owner wants parallel agents on a work item more often. In their words, "if the orchestrator wants, it should be able to spawn whatever agents it needs to under a given work item. The limit on implementers is more to reduce machine resource load, especially if they are like building code or running tests" (a note on #298, filed as #354). Until now Maximum parallel implementers counted cards: a card with a running build or waiting in Orchestrator review took one slot. Helpers ran as in-process Agent-tool subagents, which the board never saw or counted. The grill on #354 settled the shape (gh354-spawn, gh354-count, gh354-review-slot, gh354-full, gh354-worktree, gh354-handback). The owner answered no to a prototype round (gh354-proto), since #353 owns how the thread looks.

- **What the limit counts.** `domain.mjs pullOf` counts running implementer agents on open cards, one slot each: a build, a rebase run, a lander, and a helper that writes. Planners take no slot, and neither do read-only helpers. A card waiting in Orchestrator review or on the owner takes none either (gh354-review-slot). A card in review still keeps the board from idle, as before, so triage and the PR review keep waiting for it.
- **Asking for a helper.** Any session, a builder or the orchestrator, runs `board.mjs agent launch <key> --name <n> --task "<t>" [--writes] [--model opus|sonnet]` (gh354-spawn). It writes the helper's record, `agents/<id>@<name>.json`, as `requested`, with kind `helper`, the task and `writes`, and no start. It also posts a thread line. No event is sent, so the request wakes no session. The board server launches the helper headless (`server.mjs launchHelpers`, `store.mjs startHelper`, `headless.mjs helperBrief`) on Claude: `--model` if given, else the hub's Claude model, else builder pick's Claude model, Opus when the pick is Codex.
- **Waiting for a slot.** A read-only helper launches at once. A helper that writes waits while the slots are full, ahead of the pull: every waiting helper takes a free slot before any Todo card does, and the topmost card's go first (gh354-full: "The closer to the top of the page, the first in line to get the next slot").
- **Worktrees.** A helper that writes gets its own worktree, branch `<id>-<name>`, from the card's branch (`worktree.mjs helperWorktree`), so it needs the card's worktree to exist. The card's builder merges the branch back with `board.mjs agent merge <key> --name <n>`, which then removes the helper's worktree and branch (gh354-worktree). On a conflict it names the files and leaves the merge for the builder to resolve and commit. Run again, it sees the branch is already merged and only cleans up.
- **Handing back.** A helper finishes with `builder done <key> --agent <n> --text "<hand-back>"`, and the text is its record's closing note. Its spawner blocks on `board.mjs agent wait <key> --name <n>`, which prints the hand-back and, for a helper that writes, its branch (gh354-handback). While it waits, the spawner's record carries `waits: <name>`, and the limit doesn't count an agent blocked on its own open helper. That way a full board, even one with a cap of 1, can't deadlock with a build waiting on a helper that waits for that build's slot. The wait gives up after 9 minutes so it fits inside one Bash tool call, and it is run again. It refuses when the helper's process has gone without its done.
- **Display.** A helper's status lines carry its name ("Tests building: …"). #353 groups each agent's lines. The card keeps one builder line, its own run's, and `builderOf` never takes a helper's kind for the card. Helpers record no judgment calls and ask no questions: any decision goes in the hand-back. The card's builder finishes only once every helper is done (`finishesCard`, as for any other open agent).
- **No per-card cap.** Only the board-wide limit applies.
