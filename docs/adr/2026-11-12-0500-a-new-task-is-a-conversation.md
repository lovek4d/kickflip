# A new task is a conversation

Supersedes [every new task is grilled or prototyped at once](2026-11-04-0131-every-new-task-is-grilled-or-prototyped-at-once.md). Amends [every lane has phases](2026-11-11-1200-every-lane-has-phases.md) (a Todo phase is added), [every ask is a task card from the moment it arrives](2026-11-09-1900-every-ask-is-a-task-card-from-the-moment-it-arrives.md) (a reply no longer sends the card to In Review), [tickets are made at ready](2026-11-10-1600-tickets-are-made-at-ready.md) (the ticket question goes) and [reviewers ask the board in the day thread](2026-11-12-0000-reviewers-ask-the-board-in-the-day-thread.md) (a request for work is filed discussing).

The owner (card T-152) missed what a Claude Code session gives a prompt: an answer, not a grill. Forcing every Discuss task into a grill at once skipped the conversation in which the owner gets comfortable with an idea before choosing to build it.

- **Discuss is a conversation.** A task sent with the New task sheet's Discuss is answered with `reply <key>`: what the orchestrator understands, what it thinks, where it could go, with what the workspace holds that the owner may not know. No closing line offering options; the card's buttons do that. The reply sets the card's phase **discussing**, Todo's second phase (`ui-enums.js` PHASES: new, discussing, grilling, prototyping, staging, ready). The back and forth continues in the thread, `reply` on a discussing card answering again.
- **A discussing card stays in Todo.** It never reaches In Review: `reply` sets the phase and no `answered_at`. The owner closes a discussion that never builds from Todo's Close, with no ticket. A card answered before this, waiting In Review for the owner's Done, stays as it was.
- **Whose turn it is** shows at the end of the card's last line: "discussing" in blue while nothing of the owner's waits, "discussing" in grey while an owner message or answer on it is unanswered (domain.mjs `turn`, from the card's owner messages' states).
- **The board grills no discussing card.** `arrivalsOf` skips it. From discussing:
  - **grilling → staging → ready.** `item set --phase grilling` on a discussing card, or the owner's Grill tap (`planAgain`), starts the round from code as from staging or ready (`round_at`). A grill still ends in staging.
  - **prototyping → discussing.** Answering a prototype round returns the card to the conversation (`moveOnAnswered`), with a "Marked as discussing" line. An answer to a question asked during a discussion keeps it discussing.
  - **Implement → staging → ready.** The owner's Implement on a discussing card stages it as on any Todo card. The orchestrator then folds what was agreed into a **Build** notes section before ready, since builders trust the notes over the thread. A Quick build from the sheet stays as it was.
  - **A visual.** `item visual <key> --text "<what it shows>"` writes a `visual-request` of the orchestrator's own (`who: claude`), which the board server launches a visual agent on as it does the thread's image. Its thread line is Claude's and answers none of the owner's messages.
- **The orchestrator's order of preference**, written once in SKILL.md, not per card: keep discussing; a visual once the topic is complicated, the first tool to reach for; a grill or prototype when asked or clearly useful; Implement only on the owner's explicit word. Whether a card starts as a discussion is the button's choice: an Implement ask is filed ready, and a Discuss ask that asks for a grill, prototype or visual gets it.
- **Context.** Grill, prototype and visual agents already read the card's thread and notes (headless.mjs `plannerBrief`, `visualBrief`). The orchestrator keeps a short "Discussion so far" notes section on each discussed card, so later agents and a compacted orchestrator start from it.
- **Other ways in.** A reviewer's Slack request for work (`slack task`) is filed discussing. A GitHub or Linear issue named in an ask is linked to the card at intake, `item set <key> --ticket <id>`, and the card is discussed like any other.
- **Tickets.** Ready still makes the card's ticket on a board with a source: a ready card is a build, so it ends in a commit. A discussion never goes ready, so it gets none. The grill's ticket question (`ticket_gate`) is gone, and `question add` refuses it.

Considered:
- A closing line on each reply offering a grill, prototype or visual: the owner, "we don't need the closing line really … the buttons already handle it".
- Grill, Prototype and Visual buttons on the New task sheet: split out to T-154; the sheet keeps Discuss and Implement.
- A flag on `item set --phase ready` for whether the card ends in a commit: every ready card goes to a builder, which commits, so the flag would always be set; the cards that never commit are discussions closed from discussing, which never go ready.
- A prototype round ending in staging, as a grill does: the owner wants the prototype to feed the conversation, not end it.
