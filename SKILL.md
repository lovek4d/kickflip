# join-web-ts

One **hub** on this Mac answers `https://<this Mac>.<tailnet>.ts.net/` for every site. It reads `~/.claude/web-ts/manifest.json`, lists every site in a sidebar beside each board, forwards `/<route>/…` to each **site**'s port with the prefix stripped, and runs each site's `cmd`, restarting it when it exits or when its entry changes. launchd keeps the hub up across logins and session restarts. Each site has one **owner** session, the only one woken by its events. The hub never manages sleep: a sleeping Mac answers nothing.

`WT=~/.claude/skills/join-web-ts/bin/web-ts.mjs`; run it with `node`. Its header comment lists every command and flag.

## Steps

1. **Who you are.** Your session id is the directory name just above your scratchpad (`…/<session-id>/scratchpad`). Your label is the session's name if it has one, otherwise two or three words for its work.
2. **Hub up.** Run `node $WT status`. Done when it says `hub: running` and `tailscale /` points at the hub. If not installed, ask the user once (it adds a macOS login item and maps Tailscale `/` to the hub), then run `node $WT install`.
3. **Join.** Run `node $WT join <route> --session <id> --label <label> --title "<name>" --description "<one line>"`. A new route copies the starter kit into `~/.claude/web-ts/sites/<route>/`, picks a free port from 4600, and the hub starts it within 2 seconds. An existing route keeps its files and command. To serve an existing project, pass `--dir` and `--cmd '["/abs/node","/abs/server.mjs"]'`, and `--port` if it has a fixed one. `join` also records the session's folder (`--repo`, by default the session's own cwd) and an optional `--model`, which `start` and `resume` use (Board sessions, below).
   - **Icon** ([ADR 0017](docs/adr/0017-site-icons-are-line-icons-from-a-built-in-set.md)). The sidebar draws each site's row with a line icon from `hub/icons.mjs` on a tint of the site's color. Pass `--icon <key>`, such as `phone` or `book` (`--icon x` lists the keys), and `--color <css hex>`. Without a key the hub picks an icon from words in the route and title, else shows the title's first letter, on a color picked from the route. `node $WT set <route> --icon … --color …` changes them later without joining.
   - **A board** (Linear-style lanes of PRs and tickets, item threads, questions for Love): add `--template board`, plus `--items <file>` when the items come from the site's own wave.json-format file rather than every `~/.claude/waves/*/wave.json`. The site then runs the shared `board/` code, whose `server.mjs` header documents `board.json` and the API. Every board shares that code, so make board changes in `board/` and copy none of it into a site. A site's `public/` holds only its own files, such as prototype pages, and any page it overrides. Changes to the hub or the board template come in as asks on the `/hub-orchestrator` board ([ADR 0041](docs/adr/0041-hub-changes-come-as-asks-not-improvement-rounds.md)).
   - **Exit 3 means another session owns it.** Ask the user with AskUserQuestion: take it over (recommended when the old session has ended or the user asked for this), or leave it. On yes, rerun with `--force`. The takeover is total: the old owner's watcher prints `handed-over` and that session stops serving the route.
4. **Build or resume the site.** Done when `curl -s -o /dev/null -w '%{http_code}' <url>` returns 200 for each page you changed, and a page meant for the phone renders at 390px wide with no sideways scroll. Follow the prefix rule below. The page design is yours; the starter's `public/index.html` is a placeholder.
5. **Watch.** Run the `watcher` command `join` printed as a background Bash task. It exits on the next event. For each `event` line, relaunch the watcher first, then act and reply (below). Its cursor means no line is missed, and a board reads "Board watcher stopped" while none runs. On `handed-over` or `site-removed`, stop; don't relaunch. Tell the user.
6. **Record** the watcher's task id, and the site's route and URL, in your scratchpad `watchers.md`, with how to restart them after a session restart: rerun step 3 with the same `--session`, then step 5. When the hub resumes a session, it asks for exactly that.

## Reference

**Words and decisions.** [CONTEXT.md](CONTEXT.md) is the glossary for the hub and boards. [docs/adr/](docs/adr/) records why each hard-to-reverse choice was made. Read the ADR before changing what it covers. When the owner settles a new one, in an ask or a card's question, add the next numbered ADR with the domain-modeling skill.

**Prefix rule.** The hub strips `/<route>` before your server sees a request, but the browser still uses the full URL. So write links relative to the page (`notes.html`, `../claude.js`), or build them from a root the page computes. In the starter kit, `ClaudeSite.url('x')` derives that root from its own script URL. A root-absolute link (`/x`) leaves the site. Your server gets `PORT` and `PREFIX` in its environment and should serve paths with or without the prefix; a redirect `Location` starting with `/` gets the prefix added by the hub. A stray `/favicon.ico` request is harmless. A browser's page load of any site's page, a path ending in `/` or `.html`, gets the hub's app shell instead of reaching your server, and the shell shows the page in a same-origin frame beside the sidebar ([ADR 0055](docs/adr/0055-one-app-for-the-whole-hub.md)). The frame's request, curl, an API call, an image and `?alone=1` (the frame's Open alone ↗) still reach your server; a board's server answers its four view paths with the shell too. So don't send `X-Frame-Options` or a `frame-ancestors` CSP that refuses the hub, or the frame stays blank. A page that starts its body with the board header (`<!--header …-->`) shows that header in place of the shell's.

**Starter kit** (`~/.claude/skills/join-web-ts/starter`): `server.mjs`, Node with no dependencies, serving `public/` plus the event API; `public/claude.js`, the browser side; `public/index.html`, a placeholder. Their header comments document the API.
- A page sends `ClaudeSite.send(kind, data)`. That appends one line to `data/events.jsonl`, which wakes the owner.
- You **reply** to event `<id>` by writing `data/replies/<id>.html` (an HTML fragment) or `.json`. `ClaudeSite.watch(fn, {kind})` shows it on the page within 10 seconds.
- Keep replies short first, with depth behind `<details>`.
- `GET /_claude/needs` returns what waits on the owner, from `data/needs.json` (`{items: [{kind, text, url}], working?, summary?}`, `url` relative to the site root). Write that file when something starts or stops waiting on the owner, or when you start or finish the owner's message (`working` counts those in progress). Without it the site reports nothing waiting.

**What waits on the owner** ([ADR 0010](docs/adr/0010-sites-report-what-waits-through-claude-needs.md)). Any site may serve `GET /_claude/needs` as above: `kind` is a short label such as "Question" or "Tap Ready", and an empty `items` means nothing waits. The sidebar badges each running site's row with the count, and the hub caches it for about 20 seconds. The row's sub line leads with a status word (Down, Starting, Working while `working` is above 0, "N need you", Building), then a board's optional `lanes` `{review, progress, todo}` as chips; `building` is true while a builder works on a card ([ADR 0037](docs/adr/0037-the-hub-home-shows-status-not-descriptions.md)). The sum over every site is the Home Screen app's badge (`/_hub/needs.json`). A site that doesn't serve it, errs, or takes over 1.5 seconds counts as unknown and gets no badge. Another server can serve it to get a badge.

**Sidebar, app shell and hub page** ([ADR 0050](docs/adr/0050-a-sidebar-of-every-board-replaces-the-hub-home.md), [ADR 0055](docs/adr/0055-one-app-for-the-whole-hub.md)). Every page shows a sidebar of every site from `/_hub/sidebar.json`, Boards apart from Pages: a rail from 1000px wide, and narrower a drawer. The header's kickflip logo toggles it at every width, opening the drawer or collapsing and restoring the rail, which this device remembers. Its foot holds the Hub, Notifications, Polling and Settings rows. On a keyboard, s pressed twice shows each row's key, a board's number or a letter from the row's name claimed in the order sites joined (`created` in the manifest), and the next key opens that row ([ADR 0056](docs/adr/0056-switch-mode-letters-come-from-names-in-join-order.md)). Pages open in one app shell (`board/public/app.html`), where the sidebar stays put and a site's row, a foot row, or a link to a board's Settings, Waiting on you or Notes, swaps the view in place, with no reload; the shell keeps one stream to the hub, `/_hub/stream`, for every board's change signal and the sidebar's updates. Other sites' pages and a board's prototypes show in a frame under the board header, whose title follows the page's. `/` and the Home Screen app open this device's last board, or on a first visit the board with the most waiting; never a page. While the Mac is asleep the app still opens, from the shell the service worker `/sw.js` saved, with the last sidebar and each board's last visit dimmed; it caches only the shell and its `/_hub/app/` files, never a site's page, API call or upload. The hub's own pages, `/_hub/`, hub Settings and Polling, are views of the shell too, reading their data from `/_hub/api/…` and refreshing it every 30 seconds. `/_hub/` is the hub's status page: the hub's health, then Boards with their links and watchers, then Pages, polling and notifications.

**Board template** (`--template board`, `~/.claude/skills/join-web-ts/board/`): a work board over wave files. Every write an agent makes to a board site goes through `node ~/.claude/skills/join-web-ts/board/bin/board.mjs --site <route> <command>`: replies, thread lines, question topics and questions, item status and `next`, follow-ups and builder records. Its usage text lists the commands. Hand-edited JSON skips the checks the pages rely on. A new card is `board.mjs item add <wave>/<id> --title …`, never a hand edit of a wave file. The CLI refuses a bare file path in a text flag (`--html`, `--text`, `--title`…) and a `--file` that doesn't exist: write a file's contents with `--file`. Every refusal exits non-zero with one line naming the bad flag, so check the exit code. A board serves `GET /_claude/needs` itself, one item per Needs you line. The + sends an `ask` event, shown as a New card at the top of Todo until you sort it ([ADR 0047](docs/adr/0047-the-plus-makes-a-new-card.md)). Take New cards from the top, and sort each one: file it under a wave (`--from-ask`), fold it into the card it's about (`item relate-ask`), or answer it (`reply`), all below. First check it against the other boards: each one's title and description in `~/.claude/web-ts/manifest.json`, its folder (`node $WT sessions`) and its cards. Only when another board clearly fits better, add an open question on the New card (`question add`, topic `item:ask:<eventId>`): "Move to <board>" recommended, then "Keep here", each with `diagram` and `practice`. On Move, run `board.mjs --site <route> ask move <eventId> --to <other route>`, which makes it a New card there and wakes that board's session, then `question resolve`; on Keep, sort it here. Hand a long build or investigation to a builder, which reports in the card's thread. When you start on it or on a thread message, run `board.mjs --site <route> working <eventId>` so the page reads "Working on it". Answer a quick ask with `board.mjs reply <eventId>`; it moves to Done. When it needed only an answer, also push it: `board.mjs --site <route> push --now --title "Answered: <the ask's first line>" --body "<the answer's first line>" --url "/<route>/#item=ask%3A<eventId>" --tag ask-<eventId>`; the board's answer banner holds it too. Later answers in that thread push again under the same tag (Push notifications, below). When the answer waits on the owner, such as a pick between prototypes, also run `board.mjs --site <route> ask progress <eventId> --next "<what the owner picks>"`: the ask sits in In Review with Action needed instead of in Done, and the owner closes it with the Done beside Send in its thread. An `ask-done {id}` event is the owner pressing that Done; the board moves the ask itself, so it needs nothing beyond relaunching the watcher. `board.mjs ask done <eventId>` moves it to Done from your side ([ADR 0035](docs/adr/0035-an-ask-can-wait-in-progress-until-the-owner-marks-it-done.md)). To turn an ask into work, add the work item named for the change and run `board.mjs item set <wave>/<id> --from-ask <eventId>`: the New card gives way to the item, whose thread opens with the ask; then write the item's first thread line, so the item stops reading "Working on it". A card's **Notes** is your understanding of the task so far: what was asked, what's settled, what's still open. Keep it as a `.md` file in its wave's folder, set it with `board.mjs item set <wave>/<id> --notes-file <file>` (`--plan` still works), and rewrite it as the grill settles things rather than freezing it as a plan; the thread keeps the short news. The open card's Notes link opens `notes.html`, a view that renders the file for the phone, or the item's short `notes` text when it has no file ([ADR 0053](docs/adr/0053-notes-replace-the-full-plan-and-cards-start-on-their-own.md)). `item set --title` renames a card. When an ask is about an existing item, fold it in with `board.mjs item relate-ask <eventId> <wave>/<id> --summary "<one concise line>"`: the New card goes, and the owner's message moves into the item's thread marked Moved, with the summary after it. When the owner says it went to the wrong card, relate-ask it to the right one, or run `board.mjs ask unfold <eventId>` to give it a New card again. An `item-message` whose `key` is `ask:<eventId>` is the owner replying in a Done ask's thread: answer it with `board.mjs reply <its eventId>` or `board.mjs thread ask:<eventId> --text …`, as in a work item's thread. An `ask-withdrawn {id}` event (with `key` from a thread) deletes a pending message ([ADR 0014](docs/adr/0014-a-pending-ask-can-be-deleted-or-bumped.md)). An `ask-edited {id, text}` event (with `key` from a thread) replaces a pending message's text: use the new text, and if you had started, adjust the work to it and say what changed. An `ask-bump {id}` event means take that ask, or that pending prototype request, next. A `card-bump {key}` event bumps a work card ([ADR 0019](docs/adr/0019-a-card-that-hasnt-started-can-be-bumped.md)): a card that hasn't started starts next once it is unblocked, and a running card's next steps (its builder's questions, review fixes, CI) come ahead of other work, and it goes first among cards waiting for a free builder. A `card-hold {key, hold}` event is the owner's Hold (`hold: true`) or Resume (`false`) on a work card ([ADR 0023](docs/adr/0023-a-card-can-be-held-and-every-card-button-confirms.md)): run `board.mjs item set <key> --held` or `--unheld`, which ends the button's "Holding…" or "Resuming…". A held card never starts on its own, and a running one gets no new builder, review fixes or CI reruns until it is resumed; once resumed, start it if nothing blocks it. A `card-done {key}` event is the owner closing a card from its thread's Done ([ADR 0035](docs/adr/0035-an-ask-can-wait-in-progress-until-the-owner-marks-it-done.md)): stop any builder on it, run `board.mjs item set <key> --status done` (for a follow-up, `followup done <wave> <id>`), which ends the button's "Closing…", and write one thread line saying it was closed and what was left. Never touch GitHub for it: an open PR stays as it is. A `card-merge {key}` event is the owner's Merge on a card whose PR is approved, green and CLEAN while the board's auto-merge is off (Auto-merge, below): run monitor's Merge step for that card now. When a check stops the merge, say why in one thread line, which ends the button's "Merging…". Start a card as soon as its open questions are all answered and nothing blocks it, without waiting for a go; `unblocked: <key>` means start it now ([ADR 0053](docs/adr/0053-notes-replace-the-full-plan-and-cards-start-on-their-own.md)). Set `deps` for queued work: `item set --status building` refuses while a dep is unfinished, and `--status done` or `merged` prints `unblocked: <key>` for each card it frees ([ADR 0020](docs/adr/0020-cards-wait-on-explicit-blocked-by-links.md)). Every builder you start for a card runs, as required steps in its prompt, `board.mjs --site <route> builder start <key> --kind <kind> --label "<label>"` first, `builder progress <key> "<short line>"` (or `--text "<short line>"`) at each milestone and `builder done <key>` before it hands back, so the card sits in In Progress with a live status line. When a subagent stops, a SubagentStop hook, `board/bin/builder-stop-hook.mjs`, closes the records it started and left open, but not one another agent restarted later. A skill's own hooks don't fire for SubagentStop, so the hook ships as the plugin `hooks-plugin/`, which Claude Code loads as `web-ts-hooks@skills-dir` through the link `~/.claude/skills/web-ts-hooks` (`claude plugin list` shows it); a new Mac needs that link. A site card's builder hands back with `item set <key> --status checking`, never `done`: the card sits in In Progress reading "Claude checking" and unblocks nothing. The owning session then runs the tests, checks the board at phone width, writes what it checked in the card's thread, and sets `--status done` ([ADR 0022](docs/adr/0022-site-cards-build-in-parallel-when-their-files-dont-overlap.md)). **A repo card's built work always goes straight to a draft PR** once the owning session has checked it (owner, 2026-10-23). Run `item set <key> --pr <n> --clear-status`, so the card sits in In Progress while CI runs or fails, then in In Review with Action needed linking to the PR once CI passes, also while the owner tries it on a test deploy. A card's lane follows who acts next: one waiting only on the owner (open questions, a prototype pick, Ready, an ask's Done) sits in In Review with Action needed, and goes back to In Progress once Claude works on it again ([ADR 0045](docs/adr/0045-the-lane-follows-who-acts-next.md)). Never park built work as `waiting`, which reads as blocked. A card that has been grilled or built never drops back to Todo unless held; a blocked one keeps its lane with a blocked-by chip, and `item set <key> --deps <list>` sets its blockers after it exists ([ADR 0049](docs/adr/0049-a-started-card-never-returns-to-todo.md)). A PR that changes what a page looks like carries screenshots in its description, as wave-build's build step says. **A board whose cards build a device app (iOS, Android) gives each card an Install button** ([ADR 0051](docs/adr/0051-a-device-app-card-carries-an-install-link.md)): build an install for the card's draft PR and again after each later push, put its files under the site's `public/installs/<wave>-<id>/`, and run `board.mjs item set <key> --install <url> --install-sha <PR head sha>`, the url being `itms-services://?action=download-manifest&url=https://…/manifest.plist` for iOS or the https `.apk` for Android. The button reads "older build" once the PR moves past that sha, and leaves the card once it is Done. **Marking a PR ready for a reviewer includes the Slack link** (owner, 2026-10-24): add them to the board's reviewers if they're missing (Board reviewers, below), then DM the bare PR link as slack-bridge's PR links step does, even when no monitor or bridge runs for the wave, and record its ts in the wave's `review_link_ts`. Every hub feature finds boards through one registry, `hub/boards.mjs`, so each serves both kinds alike ([ADR 0040](docs/adr/0040-one-board-registry-for-every-hub-feature.md)): the hub polls every open PR on any board's card, whatever `monitor.json` watches, and a PR's `github-change` goes to every board showing it. A board whose items are its own file (`--items`) ticks through slack-bridge's PR links steps over its own items and reviewers. The hub checks GitHub on each slot of the polling interval and wakes you only on a change, or at a daily wake ([ADR 0025](docs/adr/0025-the-hub-polls-github-and-sends-pushes-on-one-interval.md)): a `github-change {prs: [{wave, id, pr, changes}]}` event, where `changes` lists `ci`, `review`, `comments`, `merged`, `mergeable` or `draft`, means run one monitor tick for those PRs, which also runs the Slack bridge's steps. A `check-github {}` event is the owner's refresh asking for a check, and `check-github {reason: "morning"}` is the hub's daily wake (8:00am and 9:00am by default), so the bridge's morning push and digests go out on a quiet day: for either, run one monitor tick. End each tick with `board.mjs --site <route> checked --every "$(node $WT polling | jq .every)"`, so the In Review header reads "12 min" after the GitHub mark, or `checked --idle` when the board shows no open PR, so the time stays muted rather than late. Either form then sends the pushes the tick queued. The hub writes the same `checked.json` after each of its checks. When the header reads "not listening", relaunch the watcher ([ADR 0021](docs/adr/0021-the-board-shows-github-checks-and-watcher-health.md)); when an event has waited 15 minutes with no watcher, the hub pushes the owner "<title> isn't listening" once. A `hello` event is the hub testing a new board's links (`join --template board` runs `node $WT handshake <route>`, which also sends the test push "<title> board connected", then asks the hub for one poll so the GitHub link passes at once): answer it with `board.mjs --site <route> hello-ack <eventId>`. The board shows a Connecting checklist until that and the hub's GitHub check reach it; cards can start meanwhile. The In Review header's GitHub mark opens the Hub links sheet (GitHub polling, events, daily wakes, pushes, reviewer links, hub code). The watcher prints each broken one at once, after the rules, as `link <name> <detail>`; the mark gets a red dot only for a link still broken past its grace period, and the sheet shows it settling until then ([ADR 0046](docs/adr/0046-hub-links-turn-red-only-after-a-grace-period.md)). Fix what is yours straight away, such as a missing reviewer link or a stopped watcher. `link hub` means the hub runs older code than its files: once no builder is mid-edit in `hub/`, restart it with `launchctl kickstart -k gui/$(id -u)/local.claude.web-ts-hub`. Tell the owner the rest. Answer a `prototype-request {key}` event, the owner's ask from a card's thread, with a throwaway `prototype-*.html` page linked from a thread line ([ADR 0015](docs/adr/0015-prototypes-come-on-request.md)). The page starts its body with the board's header, `<!--header {"lead":"back","backHref":"./#item=<wave>%2F<id>","title":"…","controls":false}-->`, and switches its takes with `prototype-switcher.js` (`PrototypeSwitcher.mount({takes, initial, render})`, loaded after `claude.js`), never its own pill. Build each take from the board's real components and classes (`style.css`, the `ui-*.js` renderers, the header), changing only what the take is about; a look-alike copy drifts from what ships (owner, on back-to-card). With each prototype, add an open question on its card: one option per take, the option ids matching the take keys and the recommended one first, with `url` set to `prototype-<topic>.html?q=<question id>`, relative to the site root and stored as given. The questions page then shows each take inline in a frame (`?take=<key>`, so hide the page's own extras under `html.ps-embed`), and the owner can pick there or on the page ([ADR 0048](docs/adr/0048-a-questions-takes-show-inline.md)). In the app, back from the page goes to Waiting on you on that question and then to the board, however the owner arrived; the header's `backHref` applies only when the page is opened alone ([ADR 0058](docs/adr/0058-back-follows-the-page-tree.md)). A page that links the board's `style.css` links `colors.css` before it, since every color lives there ([ADR 0033](docs/adr/0033-one-colour-constants-file-shared-by-the-hub-and-every-board.md)). Then push it with `board.mjs push --now`, `--url` at the page and the thread's tag. Add prototypes to a card's question unasked only when they obviously help. A choice with nothing to see, such as a code structure, a data flow or a policy, gets `diagram` and `practice` on each option instead (`question add` usage): boxes and arrows the questions page draws, and a line or two of what it means in practice (what a new feature must do, what changes, what it costs), so the pick is between concrete options, not labels (owner, 2026-10-24, on hb-model; [ADR 0048](docs/adr/0048-a-questions-takes-show-inline.md)). **Grill a card through open questions on the card**, never a separate page or a link ([ADR 0029](docs/adr/0029-a-card-is-grilled-through-its-own-open-questions.md)): `board.mjs question add` each question with topic `item:<wave>/<id>`, a recommended option first, and a prototype page in `url`. They land in Needs you and on the open card. When the ask is to grill new work, make the card first (`--from-ask`), then the questions. Questions that span several cards go under a declared topic (`topic add`).

**Board reviewers.** Each board keeps its own reviewers in its `board.json` `reviewers`, as wave.json records (`{name, slack_user, dm, github}`), and its Settings page lists them whether or not any wave is watched. A new wave on a board takes its `reviewers` from there. On a `reviewers {add, remove}` event, find each added person's Slack user, DM channel and GitHub login, write the change with `board.mjs --site <route> reviewers add --file <json>` and `reviewers remove <name>…` (`reviewers set --file` replaces the list), copy the board's list into the `reviewers` of each of its unfinished waves, then DM each added person the bare link of every PR on the board already in review (not a draft, not merged) right away, without waiting for a tick, recording each ts in its wave's `review_link_ts` (owner, 2026-10-24). Then reply to the event.

**Rules** ([ADR 0039](docs/adr/0039-rules-live-on-settings-at-hub-and-board-level.md)). On a board, the watcher prints `rule hub <text>` and `rule board <text>` lines after the `event` lines. They are the owner's standing instructions: follow them as you follow this skill. Hub rules apply to every board, and the board's own come on top. A `rules {scope, added, edited, removed}` event means the owner saved them on hub or board Settings. Read the printed list, then write one reply (`board.mjs reply <eventId>`, shown under the Rules section) saying what you will do differently. When the owner says "codify" in a thread, run `board.mjs --site <route> rules add --by claude --text "<the rule>"`. Add it at board level unless it concerns every board; then pass `--hub`. `rules list` shows both lists with their ids, for `rules edit` and `rules remove`.

**Auto-merge** ([ADR 0052](docs/adr/0052-auto-merge-is-a-board-setting-off-by-default.md)). A board's `auto_merge` setting, off unless set, decides who merges an approved PR: on, monitor does; off, the card shows the owner Merge, and monitor merges on its `card-merge` event. The watcher prints `setting auto-merge on|off` after the `rule` lines. The owner sets it with the toggle on board Settings, which writes `board.json` itself; a `settings {auto_merge}` event says it changed: when it turned on, run one monitor tick. `board.mjs --site <route> settings` prints the settings, and `settings set auto-merge on|off` sets them, only on the owner's word.

**Board sessions** ([ADR 0054](docs/adr/0054-the-hub-resumes-a-session-only-when-nothing-runs-it.md)). The manifest records each site's session in its owner: the id, its folder (`repo`) and an optional model. `node $WT start <route> [--repo <dir>] [--model <m>] [--prompt <text>]` starts a background session (`claude --bg`) in the folder, named after the board, in auto mode, with `worktree.bgIsolation` set to `"none"` so it works in the repo folder; its builders make their own worktrees. Its first prompt is `/join-web-ts <route>` plus the prompt. On a route with no site yet, the session waits in the manifest's `starting` until it joins. `node $WT resume <route>` runs `claude --resume <id> --bg` in the recorded folder and tells the session to rejoin and relaunch its watcher. `node $WT sessions` prints each board's route, session, whether it is live (in the background or a terminal) and its folder. A session is live while a `~/.claude/sessions/<pid>.json` record names it and that process runs; `start` and `resume` refuse a live session (exit 3), so a terminal session never gets a second process. The hub resumes a board's recorded session once when the board hasn't listened for 3 minutes and its session isn't live. If the board still isn't listening 5 minutes later, it pushes "<title>'s session didn't come back" once. A board whose owner has no folder recorded is never resumed.

**Bug fixes** (owner, on INT-114). Before fixing a bug on a board, check whether it is a symptom of a broader design problem: how the code reached the broken state, and what else can reach it the same way. Write the fix either way; it never waits on the larger decision. When the bug points at a design problem, add an open question on the bug's own card (`question add`, topic `item:<wave>/<id>`), naming the problem and what the review found, and asking whether to take on a larger change, with your recommendation first. When there is none, say so in one line in the card's thread.

**Models for agents** (owner, on INT-114). Run agents that only look things up or check pages on Sonnet (`model: "sonnet"`): code and docs lookups, fact-finding before a grill, research briefs, and screenshot passes that list what looks wrong. Builders, reviews, disprove passes and the final check before a card is done run on Opus. You still make the call from what a Sonnet agent returns. A skill that names a model for a specific agent overrides this.

**Push notifications.** The hub is a Home Screen app (`/manifest.webmanifest`, service worker `/sw.js` with scope `/`) that starts at `/`. iOS delivers web push only to a Home Screen app, so Love adds a board or hub page to the Home Screen once and taps **Turn on** on hub Settings or the hub's page; the sidebar leads with a Turn on row while this device's notifications are off. Every site shares that one subscription. Any session sends with `node $WT push --title "<what needs you>" --body "<one line>" --url /<route>/<page>#<anchor> --tag <stable id>`. A session on a board site sends with `node ~/.claude/skills/join-web-ts/board/bin/board.mjs --site <route> push` and the same flags instead. It adds "· and N replies" to the body for the replies written since the site's last push, since a reply never pushes by itself ([ADR 0011](docs/adr/0011-replies-ride-along-on-the-next-push.md)). A tap opens `--url`, and a newer push with the same `--tag` replaces the older one on the lock screen. A push about one thread takes that thread's tag: `ask-<eventId>` for an ask, `item-<wave>/<id>` for a work item. While it is queued, each Claude line written in that thread with `board.mjs thread` (no `--via`), or `board.mjs reply` to its ask or `item-message`, rewrites its body to the message's first line, cut to 160 characters, keeping "· and N replies", and points it at that thread; the command prints the new body. Once the push has gone out, a `board.mjs reply` to its ask or `item-message`, or a `board.mjs thread` line with `--answer`, pushes again at once under that tag. It keeps the sent push's title, opens the thread, and the line becomes its body. A board push lands where Love answers ([ADR 0036](docs/adr/0036-a-push-lands-where-the-owner-answers.md)): an `#item=` url opens that thread with its reply box focused, and a push to a prototype with `?q=` goes to the card's thread instead once that question has a pick. So pass the plain `#item=<key>` or the prototype url; the board adds the rest. Pass `--answer` only on a line that answers the owner's message in that thread, never on a progress line. Other lines never push ([ADR 0030](docs/adr/0030-pushes-go-by-kind-and-each-arrives-on-its-own.md)). Push when something waits on Love: a question, a step only they can run, a draft on Ready, an answer, a prototype they asked for, a merge summary, a stale PR, the morning digest. Progress stays on the site, and so do cards reaching Done, approvals and builders finishing. Exit 3 means no device has turned notifications on yet: say so once in the terminal. Keys, subscriptions and the queue live in `~/.claude/web-ts/push/`.
- **`--now`** sends at once. Use it for answers, replies to the owner's asks and thread messages, questions and judgement calls, steps only the owner can run, and prototypes they asked for. While pushes are held (overnight, snoozed or for the weekend), or when no device takes it, it queues instead.
- **Queued**, the default, is for merge summaries, drafts on Ready, stale PRs and the morning digest. These go out when the monitor tick ends with `board.mjs checked`, or after the hub's next GitHub check on the **polling interval**: by default every 15 minutes from 8:00am, 30 from 6:00pm and 60 from 10:00pm, this Mac's time. With **Hold pushes overnight** on (the default), pushes queued after 10:00pm wait until 8:00am, while checks go on hourly. Queued pushes that go out together arrive as separate notifications, each opening its own card. A queued push replaces a queued one with the same `--tag`. The CLI prints `sent` or `queued` with the next send time.
- **`--urgent`** sends at once, even overnight, snoozed or on a weekend. Use it only when someone has messaged about a critical production issue.
- **Off, snooze and weekends** ([ADR 0032](docs/adr/0032-notifications-can-be-off-snoozed-or-off-on-weekends.md)). With notifications off, every push is dropped, urgent ones too, and the CLI prints `dropped`, exit 0. A snooze, and Off on weekends (Friday at the last window's start until Monday at the first window's start), queue pushes until they end. Needs you, the badge, checks and wakes carry on either way.
- **Settings** are on hub Settings, `/_hub/settings`, the hub pages' gear and the sidebar's Notifications and Settings rows: this device's notifications, Push notifications on or off, Snooze, Off on weekends, and a row opening the Polling page, `/_hub/settings/polling`, which edits the windows on a day timeline, Hold pushes overnight and the daily wakes, saving each change at once. They are stored as `polling` (`{windows: [{from, every_minutes}], hold_overnight, wakes: ["HH:MM"]}`) and, beside it, `notifications` (`{on, weekends_off, snoozed_until}`) in `~/.claude/web-ts/settings.json`. The Polling page shows the current window, the next and last check, and the queue, with **Send now**. `node $WT polling` prints the current window's minutes and why pushes are held; `node $WT notifications [on | off | snooze <length> | unsnooze | weekends on|off]` sets the Notifications controls; `node $WT poll-now [--keep-queue]` runs one poll at once.

**Another server.** Any server works if it follows the prefix rule. For its events, point the watcher at its own files with `--watch <file,file>` (relative to `--dir`) and `--filter '<regex>'` on `join`; only matching lines wake the owner.

**Changes.**
- Static files are live on the next request.
- A change to the server's code needs `node $WT restart <route>`.
- A changed `cmd`, port or dir in the manifest restarts the site by itself.
- A change to the hub's own code (`hub/`) needs `launchctl kickstart -k gui/$(id -u)/local.claude.web-ts-hub`, which restarts every site. Until then each board's `hub` link reads broken.
- `node $WT logs <route>` shows the site's output. The hub's own log is `~/.claude/web-ts/hub.log`.

**Leaving.** `node $WT leave <route> --session <id>` removes the entry; the hub stops the site and keeps its files. Leave only when the user asks.
