# kickflip

One **hub** on the host answers `http://127.0.0.1:<port>/` for every site, and `https://<host>.<tailnet>.ts.net/` too while the tailnet is on (Tailnet below). It reads `~/.claude/kickflip/manifest.json`, lists every site in a sidebar beside each board, forwards `/<route>/…` to each **site**'s port with the prefix stripped, and runs each site's `cmd`, restarting it when it exits or when its entry changes. The host's service manager keeps the hub up across logins and session restarts: launchd on macOS, a systemd user unit on Linux. A site joined with a session has one **owner** session, the only one woken by its events; a **plain page** has none. The hub never manages sleep: a sleeping host answers nothing.

`KF=~/.claude/skills/kickflip/bin/kickflip.mjs`; run it with `node`. Its header comment lists every command and flag.

## Entry points

The skill has three forms, each the CLI command of the same name ([/kickflip is handoff, page and board](docs/adr/2026-11-15-0014-kickflip-is-handoff-page-and-board.md)). Anything else, the phone push included, is the CLI's alone.

- **`/kickflip handoff [board]`** sends this session's objective to a board as a New task: [Hand off](#hand-off).
- **`/kickflip page <route> [--port n | --dir d]`** puts a page that isn't a board on the hub: [Join a page](#join-a-page), or with no `--port` or `--dir` a page this session answers, by the [Steps](#steps).
- **`/kickflip board <route>`** makes or rejoins a board with this session as its orchestrator, by the [Steps](#steps). The hub starts and resumes every board's session with it too.

Any flags after the route pass on to the command. The route may be the site's name, as `"Bob's board"`, which gives its title and its route, the name hyphenated; a name that is the route itself keeps the site's title.

## Hand off

Write the session's objective in a few lines: what it is for, what is done and what is left, and the files and links a builder needs. With no board named, first run `node $KF handoff` with no objective: it prints every board as the hub's router reads it (route, title, description, its 15 most recently changed open tasks). Pick the board from that list. Then run `node $KF handoff <route> --file <objective file> --label <label>` (or `--text "<objective>"`). It files the objective as an ask on that board, which becomes a New task there, its thread opening "Routed here from a handoff: <label> named this board", and prints `handed to <link>`; give the owner the link. When you can't pick a board from the list, run it with no route and the hub's router picks, as for any request that names none ([a haiku router files each incoming request on a board](docs/adr/2026-11-12-2345-a-haiku-router-files-each-incoming-request-on-a-board.md)): it prints that the request is queued, and within 15 seconds the hub files it with the router's reason, the Hub page's Routed section showing where. An @kickflip in one of the owner's 1:1 Slack DMs is routed the same way (Reviewers, below). A board's orchestrator moving one of its own tickets runs `board.mjs handoff` instead, which leaves a pointer on the ticket it came from ([handoff moves a ticket to another board and leaves a pointer](docs/adr/2026-11-14-2340-handoff-moves-a-ticket-to-another-board-and-leaves-a-pointer.md)).

## Install on a new host

The host is a Mac or a Linux machine. With Git, Node 22+, Claude Code and gh installed (and tmux, for a hub board's session only; Tailscale only for the tailnet, below), install kickflip from public npm:

```sh
npm i -g @lovek4d/kickflip
kickflip init
```

`init` is the first-run name for `doctor --fix`; both run the same steps and finish with a doctor report. Init links `~/.claude/skills/kickflip` to the installed package's folder (with `npm link` from a clone, to the clone) and `~/.claude/skills/kickflip-hooks` through `kickflip/hooks-plugin/`. Correct skill links are checked and kept. A real folder is accepted only when it is the target itself. A skill link pointing elsewhere, including a broken link, is refused with a message; move an existing real folder or explicitly remove a wrong link before retrying. `--force` does not bypass these checks.

`kickflip feedback [--type bug|idea|question] [--title <title>]` opens GitHub's new-issue form for kickflip (`.github/ISSUE_TEMPLATE/feedback.yml`) with the type, title and the kickflip, node and OS versions filled in, and prints the URL (`--print` opens nothing); you write the details in the browser under your own GitHub account, and nothing from boards, paths or hosts goes in the URL ([an issue form with a prefilled URL, no Worker](docs/adr/2026-11-18-1900-feedback-is-a-prefilled-github-issue-form-no-worker.md)).

`kickflip update` runs `npm i -g @lovek4d/kickflip@latest`, then restarts the hub (`--no-restart` leaves it running). It refuses a clone; update that with `git pull`. An npm install's hub checks npm for a newer version as it starts and every 15 wall-clock minutes, so a Mac's sleep can't stretch the wait; it pulls a newer one itself with `kickflip update --no-restart` once you have been away 15 minutes by the hub's away reading (the moon; about 18 minutes after your last key or tap), so an update never lands mid-use, and at once when you tap the hub page's version, and the hub then restarts itself, after which the sidebar reads New version · Reload. The hub page's footer is the version line, one button reading `kickflip.sh / 0.13.0 > 0.14.0 (new)` whenever npm has a newer one, with `auto update`, a checkbox, on the line under it (a clone has no box); a tap on the line pulls and answers in place, and with the box off (`autoUpdate: false` in settings.json, unset is on) the checks still run and name the newer version but only a tap pulls ([a checkbox under the hub's version turns auto update off](docs/adr/2026-11-13-2345-a-checkbox-under-the-hubs-version-turns-auto-update-off.md)). A failed pull is logged and retried at the next check, and shows nothing; a pull still running after 10 minutes is killed, logged and retried the same way; `kickflip update` is the backup. Each check logs `kickflip update check: npm <latest>, running <installed>` to hub.log when that changes and otherwise at most hourly, and every update line starts with `kickflip update`. A clone never pulls ([the hub offers a newer kickflip from npm](docs/adr/2026-11-03-1521-the-hub-offers-a-newer-kickflip-from-npm.md), [the update row shows only New version and Reload](docs/adr/2026-11-06-0800-the-update-row-shows-only-new-version-and-reload.md), [the npm check rides the hub's tick every 15 wall-clock minutes](docs/adr/2026-11-12-0110-the-npm-check-rides-the-hubs-tick-every-15-wall-clock-minutes.md), [an npm hub pulls only once the owner has been away 15 minutes](docs/adr/2026-11-12-0300-an-npm-hub-pulls-only-once-the-owner-has-been-away-15-minutes.md)).

For development, clone the private repo, run `npm install`, `npm link`, then `kickflip init`. `npm run build` makes the minified package in `dist/`, which is what gets published. A release is an ordinary task: its builder runs `node scripts/release.mjs <x.y.z> --ref <ref>` in its worktree, which bumps the version and commits `chore(release): <x.y.z>` with the subjects landed since the last tag listed below it and the task's `Refs:` trailer. Its land runs the repo's executable `.kickflip/release check <x.y.z> <commit>` before landing and `.kickflip/release ship <x.y.z> <commit>` once main reached origin, while the board's Run release script box is on; a repo with no `.kickflip/release` can't land a release, and a board whose scripts are in kickflip runs its `scripts/release` instead ([a repo's .kickflip/release replaces land's tag release](docs/adr/2026-11-16-0200-a-repos-kickflip-release-replaces-lands-tag-release.md)). The landed release task stays in In Review, its ticket open, reading publishing v<x.y.z> while the hub's poll reads its tag's runs and npm, whether the land shipped it or you push the tag by hand; once every run passed and npm serves the version it reads published <x.y.z> and waits on the owner's Done. On `release-failed {key, version, url, failure}` it reads red with the run's link and its first failing test: fix the cause and ship a patch release as a new task; a passing rerun of the run publishes this one ([a release card waits in In Review until its release is published](docs/adr/2026-11-18-0200-a-release-card-waits-in-in-review-until-its-release-is-published.md)). Kickflip's own script checks `package.json`'s version and that `v<x.y.z>` is new, then tags the landed commit `v<x.y.z>` and pushes the tag. A commit you make by hand, outside any task's land, follows the same commit standard: a Conventional subject of at most 100 characters ending " (#N)" when it is for a task with a ticket, and a `Refs: #N` trailer for that ticket and each related task's ticket, with none for a task that has no ticket ([commits are Conventional and name their card in a Refs trailer](docs/adr/2026-11-11-1700-commits-are-conventional-and-name-their-card-in-a-refs-trailer.md), [outside text cites only external refs, and a subject ends with its ticket](docs/adr/2026-11-24-2100-outside-text-cites-only-external-refs-and-a-subject-ends-with-its-ticket.md)). The tag runs `.github/workflows/release.yml`, which runs the suite, builds, checks the tag against `dist/package.json`'s version, smoke-installs the packed `dist/` and publishes it to npm by trusted publishing ([a v* tag publishes kickflip to npm](docs/adr/2026-11-03-1345-a-v-tag-publishes-kickflip-to-npm.md)).

Init also links `~/.claude/statusline.sh` through `kickflip/bin/statusline.mjs`, replacing a dangling link, a link into `~/.claude/kickflip/sites/` (a status-line prototype) or one pointing directly at the running package folder or clone. A real file or another working status-line link is refused. It adds `statusLine` to `~/.claude/settings.json` only when absent; an existing choice stays, with a note if it points elsewhere. Settings writes preserve other keys and hooks. Rerunning checks the links and skips unchanged settings. The status line prints directory, branch (with `*` for tracked changes), model, context percentage and Claude's usage (`5h 23% · 7d 57%`), then atomically saves Claude's rate-limit reading in `~/.claude/kickflip/usage.json` for the hub. The plugin supplies Codex sharing and pause line reminders on SessionStart and UserPromptSubmit, denies new Agent/Task calls while paused, shows a board's session the owner's new words after each tool call (PostToolUse), and supplies builder cleanup on SubagentStop; it adds no settings.json hook entries. Init adds the watcher Stop hook, `hooks-plugin/hooks/watcher-stop.mjs`, to settings.json's `Stop` hooks, which the plugin can't supply, and doctor reports it missing; every session the hub starts or resumes also gets it through its `--settings`, so a board's session keeps the guard whatever settings.json carries. Doctor lists the hub’s try ports and their board/task or main; on Linux a non-root hub user needs `sudo tailscale set --operator=$USER` if doctor reports an operator mismatch ([a try build serves on its own Tailscale port](docs/adr/2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)). Setup needs no dotfiles scripts ([kickflip installs its own status line and hooks](docs/adr/2026-11-01-1322-kickflip-installs-its-own-status-line-and-hooks.md)). `uninstall` removes kickflip's status-line link along with the hub's service and Tailscale mapping; skill links, Claude settings and live state stay.

Kickflip doesn't ship `slack-bridge` or `codex-share`; init doesn't add them and doctor doesn't check them. The mattpocock skills an architecture review follows, improve-codebase-architecture, codebase-design, grilling and prototype, are a prerequisite kickflip doesn't pin: init adds any that are missing with the skills CLI (`npx skills add mattpocock/skills -g -y -a claude-code --skill …`), and doctor marks a missing or out-of-date one optional with the command that fixes it (`shared/skills.mjs`). The `monitor` skill is optional: the hub polls GitHub itself and, when Hub's Linear key is set, moves the owner's Linear tickets from PR state ([the hub's poll moves the owner's Linear tickets](docs/adr/2026-11-02-0023-the-hubs-poll-moves-the-owners-linear-tickets.md)); without a key it moves none. The session leaves these PR-based moves to the hub. This skill's GitHub tick handles `github-change` and `check-github`. When the owner's monitor skill is installed, a session may run its tick instead, which can add its own steps; kickflip owns the reviewer steps below.

The same command installs the hub's service, which starts the hub through the `~/.claude/skills/kickflip` link, starts it, and, while the tailnet is on, maps Tailscale `/` to it. Off, init runs no tailscale and leaves an existing mapping as it is (Tailnet below). Every tailscale call goes to the daemon recorded as `tailscale` in `~/.claude/kickflip/settings.json`: on macOS brew's `tailscaled`, reached by `tailscale` on PATH with `--socket /var/run/tailscaled.socket`, or the GUI app's, reached by its own binary `/Applications/Tailscale.app/Contents/MacOS/Tailscale` (or in `~/Applications`), which the App Store build never puts on PATH. With none recorded, the first call picks the running daemon that serves `/` to the hub, else the app's, and records it with the node it answered as; `doctor --fix` and init pick again. A recorded daemon that's down stays chosen: doctor faults, and every write (try ports, the `/` mapping, uninstall's unmap) refuses rather than land on another daemon, until a re-pick. Doctor's Tailscale line names the chosen daemon and its machine and notes any other running one ([kickflip records the Tailscale daemon it uses, CLI or app](docs/adr/2026-11-17-0311-kickflip-records-the-tailscale-daemon-it-uses.md)). With neither, the hub still starts and serves this host, init skips only the mapping with the reason and the install hint, and doctor and the Hub page's Tailscale row say what's missing ([a board starts and lands without Tailscale](docs/adr/2026-11-04-1513-a-board-starts-and-lands-without-tailscale.md)). `shared/service.mjs` picks the service by platform: on macOS a launchd login item, `~/Library/LaunchAgents/local.claude.kickflip-hub.plist`; on Linux a systemd user unit, `~/.config/systemd/user/kickflip-hub.service`, enabled and started with `systemctl --user`. A user unit stops with the owner's last login session unless the user lingers, so on a server run `sudo loginctl enable-linger "$USER"` once; doctor notes it ([the hub runs under the host's service manager](docs/adr/2026-11-01-1542-the-hub-runs-under-the-hosts-service-manager.md)). Live state (manifest, sites, settings and builder worktrees) stays in `~/.claude/kickflip/`. Paths saved for later use inside the kickflip package folder or clone go through `~/.claude/skills/kickflip` when that link resolves to the running root, including board commands, session hooks and prompts, session folders and builder records; moving the folder and repointing that link keeps them valid. `storedPath()` in `bin/install.mjs` owns this conversion; paths used only while code runs can stay real. Board repo clones live in `~/.claude/kickflip/repos/<owner>/<repo>`, or `<host>/<path…>` there for a repo on another git host, whether kickflip runs from a clone or an installed package; `shared/repos.mjs` owns the base path. Doctor lists each clone left in an old place (a clone's `.repos/`) that no board uses as optional, and `doctor --fix` asks in a terminal whether to remove each one; a clone a board uses gets no row ([board clones live outside the package](docs/adr/2026-11-04-0103-board-clones-live-outside-the-package.md)). `.repos/` stays gitignored and excluded from land's test suite along with `node_modules/` ([kickflip ships as a minified npm package](docs/adr/2026-11-01-2247-kickflip-ships-as-a-minified-npm-package.md)).

## Tailnet

The hub listens on `127.0.0.1` only, so by default it serves this host and nothing runs tailscale. `kickflip tailnet on` puts it on your Tailscale network for the phone: it maps Tailscale `/` to the hub through the daemon init picks, records `tailnet: true` in `~/.claude/kickflip/settings.json` and prints the hub's `https://<host>.<tailnet>.ts.net/` address, or why it has none yet (HTTPS certificates off for the tailnet). It refuses, still off, with no Tailscale installed. `kickflip tailnet off` unmaps `/` and the try ports and records off; `kickflip tailnet` or `kickflip tailnet status` prints which, with the address. Off is the default for every install, an existing one whose Tailscale `/` already serves the hub included: nothing detects it, and off leaves that mapping until `tailnet off` removes it. While it's off, `kickflip url` and the URLs join prints are `http://127.0.0.1:<port>/…`, doctor shows one optional `Tailnet` line with `→ kickflip tailnet on` in place of its Tailscale lines, the Hub page's Integrations shows one grey Tailnet row reading off, and uninstall leaves Tailscale alone. A served task's, Main's and a served prototype's try port listens on `127.0.0.1:<port>` either way, which the host's own page opens; on, Tailscale maps the same port on the tailnet. Off, the hub's owner is a loopback caller alone and no Tailscale login is read ([off the tailnet, try ports serve this host and only loopback is owner](docs/adr/2026-11-17-2333-off-the-tailnet-try-ports-serve-this-host-and-only-loopback-is-owner.md)). `shared/tailnet.mjs` owns the setting and the address; every caller reads it on each call ([the tailnet is opt-in with kickflip tailnet](docs/adr/2026-11-18-0300-the-tailnet-is-opt-in-with-kickflip-tailnet.md)).

## Prereqs

`node $KF doctor` checks Git; Node on the PATH this Claude Code session inherited; gh installed and signed in; Git reaching GitHub over https with gh's token, as the hub clones; while the tailnet is on, Tailscale installed, on PATH or as the macOS app, naming the binary it found, signed in and serving `/` to the hub; an optional Codex, installed on that PATH and logged in (`~/.codex/auth.json`); the optional mattpocock skills, installed and matching their source's tree in `~/.agents/.skill-lock.json`; and an optional tmux, which only a hub board's session needs. It also checks the kickflip and kickflip-hooks links, `~/.claude/statusline.sh`, `statusLine` in Claude settings, the running hub service (the login item on macOS), on macOS whether Spotlight indexes `~/.claude/kickflip` (asked by finding its `manifest.json` in the index; when it does, the item is yours, with the step to add the folder in System Settings › Spotlight › Search Privacy, since that list needs root and a `.noindex` folder isn't honoured: [Spotlight's Privacy list is the owner's step](docs/adr/2026-11-06-1500-spotlight-privacy-is-the-owners-step.md)), the hub and every site, and each board's repo as the hub fetches it, with Git's own login (`git ls-remote --exit-code origin HEAD` from the repo), which can fail while gh's token reaches GitHub; on Linux also whether the user lingers and what reads differently off macOS. It changes nothing. Install hints name Homebrew on macOS and apt elsewhere, with Tailscale's install script and `npm i -g @openai/codex` where apt has no package. Each line is `<mark> <item>: <detail>`, marked **ok**; **fixable**, which `kickflip doctor --fix` sets up; **yours**, which only the person can fix; **optional**, Codex, needed only for Codex builds and reviews, the mattpocock skills, needed only for architecture reviews, or tmux, needed only for a hub board's session; or **note**, a down site the running hub restarts. A fixable, yours or optional line is followed by `→ <command>`. `--json` prints `{items: [{group, item, state, detail, fix}]}`. Exit 1 means something is fixable or yours.

## Add a repo as a board

In a terminal in a git repo's folder, the owner runs `kickflip join`. It asks for the board name, default the folder's name, in letters, digits and spaces; the route is the name lowercased with dashes for spaces. It makes a board from the board template, records the folder's GitHub origin and branch, marks the folder trusted for Claude Code, and starts the board's session in the background, as New board does; `--hub` flags it as the hub board and starts its session in the foreground in tmux instead, attaching that terminal to it ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)). Its builders branch from the folder's local `main` and `land` there. It refuses a folder outside git, says to run `kickflip init` while the hub isn't running, and for a folder that already has a board names it and offers to restart its session. With no terminal, pass `--name "<Board name>"` ([kickflip join adds the current repository as a board](docs/adr/2026-11-03-0248-kickflip-join-adds-the-current-repository-as-a-board.md)). A session doesn't run this form; it joins with `--session` as in the steps below.

## Join a page

`page` and `board` take the site's name as their first word, which gives its title and its route as above; both run `join`, the plumbing every site goes through.

To put a page on the owner's phone with nothing for Claude to answer, join it as a plain page. It needs no session id, owner, watcher or needs.json ([a page joins without a session](docs/adr/2026-11-01-1446-a-page-joins-without-a-session.md)).

- **A server this session runs:** `node $KF page <route> --port <n>`. The hub forwards `/<route>/…` to that port with the prefix stripped. It doesn't run or restart the server, so while nothing answers the page reads Down.
- **Plain files:** `node $KF page <route> --dir <folder>`. The hub serves the folder itself, a folder's `index.html` included, and refuses any path with a part starting with `.`. With `--session <id>` the same files page records this session as its owner, as a New course's session does once lesson 1 is written.
- **A server the hub runs:** add `--cmd '["/abs/node","/abs/server.mjs"]'` to `--dir`, with `--port` if it has a fixed one. The hub starts and restarts it, as for any site.

`page` prints `{route, url, serves, …}`; give the owner the `url`. The page shows under Pages in the sidebar, in a frame beside the hub's header and sidebar. Follow the prefix rule below. `--description`, `--icon` and `--color` work as in step 3. A rejoin passes `--port`, `--dir` or `--cmd` again: `page` refuses a call with none of them and no `--session`, and a route a board holds. `node $KF leave <route>` takes the page off and keeps its files. Exit 3 means a session owns that route. For a page that wants Claude to answer it, with events, the watcher and the Needs you badge, follow the steps below instead.

## Steps

These make a site Claude answers: a board (`/kickflip board <route>`), or a page this session answers (`/kickflip page <route>` with no `--port` or `--dir`).

1. **Who you are.** Your session id is the directory name just above your scratchpad (`…/<session-id>/scratchpad`). Your label is the session's name if it has one, otherwise two or three words for its work.
2. **Hub up.** Run `node $KF doctor`. When anything is fixable, ask the user once (it adds the hub's service, a login item on macOS or a systemd user unit on Linux, maps Tailscale `/` to the hub while the tailnet is on and sets up kickflip's status line and hooks as above), then run `node $KF doctor --fix` and read its new report. For anything marked yours, tell the person the printed command once and go on; a foreign status line needs their explicit replacement. Done when doctor reports nothing fixable: yours, optional and note lines are the person's and never hold up the join, so a session the hub started in the background, which nobody watches, still joins and lands its board ([a board starts and lands without Tailscale](docs/adr/2026-11-04-1513-a-board-starts-and-lands-without-tailscale.md)). See [doctor checks and fixes a hub](docs/adr/2026-11-01-1433-doctor-checks-and-fixes-a-hub.md).
3. **Join.** Run `node $KF board "<Board name>" --session <id> --label <label> --description "<one line>"` for a board, or `node $KF page <route> --session <id> --label <label> --description "<one line>"` for a page; both add `--watch`. The name is the one your first prompt gave (`/kickflip board '<Board name>' …`, plus any flags after it, which you pass on), which may be the route itself and then keeps the site's title; the route is the name hyphenated. A new board copies the board template; a new page route copies the starter kit into `~/.claude/kickflip/sites/<route>/`, picks a free port from 4600, and the hub starts it within 2 seconds. An existing route keeps its files and command. To serve an existing project, pass `--dir` and `--cmd '["/abs/node","/abs/server.mjs"]'`, and `--port` if it has a fixed one. `join` also records the session's folder (`--repo`, by default the session's own cwd), which `start` and `resume` use (Board sessions, below). A rejoin keeps the label and folder it leaves out.
   - **Icon** ([site icons are line icons from a built-in set](docs/adr/2026-10-29-1639-site-icons-are-line-icons-from-a-built-in-set.md)). The sidebar draws each site's row with a line icon from `hub/icons.mjs` on a tint of the site's color. Pass `--icon <key>`, such as `phone` or `book` (`--icon x` lists the keys), and `--color <css hex>`. Without a key the hub picks an icon from words in the route and title, else shows the title's first letter, on a color picked from the route. `node $KF set <route> --icon … --color …` changes them later without joining.
   - **A board** (Linear-style lanes of PRs and tickets, item threads, questions for the owner): `board` joins with `--template board`. A new board starts on its own cards, `data/items.json`; pass `--items <file>` for another item file, or `waves` for every `~/.claude/waves/*/wave.json`. A rejoin keeps the items its `board.json` names, and `board` refuses a route a page holds. The site then runs the shared `board/` code, whose `server.mjs` header documents `board.json` and the API. Every board shares that code, so make board changes in `board/` and copy none of it into a site. A site's `public/` holds only its own files, such as prototype pages, and any page it overrides. Changes to the hub or the board template come in as asks on the hub board ([hub changes come as asks, not Improvements rounds](docs/adr/2026-10-29-1639-hub-changes-come-as-asks-not-improvement-rounds.md)).
   - **Exit 3 means another session owns it.** Ask the user with AskUserQuestion: take it over (recommended when the old session has ended or the user asked for this), or leave it. On yes, rerun with `--force`. The takeover is total: the old owner's watcher prints `handed-over` and that session stops serving the route.
4. **Build or resume the site.** Done when `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<site port>/<page>` returns 200 for each page you changed (the site's own port: through the hub a page needs the owner's sign-in, [the owner signs in with a link that sets a device cookie](docs/adr/2026-11-18-1200-the-owner-signs-in-with-a-link-that-sets-a-device-cookie.md)), and a page meant for the phone renders at 390px wide with no sideways scroll. Follow the prefix rule below. The page design is yours; the starter's `public/index.html` is a placeholder.
5. **Watch.** When `join` printed `brief`, the hub started this session fresh, since the board's last one sat idle past its prompt cache: run that command first and read it, the cards In Progress, the cards on the owner, the owner's last day of messages and the memory index, in place of a long session's memory; anything you need later and can't find on the board is a board gap, so file it ([an idle orchestrator restarts fresh once its prompt cache lapses](docs/adr/2026-11-17-2330-an-idle-orchestrator-restarts-fresh-once-its-prompt-cache-lapses.md)). ## Reference

**Hub session.** Every board's session runs in the background; a hub board is optional. The hub board is the one board whose manifest entry has `hub: true`: `node $KF set <route> --hub` (or `join … --hub`, which `kickflip join --hub` in a repo folder passes) sets it and clears it from any other site, and `--no-hub` clears it. That flag only means its session runs in the foreground in the tmux session `kickflip-<route>`, which the hub starts when it wakes or restarts the board, with the same flags and phone permission hook as a background session. In the owner's terminal, `node $KF hub [--repo <dir>]` attaches to that tmux session, starting it first when none runs; while it runs, nothing starts another. The session follows [docs/hub-session.md](docs/hub-session.md). tmux is needed only for a hub board; `kickflip doctor` lists it as optional ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)).

**Words and decisions.** [CONTEXT.md](CONTEXT.md) is the glossary for the hub and boards. [docs/adr/](docs/adr/) records why each hard-to-reverse choice was made. Read the ADR before changing what it covers. When the owner settles a new one, in an ask or a task's question, add an ADR with the domain-modeling skill, named by the minute you write it, `docs/adr/YYYY-MM-DD-HHMM-<slug>.md`, never by a number. Prose and comments link an ADR with its title as the link text, as in [a build tap starts the build in the board server](docs/adr/2026-11-03-0219-a-build-tap-starts-the-build-in-the-board-server.md).

**Prefix rule.** A served try build opens at its own `https://<host>:<port>/` origin, serves at `/` and needs no prefix or `KICKFLIP_BASE` ([a try build serves on its own Tailscale port](docs/adr/2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)). For sites joined to the hub, the hub strips `/<route>` before your server sees a request, but the browser still uses the full URL. So write links relative to the page (`notes.html`, `../claude.js`), or build them from a root the page computes. In the starter kit, `ClaudeSite.url('x')` derives that root from its own script URL. A root-absolute link (`/x`) leaves the site. Your server gets `PORT` and `PREFIX` in its environment and should serve paths with or without the prefix; a redirect `Location` starting with `/` gets the prefix added by the hub. A stray `/favicon.ico` request is harmless. A browser's page load of a site's page, a path ending in `/` or `.html`, gets the hub's app shell instead of reaching your server, and the shell shows the page in a same-origin frame beside the sidebar ([one app for the whole hub](docs/adr/2026-10-29-2005-one-app-for-the-whole-hub.md)). The frame's request, curl, an API call, an image and `?alone=1` (the frame's Open alone ↗) still reach your server; a board's server answers its four view paths with the shell too. So don't send `X-Frame-Options` or a `frame-ancestors` CSP that refuses the hub, or the frame stays blank. A page that starts its body with the board header (`<!--header …-->`) shows that header in place of the shell's.

**Browser writes.** The hub, board server and starter guard every non-GET/HEAD request with `starter/cross-site.mjs`: 403 when `Sec-Fetch-Site` is present and neither `same-origin` nor `none`, or when `Origin` is present and its host differs from `X-Forwarded-Host` (falling back to `Host`). The proxy preserves those browser headers and the external host. JSON body routes require `content-type: application/json`; hub settings forms keep form encoding, and uploads keep the file's type. Use same-origin URLs and `ClaudeSite.send` for events; use `fetch` with `keepalive` for JSON sent while leaving a page. Node callers may omit both browser headers. `/_hub/build` also requires loopback and refuses every Origin and forwarded header.

**Starter kit** (`~/.claude/skills/kickflip/starter`): `server.mjs`, Node with no dependencies, serving `public/` plus the event API; `cross-site.mjs`, the guard copied with it and shared by the hub and board; `public/claude.js`, the browser side; `public/index.html`, a placeholder. **Tasks and tickets** ([work items are tasks, and tickets attach to them](docs/adr/2026-11-13-1126-work-items-are-tasks-and-tickets-attach-to-them.md)). A board's work item is a **task**, keyed `<file>/T-<n>`: say task, never card, in threads, notes, questions and replies. A **ticket** is the upstream or internal issue attached to a task, a GitHub issue or a Linear issue from the board's ticket source; a task reads as its ticket once it has one (`#27`, `ENG-12`), and a task with none shows a quiet badge of its `T-<n>`.

**Script offers.** Any action you are denied that the owner would plainly want (a `kill`, `tailscale serve`, `gh issue close`, an install, a pushed tag's move, an amend on a builder's branch) goes to them as a script, never as a command typed in prose for them to paste: write it to a file and run `board.mjs thread <key> --script <file> --text "<what it does and why you couldn't>"`. Never offer one for anything the task doesn't need. The task's thread shows the whole script, "Runs on <host> as <user>", and Run, which only the owner can tap and must hold, and Decline; the task reads Action needed and pushes until one is tapped, and a newer offer on the task replaces a waiting one. The board server runs it once in the board's repo folder, 10 minutes at most, its output in a log. The owner's Run wakes you as a `script-run {key, id, sha}` event: nothing to do yet. Its end wakes you as `script-result {key, id, exit, output, timedOut, ms, log}`, its output's last 64 KB, with the tail in the watcher's line: carry on from it in the thread. A `script-decline {key, id}` means don't run it another way; ask in the thread what they want instead ([the orchestrator offers a script and the owner holds Run](docs/adr/2026-11-14-2359-the-orchestrator-offers-a-script-and-the-owner-holds-run.md)).

A fenced block in a thread message, question context or option detail draws as code: monospace, lines kept, scrolling sideways, with a Copy button. Use it for code the owner reads or copies; a command they should run goes as a Run card above.

**Your role on a board.** A board has settled towards mostly being a mechanical task board: the board server and `board.mjs` move tasks across lanes, launch planners and builders, and apply the owner's button taps themselves. You step in where judgment is needed. Make sure a task marked as staging is prepared to move to ready, judging it against the whole board, since that is when the task board is freshest before implementation begins; from ready it moves across lanes on its own. Answer questions across tasks, and be available for being grilled by or grilling the implementing agents and the grilling agents that might have questions before those questions surface to the owner: a builder's reach you as `builder-ask`, a finished grill's as a `screen` wait, which `question publish <card>` passes on to the owner; you settle first, with `question settle <id> --answered-by <T-N|commit|notes heading> --note <answer>`, only a question whose answer already lives in a task, a commit or a notes section, never as a sign-off that screening is done. **Incoming reviews** ([an incoming review leads with the board's overlap](docs/adr/2026-11-25-0000-an-incoming-review-leads-with-the-boards-overlap.md)). A review of a teammate's PR, an auto review's `pr-review` or one asked in Slack, adds what only the board knows, not what the repo's automated reviewer covers. First run `board.mjs --site <route> review overlap <pr>` (its link, owner/repo#n or number): it prints the open tasks whose worktree changes the PR's files, the tasks landed on main since the PR branched that changed them, the lines of their notes naming those files, every review, comment and inline comment already on the PR, the read time for `--read-at`, and whether a line-level review is due. Then write the review:
1. **Overlap first.** For each task it names, say what the PR does to it: builds on it, undoes it, contradicts a decision in its notes, or will conflict with it at land, and triage it: link the task (cite its ticket or PR, never its key), add a note to it, or drop it as unrelated. With none, say "no overlap with this board's work".
2. **What the board's work says to consider**: a pattern a board task settled, a bench or guide rule the board has hit, only where no review or comment on the PR has said it.
3. **Line-level** (logic, missed inputs, duplicated helpers, missing tests) only when `review overlap` says due, meaning no bot has submitted a review or inline review comments (a deploy or coverage bot's plain comment doesn't count), or when the owner or the asker asks for it in words. While it says wait, CI is still running and the repo's reviewer may yet post: run it again once checks finish.

Repeat no point any review or comment already made. With nothing to add, post nothing: `review record` an auto review posted, and say so in the reply to a Slack ask.

- `node $KF logs <route>` shows the site's output. The hub's own log is `~/.claude/kickflip/hub.log`.

**Closing a board** ([a closed board keeps its folder and can be reopened](docs/adr/2026-10-31-1603-a-closed-board-keeps-its-folder-and-can-be-reopened.md)). On the owner's request, `node $KF close <route> --name '<exact board title>'` stops its session, ends its running builder records with a note and removes its server and sidebar row. Its folder, tasks, threads and notes stay on the host; its PRs stay open on GitHub, with no polling from this board. Board Settings has the same action with an active-work warning and a typed-name confirmation. A board whose session is also recorded by another active board cannot be closed. The Hub page’s Closed boards row lists closed boards; `node $KF reopen <route>` restores the saved manifest entry and resumes its recorded session. A closed route stays reserved; use Reopen rather than join or start. A failed resume keeps the board on the closed list for retry. Reopen rewinds to the watcher position saved before Close, so an event delivered near Close may be replayed.

**Moving a board to another host.** On the owner's request, once no builder is open on the board, `node $KF export <route> [--out <file>]` writes one .tgz: the board's folder, its manifest entry without this host's folder, port, command, owner session or restart times, the hub's Notifications, Quiet hours and Codex share settings, and a README.md of the steps. No API key, integration file, GitHub or Codex sign-in, or other hub setting goes in; the README lists what to set up again. It moves only a board whose tasks live in its own folder. On the new host, after `kickflip init`, `kickflip import <file>` unpacks the board into `~/.claude/kickflip/sites/<route>/`, adds its entry with a free port, writes those settings over that host's, and prints the `join … --force` line a fresh session there runs to take the board over. It refuses a route that host already has. The old host keeps its copy until the owner leaves it there.

**Leaving.** `node $KF leave <route> --session <id>` removes the entry; the hub stops the site and keeps its files. A plain page needs no `--session`. It does not stop the session or record a closed board for Reopen. Leave only when the user asks.
