# kickflip

One **hub** on the host answers `https://<host>.<tailnet>.ts.net/` for every site. It reads `~/.claude/kickflip/manifest.json`, lists every site in a sidebar beside each board, forwards `/<route>/…` to each **site**'s port with the prefix stripped, and runs each site's `cmd`, restarting it when it exits or when its entry changes. The host's service manager keeps the hub up across logins and session restarts: launchd on macOS, a systemd user unit on Linux. A site joined with a session has one **owner** session, the only one woken by its events; a **plain page** has none. The hub never manages sleep: a sleeping host answers nothing.

`KF=~/.claude/skills/kickflip/bin/kickflip.mjs`; run it with `node`. Its header comment lists every command and flag.

## Install on a new host

The host is a Mac or a Linux machine. With Git, Node 22+, Claude Code, gh and Tailscale installed (and tmux, for a hub board's session only), and HTTPS certificates turned on for the tailnet (the hub's `tailscale serve` needs them), install kickflip from public npm:

```sh
npm i -g @lovek4d/kickflip
kickflip init
```

`init` is the first-run name for `doctor --fix`; both run the same steps and finish with a doctor report. Init links `~/.claude/skills/kickflip` to the installed package's folder (with `npm link` from a clone, to the clone) and `~/.claude/skills/kickflip-hooks` through `kickflip/hooks-plugin/`. Correct skill links are checked and kept. A real folder is accepted only when it is the target itself. A skill link pointing elsewhere, including a broken link, is refused with a message; move an existing real folder or explicitly remove a wrong link before retrying. `--force` does not bypass these checks.

`kickflip update` runs `npm i -g @lovek4d/kickflip@latest`, then restarts the hub (`--no-restart` leaves it running). It refuses a clone; update that with `git pull`. An npm install's hub checks npm for a newer version as it starts and every 15 wall-clock minutes, so a Mac's sleep can't stretch the wait; it pulls a newer one itself with `kickflip update --no-restart` once you have been away 15 minutes by the hub's away reading (the moon; about 18 minutes after your last key or tap), so an update never lands mid-use, and at once when you tap the hub page's version, and the hub then restarts itself, after which the sidebar reads New version · Reload. A failed pull is logged and retried at the next check, and shows nothing; a pull still running after 10 minutes is killed, logged and retried the same way; `kickflip update` is the backup. Each check logs `kickflip update check: npm <latest>, running <installed>` to hub.log when that changes and otherwise at most hourly, and every update line starts with `kickflip update`. A clone never pulls ([the hub offers a newer kickflip from npm](docs/adr/2026-11-03-1521-the-hub-offers-a-newer-kickflip-from-npm.md), [the update row shows only New version and Reload](docs/adr/2026-11-06-0800-the-update-row-shows-only-new-version-and-reload.md), [the npm check rides the hub's tick every 15 wall-clock minutes](docs/adr/2026-11-12-0110-the-npm-check-rides-the-hubs-tick-every-15-wall-clock-minutes.md), [an npm hub pulls only once the owner has been away 15 minutes](docs/adr/2026-11-12-0300-an-npm-hub-pulls-only-once-the-owner-has-been-away-15-minutes.md)).

For development, clone the private repo, run `npm install`, `npm link`, then `kickflip init`. `npm run build` makes the minified package in `dist/`, which is what gets published. To release, when the owner asks: run `node scripts/release.mjs <x.y.z>` in the clone, which runs `npm version` with the message `chore(release): <x.y.z>` and the subjects landed since the last tag listed below it, then `git push origin main v<x.y.z>`. A commit you make by hand, outside any card's land, follows the same commit standard: a Conventional subject of at most 100 characters with no card ref in it, and a `Refs: <ref>` trailer when it is for a card ([commits are Conventional and name their card in a Refs trailer](docs/adr/2026-11-11-1700-commits-are-conventional-and-name-their-card-in-a-refs-trailer.md)). The tag runs `.github/workflows/release.yml`, which runs the suite, builds, checks the tag against `dist/package.json`'s version, smoke-installs the packed `dist/` and publishes it to npm by trusted publishing ([a v* tag publishes kickflip to npm](docs/adr/2026-11-03-1345-a-v-tag-publishes-kickflip-to-npm.md)).

Init also links `~/.claude/statusline.sh` through `kickflip/bin/statusline.mjs`, replacing a dangling link, a link into `~/.claude/kickflip/sites/` (a status-line prototype) or one pointing directly at the running package folder or clone. A real file or another working status-line link is refused. It adds `statusLine` to `~/.claude/settings.json` only when absent; an existing choice stays, with a note if it points elsewhere. Settings writes preserve other keys, and init removes only commands for the old `~/.claude/hooks/no-paths.py` when that script is missing. Rerunning checks the links and skips unchanged settings. The status line prints directory, branch (with `*` for tracked changes), model, context percentage and Claude's usage (`5h 23% · 7d 57%`), then atomically saves Claude's rate-limit reading in `~/.claude/kickflip/usage.json` for the hub. The plugin supplies Codex sharing and pause line reminders on SessionStart and UserPromptSubmit, denies new Agent/Task calls while paused, shows a board's session the owner's new words after each tool call (PostToolUse), and supplies builder cleanup on SubagentStop; it adds no settings.json hook entries. Init adds the watcher Stop hook, `hooks-plugin/hooks/watcher-stop.mjs`, to settings.json's `Stop` hooks, which the plugin can't supply, and doctor reports it missing. Doctor lists the hub’s try ports and their board/card or main; on Linux a non-root hub user needs `sudo tailscale set --operator=$USER` if doctor reports an operator mismatch ([a try build serves on its own Tailscale port](docs/adr/2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)). Setup needs no dotfiles scripts ([kickflip installs its own status line and hooks](docs/adr/2026-11-01-1322-kickflip-installs-its-own-status-line-and-hooks.md)). `uninstall` removes kickflip's status-line link along with the hub's service and Tailscale mapping; skill links, Claude settings and live state stay.

Kickflip doesn't ship `wave-build`, `slack-bridge` or `codex-share`; init doesn't add them and doctor doesn't check them. The mattpocock skills an architecture review follows, improve-codebase-architecture, codebase-design, grilling and prototype, are a prerequisite kickflip doesn't pin: init adds any that are missing with the skills CLI (`npx skills add mattpocock/skills -g -y -a claude-code --skill …`), and doctor marks a missing or out-of-date one optional with the command that fixes it (`shared/skills.mjs`). The `monitor` skill is optional: the hub polls GitHub itself and, when Hub's Linear key is set, moves the owner's Linear tickets from PR state ([the hub's poll moves the owner's Linear tickets](docs/adr/2026-11-02-0023-the-hubs-poll-moves-the-owners-linear-tickets.md)); without a key it moves none. The session leaves these PR-based moves to the hub. This skill's GitHub tick handles `github-change` and `check-github`. When the owner's monitor skill is installed, a session may run its tick instead, which can add its own steps; kickflip owns the reviewer steps below.

The same command installs the hub's service, which starts the hub through the `~/.claude/skills/kickflip` link, starts it, and maps Tailscale `/` to it. Every tailscale call runs the CLI `shared/tailscale.mjs` finds on each call: `tailscale` on PATH, else on macOS the GUI app's own binary, `/Applications/Tailscale.app/Contents/MacOS/Tailscale` (or in `~/Applications`), which the App Store build never puts on PATH. When it finds more than one (brew's formula and the GUI app), it runs the first whose daemon is Running, else the first found, and doctor's Tailscale line names the one it skipped ([kickflip runs the Tailscale CLI whose daemon is running](docs/adr/2026-11-06-1530-kickflip-runs-the-tailscale-cli-whose-daemon-is-running.md)). With neither, the hub still starts and serves this host, init skips only the mapping with the reason and the install hint, and doctor and the Hub page's Tailscale row say what's missing ([a board starts and lands without Tailscale](docs/adr/2026-11-04-1513-a-board-starts-and-lands-without-tailscale.md)). `shared/service.mjs` picks the service by platform: on macOS a launchd login item, `~/Library/LaunchAgents/local.claude.kickflip-hub.plist`; on Linux a systemd user unit, `~/.config/systemd/user/kickflip-hub.service`, enabled and started with `systemctl --user`. A user unit stops with the owner's last login session unless the user lingers, so on a server run `sudo loginctl enable-linger "$USER"` once; doctor notes it ([the hub runs under the host's service manager](docs/adr/2026-11-01-1542-the-hub-runs-under-the-hosts-service-manager.md)). Live state (manifest, sites, settings and builder worktrees) stays in `~/.claude/kickflip/`. Paths saved for later use inside the kickflip package folder or clone go through `~/.claude/skills/kickflip` when that link resolves to the running root, including board commands, session hooks and prompts, session folders and builder records; moving the folder and repointing that link keeps them valid. `storedPath()` in `bin/install.mjs` owns this conversion; paths used only while code runs can stay real. Board repo clones live in `~/.claude/kickflip/repos/<owner>/<repo>`, or `<host>/<path…>` there for a repo on another git host, whether kickflip runs from a clone or an installed package; `shared/repos.mjs` owns the base path. Doctor lists each clone left in an old place (a clone's `.repos/`) as optional, naming the boards that use it, and `doctor --fix` asks in a terminal whether to remove each one ([board clones live outside the package](docs/adr/2026-11-04-0103-board-clones-live-outside-the-package.md)). `.repos/` stays gitignored and excluded from land's test suite along with `node_modules/` ([kickflip ships as a minified npm package](docs/adr/2026-11-01-2247-kickflip-ships-as-a-minified-npm-package.md)).

## Prereqs

`node $KF doctor` checks Git; Node on the PATH this Claude Code session inherited; gh installed and signed in; Git reaching GitHub over https with gh's token, as the hub clones; Tailscale installed, on PATH or as the macOS app, naming the binary it found, signed in and serving `/` to the hub; an optional Codex, installed on that PATH and logged in (`~/.codex/auth.json`); the optional mattpocock skills, installed and matching their source's tree in `~/.agents/.skill-lock.json`; and an optional tmux, which only a hub board's session needs. It also checks the kickflip and kickflip-hooks links, `~/.claude/statusline.sh`, `statusLine` in Claude settings, the running hub service (the login item on macOS), on macOS whether Spotlight indexes `~/.claude/kickflip` (asked by finding its `manifest.json` in the index; when it does, the item is yours, with the step to add the folder in System Settings › Spotlight › Search Privacy, since that list needs root and a `.noindex` folder isn't honoured: [Spotlight's Privacy list is the owner's step](docs/adr/2026-11-06-1500-spotlight-privacy-is-the-owners-step.md)), the hub and every site, and each board's repo as the hub fetches it, with Git's own login (`git ls-remote --exit-code origin HEAD` from the repo), which can fail while gh's token reaches GitHub; on Linux also whether the user lingers and what reads differently off macOS. It changes nothing. Install hints name Homebrew on macOS and apt elsewhere, with Tailscale's install script and `npm i -g @openai/codex` where apt has no package. Each line is `<mark> <item>: <detail>`, marked **ok**; **fixable**, which `kickflip doctor --fix` sets up; **yours**, which only the person can fix; **optional**, Codex, needed only for Codex builds and reviews, the mattpocock skills, needed only for architecture reviews, or tmux, needed only for a hub board's session; or **note**, a down site the running hub restarts. A fixable, yours or optional line is followed by `→ <command>`. `--json` prints `{items: [{group, item, state, detail, fix}]}`. Exit 1 means something is fixable or yours.

## Add a repo as a board

In a terminal in a git repo's folder, the owner runs `kickflip join`. It asks for the board name, default the folder's name, in letters, digits and spaces; the route is the name lowercased with dashes for spaces. It makes a board from the board template, records the folder's GitHub origin and branch, marks the folder trusted for Claude Code, and starts the board's session in the background, as New board does; `--hub` flags it as the hub board and starts its session in the foreground in tmux instead, attaching that terminal to it ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)). Its builders branch from the folder's local `main` and `land` there. It refuses a folder outside git, says to run `kickflip init` while the hub isn't running, and for a folder that already has a board names it and offers to restart its session. With no terminal, pass `--name "<Board name>"` ([kickflip join adds the current repository as a board](docs/adr/2026-11-03-0248-kickflip-join-adds-the-current-repository-as-a-board.md)). A session doesn't run this form; it joins with `--session` as in the steps below.

## Join a page

Every join names its site with `--name "<name>"`, which gives its title and its route, the name hyphenated; a name that is the route itself keeps the site's title.

To put a page on the owner's phone with nothing for Claude to answer, join it as a plain page. It needs no session id, owner, watcher or needs.json ([a page joins without a session](docs/adr/2026-11-01-1446-a-page-joins-without-a-session.md)).

- **A server this session runs:** `node $KF join --name "<name>" --port <n>`. The hub forwards `/<route>/…` to that port with the prefix stripped. It doesn't run or restart the server, so while nothing answers the page reads Down.
- **Plain files:** `node $KF join --name "<name>" --dir <folder>`. The hub serves the folder itself, a folder's `index.html` included, and refuses any path with a part starting with `.`.
- **A server the hub runs:** add `--cmd '["/abs/node","/abs/server.mjs"]'` to `--dir`, with `--port` if it has a fixed one. The hub starts and restarts it, as for any site.

`join` prints `{route, url, serves, …}`; give the owner the `url`. The page shows under Pages in the sidebar, in a frame beside the hub's header and sidebar. Follow the prefix rule below. `--description`, `--icon` and `--color` work as in step 3. A rejoin passes `--port`, `--dir` or `--cmd` again, since a join with none of them and no `--session` adds the cwd's repo as a board. `node $KF leave <route>` takes the page off and keeps its files. Exit 3 means a session owns that route. For a page that wants Claude to answer it, with events, the watcher and the Needs you badge, follow the steps below instead.

## Steps

These make a site Claude answers: a board, or a page joined with `--watch`.

1. **Who you are.** Your session id is the directory name just above your scratchpad (`…/<session-id>/scratchpad`). Your label is the session's name if it has one, otherwise two or three words for its work.
2. **Hub up.** Run `node $KF doctor`. When anything is fixable, ask the user once (it adds the hub's service, a login item on macOS or a systemd user unit on Linux, maps Tailscale `/` to the hub and sets up kickflip's status line and hooks as above), then run `node $KF doctor --fix` and read its new report. For anything marked yours, tell the person the printed command once and go on; a foreign status line needs their explicit replacement. Done when doctor reports nothing fixable: yours, optional and note lines are the person's and never hold up the join, so a session the hub started in the background, which nobody watches, still joins and lands its board ([a board starts and lands without Tailscale](docs/adr/2026-11-04-1513-a-board-starts-and-lands-without-tailscale.md)). See [doctor checks and fixes a hub](docs/adr/2026-11-01-1433-doctor-checks-and-fixes-a-hub.md).
3. **Join.** Run `node $KF join --name "<Board name>" --session <id> --watch --label <label> --description "<one line>"`. The board name is the `--name` your first prompt gave (`/kickflip --name '<Board name>' …`, plus any join flags after it, which you pass on), else the route you were given, which keeps the site's title; the route is the name hyphenated. A new route copies the starter kit into `~/.claude/kickflip/sites/<route>/`, picks a free port from 4600, and the hub starts it within 2 seconds. An existing route keeps its files and command. To serve an existing project, pass `--dir` and `--cmd '["/abs/node","/abs/server.mjs"]'`, and `--port` if it has a fixed one. `join` also records the session's folder (`--repo`, by default the session's own cwd) and an optional `--model`, which `start` and `resume` use (Board sessions, below). A rejoin keeps the label, model and folder it leaves out.
   - **Icon** ([site icons are line icons from a built-in set](docs/adr/2026-10-29-1639-site-icons-are-line-icons-from-a-built-in-set.md)). The sidebar draws each site's row with a line icon from `hub/icons.mjs` on a tint of the site's color. Pass `--icon <key>`, such as `phone` or `book` (`--icon x` lists the keys), and `--color <css hex>`. Without a key the hub picks an icon from words in the route and title, else shows the title's first letter, on a color picked from the route. `node $KF set <route> --icon … --color …` changes them later without joining.
   - **A board** (Linear-style lanes of PRs and tickets, item threads, questions for Love): add `--template board`, plus `--items <file>` when the items come from the site's own item file rather than every `~/.claude/waves/*/wave.json`. The site then runs the shared `board/` code, whose `server.mjs` header documents `board.json` and the API. Every board shares that code, so make board changes in `board/` and copy none of it into a site. A site's `public/` holds only its own files, such as prototype pages, and any page it overrides. Changes to the hub or the board template come in as asks on the hub board ([hub changes come as asks, not Improvements rounds](docs/adr/2026-10-29-1639-hub-changes-come-as-asks-not-improvement-rounds.md)).
   - **Exit 3 means another session owns it.** Ask the user with AskUserQuestion: take it over (recommended when the old session has ended or the user asked for this), or leave it. On yes, rerun with `--force`. The takeover is total: the old owner's watcher prints `handed-over` and that session stops serving the route.
4. **Build or resume the site.** Done when `curl -s -o /dev/null -w '%{http_code}' <url>` returns 200 for each page you changed, and a page meant for the phone renders at 390px wide with no sideways scroll. Follow the prefix rule below. The page design is yours; the starter's `public/index.html` is a placeholder.
5. **Watch.** Run the `watcher` command `join` printed as a background Bash task (`run_in_background`), never with `&` or with its output thrown away: a detached copy takes events no one reads. Check for one already running with `pgrep -f 'wait-events.mjs <route>'`. It exits on the next event that needs you; record-only events (`main-pulled`, `settings`, `reviewers-removed`, `reviewers-added`, `question-reopen`, `repo-changed`, `ping`, and the button taps the board server applies itself: `card-hold`, `card-done`, `card-reopen`, `card-unbump`, `card-unblocked`, `grill-more`, `prototype-request`, `visual-request`, and `usage-resumed`, since the watcher reads the pause itself and the work a pause held wakes you once it lifts) never wake it, and their lines print ahead of the new events on the next wake. For each `event` line, relaunch the watcher first, then act and reply (below); its plain line says what to do, and every kind that wakes you has one and an entry here (`bin/event-lines.mjs`, kept so by its test; [every signal that wakes the orchestrator says what to do](docs/adr/2026-11-07-0043-every-signal-that-wakes-the-orchestrator-says-what-to-do.md)). Its cursor means no line is missed. While you work, the plugin's PostToolUse hook `hooks-plugin/hooks/board-messages.mjs` shows the owner's new thread messages, asks and ask edits after your next tool call, each with its sent time and age, and marks them thinking…; read and handle them before carrying on. The next wake prints them again with their plain line prefixed `already shown: `, so don't act on them twice ([the owner's words reach the orchestrator after its next tool call](docs/adr/2026-11-10-1056-the-owners-words-reach-the-orchestrator-after-its-next-tool-call.md)). The board reads "not listening" while no watcher runs in your running session, or while your session isn't running and the hub can't wake it. A background session that idles out reads asleep, in grey, and the hub resumes it when the next event lands or the owner taps the board's page, the header's refresh included; the header reads waking… until it listens ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md), [boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)). On `handed-over` or `site-removed`, stop; don't relaunch. Tell the user. The Stop hook `hooks-plugin/hooks/watcher-stop.mjs` keeps a turn from ending once while a board your session owns has no live watcher, naming the command to relaunch, or while a message there reads Working on it with no answer, naming each ([the CLI and board server do the board's housekeeping](docs/adr/2026-11-02-2044-the-cli-and-board-server-do-the-boards-housekeeping.md), [the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)). On a board, follow the `quiet` line the watcher prints on every wake: the terminal gets only the one-liners `board.mjs` and the watcher print, except in answer to a prompt typed there. Every wake on a board also prints `waits <kind> <ref> <key>[ bumped] since <iso>[, picked up <iso>]: <next>`, one line per card idle on you: bumped cards first, the earliest bump first, then In Progress then Todo in the board's order. Never filter them out of the watcher's output; filter only its rule, setting, quiet and link lines. Each lane works as your queue: after the events, walk that list top-down and handle every card on it, not only the cards the events named: `calls`, verify the builder's judgment calls; `checking`, land the checked build; `answer`, act on the owner's answer; `reply`, the owner's reply on a reopened card waiting in In Review: answer it in the thread, or start a builder on it, which alone moves it to In Progress ([In Progress means a builder runs](docs/adr/2026-11-09-1804-in-progress-means-a-builder-runs.md)); `ask`, answer or defer the builder's ask; `staging`, judge the staged card against the whole board (the checklist under Staging, below), then `item set <key> --phase ready --text "<what you checked>"` or send it back to grilling or prototyping; `screen`, screen a finished grill's questions before they reach the owner: `question settle <id> --note "<the answer>"` for each one the card's notes and thread, merged code or another card already answer, never the prototype question, then `question publish <key>` for the rest, which the board publishes itself once they wait 15 minutes unscreened; `intake`, sort the new task, answer the owner's message in an ask's thread, or link and file the card an agent added; `triage`, run the overnight triage and `reply` to its event; `brief`, write the grill, prototype or visual brief the card owes, `item brief <key> --kind <kind> --file <draft.md>`: what the discussion settled, what is still open, what the agent should cover and the files that matter, which the board launches the agent from; `grill` or `prototype`, start the planner asked for; `refused`, fix what refused the build and start it, or say on the card why it waits; `unowned`, start a builder on the card or set its Next; `unasked`, a grill or prototype planner ended without posting a question: read its log, then post the question, start the planner again, or move the card's phase ([a planner that ends without its question waits on the orchestrator](docs/adr/2026-11-11-1300-a-planner-that-ends-without-its-question-waits-on-the-orchestrator.md)); `unblocked`, a card past Todo whose block ended (a dep finished or `--blocked-until ""`), so act on what it waited for or set its Next, a thread line ending the wait ([an unblock past Todo waits on the orchestrator](docs/adr/2026-11-07-1500-an-unblock-past-todo-waits-on-the-orchestrator.md)); `recheck`, a ready Todo card whose block ended, which the pull leaves until you re-read its notes and answered questions against what landed, answer a stale one again with `question settle <id> --note` or send the card back with `item set --phase grilling`, then release it with `item set --phase ready --text "<what you re-checked>"` ([a block only keeps a card from In Progress](docs/adr/2026-11-09-1939-a-block-only-keeps-a-card-from-in-progress.md)); `stale` on a run, check the builder's process and log, then finish the run or restart it once from its worktree with one thread line, and if the restarted run goes stale too, `item stall` it with the reason; `stale` on a review, seven days in Review: find out why (CI red, a conflict, changes requested, reviewers silent), fix what you can (rebase, fix CI, answer comments), re-ping silent reviewers once in Slack, write one thread line, naming who when only a reviewer owes it, and ask the owner only when a decision is needed (close it, change reviewers), or `item stall` it. Once you pick up a stale review it wakes you again once a day, and sooner by `github-change` when anything changes on its PR. The waits list is your per-lane review; on the hub's morning wake, `check-github {reason: "morning"}`, also walk every lane top-down once: clear each blocked-until condition that holds and act on any card stuck with no wait. Report only in a thread line on each card you act on, nothing on the cards you pass over ([the orchestrator reviews every lane on a schedule](docs/adr/2026-11-06-1653-the-orchestrator-reviews-every-lane-on-a-schedule.md)). A line with `picked up` is one you started and didn't finish. The server appends `orchestrator-waits {added: [key], again}` when a card joins the list, a hand-back with calls included, and again for each card still waiting 15 minutes after its last wake, or an hour once you picked it up (a day for a stale review), so the event lines alone name every wait; it pushes the owner once about a card left waiting 30 minutes. A builder whose launch a usage pause holds is no wait: the board launches it when the pause lifts ([nothing waiting on the orchestrator is missed](docs/adr/2026-11-05-2358-nothing-waiting-on-the-orchestrator-is-missed.md)). The card reads waiting for orchestrator until your first write on it (a thread line, `builder verified`, a builder start, or the watcher's working mark on its event), then orchestrator review ([each lane is a queue for the orchestrator](docs/adr/2026-11-04-2300-each-lane-is-a-queue-for-the-orchestrator.md)).

## Reference

**Hub session.** Every board's session runs in the background; a hub board is optional. The hub board is the one board whose manifest entry has `hub: true`: `node $KF set <route> --hub` (or `join … --hub`, which `kickflip join --hub` in a repo folder passes) sets it and clears it from any other site, and `--no-hub` clears it. That flag only means its session runs in the foreground in the tmux session `kickflip-<route>`, which the hub starts when it wakes or restarts the board, with the same flags and phone permission hook as a background session. In the owner's terminal, `node $KF hub [--repo <dir>]` attaches to that tmux session, starting it first when none runs; while it runs, nothing starts another. **Prefix rule.** A served try build opens at its own `https://<host>:<port>/` origin, serves at `/` and needs no prefix or `KICKFLIP_BASE` ([a try build serves on its own Tailscale port](docs/adr/2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)). For sites joined to the hub, the hub strips `/<route>` before your server sees a request, but the browser still uses the full URL. So write links relative to the page (`notes.html`, `../claude.js`), or build them from a root the page computes. In the starter kit, `ClaudeSite.url('x')` derives that root from its own script URL. A root-absolute link (`/x`) leaves the site. Your server gets `PORT` and `PREFIX` in its environment and should serve paths with or without the prefix; a redirect `Location` starting with `/` gets the prefix added by the hub. A stray `/favicon.ico` request is harmless. A browser's page load of a site's page, a path ending in `/` or `.html`, gets the hub's app shell instead of reaching your server, and the shell shows the page in a same-origin frame beside the sidebar ([one app for the whole hub](docs/adr/2026-10-29-2005-one-app-for-the-whole-hub.md)). The frame's request, curl, an API call, an image and `?alone=1` (the frame's Open alone ↗) still reach your server; a board's server answers its four view paths with the shell too. So don't send `X-Frame-Options` or a `frame-ancestors` CSP that refuses the hub, or the frame stays blank. A page that starts its body with the board header (`<!--header …-->`) shows that header in place of the shell's.

**Browser writes.** The hub, board server and starter guard every non-GET/HEAD request with `starter/cross-site.mjs`: 403 when `Sec-Fetch-Site` is present and neither `same-origin` nor `none`, or when `Origin` is present and its host differs from `X-Forwarded-Host` (falling back to `Host`). The proxy preserves those browser headers and the external host. JSON body routes require `content-type: application/json`; hub settings forms keep form encoding, and uploads keep the file's type. Use same-origin URLs and `ClaudeSite.send` for events; use `fetch` with `keepalive` for JSON sent while leaving a page. - **Reactions:** every posted message about one PR (its links, a one-PR digest reply, and bumps sent before they stopped) gets `git_approved` once GitHub's review decision is APPROVED (a code owner's approval where the branch asks for one; any approval where it asks for none, [a chip per PR reviewer, and git_approved waits for GitHub's decision](docs/adr/2026-11-12-1400-a-chip-per-pr-reviewer-and-git-approved-waits-for-githubs-decision.md)), then `git_merged` on merge or `x` on a close. The header and a digest reply naming several PRs get none.
- **Digest:** “<board title> digest: <n> PRs pending your review”, with one item per PR, “<PR link> · <card title>”, plus “ (<n> days old)” for a link over two days old.

Each message is recorded as it posts. A failed send stays owed and goes again next poll; failures go to the hub log only. While Slack is not ready (no token, or Slack refused it), `review due` answers `waiting` and the hub sends nothing; a refused token pushes once while any board has reviewers. The digest is owed to each reviewer on weekdays from 09:00 to 17:00 in the Slack identity timezone (`board.mjs slack set --timezone Area/City`; with none set, the host timezone), until its header and every reply have gone; a day missed by 17:00 is skipped. `board.mjs slack` reads the identity in `~/.claude/kickflip/slack.json`.

**Reviewers ask the board in the day thread** ([reviewers ask the board in the day thread](docs/adr/2026-11-12-0000-reviewers-ask-the-board-in-the-day-thread.md)). The hub hears each day thread for 7 days after it opens, and each new message wakes you with a `slack-question {reviewer, channel, thread_ts, ts, from, answer}` event, which holds where the message is, never its words. `from` is `reviewer` or `owner`; the board's own posts and your answers wake nobody. Read it with `board.mjs --site <route> slack thread <event>`, which prints the thread and marks the message with →. With `answer: true` (every reviewer message, and the owner's when it names @kickflip), you may reply; you don't owe one. Reply only when the message asks something; a thanks or an acknowledgement gets nothing. Then do one of two things:
- **A question:** `slack answer <event> --text "<answer>"` posts your answer in the thread, at most 250 characters, and the Slack client adds the "- :claude_kickflip:" sign-off line itself. Keep it brief, and speak only about this board's cards, PRs and code. Answers stay in Slack; record nothing on the board.
- **A request for work**, whatever its size: `slack task <event> <file> --title <t> --notes-from <draft.md>` files a new card discussing for the owner's review, with the Slack message as its first thread line; reply on it as on any discussion. Never file a reviewer's request any other way, and never build it Quick. Then `slack answer` saying it is filed for the owner.

An owner's message with `answer: false` is context: read it, reply nothing. Until the token has `im:history`, the hub pushes once, the Integrations Slack row says to reinstall the app, and sends go on.

**You write in a day thread only when asked** ([a day thread carries only each PR's link](docs/adr/2026-11-12-0044-a-day-thread-carries-only-each-prs-link.md)): to answer a message there that asks something, or when the owner explicitly asks you to message a reviewer. Then `board.mjs --site <route> slack say <reviewer> --text "<words>"` posts the words, at most 250 characters and signed off the same way, in that reviewer's day thread for today, opening it with the "<board title> reviews" header when none is open. Never volunteer an update, a push, a comment or a status in Slack: a reviewer reads the PR on GitHub.

**Held Merge and PRs** ([a land waits for your Merge](docs/adr/2026-11-04-2100-a-land-waits-for-your-merge.md)). **Board sessions** ([the hub resumes a session only when nothing runs it](docs/adr/2026-10-29-1811-the-hub-resumes-a-session-only-when-nothing-runs-it.md)). The manifest records each site's session in its owner: the id, its folder (`repo`) and an optional model. `node $KF start <route> [--repo <dir>] [--model <m>] [--prompt <text>]` starts a background session (`claude --bg`) in the folder, named after the board, in auto mode, with `worktree.bgIsolation` set to `"none"` so it works in the repo folder; its builders make their own worktrees. Its first prompt is `/kickflip --name '<board name>'` plus the prompt. When the folder is a board repo the hub cloned, `start` first marks it trusted (`kickflip join` marks its own folder once, as it adds the board) in Claude Code's `.claude.json`, since `claude --bg` refuses an untrusted folder; it writes nothing when that file is missing or isn't valid JSON, and the start fails with the reason ([the hub trusts the clones it makes](docs/adr/2026-11-02-1549-the-hub-trusts-the-clones-it-makes.md)). On a route with no site yet, the session waits in the manifest's `starting` until it joins. `node $KF resume <route>` runs `claude --resume <id> --bg` in the recorded folder, with no other flags for a background session so it wakes in place under its id, tells the session to rejoin and relaunch its watcher, and records the id it comes back under as the owner, keeping its label, model and folder. `node $KF sessions` prints each board's route, session, whether it is live (in the background or a terminal) and its folder. A session is live while a `~/.claude/sessions/<pid>.json` record names it and that process runs; `start` and `resume` refuse a live session (exit 3), so a terminal session never gets a second process. A board listens only while its session is live and a watcher runs for it. Claude Code stops a background session that has idled unattached for about an hour; it stays stopped until an event lands for its board, and then the hub resumes it at once, as `resume` does. As a fallback, a board not listening for 3 minutes whose session hasn't heard an event is resumed too. Either happens once per outage, and if the board still isn't listening 5 minutes later, the hub pushes "<title>'s session didn't come back" once. A board whose owner has no folder recorded is never resumed ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md)). A session the hub starts or resumes also gets a `PermissionRequest` hook (`hub/permission-hook.mjs`), so its permission prompts and `AskUserQuestion`s, which have no terminal to show in, come to the owner's phone: the hub pushes "<title> wants to <action>", or the question, and the board's Needs you shows the pending prompt with Allow once, Always allow and Deny, or the question's options. Always allow returns a session rule to Claude Code and keeps the same rule in the hub's `prompts.json`, keyed by session id. The hub remembers rules only with a reliable process start time and binds board rules to the current ownership's `owner.since`; ownership commands clear remembered rules and pending prompts for both the old and new sessions, including boardless entries, even while the hub is stopped. The hub immediately allows a later exact match on its command, absolute path, domain or bare tool name, with no push or Needs you line; prefixes and globs never widen a match, and `AskUserQuestion` always asks. The remembered rules end when that session stops or the board's owning session changes, and the hub page lists them read-only under the board. With no answer in 10 minutes, the call is denied with a note telling you to ask on the card instead: do that, with `question add` on the card's topic. A session started by hand in a terminal keeps its own dialog ([a background session's prompts and questions come to the phone](docs/adr/2026-10-30-1516-background-sessions-prompts-come-to-the-phone.md)). Board settings' Permissions switches (push main after a land, push release tags, open draft PRs) write allow rules into the board folder's `.claude/settings.local.json`, which your session picks up live; only the signed-in owner can change them, from any device signed in to Tailscale as the owner ([only the signed-in owner changes permissions or restarts](docs/adr/2026-11-04-0502-only-the-signed-in-owner-changes-permissions-or-restarts.md)). A `PermissionDenied` hook (`hub/permission-denied-hook.mjs`) notes under its switch a command auto mode still refused ([board settings grant a board's session permissions](docs/adr/2026-11-03-1921-board-settings-grant-a-boards-session-permissions.md)).

**Reviewing PRs.** When Board settings' Approve PRs switch is on for a board, its session may run `gh pr review` (approve, request changes or comment), and only on a PR the owner names on the board; it never reviews on its own initiative. **Closing a board** ([a closed board keeps its folder and can be reopened](docs/adr/2026-10-31-1603-a-closed-board-keeps-its-folder-and-can-be-reopened.md)). On the owner's request, `node $KF close <route> --name '<exact board title>'` stops its session, ends its running builder records with a note and removes its server and sidebar row. Its folder, cards, threads and notes stay on the host; its PRs stay open on GitHub, with no polling from this board. Board Settings has the same action with an active-work warning and a typed-name confirmation. A board whose session is also recorded by another active board cannot be closed. The Hub page’s Closed boards row lists closed boards; `node $KF reopen <route>` restores the saved manifest entry and resumes its recorded session. A closed route stays reserved; use Reopen rather than join or start. A failed resume keeps the board on the closed list for retry. Reopen rewinds to the watcher position saved before Close, so an event delivered near Close may be replayed.

**Moving a board to another host.** On the owner's request, once no builder is open on the board, `node $KF export <route> [--out <file>]` writes one .tgz: the board's folder, its manifest entry without this host's folder, port, command, owner session or restart times, the hub's Notifications, Quiet hours and Codex share settings, and a README.md of the steps. No API key, integration file, GitHub or Codex sign-in, or other hub setting goes in; the README lists what to set up again. It moves only a board whose cards live in its own folder. On the new host, after `kickflip init`, `kickflip import <file>` unpacks the board into `~/.claude/kickflip/sites/<route>/`, adds its entry with a free port, writes those settings over that host's, and prints the `join … --force` line a fresh session there runs to take the board over. It refuses a route that host already has. The old host keeps its copy until the owner leaves it there.

**Leaving.** `node $KF leave <route> --session <id>` removes the entry; the hub stops the site and keeps its files. A plain page needs no `--session`. It does not stop the session or record a closed board for Reopen. Leave only when the user asks.
