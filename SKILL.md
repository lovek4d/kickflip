# kickflip

One **hub** on the host answers `https://<host>.<tailnet>.ts.net/` for every site. It reads `~/.claude/kickflip/manifest.json`, lists every site in a sidebar beside each board, forwards `/<route>/…` to each **site**'s port with the prefix stripped, and runs each site's `cmd`, restarting it when it exits or when its entry changes. The host's service manager keeps the hub up across logins and session restarts: launchd on macOS, a systemd user unit on Linux. A site joined with a session has one **owner** session, the only one woken by its events; a **plain page** has none. The hub never manages sleep: a sleeping host answers nothing.

`KF=~/.claude/skills/kickflip/bin/kickflip.mjs`; run it with `node`. Its header comment lists every command and flag.

## Install on a new host

The host is a Mac or a Linux machine. With Git, Node 22+, Claude Code, gh and Tailscale installed (and tmux, for a hub board's session only), and HTTPS certificates turned on for the tailnet (the hub's `tailscale serve` needs them), install kickflip from public npm:

```sh
npm i -g @lovek4d/kickflip
kickflip init
```

`init` is the first-run name for `doctor --fix`; both run the same steps and finish with a doctor report. Init links `~/.claude/skills/kickflip` to the installed package's folder (with `npm link` from a clone, to the clone) and `~/.claude/skills/kickflip-hooks` through `kickflip/hooks-plugin/`. Correct skill links are checked and kept. A real folder is accepted only when it is the target itself. A skill link pointing elsewhere, including a broken link, is refused with a message; move an existing real folder or explicitly remove a wrong link before retrying. `--force` does not bypass these checks.

`kickflip update` runs `npm i -g @lovek4d/kickflip@latest`, then restarts the hub. It refuses a clone; update that with `git pull`. An npm install's hub checks npm for a newer version as it starts and hourly; the sidebar's New version row then reads Update available · Upgrade, which runs `kickflip update` once no builder runs (Update waits for 2 builders meanwhile); the reload row follows when the new hub runs. A clone never shows it ([the hub offers a newer kickflip from npm](docs/adr/2026-11-03-1521-the-hub-offers-a-newer-kickflip-from-npm.md)).

For development, clone the private repo, run `npm install`, `npm link`, then `kickflip init`. `npm run build` makes the minified package in `dist/`, which is what gets published. To release, when the owner asks: run `npm version <x.y.z>` in the clone, then `git push origin main v<x.y.z>`. The tag runs `.github/workflows/release.yml`, which runs the suite, builds, checks the tag against `dist/package.json`'s version, smoke-installs the packed `dist/` and publishes it to npm by trusted publishing ([a v* tag publishes kickflip to npm](docs/adr/2026-11-03-1345-a-v-tag-publishes-kickflip-to-npm.md)).

Init also links `~/.claude/statusline.sh` through `kickflip/bin/statusline.mjs`, replacing a dangling link, a link into `~/.claude/kickflip/sites/` (a status-line prototype) or one pointing directly at the running package folder or clone. A real file or another working status-line link is refused. It adds `statusLine` to `~/.claude/settings.json` only when absent; an existing choice stays, with a note if it points elsewhere. Settings writes preserve other keys, and init removes only commands for the old `~/.claude/hooks/no-paths.py` when that script is missing. Rerunning checks the links and skips unchanged settings. The status line prints directory, branch (with `*` for tracked changes), model, context percentage and Claude's usage (`5h 23% · 7d 57%`), then atomically saves Claude's rate-limit reading in `~/.claude/kickflip/usage.json` for the hub. The plugin supplies Codex sharing and pause line reminders on SessionStart and UserPromptSubmit, denies new Agent/Task calls while paused, and supplies builder cleanup on SubagentStop; it adds no settings.json hook entries. Init adds the watcher Stop hook, `hooks-plugin/hooks/watcher-stop.mjs`, to settings.json's `Stop` hooks, which the plugin can't supply, and doctor reports it missing. Doctor lists the hub’s try ports and their board/card or main; on Linux a non-root hub user needs `sudo tailscale set --operator=$USER` if doctor reports an operator mismatch ([a try build serves on its own Tailscale port](docs/adr/2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)). Setup needs no dotfiles scripts ([kickflip installs its own status line and hooks](docs/adr/2026-11-01-1322-kickflip-installs-its-own-status-line-and-hooks.md)). `uninstall` removes kickflip's status-line link along with the hub's service and Tailscale mapping; skill links, Claude settings and live state stay.

Kickflip doesn't ship `wave-build`, `slack-bridge` or `codex-share`; init doesn't add them and doctor doesn't check them. The mattpocock skills an architecture review follows, improve-codebase-architecture, codebase-design, grilling and prototype, are a prerequisite kickflip doesn't pin: init adds any that are missing with the skills CLI (`npx skills add mattpocock/skills -g -y -a claude-code --skill …`), and doctor marks a missing or out-of-date one optional with the command that fixes it (`shared/skills.mjs`). The `monitor` skill is optional: the hub polls GitHub itself and, when Hub's Linear key is set, moves the owner's Linear tickets from PR state ([the hub's poll moves the owner's Linear tickets](docs/adr/2026-11-02-0023-the-hubs-poll-moves-the-owners-linear-tickets.md)); without a key it moves none. The session leaves these PR-based moves to the hub. This skill's GitHub tick handles `github-change`, `check-github` and `card-merge`. When the owner's monitor skill is installed, a session may run its tick instead, which can add its own steps; kickflip owns the reviewer steps below.

The same command installs the hub's service, which starts the hub through the `~/.claude/skills/kickflip` link, starts it, and maps Tailscale `/` to it. `shared/service.mjs` picks the service by platform: on macOS a launchd login item, `~/Library/LaunchAgents/local.claude.kickflip-hub.plist`; on Linux a systemd user unit, `~/.config/systemd/user/kickflip-hub.service`, enabled and started with `systemctl --user`. A user unit stops with the owner's last login session unless the user lingers, so on a server run `sudo loginctl enable-linger "$USER"` once; doctor notes it ([the hub runs under the host's service manager](docs/adr/2026-11-01-1542-the-hub-runs-under-the-hosts-service-manager.md)). Live state (manifest, sites, settings and builder worktrees) stays in `~/.claude/kickflip/`. Paths saved for later use inside the kickflip package folder or clone go through `~/.claude/skills/kickflip` when that link resolves to the running root, including board commands, session hooks and prompts, session folders and builder records; moving the folder and repointing that link keeps them valid. `storedPath()` in `bin/install.mjs` owns this conversion; paths used only while code runs can stay real. Board repo clones live in `~/.claude/kickflip/repos/<owner>/<repo>`, or `<host>/<path…>` there for a repo on another git host, whether kickflip runs from a clone or an installed package; `shared/repos.mjs` owns the base path. Doctor lists each clone left in an old place (a clone's `.repos/`) as optional, naming the boards that use it, and `doctor --fix` asks in a terminal whether to remove each one ([board clones live outside the package](docs/adr/2026-11-04-0103-board-clones-live-outside-the-package.md)). `.repos/` stays gitignored and excluded from land's test suite along with `node_modules/` ([kickflip ships as a minified npm package](docs/adr/2026-11-01-2247-kickflip-ships-as-a-minified-npm-package.md)).

## Prereqs

`node $KF doctor` checks Git; Node on the PATH this Claude Code session inherited; gh installed and signed in; Git reaching GitHub over https with gh's token, as the hub clones; Tailscale installed, signed in and serving `/` to the hub; an optional Codex, installed on that PATH and logged in (`~/.codex/auth.json`); the optional mattpocock skills, installed and matching their source's tree in `~/.agents/.skill-lock.json`; and an optional tmux, which only a hub board's session needs. It also checks the kickflip and kickflip-hooks links, `~/.claude/statusline.sh`, `statusLine` in Claude settings, the running hub service (the login item on macOS), the hub and every site, and each board's repo as the hub fetches it, with Git's own login (`git ls-remote --exit-code origin HEAD` from the repo), which can fail while gh's token reaches GitHub; on Linux also whether the user lingers and what reads differently off macOS. It changes nothing. Install hints name Homebrew on macOS and apt elsewhere, with Tailscale's install script and `npm i -g @openai/codex` where apt has no package. Each line is `<mark> <item>: <detail>`, marked **ok**; **fixable**, which `kickflip doctor --fix` sets up; **yours**, which only the person can fix; **optional**, Codex, needed only for Codex builds and reviews, the mattpocock skills, needed only for architecture reviews, or tmux, needed only for a hub board's session; or **note**, a down site the running hub restarts. A fixable, yours or optional line is followed by `→ <command>`. `--json` prints `{items: [{group, item, state, detail, fix}]}`. Exit 1 means something is fixable or yours.

## Add a repo as a board

In a terminal in a git repo's folder, the owner runs `kickflip join`. It asks for the board name, default the folder's name, in letters, digits and spaces; the route is the name lowercased with dashes for spaces. It makes a board from the board template, records the folder's GitHub origin and branch, marks the folder trusted for Claude Code, and starts the board's session in the background, as New board does; `--hub` flags it as the hub board and starts its session in the foreground in tmux instead, attaching that terminal to it ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)). Its builders branch from the folder's local `main` and `land` there. It refuses a folder outside git, says to run `kickflip init` while the hub isn't running, and for a folder that already has a board names it and offers to restart its session. With no terminal, pass `--name "<Board name>"` ([kickflip join adds the current repository as a board](docs/adr/2026-11-03-0248-kickflip-join-adds-the-current-repository-as-a-board.md)). A session doesn't run this form; it joins with `--session` as in the steps below.

## Join a page

Every join names its site with `--name "<name>"`, which gives its title and its route, the name hyphenated; a name that is the route itself keeps the site's title.

To put a page on the owner's phone with nothing for Claude to answer, join it as a plain page. It needs no session id, owner, watcher or needs.json ([a page joins without a session](docs/adr/2026-11-01-1446-a-page-joins-without-a-session.md)).

- **A server this session runs:** `node $KF join --name "<name>" --port <n>`. The hub forwards `/<route>/…` to that port with the prefix stripped. It doesn't run or restart the server, so while nothing answers the page reads Down.
- **Plain files:** `node $KF join --name "<name>" --dir <folder>`. The hub serves the folder itself, a folder's `index.html` included, and refuses any path with a part starting with `.`.
- **A server the hub runs:** add `--cmd '["/abs/node","/abs/server.mjs"]'` to `--dir`, with `--port` if it has a fixed one. The hub starts and restarts it, as for any site.

`join` prints `{route, url, serves, …}`; give the owner the `url`. The page shows under Pages in the sidebar, in a frame beside the hub's header and sidebar. Follow the prefix rule below. `--description`, `--icon` and `--color` work as in step 3. A rejoin passes `--port`, `--dir` or `--cmd` again, since a join with none of them and no `--session` adds the cwd's repo as a board. `node $KF leave <route>` takes the page off and keeps its files. Exit 3 means a session owns that route. For a page that wants Claude to answer it, with events, the watcher and the Needs you badge, follow the steps below instead.

## Steps

These make a site Claude answers: a board, or a page joined with `--watch`.

1. **Who you are.** Your session id is the directory name just above your scratchpad (`…/<session-id>/scratchpad`). Your label is the session's name if it has one, otherwise two or three words for its work.
2. **Hub up.** Run `node $KF doctor`. When anything is fixable, ask the user once (it adds the hub's service, a login item on macOS or a systemd user unit on Linux, maps Tailscale `/` to the hub and sets up kickflip's status line and hooks as above), then run `node $KF doctor --fix` and read its new report. For anything marked yours, tell the person the printed command; a foreign status line needs their explicit replacement. Done when doctor exits 0; optional and note lines can be left to the person. See [doctor checks and fixes a hub](docs/adr/2026-11-01-1433-doctor-checks-and-fixes-a-hub.md).
3. **Join.** Run `node $KF join --name "<Board name>" --session <id> --watch --label <label> --description "<one line>"`. The board name is the `--name` your first prompt gave (`/kickflip --name '<Board name>' …`, plus any join flags after it, which you pass on), else the route you were given, which keeps the site's title; the route is the name hyphenated. A new route copies the starter kit into `~/.claude/kickflip/sites/<route>/`, picks a free port from 4600, and the hub starts it within 2 seconds. An existing route keeps its files and command. To serve an existing project, pass `--dir` and `--cmd '["/abs/node","/abs/server.mjs"]'`, and `--port` if it has a fixed one. `join` also records the session's folder (`--repo`, by default the session's own cwd) and an optional `--model`, which `start` and `resume` use (Board sessions, below).
   - **Icon** ([site icons are line icons from a built-in set](docs/adr/2026-10-29-1639-site-icons-are-line-icons-from-a-built-in-set.md)). The sidebar draws each site's row with a line icon from `hub/icons.mjs` on a tint of the site's color. Pass `--icon <key>`, such as `phone` or `book` (`--icon x` lists the keys), and `--color <css hex>`. Without a key the hub picks an icon from words in the route and title, else shows the title's first letter, on a color picked from the route. `node $KF set <route> --icon … --color …` changes them later without joining.
   - **A board** (Linear-style lanes of PRs and tickets, item threads, questions for Love): add `--template board`, plus `--items <file>` when the items come from the site's own wave.json-format file rather than every `~/.claude/waves/*/wave.json`. At each session start after joining, run `board.mjs --site <route> integrations report --slack yes|no`: yes when Claude’s Slack connector tools such as `slack_send_message` are available in this session, no otherwise ([integrations show readiness, and features wait until theirs is ready](docs/adr/2026-11-02-1118-integrations-show-readiness-and-features-wait.md)). The site then runs the shared `board/` code, whose `server.mjs` header documents `board.json` and the API. Every board shares that code, so make board changes in `board/` and copy none of it into a site. A site's `public/` holds only its own files, such as prototype pages, and any page it overrides. Changes to the hub or the board template come in as asks on the hub board ([hub changes come as asks, not Improvements rounds](docs/adr/2026-10-29-1639-hub-changes-come-as-asks-not-improvement-rounds.md)).
   - **Exit 3 means another session owns it.** Ask the user with AskUserQuestion: take it over (recommended when the old session has ended or the user asked for this), or leave it. On yes, rerun with `--force`. The takeover is total: the old owner's watcher prints `handed-over` and that session stops serving the route.
4. **Build or resume the site.** Done when `curl -s -o /dev/null -w '%{http_code}' <url>` returns 200 for each page you changed, and a page meant for the phone renders at 390px wide with no sideways scroll. Follow the prefix rule below. The page design is yours; the starter's `public/index.html` is a placeholder.
5. **Watch.** Run the `watcher` command `join` printed as a background Bash task. It exits on the next event. For each `event` line, relaunch the watcher first, then act and reply (below). Its cursor means no line is missed. The board reads "not listening" while no watcher runs in your running session, or while your session isn't running and the hub can't wake it. A background session that idles out reads asleep, in grey, and the hub resumes it when the next event lands or the owner taps the board's page, the header's refresh included; the header reads waking… until it listens ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md), [boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)). On `handed-over` or `site-removed`, stop; don't relaunch. Tell the user. The Stop hook `hooks-plugin/hooks/watcher-stop.mjs` keeps a turn from ending once while a board your session owns has no live watcher, naming the command to relaunch, or while a message there reads Working on it with no answer, naming each ([the CLI and board server do the board's housekeeping](docs/adr/2026-11-02-2044-the-cli-and-board-server-do-the-boards-housekeeping.md), [the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)). On a board, follow the `quiet` line the watcher prints on every wake: the terminal gets only the one-liners `board.mjs` and the watcher print, except in answer to a prompt typed there.
6. **Record** the watcher's task id, and the site's route and URL, in your scratchpad `watchers.md`, with how to restart them after a session restart: rerun step 3 with the same `--name` and `--session`, then step 5. When the hub resumes a session, it asks for exactly that, naming the id to rejoin with; use that id, since a resumed session can come back under a new one. A rejoin keeps the label, model and folder it leaves out.

## Reference

**Hub session.** Every board's session runs in the background; a hub board is optional. The hub board is the one board whose manifest entry has `hub: true`: `node $KF set <route> --hub` (or `join … --hub`, which `kickflip join --hub` in a repo folder passes) sets it and clears it from any other site, and `--no-hub` clears it. That flag only means its session runs in the foreground in the tmux session `kickflip-<route>`, which the hub starts when it wakes or restarts the board, with the same flags and phone permission hook as a background session. In the owner's terminal, `node $KF hub [--repo <dir>]` attaches to that tmux session, starting it first when none runs; while it runs, nothing starts another. The session follows [docs/hub-session.md](docs/hub-session.md). tmux is needed only for a hub board; `kickflip doctor` lists it as optional ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)).

**Words and decisions.** [CONTEXT.md](CONTEXT.md) is the glossary for the hub and boards. [docs/adr/](docs/adr/) records why each hard-to-reverse choice was made. Read the ADR before changing what it covers. When the owner settles a new one, in an ask or a card's question, add an ADR with the domain-modeling skill, named by the minute you write it, `docs/adr/YYYY-MM-DD-HHMM-<slug>.md`, never by a number. Prose and comments link an ADR with its title as the link text, as in [a build tap starts the build in the board server](docs/adr/2026-11-03-0219-a-build-tap-starts-the-build-in-the-board-server.md).

**Prefix rule.** A served try build opens at its own `https://<host>:<port>/` origin, serves at `/` and needs no prefix or `KICKFLIP_BASE` ([a try build serves on its own Tailscale port](docs/adr/2026-11-01-2254-a-try-build-serves-on-its-own-tailscale-port.md)). For sites joined to the hub, the hub strips `/<route>` before your server sees a request, but the browser still uses the full URL. So write links relative to the page (`notes.html`, `../claude.js`), or build them from a root the page computes. In the starter kit, `ClaudeSite.url('x')` derives that root from its own script URL. A root-absolute link (`/x`) leaves the site. Your server gets `PORT` and `PREFIX` in its environment and should serve paths with or without the prefix; a redirect `Location` starting with `/` gets the prefix added by the hub. A stray `/favicon.ico` request is harmless. A browser's page load of a site's page, a path ending in `/` or `.html`, gets the hub's app shell instead of reaching your server, and the shell shows the page in a same-origin frame beside the sidebar ([one app for the whole hub](docs/adr/2026-10-29-2005-one-app-for-the-whole-hub.md)). The frame's request, curl, an API call, an image and `?alone=1` (the frame's Open alone ↗) still reach your server; a board's server answers its four view paths with the shell too. So don't send `X-Frame-Options` or a `frame-ancestors` CSP that refuses the hub, or the frame stays blank. A page that starts its body with the board header (`<!--header …-->`) shows that header in place of the shell's.

**Browser writes.** The hub, board server and starter guard every non-GET/HEAD request with `starter/cross-site.mjs`: 403 when `Sec-Fetch-Site` is present and neither `same-origin` nor `none`, or when `Origin` is present and its host differs from `X-Forwarded-Host` (falling back to `Host`). The proxy preserves those browser headers and the external host. JSON body routes require `content-type: application/json`; hub settings forms keep form encoding, and uploads keep the file's type. Use same-origin URLs and `ClaudeSite.send` for events; use `fetch` with `keepalive` for JSON sent while leaving a page. Node callers may omit both browser headers. `/_hub/build` also requires loopback and refuses every Origin and forwarded header.

**Starter kit** (`~/.claude/skills/kickflip/starter`): `server.mjs`, Node with no dependencies, serving `public/` plus the event API; `cross-site.mjs`, the guard copied with it and shared by the hub and board; `public/claude.js`, the browser side; `public/index.html`, a placeholder. Their header comments document the API. A rejoin doesn't recopy the starter, so an existing site keeps the server it was copied with.
- A page sends `ClaudeSite.send(kind, data)`. That appends one line to `data/events.jsonl`, which wakes the owner.
- You **reply** to event `<id>` by writing `data/replies/<id>.html` (an HTML fragment) or `.json`. `ClaudeSite.watch(fn, {kind})` shows it on the page within 10 seconds.
- Keep replies short first, with depth behind `<details>`.
- `GET /_claude/needs` returns what waits on the owner, from `data/needs.json` (`{items: [{kind, text, url}], working?, summary?}`, `url` relative to the site root). Write that file when something starts or stops waiting on the owner, or when you start or finish the owner's message (`working` counts those in progress). Without it the site reports nothing waiting.

**What waits on the owner** ([sites report what waits on the owner through `GET /_claude/needs`, and the hub reads only that](docs/adr/2026-10-29-1639-sites-report-what-waits-through-claude-needs.md)). Any site with an owning session may serve `GET /_claude/needs` as above; the hub never asks a plain page: `kind` is a short label such as "Question" or "Tap Ready", and an empty `items` means nothing waits. The sidebar badges each running site's row with the count, and the hub caches it for about 20 seconds. The row's sub line leads with a status word (Down, not listening for a board that isn't listening and the hub can't wake, Starting, "N need you" while anything waits, Working while `working` is above 0 and nothing waits, waking… for one whose session the hub is resuming, asleep for one whose stopped session the hub wakes on the next event or a tap on its page, Building), then a board's optional `lanes` `{review, progress, todo}` as chips; `building` is true while a builder works on a card ([the hub home shows status, not descriptions](docs/adr/2026-10-29-1639-the-hub-home-shows-status-not-descriptions.md)). The sum over every site is the Home Screen app's badge (`/_hub/needs.json`). A site that doesn't serve it, errs, or takes over 1.5 seconds counts as unknown and gets no badge. Another server can serve it to get a badge.

**Sidebar, app shell and hub page** ([a sidebar of every board replaces the hub home](docs/adr/2026-10-29-1639-a-sidebar-of-every-board-replaces-the-hub-home.md), [one app for the whole hub](docs/adr/2026-10-29-2005-one-app-for-the-whole-hub.md)). On that event, use the new repo and branch for new builders and GitHub links, reply to acknowledge the change, and leave existing builders' worktrees intact. Keep the shared clone's checkout in place. Resume uses the newly recorded folder.

**Main pulls** ([a local board's Main pulls from origin on its own](docs/adr/2026-11-03-1914-a-local-boards-main-pulls-from-origin-on-its-own.md)). Each poll fast-forwards a local board's branch from origin, and Main's refresh icon pulls now; a pull that can't fast-forward turns the icon red with its reason. A pull that brought commits sends `main-pulled {branch, from, to, commits}`. Act on it only as a board rule says; with no rule, there is nothing to do.

**Tickets** ([a board has one ticket source](docs/adr/2026-11-01-1348-a-board-has-one-ticket-source.md)). Each board’s `board.json` `tickets` selects Internal with a 2–6 uppercase letter prefix (empty or absent means INT), GitHub issues in its repo (only when that repo is on GitHub), or Linear with workspace, team and project. New board and Board Settings share that choice, and `settings set tickets <json>` sets it. A GitHub source's optional `account` runs its issue calls as that gh login, with the token from `gh auth token -u`; other gh calls stay on the active account, and a login gh doesn't have fails the ticket call. The hub board's repo is its entry's `github`, recorded from its folder's origin like any joined board's ([boards run in the background, sleep and wake from the page, and the hub board runs in tmux](docs/adr/2026-11-03-0313-boards-run-in-the-background-and-the-hub-board-in-tmux.md)). `item add` creates a ticket from the title and notes unless `--ticket <id>` links an existing one after checking its prefix, team or GitHub repo. A card reads as its ticket from the board's source (`#27`, `ENG-12`, `INT-5`) while its key keeps its id ([a card is named by its board's ticket source](docs/adr/2026-11-02-2100-a-card-is-named-by-its-boards-ticket-source.md)). `item set --ticket <id>` links one too. Internal takes the next board number, or an internal wave card's own id (`INT-200`, or `S12` as `INT-12`); GitHub uses `gh issue create`. Linear works through Hub's Linear key ([kickflip reaches Linear with a key on the Mac](docs/adr/2026-11-01-1436-kickflip-reaches-linear-with-a-key-on-the-mac.md)), kept in `~/.claude/kickflip/linear.json` (mode 600) and never sent to a page: the Tickets control lists its teams and projects, New board's New project… is created on Start, `item add` creates the issue in the board's team and project, and `--ticket TEAM-n` must exist in that team. New board and Board Settings pick Linear only while the key works: tapping Linear without one opens Hub's Linear key field inline in Board Settings, whose Tickets row reads its state as a status word such as `linear · connected` or `internal · no Linear key`, and the key modal over New board; the hub remembers a key Linear refused ([a board picks Linear only while Hub's key works](docs/adr/2026-11-02-1712-a-board-picks-linear-only-while-hubs-key-works.md)). `settings set tickets` refuses Linear without the key too, and once the key is removed the hub moves every Linear board to internal tickets, with a `settings {tickets}` event; cards keep the tickets they have ([every new card gets a ticket in the board’s current source](docs/adr/2026-11-04-0227-every-new-card-gets-a-ticket-in-the-boards-current-source.md)). Every way a card is made gets its ticket in the source at that moment, and a card is never left without one: when the source can’t make it, the command fails and writes nothing. An Internal ticket another card holds is refused. An ask, including an answered ask, gets none; `item set --from-ask` creates one if the card has none. A source change touches only new cards: move old cards to the new source only when Love asks for it, as its own task. A card’s badge shows only a ticket from the board’s current source; a stored ticket from another source shows its own id, unlinked, never relabelled. A `settings {tickets}` event means the source changed; acknowledge it. Existing boards without a source keep their legacy badges until configured; `board.mjs tickets backfill [--dry-run]` then links the ids in open cards' titles and creates the rest, including for an internal wave's card whose ticket is its own id. `item set` moves the card's ticket one way (building or fixing → In Progress, `--pr` → In Review, done or merged → Done, closing a GitHub issue) when the owner is assigned it or kickflip created it, printing a `ticket <id>: …` line; a failure never blocks the status change.

## Reviewers

Kickflip owns reviewer links, reactions and weekday digests ([kickflip owns the reviewer record](docs/adr/2026-11-01-2347-kickflip-owns-the-reviewer-record.md)). `slack-bridge` is optional: kickflip reads its topic files only as a fallback. Each board's `board.json` and each wave keep `reviewers: [{name, slack_user, dm, github}]`; new waves copy the board's list. On a `reviewers {add}` event, find each added person's Slack user, DM channel and GitHub login, run `board.mjs --site <route> reviewers add --file <json>` (`reviewers set --file` replaces the list), which also copies the list to unfinished waves, send added reviewers every PR already in review using the steps below, then reply to the event. The board server removes reviewers itself; its `reviewers-removed {remove}` event is a record, so take no action on it ([the board server removes reviewers itself](docs/adr/2026-11-04-0119-the-board-server-removes-reviewers-itself.md)).

Reviewer DMs and digests wait on Slack. Before steps 1–3, run `board.mjs --site <route> review due`: it lists the reviewer DMs (`dms`), `git_merged` reactions (`reactions`) and digest (`digest`) still owed, each with the `record` command to run once it is sent, and sends nothing ([the board records what it knows, and commands make the rule calls](docs/adr/2026-11-03-0003-the-board-records-what-it-knows-and-commands-make-the-rule-calls.md)). While Slack is not ready it answers `waiting` saying why and nothing else: skip those steps and leave the reviewer record unchanged. Read hub Slack identity with `board.mjs slack`: `self_dm`, `owner_slack_user`, `slack_domain`, `timezone` in `~/.claude/kickflip/slack.json`. On an empty setting it imports slack-bridge's config once. Set it with `board.mjs slack set --self-dm D… --user U… --domain <workspace> --timezone Area/City`. Top-level Slack prose starts with “🤖 ”; a ready-for-review DM is the bare PR link alone, without a prefix or extra text.

1. **Ready for review.** For each of `review due`'s `dms`, use Claude's Slack connector `slack_send_message` to its `channel` with its `text`, the bare PR URL alone. Then run its `record` with the message ts: `board.mjs --site <route> review sent <wave>/<id> <reviewer> --ts <message ts> --channel <dm>`. This writes the item's `review_link_ts: {<name>: {ts, channel}}`, shared by the chips, review age, Stale lane and hub link. Check the command succeeded before treating the send as recorded.
2. **Changes and merge.** After a behavior change, reply under each recorded link for reviewers who haven't approved: “🤖 Updated: <what changed>”. Changes only to comments, names, docs or tests stay silent. For each of `review due`'s `reactions`, use `slack_add_reaction` with `channel_id` its `channel`, `message_ts` its `ts`, and `emoji` `git_merged`. Then run its `record`, `board.mjs --site <route> review react <wave>/<id> <reviewer> git_merged`. It records each reaction once. A reaction on Slack must succeed before recording it.
3. **Morning digest.** A `digest` in `review due` is `review digest`'s answer while one is due; it reads local PR state without calling GitHub. Send each returned reviewer a top-level message to their `dm`: “🤖 <board title> digest: <n> PRs pending your review”. For each item, send a thread reply under that message: “<PR link> · <title>”, appending “ (<n> days old)” only when `days_old` is set. Then run `board.mjs --site <route> review digest sent <reviewer> --ts <top-level ts> --channel <dm> --items <key,key>`. Send every reviewer returned by that digest before reading `due` again: the first recorded send marks the board's date sent. Digests are due weekdays from 09:00 in the Slack identity timezone; with no timezone set, they use the host timezone.

**Rules** ([rules live on Settings, at hub and board level](docs/adr/2026-10-29-1639-rules-live-on-settings-at-hub-and-board-level.md)). On a board, the watcher prints `rule hub <text>` and `rule board <text>` lines after the `event` lines. They are the owner's standing instructions: follow them as you follow this skill. Hub rules apply to every board, and the board's own come on top. A `rules {scope, added, edited, removed}` event means the owner saved them on hub or board Settings. Read the printed list, then write one reply (`board.mjs reply <eventId>`, shown under the Rules section) saying what you will do differently. When the owner says "codify" in a thread, run `board.mjs --site <route> rules add --by claude --text "<the rule>"`. Add it at board level unless it concerns every board; then pass `--hub`. `rules list` shows both lists with their ids, for `rules edit` and `rules remove`.

**Auto-merge** ([Auto-merge is a board setting, off by default, and the owner merges from the card](docs/adr/2026-10-29-1752-auto-merge-is-a-board-setting-off-by-default.md)). A board's `auto_merge` setting, off unless set, decides who merges an approved PR: on, the GitHub tick does; off, the card shows the owner Merge, and the session merges on its `card-merge` event. The watcher prints `setting auto-merge on|off` after the `rule` lines. **Board sessions** ([the hub resumes a session only when nothing runs it](docs/adr/2026-10-29-1811-the-hub-resumes-a-session-only-when-nothing-runs-it.md)). The manifest records each site's session in its owner: the id, its folder (`repo`) and an optional model. `node $KF start <route> [--repo <dir>] [--model <m>] [--prompt <text>]` starts a background session (`claude --bg`) in the folder, named after the board, in auto mode, with `worktree.bgIsolation` set to `"none"` so it works in the repo folder; its builders make their own worktrees. Its first prompt is `/kickflip --name '<board name>'` plus the prompt. When the folder is a board repo the hub cloned, `start` first marks it trusted (`kickflip join` marks its own folder once, as it adds the board) in Claude Code's `.claude.json`, since `claude --bg` refuses an untrusted folder; it writes nothing when that file is missing or isn't valid JSON, and the start fails with the reason ([the hub trusts the clones it makes](docs/adr/2026-11-02-1549-the-hub-trusts-the-clones-it-makes.md)). On a route with no site yet, the session waits in the manifest's `starting` until it joins. `node $KF resume <route>` runs `claude --resume <id> --bg` in the recorded folder, with no other flags for a background session so it wakes in place under its id, tells the session to rejoin and relaunch its watcher, and records the id it comes back under as the owner, keeping its label, model and folder. `node $KF sessions` prints each board's route, session, whether it is live (in the background or a terminal) and its folder. A session is live while a `~/.claude/sessions/<pid>.json` record names it and that process runs; `start` and `resume` refuse a live session (exit 3), so a terminal session never gets a second process. A board listens only while its session is live and a watcher runs for it. Claude Code stops a background session that has idled unattached for about an hour; it stays stopped until an event lands for its board, and then the hub resumes it at once, as `resume` does. As a fallback, a board not listening for 3 minutes whose session hasn't heard an event is resumed too. Either happens once per outage, and if the board still isn't listening 5 minutes later, the hub pushes "<title>'s session didn't come back" once. A board whose owner has no folder recorded is never resumed ([a board's session wakes when an event arrives, and live means its session runs](docs/adr/2026-10-30-1601-a-boards-session-wakes-when-an-event-arrives.md)). A session the hub starts or resumes also gets a `PermissionRequest` hook (`hub/permission-hook.mjs`), so its permission prompts and `AskUserQuestion`s, which have no terminal to show in, come to the owner's phone: the hub pushes "<title> wants to <action>", or the question, and the board's Needs you shows the pending prompt with Allow once, Always allow and Deny, or the question's options. Always allow returns a session rule to Claude Code and keeps the same rule in the hub's `prompts.json`, keyed by session id. The hub remembers rules only with a reliable process start time and binds board rules to the current ownership's `owner.since`; ownership commands clear remembered rules and pending prompts for both the old and new sessions, including boardless entries, even while the hub is stopped. The hub immediately allows a later exact match on its command, absolute path, domain or bare tool name, with no push or Needs you line; prefixes and globs never widen a match, and `AskUserQuestion` always asks. The remembered rules end when that session stops or the board's owning session changes, and the hub page lists them read-only under the board. With no answer in 10 minutes, the call is denied with a note telling you to ask on the card instead: do that, with `question add` on the card's topic. A session started by hand in a terminal keeps its own dialog ([a background session's prompts and questions come to the phone](docs/adr/2026-10-30-1516-background-sessions-prompts-come-to-the-phone.md)). Board settings' Permissions switches (push main after a land, push release tags, open draft PRs) write allow rules into the board folder's `.claude/settings.local.json`, which your session picks up live; only the signed-in owner can change them, from any device signed in to Tailscale as the owner ([only the signed-in owner changes permissions or restarts](docs/adr/2026-11-04-0502-only-the-signed-in-owner-changes-permissions-or-restarts.md)). A `PermissionDenied` hook (`hub/permission-denied-hook.mjs`) notes under its switch a command auto mode still refused ([board settings grant a board's session permissions](docs/adr/2026-11-03-1921-board-settings-grant-a-boards-session-permissions.md)).

- Static files are live on the next request.

**Closing a board** ([a closed board keeps its folder and can be reopened](docs/adr/2026-10-31-1603-a-closed-board-keeps-its-folder-and-can-be-reopened.md)). On the owner's request, `node $KF close <route> --name '<exact board title>'` stops its session, ends its running builder records with a note and removes its server and sidebar row. Its folder, cards, threads and notes stay on the host; its PRs stay open on GitHub, with no polling from this board. Board Settings has the same action with an active-work warning and a typed-name confirmation. A board whose session is also recorded by another active board cannot be closed. The Hub page’s Closed boards row lists closed boards; `node $KF reopen <route>` restores the saved manifest entry and resumes its recorded session. A closed route stays reserved; use Reopen rather than join or start. A failed resume keeps the board on the closed list for retry. Reopen rewinds to the watcher position saved before Close, so an event delivered near Close may be replayed.

**Moving a board to another host.** On the owner's request, once no builder is open on the board, `node $KF export <route> [--out <file>]` writes one .tgz: the board's folder, its manifest entry without this host's folder, port, command, owner session or restart times, the hub's Notifications, Quiet hours and Codex share settings, and a README.md of the steps. No API key, integration file, GitHub or Codex sign-in, or other hub setting goes in; the README lists what to set up again. It moves only a board whose cards live in its own folder. On the new host, after `kickflip init`, `kickflip import <file>` unpacks the board into `~/.claude/kickflip/sites/<route>/`, adds its entry with a free port, writes those settings over that host's, and prints the `join … --force` line a fresh session there runs to take the board over. It refuses a route that host already has. The old host keeps its copy until the owner leaves it there.

**Leaving.** `node $KF leave <route> --session <id>` removes the entry; the hub stops the site and keeps its files. A plain page needs no `--session`. It does not stop the session or record a closed board for Reopen. Leave only when the user asks.
